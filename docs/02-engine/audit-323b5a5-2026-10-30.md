## 2. C 类逐条展开

> 每条给 ≤5 行代码、为什么是 C、可行的正确做法（能从语料看出时）。

### C-01 `service_advance_wait`：长按连发（→ 用户分歧 ②）

```cpp
// vm_ops_texture.cpp:786
const bool have = mouse_button_source_ && mouse_button_source_(mask);
...
if ((have && (mask & 1) != 0) || skip) { state_flags_ &= ~(1u << 31); ... }
```

- 为什么 C：`mouse_button_source_` 是 SDL 的**当前按住状态**（`window.cpp:109-121`），不是“本拍新按下”。脚本重新武装 `0x72` 后，
  只要左键仍按着，**下一拍立刻放行** ⇒ 按住 = 每 16ms 推进一句。
- 语料：引擎清 bit31 的条件是 `[5EC6C] != 0`（`.lst 0x40923D`），而 `5EC6C` 只由 opcode 0x19C 的 handler 置一次（`0x41913C`）、
  opcode 0x19B 清（`0x4190F8`）；**没有任何一处把鼠标掩码直接拿去清 bit31**。
- 正确做法：把放行改成**一次消费**（边沿）：`0x72` 武装后，等到“新按下”事件才清位；或照引擎补上 `5EC6C` 这个一次性标志，
  由输入层注入的“推进”命令置位、服务一拍后清。

### C-02 `0x72` 少了“起播 + 计时器”

```cpp
// vm_ops_texture.cpp:774-778
write_length(3);
const auto slot = read_int(ops[0]);
current_text_slot_ = slot;
state_flags_ |= (1u << 31);
state_flags_ |= (1u << 30);
```

- 为什么 C：`0x41F069-0x41F076` 在置位前调 `sub_45A940(slot, -1, &692E4)`（起播消息 / 从头），
  `0x41F08B-0x41F0AD` 只在 bit30 **未置**时置它并 `[692E0]=0` + `call sub_453A90`（启动自动消息计时器）。
  实现把 bit30 无条件 OR（位值一样，但**漏了计时器的副作用**），也没有起播。
- 正确做法：按 `.lst` 先调起播入口、再置 bit31；bit30 分支补 `[692E0]=0` + 计时器启动。

### C-03 `service_bgm_fade`：自造服务 + 与门自相矛盾

```cpp
// vm_timing.cpp:11
if ((state_flags_ & (1u << 9)) == 0) { bgm_fade_last_ms_ = 0; return; }
...
while (now >= bgm_fade_last_ms_ + interval) { ... }
if (bgm_fade_progress_ == target) state_flags_ &= ~(1u << 9);
```

- 为什么 C：注释自认“规范没有规定这个分支”，却实现了一个**按 `0xC2` 自己算的间隔**推进的循环；`.lst` 里 bit9 的服务在
  音乐对象/虚表那一路（本提交自己也写“真正生效在虚表”），不在 VM 主循环。更糟的是同提交 `vm.cpp:466` 的
  `kServicedGateBits` 不含 bit9 ⇒ 门把它当“无服务位”。
- 实测：`apps/emulator-cxx/out/emulator-cxx --play-headless … --input-script route-gamestart-newgame.txt` 打出
  `error[0]=gate-bit-unserviced:0x200`（bit9 卡住派发，clock 8.5s 仍未清）。
- 正确做法：要么把 bit9 的清除交给平台/音乐后端的“淡变完成”回调（并在门里把 bit9 列为已服务），
  要么**不实现**、把 bit9 当平台边界（spec 残差），而不是用一条无证据的时钟循环。

### C-04 `0x305` 是死代码 + 两处与语料不符（→ 打字机 / “点击跳下一幕”）

```cpp
// vm_ops_text.cpp:925
const bool armed = (msg_arm_ & 1) != 0 && (msg_arm_ & 0x10000) != 0;
if (!armed) { msg_arm_ = 0; return; }
```

- 为什么 C：`msg_arm_` 的写者只有 `op_304`（只写 1）与本条（写 0）；`0x6e` / `0x196` **从不** `|= 0x10000`
  （`.lst 0x41EB7D` / `0x41FCD8`）⇒ `armed` 恒 false，块结束的“回卷 / 读 skip / 全揭示 / 写等待三格”整段不发生。
- 附带：`bit27` 只要配置非 0 就置（引擎要“已读命中”，`0x41B292/0x41B29C`）；等待三格无条件写（漏 `0x0A30D0==1` 与 `5A2D0&2`；
  `0x41B31B` / `0x41B323`）；`vm.cpp:449` 注释说“本模型不置 bit27” ⇒ 修好 bit16 后必然 `gate-stalled`。
- 正确做法：`0x6e` / `0x196` 成功追加时 `if (msg_arm_&1) msg_arm_ |= 0x10000`；`0x305` 按 `.lst` 顺序 ①回卷 ②读 skip + 已读命中
  （无已读表就不要置 bit27，或补表）③自旋揭示 ④`if ([0A30D0]==1 && !([5A2D0]&2))` 写三格；三出口清臂位。

### C-05 `0x214`：读序 / 交换 / 标脏三处错

```cpp
// vm_ops_scene.cpp:321-331
const auto target_key = read_int(ops[0]);
const auto source_key = read_int(ops[1]);
...
scene_records_.erase(it);
scene_records_[target_key] = copy;
```

- 为什么 C：引擎先读 2（`.lst 0x423AFB push 2`）再读 1（`0x423B05 push 1`）；目标存在时是**交换**
  （`0x4ABF5C` 源→缓冲、`0x4ABF80` 源→目标、`0x4ABF9D` 缓冲→源），不是“复制后删除源”；四个出口都写 `B5AC=1`。
  实现把源删掉、目标覆盖，且不标脏。
- 正确做法：读序 2→1；源不存在 ⇒ 什么都不做；目标不存在 ⇒ 搬运源；两边都在 ⇒ 交换载荷；三条出口置 `scene_dirty_`。

### C-06 `0x220` / `0x219`：写进无人读的平行记录（→ 用户分歧 ① / ③）

```cpp
// vm_ops_texture.cpp:494-518
const double z = read_float(ops[5]);        // 读序 6→5→4（引擎 4→5→6）
...
SceneRecord& record = scene_records_[key];   // 渲染消费者读 DrawItem
record.g[1] = second; record.g[3] = 1;       // +0x68 与 flag_256 同一格
```

- 为什么 C：
  1) 读序与 `.lst` 相反（`sub_423DE0`：`0x423E01/0E/19` 先读 4/5/6，`0x423E3E/46/50` 再读 3/2/1；`sub_423BA0` 对 0x219 是 2/3/4）。
  2) 引擎的 `+0x34/+0x44/+0x58/+0x68/+0x1AC` 与 `0x202`（`+0x34/+0x38/+0x4C/+0x64`）在**同一张记录表**上；
     实现把 0x220 写进 `SceneRecord.g/translate4`，而 `scene_raster.cpp:163` 与 `op_202` 读 `DrawItem` ⇒ 0x220 的窗标志 /
     窗起点 / 两个属性**永远不可见**。实测 `--trace-opcodes 0x220` 在 TITLE 为 0 次、在 SN0000 为 3 次，两条路径都拿不到效果。
  3) `+0x68` 在 0x220（`0x4AD453`）与 0x256（`0x4ACDAB`）是**同一格**，模型里却拆成 `g[3]` 与 `flag_256`。
- 正确做法：先定“一条场景记录”的模型（引擎 `scene+408h` 的 map，字段 +0x34/+0x38/+0x44/+0x4C/+0x58/+0x64/+0x68/+0x16C/+0x1AC），
  再让绘制/窗消费者读同一份；`g[3]`/`flag_256` 合并；读序照 `.lst`。

### C-07 `0x258` 读序（spec 与实现同错）

```cpp
// vm_ops_texture.cpp:235-236
const auto index = read_int(ops[0]);
const auto mask = read_int(ops[1]);
```

- 为什么 C：`.lst 0x425D3D push 2`（先读位掩码）→ `0x425D4B push 1`（后读编号）；spec `60-ops-scene.md:694` 也写“1 → 2”，
  与它自己的 `bindings.json` 站点顺序相反。类型非法时的抛出点因此不同。
- 正确做法：先 `mask=read_int(ops[1])`、后 `index=read_int(ops[0])`；spec 同步改。

### C-08 `0x238` 的格身份（spec 直接与语料矛盾）

```cpp
// vm_ops_scene.cpp:239-244
const auto value = read_int(ops[0]);
cell_238_left_ = 0;
cell_238_value_ = value;
```

- 为什么 C：引擎写 `[5A2C8]=0` / `[5A2CC]=op`（`.lst 0x4248E4/EE`），正是 `0x243` / `0x305` 的消息等待三格 B/C；
  spec `60-ops-list.md:378` 写“互不相邻、也不在同一组”是**反的**。实现又另造两个私有格 ⇒ 0x238 对消息等待没有影响。
- 正确做法：写 `msg_wait_b_=0; msg_wait_c_=value`（A 不动），并让 `0x243`/`0x305` 读同一组。

### C-09 `0x242`：把“两条记录各一格”写成“一条记录两格”

```cpp
// vm_ops_scene.cpp:270-277
SceneRecord& object = scene_records_[key]; (void)object;
KeyedPairRecord& record = scene_keyed_pair_[key];
record.field_a = value; record.field_b = value;
```

- 为什么 C：`.lst sub_4AD9A0` 是 `[eax+2D0h]=edi`（表 `scene+408h`）与 `[eax+1F8h]=edi`（表 `scene+438h`）：
  **两条平行记录，各写一格**。实现第一条一个字段都不写（`(void)object`），第二条写两个字段。
- 正确做法：`SceneRecord.field_2d0 = value`（第一表）+ 第二表记录的单格 = value；`field_a/b` 的造法没有语料依据。

### C-10 `0x7a` 的槽 0 + 无消费者

```cpp
// vm_ops_text.cpp:858
const auto resolved = slot == 0 ? 0 : slot;  // 0 = 默认槽（本模型把默认槽记为 0）
```

- 为什么 C：引擎 `sub_45A910` 在 `slot==0` 时读 `[ecx+4CCh]`（**默认组**，初值 1；`.lst 0x45A918-0x45A920`），
  实现却落第 0 槽；且注释把“默认槽 = 0”当事实。消费者整段未建模（承认残差），所以该条在模型里是纯写。
- 正确做法：走 `resolve_text_layer(slot)`；消费者（把 run 头变成绘制请求）要么补，要么在 spec 里明确“不可观察”。

### C-11 `0x32d`：ARGB 请求是模型自造

```cpp
// vm_ops_scene.cpp:216-218
scene_color_request_.argb = (alpha << 24) | (r << 16) | (g << 8) | b;
scene_color_request_.count += 1;
```

- 为什么 C：引擎 `sub_427040` 把四通道 **/255 成 0..1 浮点**，再以 **4 个 float** 调 `sub_499DF0`（`0x4270BF`、`0x4270F5-0x4270FD`），
  不是 ARGB；spec `60-ops-scene.md:1107` 跟着写错。并且该请求无消费者（只有测试 getter）⇒ 指令在模拟器里是 no-op。
- 正确做法：把归一化的 4 个 float 交给渲染/合成层（或至少把“未接线”写进残差并让门可观测），spec 改掉“参数 = ARGB”。

### C-12 `0x10a`：请求发不出去

```cpp
// vm_ops_texture.cpp:800-802
cursor_request_x_ = read_int(ops[0]);
cursor_request_y_ = read_int(ops[1]);
cursor_requests_ += 1;
```

- 为什么 C：引擎做 `GetCursorPos` / `ScreenToClient` / 虚拟屏换算 / `SetCursorPos`（`.lst 0x421EA0`，`display:VirtualFullScreenType`），
  并读配置；实现只记两个整数，窗口层不读（`cursor_request_x()` 只有 getter）⇒ 光标不动。spec 同时说“引擎换算”“平台边界”“请求 = 换算前”，三句互斥。
- 正确做法：在平台层接 `set_cursor`（宿主回调），核心只发换算前的虚拟屏坐标；或明确“本版不实现、该条不可观察”。

### C-13 `kTextLayerFallbackBase`：为了“有字”而造键空间

```cpp
// vm_ops_engine.cpp:809
if (record.f68 <= 0) record.f68 = kTextLayerFallbackBase + group * 1000;
```

  脚本可见的 `draw_items_` 键空间，`0x1f7` 区间删除会误伤 / 漏删。spec 把它登记成“宿主选择”是对的，但实现没有
  “是否写过”的独立标志（后来 `ab57b47`/`b013648` 才拆 `key_base_set`/`key_base_fallback`）。
- 正确做法：独立 `key_base_set` 标志；兜底键与脚本键不重叠（或干脆不建条目、把“无字”作为可见残差）；加一条会红的守卫。

### C-14 `op_93` 漏清 bit23 / `reset_choice_table` 六格 / `op_90` 不清 arm

### C-15 `0x224` / `0x1bc`：只有测试钩子能走到的“行为”

### C-16 `0x2e9` 的 spec 残差是错的（语料有读者）


- 为什么 C：`[esi+77980h]` 的读点是 `0x409187` / `0x4091E5` / `0x41F118` / `0x41F1A6`，上下文是
  `message:AutoMessagePitch1/0` 与 `AutoMessageTime1/0` 的时长计算（`time + pitch*(n-1-cell)`）⇒ 读者与领域都已取证。
- 正确做法：spec 删掉该残差、写“读作自动消息时长的减项”；实现接上消费者（`b013648` 已接）。

### C-17 spec 的“引擎只有左对齐”是过强断言


- 正确做法：把断言限定到 `0x6e/0x196` 的普通追加；`0x73` 的格内居中另立规则（含证据）。

### C-18 `tools/routes.mjs` / `screens.json` 的机器路径

- 为什么 C：工具常量 `DEFAULT_INSTALL = 'E:\\Games\\…'`（`routes.mjs:57`）与 `EMULATOR_EXE = …exe`（`:52`）在 macOS 跑不了；

  `evidence-shape` 只查“非空 + 日期” ⇒ 纪律没有守卫。已由 `ab57b47` 改成 `$AMAYUI_INSTALL`。

### C-19 `0x1cb` 与 `0x1ca` 不是同一存储

```cpp
// vm_ops_engine.cpp:944
```

- 为什么 C：引擎 0x1cb（`sub_42D3D0`）从配置库读命名键，0x1ca（`sub_42D290`）把 `[5EC68]`（推进/取消的一次性标志）
  **读进操作数**，不是“写配置键”。实现把 0x1ca 写成私有格 `named_message_read_text_skip_` ⇒ `0x1ca 1; 0x1cb dst` 得 0，
  spec 的 falsifier“设成 1 再执行落点必须是 1”**不可满足**。
- 正确做法：0x1ca 改成“读 `[5EC68]` 到落点”，0x1cb 保持读配置；或反过来把两者统一到同一命名键（需先证 0x1ca 的落点语义）。
  已由 `b013648` 把 0x1ca 改成写同一命名键（可过 falsifier，但仍需确认是否真是“写”）。

### C-20 `0x229` 的“命令档按区间 A 起点跳过”只存在于注释

```cpp
// vm.h:171-172
// 绘制项的消费者对**键落在区间内**的条目额外加这一次平移
// （命令档则按「区间 A 的起点」跳过它）。
```

- 为什么 C：全仓 `draw_item()` / `paint_interval` 都没有“按区间起点跳过”的形参或分支（`scene_raster.cpp:180-184`
  只是给命中的条目加平移）；spec `60-ops-scene.md:1084` 也没有这条。这是把“看起来像”的一句
  （可能是 3D 命令档的别处行为）写成了合同，且无法证伪。
- 正确做法：删掉这半句，或在 spec 里只写“2D 光栅的近似：键在区间内加 X/Y 平移（Z 不参与）”，并加一条会红的守卫。

## 3. 与四条用户分歧的对应关系

### 3.1 ① TITLE 退回时按钮提前渲染 —— **最可能不是本提交的新逻辑**

- 实测（HEAD 二进制，`--trace-script 21092 --trace-opcodes 0x1fb,0x1f7,0x202,0x203,0x1f4,0x1f5`）：
  - 首次进 TITLE（clock 368ms）：`0x202` 大量出现（11324/11424/11672/11772/12020/12120/12396/12524），之后 `0x1F7/0x203/0x1FB`；
  - **第二次进 TITLE（1776ms）与第三次（2368ms）**：只有 `0x1F7`（13060/13340）、`0x203`（13248/13548）、`0x1FB`（13928/13584），
    **一次 `0x202` 都没有**。
- 判读：退回 TITLE 时按钮是 `0x1F7`（拆离）→ `0x1FB`（重建）→ `0x203`（直接设色）**重新造出来的**；重建条目的颜色窗
  没有被重排（没有 `0x202`），而首次进 TITLE 的窗早已到期 ⇒ 新按钮以默认色（不透明）出现，和“其余内容在渐变”不同拍。
  这正好复现“按钮提前一整块、像上一帧残留”。
- 归因：`0x202` / `0x1F7` / `0x1FB` / `0x203` **全部是既有 opcode**（本提交只给 `0x1FB` 加了一条**不参与渲染**的
  `SceneRecord.tag` 镜像；`vm_ops_texture.cpp:211-215`），本提交的新逻辑（`0x220/0x229/0x32d/0x258`）在 TITLE 里**一次都没执行**
  ⇒ **没有证据指向本提交**；责任在既有的条目生命周期（`0x1F7` 删除时是否应保留颜色窗 / `0x1FB` 重建时是否应从记录恢复窗）。
- 置信度：中（脚本序列是实测；引擎侧“0x1F7 是否保留窗”未取证）。

### 3.2 ② ADV 长按鼠标持续推进 —— **就是 `service_advance_wait`**

- 对应 `vm_ops_texture.cpp:782-791`（电平触发）+ `window.cpp:109-121`（SDL 当前按住状态）。证据链：
  `.lst 0x40923D`（只认 `[5EC6C]`）/ `0x41913C`（一次性置）/ `0x4190F8`（一次性清）⇒ 引擎是**一次按下放一次**，不是轮询。
- 这条是**本提交新写**（父提交没有该函数），且与用户观测完全同构：按住 → 每次重新武装后当拍放行。
- 附带：`op_72` 没有“起播 + 自动消息计时器”（C-02），会让“一次点击推进一条”的时序也不对。

### 3.3 ③ SN0000 遮罩渐变方向反了 —— **`0x220` 的平行记录 + `0x202` 的目标色**

- 反汇编 `SN0000.BIN`（`/tmp/SN0000.asm`）：`0x202`（`set-draw-color`）出现 **11 次**、`0x220` **3 次**、`0x32d` **0 次**、
  `0x32` **0 次**。两次遮罩切换的形状是：
  - 分支 A：16 条 `i220 key 0 c8 0 0 0`（op2=0、op3=200），随后 `set-draw-color key 0 c8 0 local1`（目标 alpha 0、时长 200）；
  - 分支 B：16 条 `i220 key 0 c8 6e 0 0`（op2=0、op3=110），随后 `set-draw-color key 0 c8 ff local1`（目标 alpha 255、时长 200）。
- 引擎里 `0x220` 写的 `+0x34=0`（窗起点）、`+0x44=op2`、`+0x58=op3`、`+0x68=1` 与 `0x202` 写的 `+0x34/+0x38/+0x4C/+0x64`
  是**同一张记录**（`sub_4AD3C0` / `sub_4AD0C0`）；所以 `0x220` 每次切换都在**重置窗起点并写起始参数**。
  实现只把它写进 `SceneRecord`（`g[]`），渲染读 `DrawItem` ⇒ **两个分支的 op3（200 / 110）与窗起点重置全部丢失**，
  只剩 `0x202` 的终色 0 / 255。两个分支的“起始状态”一样 ⇒ 先暗后亮 / 先亮后暗的方向必然错。
- 归因：`op_220`（C-06）+ `0x202`/`advance_scene`（本提交未改）的组合；**`0x32d` 不是原因**（SN0000 不执行它）。
- 置信度：中高（脚本形状、字段同源、实现丢字段都是实测；`+0x58` 的领域名仍可再证）。

### 3.4 ④ SN0000 旁白应居中却渲染在边缘 —— **`0x73` 的格内定位没实现 + `0x7a` 只写不消费**

- `SN0000.BIN` 里旁白块的形状（`/tmp/SN0000.asm:1216-1240`）：
  `i304 → show-text 0 … → i305 → i073 8 0 <x> c 0 <y> 38 38 8 64 → wait-for-input 0 → i07a 8 8c <x>`。
  `0x73`（`op_73`，**既有**）只把 9 个整数存进 `list_records_`（`vm_ops_engine.cpp:756-782`），**没有任何绘制**；
  `0x7a`（本提交新增）只写 `run_header_`，注释自认“消费者未建模”。
- `0x73` 的 10 个参数（`group, x, y, ?, left, top, w, h, ?, ?`）正是“格”的几何；spec `62-adv-text.md:112-113`
  写了“格宽 − 整串量度宽 ≤ 0 ⇒ 以格中心对齐” ⇒ **居中在引擎里存在**，只是走 `0x73` 这条格内路径。实现没有它 ⇒
  旁白退回普通文本层原点（层矩形左上）⇒ 贴边。
- 归因：`0x73` 消费者缺失（既有）+ 本提交新增的 `0x7a` 也只写不消费（C-10）；**本提交没有让位置变坏，但也没有把这条链接上**。
  另外 spec 的“引擎只有左对齐”误导了这条链的验收（C-17）。
- 置信度：中（`0x73` 的参数语义未逐项取证；但“只存不画”是代码事实）。
