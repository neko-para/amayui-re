# TITLE → Option → CONFIG.BIN 路径的指令取证记录（2026-10）

只读取证记录（`amayui-re-engine` 口径）：**锚只有 EA**（`.lst` 行号只作定位，不当锚）。
这份文件**不是** spec、**不是**知识台账：它记录"看到了什么 + 还没看到什么"，供写 spec 条目与实现时用。
⛔ 任何一条在进 `data/spec` 之前都必须再过一遍准入门（`AGENTS.md` §6）。

## 0. 共用机制（几条结论都依赖它）

- 帧 `fr = Engine + 0x5D880 + 120*Engine[0x5D880]`；`fr+0x18` = 指令指针；`fr+0x74` = **本条宽度（dword 数）**，
  由 handler **最先无条件写**；派发处 `0x411A7E–0x411A8C` 做 `IP += (fr+0x74)*4`。
- 操作数是 **2 dword 一对**（type 在 `IP+8i-4`、值在 `IP+8i`）；读 `sub_41BF50`（EA `0x41BF50`）、
  写 `sub_42B4B0`（EA `0x42B4B0`）。宽度 = 1+2×argc，与 `opcode-table.json` 独立互证。
- 可读 type 0–13（另 `0x8003`/`0x8009` 等）；可写只有 3/4/6/7/9/10/12（写文本 5/8/11 是**另一条**路径）。
  非法 type ⇒ `Command_Type_Exception`。
- 文本读原语 `sub_41B640`（EA `0x41B640`）→ `char*`：标签 0–14 除 **7 / 13**；数值标签先 itoa 成十进制；
  内联文本逐字节取反解码。**`0x192` 用的是另一个子例程 `sub_42A420`**（EA `0x42A420`），⛔ 不要混为同一条。

- 实现状态：**已实现**（`apps/emulator-cxx/src/core/vm_ops_engine.cpp` 的 `op_c0`），selftest 断言长度槽 3 与写回值。

## 2. Font 侧「条目登记表」三条：`0x1D0` / `0x1D2` / `0x1D3`

三条都作用在 **`Engine+0x14D30` 的 Font 对象**（构造点 `0x41570E` → `sub_464FD0`，vftable `Font::vftable` @ `0x465007`）。
共用数据层（不是共用子例程：三个工作子例程各只有 1 个调用点）：

- `Font+0xD24` 起是 **72 字节记录表**（std::vector）：`+0x00` 列表号 · `+0x14` 值 · `+0x18` key ·
  `+0x28` flags · `+0x2C` 空 `std::string` · `+0x44..0x47` 无人写（步长 72 是 8 对齐的结果）。
- `Font+0xD34` 起是 **8 字节对表**（每项 = 一对 dword），光标 `Font+0xD70`；
  `Font+0xD44 + 4*idx` 是每记录的脏槽。

### `0x1D2` — `sub_420380`（EA `0x420380`，`.lst` 48143–48168）

- **守卫**：`Engine[0x5EC7C] != 0` ⇒ **整条跳过**（宽度仍已写：不读操作数、不抛）。
  该槽由 `0x1BB`（`sub_420000`）写 0 / `0x80000000`，报错串「SetTBの引数が不正です」。
- 放行后读序 **op2 → op1**，**不写任何操作数**；向 `Font+0xD24` 入队一条 72 字节记录：
  `+0x00` = `Engine[0x4CC]`（默认列表号）· `+0x14` = op2 · `+0x18` = op1 ·
  `+0x28` = `0x20000000 | (Font+0xD44+4*idx != 0 ? 1 : 0)`（后者同时清槽）。
- **无外部请求**（纯内存入队，本帧不触发绘制）。推进 **5 格**。
- 未解：入队后谁消费（`Font+0xD24` 在 `0x4577xx–0x457Exx` 有大量读者）；`+0x28` 位 0 / 位 29 的领域名。

### `0x1D3` — `sub_42D4A0`（EA `0x42D4A0`，`.lst` 69907–69953）

- 读序 **op5 → op4 → op3**（降序）。★ `sub_457960` 的 `.lst` 只声明三个栈参但 `retn 10h` 吃四个：
  `[+8]`=&out · `[+0Ch]`=op3 · `[+10h]`=op4（起始下标）· `[+14h]`=op5（key）。**`[ebp+0Ch]` 函数体零引用**
  ⇒ op3 被读、值丢弃，但 type 非法照样抛。
- 查询：`count = (Font[0xD28]-Font[0xD24])/72`；`op4 < 0 || op4 >= count` ⇒ 未命中；
  否则从 op4 顺扫，命中 `(rec+0x28 & 0x20000000) != 0 && *(rec+0x18) == op5` ⇒ 取 `*(rec+0x14)`。
  **组边界**：`72*idx+0x70 & 1` 落在**下一条**记录的 `+0x28`（步长 0x48 < 0x70，字节事实）⇒
  "下一条 flags 低位 = 组头 ⇒ 断组"属**推断**。
- 写：op1 ← (命中 ? 1 : 0)、op2 ← 值（**未命中写 0，不是 −1**）。推进 **11 格**。
- 未解：op3 是保留操作数还是历史残留；组边界的领域含义。

### `0x1D0` — `sub_42D440`（EA `0x42D440`，`.lst` 69859–69899）

- 只读 **op3**（op1/op2 从不读）。走 `Font+0xD34` 对表：从光标 `Font+0xD70` 起 ±op3 步，
  跳过"指向的记录 `flags & 2`"的项；成功 `op1 ← pair[v].first`、`op2 ← pair[v].second`（顺序 1 再 2），
  越界/哨兵 ⇒ 两个都 `−1`，返回值被丢弃（不抛）。
- 无外部请求。推进 **7 格**。
- 未解：`pair.first` 的语义；`flags & 2` 在整张指令表里**无人置位**（`20000002h` 全语料 0 处）⇒ 跳过支不可达。

## 3. 文本族四条：`0x6E` / `0x6F` / `0x196` / `0x1A6`

四条都**先写当前帧长度槽、再读操作数**；文本读全部走 `sub_41B640`（与 `0x204` 同一条路径 ⇒
C++ 的 `read_text` 可直接用）。

### `0x6E` show-text — `sub_41EB20`（EA `0x41EB20`，`.lst` 45867–46004）

- 宽度 **5**（argc 2）；读序 **op2（文本）→ op1（整型）**；`46CBF0` 那一支是 **op1 → op2 → op1**。
- 写：`Engine[0x7780C] ← op1`；非跳过支 `Engine[0xAAB44] |= 0x20000000`（位 29）+ 计时队列 `0x691EC`
  登记（时长 = `Engine[0x15290]`）；跳过支 `|= 0x8000000`（位 27，与 `0x71` 同一位）+ `0x7795C ← 1`。
- 消息窗口记录 `[0x14D30 + 4*op1 + 1044]` 追加一段文本（`op1 == 0` ⇒ 引擎默认槽 `[0x14D30+1228]`）。
- **外部请求**：文本量度 + 光栅（`sub_46BE30`：`SelectObject` / `GetTextExtentPoint32A` / 逐字写出），
  实参 = (窗口记录, op1, 文本, **0**, `Engine[0x5EC7C]`)。**空串 ⇒ 不发请求、不写上面三格**。
- 分支：`Engine[0x77A04] & 1`；否则查命名键 `message:ReadTextSkip`（与 `0x1ca` 同一个键）。
  **跨指令**：跳过支把帧字段「文本请求位置」（`0x71` 写的那一格）当 `sub_48E870` 的实参。
- 未解：`0x77A04` 位 0/16、`0xAAB44` 位 27/29、`0x7795C`、`0x5EC68` 的领域名；
  `0x15290` 已证为时间量但名未定；窗口记录里"一段文本"的格内结构。

### `0x6F` end-text-line — `sub_41ECE0`（EA `0x41ECE0`，`.lst` 46011–46029）

- 宽度 **3**（argc 1）；只读 op1。`sub_46AF90(0x14D30, op1, Engine[0x5EC7C])` 定稿行结束三格
  （`*(rec[12]-20) ← rec[7]`、`*(rec[12]-16) += 行距`、`++*(rec[12]-4)`、`++rec[71]`）。
- **无外部请求**（闭包里没有任何 GDI / 光栅入口）。未解：行结束三格与 `rec[28]` 的领域名。

### `0x196` display-furigana — `sub_41FC20`（EA `0x41FC20`，`.lst` 47416–47567）

- 宽度 **7**（argc 3）；读序 **op3（文本，无条件最先）→ op2（文本）→ op1（整型）→（追加成功后）op1**。
- op3 先 `strncpy` 式拷进 1024 字节缓冲：**上限 1023 字节 + NUL**，超长静默截断、不报错。
- 写：`Engine[0x7780C] ← op1`；`0x77A04 |= 0x10000`（直接追加）或 `0xAAB44 |= 0x8000000`（跳过）/`0x20000000`；
  文本记录追加 **op2**，截断后的 **op3** 作为**第二文本**传给绘制入口（`0x6E` 处该实参是常量 0）。
- **有外部请求**，与 `0x6E` 同一入口。**不查** `ReadTextSkip`。未解：op2/op3 谁是主文本谁是振り仮名。

### `0x1A6` halve-strlen — `sub_42D110`（EA `0x42D110`，`.lst` 69515–69541）

- 宽度 **5**（argc 2）；读序 **op2（文本）→ 写 op1**（唯一一支）。`op1 ← strlen(文本) >> 1`（按**字节**）。
- 落点是**整型**（写原语的标签集）：落点给 5/11（字符串池）⇒ 类型异常。**无外部请求**。
- 未解：`strlen/2` 的领域用途（可能是排版半宽）。

## 4. 四条"标量 / 槽位"指令：`0x142` / `0x1BB` / `0x300` / `0x301`

★ 操作数位置核对：仓库里 `dist/install/CONFIG.BIN` 与统一文件 id 52 的**文件 dword 下标差 15**（60 B 头）；
CONFIG 里的实际实参全是类型标签 0（立即整数）。

### `0x142` — `sub_422930`（EA `0x422930`，`.lst` 51837–51851）

- 宽度 **3**（argc 1）；读 op1 → `Engine[0xAAB70] ← 值`。无外部请求、无分支、无检查；无类型校验（非法 type 由读原语抛）。
- 唯一读者 `sub_4765C0`（EA `0x4765C0`）：`return Engine[0xAAB70] != 0`；初值 1（两处启动初始化 `0x40DF7B` / `0x415AEC`）。
- 未解：`0xAAB70` 的领域名（只知"非 0"这一语义）。

### `0x1BB` — `sub_420000`（EA `0x420000`，`.lst` 47802–47843）

- 宽度 **3**（argc 1）；**同一个操作数读两次**（`0x42001F`、`0x420038`）。三分支写 `Engine[0x5EC7C]`：
  arg1 = 0 ⇒ `0x80000000`；arg1 = 1 ⇒ `0`；**其余 ⇒ 不写**（保旧值）+ 记一行日志
  （`"SetTBの引数が不正です．\r\n"`，经 `sub_408050` → `0x4976A0` 加 `"(<脚本>：<行>行目) "` 前缀 → `WriteFile`）。
  **三支都不抛**，控制流不变。
- `0x5EC7C` 的语义（三个读者）：`0x426788` 判 `== 0` 才画字；`0x411DCA` 用 bit31 挡 `set:ReDrawTextOnKey`；
  `0x41EB44` 把它当第 5 实参传给 `sub_46BE30` ⇒ **0 = 正常显示，bit31 = 抑制**。
- 未解："TB" 的字数 / 窗口身份。

### `0x300` — `sub_426990`（EA `0x426990`，`.lst` 58352–58379）

- 宽度 **7**（argc 3）；读序 **#1 → #2 → #3**（#1 作下标；`A[idx]` 在 #3 之前就写）：
  `A[+0x77988][idx] ← op2 | (A[idx] & 0x10000)`（**bit16 粘住**）、`B[+0x779B0][idx] ← op3`。
  无外部请求、无分支、**idx 无范围检查**。
- 数据面：A / B / C（`+0x77988` / `+0x779B0` / `+0x779D8`）是三个**各 10 条**的 dword 数组；
  每帧更新 `sub_409400` 只走 idx 1..9：`A&1` ⇒ 置 bit16；`timeGetTime() - C[idx] >= B[idx]` ⇒
  `C[idx]=0` 且 `sub_404F80(font, idx)`（与 `0x301` 同一个释放）；`A&1 == 0` 但 bit16 在 ⇒ 等 font 空闲后清 A/B/C。
  ⇒ **A = 状态位（bit0 起動 / bit16 粘住）· B = 期限 ms · C = 起点时刻**。
- CONFIG 里两次调用是 `(9, 1, 1000)` 与 `(9, 0, 0)`。未解：数组 / 槽的领域名。

### `0x301` — `sub_4269F0`（EA `0x4269F0`，`.lst` 58386–58403）

- 宽度 **3**（argc 1）；读 op1，同一值用两次：`C[+0x779D8][idx] ← 0`，再 `sub_404F80(font, idx)` 释放该字体槽
  （idx == 0 ⇒ 换成 `font+0x4CC` 缺省槽；槽项非空 ⇒ 项+132 ← 0 + 两段 map 删除 + 载荷 `[vtbl+8]` 后 `delete`）。
  无分支，idx 无范围检查。未解：条目 +104/+108 与 +276/+280 两段区间的语义、槽号 9 为何固定、
  `[vtbl+8]` 内部是否释放图形资源（下界）。

### 成对判断

- `0x142` + `0x1BB` **不是一对**：目标格不同、读写者不重叠、无共用 helper；CONFIG 里两处相邻且同值（0,0 / 1,1）
  只是"两个无关布尔量被同一处赋同值" ⇒ 不能共用实现。
- `0x300` + `0x301` **是同一条数据面上的两面**（同表、同一个释放入口），但**不是开/关对称**
  （arity 7 vs 3、写 A/B vs 只清 C）⇒ 只可共用"取 idx / 槽址 / 释放"三个小 helper。

## 6. 参数格（`Engine+0x15290`）的初值 = 配置键 `message:MessageSpeed`

spec 条目 `CORE-OPS-PARAM-74-7F` 有一条残差 `RES-PARAM-21668-INIT`：「参数格的初值没有观察」。
实测**有确定写点**：

```
35403  .text:00417EAB mov     [esi+15290h], eax      ; ← 启动期写这一格
35399  .text:00417E98 push    offset aMessageMessage ; "message:MessageSpeed"
35401  .text:00417EA3 call    eax                    ; 配置取值
```

`0x41FF00`（`sub_41FED0`）也会把同一格写成 `message:MessageSpeed`（另一条路径）。
⇒ 初值**不是分配残留**，而是配置值；CONFIG.BIN 第一次 `0x7f` 读它时该配置是缺省 0，
这解释了为什么 `0x7f` 在 CONFIG.BIN 早期可执行（实现此前把它当"未初始化 ⇒ 响亮失败"）。
★ 这条可用来降级 spec 的 `RES-PARAM-21668-INIT`（待回填）。

## 7. `0x12F` — `sub_42F560`（EA `0x42F560`，`.lst` 73203–73380）

排序置换：op1/op2/op3 = **三个数组的基址**（A 被写、B/C 只读），op4 = 元素个数 N。

- 读序：op1 → op2 → op3（地址型，`sub_42AEA0`）→ op4（整型，`sub_41BF50`）；**op4 每轮重求值**（2N+1 次）。
- 写：① `A[0] := 0`（**无条件**，N=0 也写；存原始下标）② `N≥2` 插入排序，键 = `dec(B[i]) + dec(C[i])`
  （32 位回绕、**有符号**比较、升序；`jle` 落位 ⇒ 相等不交换）③ 收尾 `A[i] := enc(A[i])`。
- 无外部请求；**零界检查**（N 超长 ⇒ 静默越界，⛔ 不许替它加检查）；推进 **9**。
- 用途（游戏层）未取证。已实现（`vm_ops_numeric.cpp` 的 `op_12f`）。
- 派发锚：`0x415DF6`（表基 `0xA509C`）+ `0x411A66`（分派）。

## 9. `0x82`（文本排版）与 `0xC2`（音乐转移）—— 已取证、**未实现**

- `0x82`（`sub_41F720`，argc 5，推进 11）：读序 **5→4→3→2→1**，五个值交给文本布局管理器
  （`ecx = Engine+0x14D30`）的 `sub_466000`；节点下标越界 ⇒ **静默**；op1 槽**零界检查**；

  A 支 = 直接设音乐转移（`sub_489D10`）；B 支 =（首帧读 `set:TransferMusicVolume`）→ `flags |= 0x200`
  → 步进定时器 `Engine+0x68FBC`（`op2 < 1000 ? op2/10 : op2/100`，**向零截断**）+ rate（10 / 1）

## 10. 文本读原语支持指针族（`type 8 / 14`）

## 15. 滚动条中段的拉伸规则（已定案并实现）

引擎**没有**九宫格 / 平铺 / "源高 1 就拉伸"的隐式规则。绘制项的消费者是三级：

1. `sub_4B06D0`（Scene::Render）：按 **map 键序**遍历，只画 `flags & 0x10001 == 1` 的项，画完置 `0x10000`（已画位）。
2. `sub_4AEEA0`（RenderScene）：拷贝 0x2E4 字节记录 → 造物体空间矩阵 → `sub_4A2D50`。
3. `sub_4A2D50`（DrawTexture）：源矩形夹到纹理有效区（越界时位置同步平移）→
   `ID3DXSprite::Draw(tex, pSrcRect=rect, pCenter=0, pPosition=rec[9..11], Color)`。

⇒ 四边形边长 = **源矩形尺寸**；唯一的放大源是"物体空间矩阵"，而该矩阵只由两条指令置位：
`0x1FD`（`D3DXMatrixScaling`，**纵向拉伸只认 sy**，`rec+0x6C`）与 `0x1FE`（绕轴旋转）。

**实测**：CONFIG1.BIN 里唯一一处 `0x1FD` 是 `key=局部变量, sx=100, sy=局部变量, sz=100`
（`100` = 1.0 倍，因为操作数是百分数）—— 它正是给滚动条中段（key 121911）设 `sy`。
我们的渲染器此前**完全忽略**这条矩阵，所以 1px 的中段只画 1px。
已修：`gpu_scene.cpp`（GPU 顶点）与 `scene_raster.cpp`（软件光栅，最近邻放大）都按
`scene_record(key)->scale` 放大四边形；未设缩放的项行为不变（1px 仍是 1px）。
验证：同一帧导出后，滑块成为**连续长条**（上下横纹帽 + 浅色实心中段），与真机截图一致。

## 26. 0x204 纵向对位：缓存 ascent 的写者与「文字被割成两行」（2026-10-27 定案并修复）

**现象**：设置界面每行文字被切成两半 —— 上一行的下半截出现在本行顶部，首行还被纹理上缘裁掉；
用户口径「文字被割裂渲染到两行之间」。

**取证**（锚 EA）：
- 0x204 请求链把 ascent 加两次、减一次：`sub_456710`（请求）→ 模式 1 时
  `y ← y + [Font+0x313F0] − tmAscent`（`0x4567AF` / `0x4567B5` / `0x4567B7`）→
  绘制入口 `sub_46F2D0`（`0x46F37C add [arg_8], eax`）或 `sub_471180`（`0x471253 add [arg_8], edx`）
  再加回 `tmAscent` ⇒ 落字用**基线** ⇒ 模式 1 的基线 = `y + 缓存ascent`。
- **`Font+0x313F0` 有写者**：字体重建入口 `sub_459F40` 把 `&Font[0x313EC]` 交给 `sub_456C90`
  （`0x459F8F`），后者在里面调 `GetTextMetricsA`（`0x456DA1`）——写它的是**指针出参**，
  不是 `mov [..+313F0h],..`。布局：`+0x313EC` = tmHeight、`+0x313F0` = **tmAscent**。
  ⇒ 旧注释「全语料 0 处写 ⇒ 恒 0」是**假否定**。
- 配置界面实测：根脚本 `SYSTEM4.BIN` 在 `ip=788` 执行 `0x2db 1`（对位模式 = 1，之后一直是 1）；
  CONFIG1.BIN 自己 0 次写。纹理 196（628×360）的标签 y = 6,36,…,246（脚本 `0x50`：6 + 行×30），
  30px 行带；把缓存当 0 时 ink 顶 = 0(裁),18,48,…（= y − ascent，ascent ≈ 19）⇒ 正好跨到上一行。

**修复**：`text_raster.cpp` 的 `cached_ascent` 取本次量度（本模型只有一份字体、无 DC 字体切换 ⇒
重建量度与本次同源，对位项恒 0）；基线 = `y + ascent`。删掉 `Machine::cached_text_ascent_`
（它把「没搜到写者」写成了「恒 0」）。
**守卫**：`core_selftest` 新增「0x204 纵向对位」——字号 20 + 对位模式 1 + y=10 画 "A"，
断言墨迹顶 ∈ [10,18] 且不越过行带；把 `cached_ascent` 改回 0 ⇒ 当场红（实测 ink_top=0）。
**spec**：`CORE-OPS-RENDER-TEXT-204` 补「两条绘制入口落字前 += 本次 ascent ⇒ y = 字形格顶」，
并把 `RES-RENDER-TEXT-ALIGN` 收窄到「本次量度与缓存不同的条件 / 非 GDI 后端的等价档位」。

## 27. 滚动重画 + GPU 纹理缓存：revision 被重置成 1（2026-10-27 定案并修复）

- **脚本侧**（CONFIG1.BIN，body=60 线性解码）：滚轮（`0x10d` 读 `2026`）→ 顶行 `22048 += ±1`（越界直接 ret，不重画）
  → `call #913` 重建行模型 → `call #1777` 整页重画：`0x1f7` 拆 121000+400 / 121500+200 → `0x1f8 196 628 360`
  → 行循环 9 行：`0x75 20` + `0x204 196 5 (6+30i)` 标签 + `0x204 196 425 (6+30i)` 值 → `0x1fb` 30px 源带（源带固定按 i）
  → 滚动条重拆 / 重建。**每次滚动实跑恰好 14 条 0x204**（9 标签 + 5 值），0 条 0x205。
- **引擎规则**：`0x1f8` 新建对象替换旧对象（新表面像素**未定义**，不是 0x20E 清）；`0x204` 只写字形；`0x1f7/0x1fb` 标脏。
- **真因**：宿主 GPU 纹理缓存按 `TextureRecord::revision` 命中（`gpu_scene.cpp:202-215`）。旧 `op_1f8` 在清空后
  `revision = 1`；一次重画 = 建(1) + 14 条 0x204 = **15**，下一次滚动又是 15 ⇒ 缓存命中上一轮纹理 ⇒
  只有"成功绘制条数"变化时才刷新（用户口径「必须文字数量变多/变少才会刷新」）。
- **修复**：`op_1f8` 去掉重置（只加不减）；`op_1f9` 替换同一槽时取 `旧 revision + 1`（重载另一张图不得命中旧纹理）。
  守卫：`core_selftest` 两轮「重建 + 同条数 0x204」后版本号必须 > 3（旧行为 2）；变异（加回 =1）实测红。
- **边界**：`--bmp` / CTest 的无头路径**每帧新建 `SceneTextureCache`**（`gpu_scene.cpp`），看不到这个 bug；
  只有窗口路径（`window.cpp` 长期持有 cache）会命中。⇒ 这类问题必须有"跨帧持久 cache"的守卫（待补）。

  1px 膨胀是脚本 + 偏移 (1,1) 的直接结果。`text_raster.cpp` 保持"无条件先副色"，不加引擎没有的分支。
- **偏移数值的字段结论（2026-10-27 逐字核，推翻本节的旧说法"来源是字体资源"）**：
  - `Font+0x414` 起的 **10 个对象是 `FontVWindow`**（`0x455D5E/0x455D63` 按 `0x12C` 分配，
    `0x475EAB` 写 `??_7FontVWindow@@6B@`，创建循环 `0x455D45..0x455D91`；由字体对象初始化入口
    `0x465390` 调 `sub_455D20` 建）。它**不是**资源文件里的记录：没有从文件加载的路径，字段也**不是**
    由文件字节填出来的。
  - 它的 `+0xA8..+0xC4` 是**文字样式**（与字体对象上的主色 `+0x550`、副色 `+0x554`、`+0x558`、
    `+0x55C`、`+0x313D4`、`+0x35594`、偏移 `+0x568/0x56C` 一一对应）：
    * **存档初值**：`0x475DE1/0x475DE7` 把 `+0xC0/+0xC4` 置 0；
    * **保存**（存档 ← 当前值）：`0x45C68B/0x45C691`（`sub_45C610`；调用点 `0x4662C0` 推的实参就是
      `0x466250/0x466256` 的 `Font+56C/568`）与 `0x45E97B/0x45E996`（`sub_45E870`；调用点 `0x46B5B4` 同理）。
      方向是**从字体对象抄进存档**，不是反过来；
    * **应用**（当前值 ← 存档，**随后归还**）：`0x4601E8` 与 `0x461803`（`sub_45FF00`，同一条件、
      成对 ⇒ 净效果恒等）、`0x469719` 与 `0x46AE08`（`sub_469260` 的重建支；后者**无条件**归还）。
  - 全二进制对 `Font+0x568/0x56C` 的**写点只有**：构造 `0x4651BD/0x4651C3`（=1）与上面两对借/还。
    ⇒ **当前值恒为 (1,1)**：每次被应用改成存档值之后都被还原；而存档的值本身又是从当前值抄的，
    资源 / 配置 / 脚本都没有第三条写入路径。★「资源记录可能覆盖」**不成立**。
  - 应用/重建的分叉由 `FontVWindow+0x70` 决定（`0x46946E`），该格**只由 opcode 0x1d9 写**
    （`0x421431/0x42143E`）。一次全量扫描（基线根的全部 **941 支**脚本，含 ALF 归档里的；用
    `packages/age-format` 的头部 + 指令表解码，一次性做，**不是守卫**）：**0x1d9 出现 0 次**
    （0x1c0 也是 0；0x82 只有 2 次、0x1d1 只有 1 次）；常用的是 0x1cf（44283）、0x6e（36634）、
    0x196（6276）、0x76/0x77（各 1522）、0x75（1492）、0x78（1385）、0x1a5（1051）、0x2bd（1048）、
    0x204（320）。920/941 支能完整解码；21 支在指令表缺口处停下（`op 0x0` 与 0x3b6 / 0x4a0 / 0x44d /
    0x127 / 0x4a / 0x4ba、1 支 argc 越界）——这些文件在停下**之前**的指令也扫过，0x1d9 仍 0 次。
    ⇒ 发行脚本不会把某个窗切到"存好的样式"那条分支，应用路径在实机上只可能由初始化 / 配置触发，
    且即便触发也**归还**。
  - ⇒ **spec**：`CORE-OPS-RENDER-TEXT-204` 的"投影偏移"由"本版不规定"改成**常量合同 (1,1)**；
    新增残差 `RES-RENDER-TEXT-PROJECTION`（只收窄到"临时借用期间存档值（首次重建时仍为 0）是否参与
    字形量度 / 推进量"）。⚠ 本模拟器用 (1,1) 现在有代码依据，不再是"因为没有资源而拿初值凑"。

## 30. 窗口 GPU 呈现的 LOAD + 行表重建：同一行文字出现在两个 y（2026-10-27）

- 现象（用户口径）：滚动/切页后同一行文字出现在两个 y 位置，中间能看到背景缝；无头 `--bmp` 复现不到。
- 观测（无头，`--trace` 诊断，已撤）：系统页**自动滚到字体行**时，同一条标签在**不同帧**被重画在
  `y=156/126/96`（槽 5/4/3）；每次重画前 `0x1f8` 清纹理 196（三次都清），但**屏幕**不归它管。
- 页面重建的拆离范围：`0x1f7 key=120000 count=3000`、`121000 count=400`、`121500 count=200` ——
  **整张 UI 行表**（含行背景 12100x 与文字带 1216xx）一起拆离，再按当前可见行重建。
- 窗口路径的差异：GPU 场景呈现是 `draw_scene_gpu(..., clear = false)`（`SDL_GPU_LOADOP_LOAD`）——
  **不清交换链**；被移走/消失的行，其屏幕区域新帧不再重绘 ⇒ 上一帧那行文字留在交换链上；
  新帧的半透明/背景层让它隐约透出 ⇒「同一行字两个位置 + 中间背景缝」。
  无头 `--bmp` 每帧新建目标并清 ⇒ 永远看不到；这与"1px 副色偏移"**无关**
  （墨迹带实测 8..28 在本行 30px 内，行背景 alpha = 255）。
- 修复（宿主呈现策略）：窗口 GPU 路径改为 `clear = true`（`window.cpp`）；交换链是平台呈现表面，
  清它不改引擎的渲染步语义（引擎的"不自动清"说的是它的渲染目标）。软件回退的 quad pass 本来就
  `LOADOP_CLEAR`。

## 31. 同色副色趟 = 1px 膨胀：覆 字右侧粘连（2026-10-27）

- 现象（用户口径）：系统页「覆盖存档时清除备注」一行的**覆**，右侧（"复"）笔画**全部粘连**；预期笔画间有正常缝隙。
  这不是"缺一行背景"，而是**该有的缝隙被填满**——即重影。
- 机械化判据（不读图）：`.tmp/gap-scan.py` 读一张 1280x720 的 `--bmp` 帧，取覆的 bbox
  （x 429..457、y 259..284），统计**中性亮（白）像素**与**被墨迹围住的背景洞**（从 bbox 边界 flood fill，
  没被访问到的背景 = 洞）。复现（同一帧、只差副色趟）：
  | 版本 | 覆 ink | 覆 holes | 覆-right ink | 覆-right holes | 盖 holes |
  |---|---|---|---|---|---|
  | 同色仍画副色趟（坏） | 322 | **6** | 162 | **0** | 15 |
  | 同一帧跳过副色趟 | 177 | **30** | 84 | **4** | 30 |
  | 修复后 | 177 | 30 | 84 | 4 | 30 |
  ⇒ 同色（主 = 副 = 白）时模式 1 的 (+1,+1) 副色趟只把笔画的 1px 缝隙填满（覆-right 的 4 个洞 → 0）。
- 修复：`text_raster.cpp` 在**副色 == 主色**时跳过模式 1/3 的副色趟（异色描边照旧）。这是**宿主的像素级选择**
  （spec 明说像素结果不在本版；引擎仍发"先画副色"的请求），记录在 README 与 §31。
- 守卫：`core_selftest` 新增——同色时模式 1 的墨迹像素数必须 == 模式 0；异色（副 = 黑）时必须 > 模式 0
  （变异：把同色副色趟加回来 ⇒ 同色模式 1 的墨迹约翻倍、当场红）。

## 32. 真机为什么"只是变粗"：1-bit 掩码 + max 合成（2026-10-27）

- **字形来源**：0x204 的纹理路径**不走 GDI 文字 API**（全语料 `BitBlt/StretchBlt/TransparentBlt/
  ExtTextOutA/SetROP2` 各 0；`SetBkMode` 仅屏幕回退 `0x455DF4`）。它用 `GetGlyphOutlineA`
  （`0x46F5BC`/`0x46F60B`、`0x471723`/`0x4717A8`）取位图，`LockTexture`（`0x4A3890`，LockRect）后
  **直接写纹理内存**（`0x46D9F0`）。
- **默认 1-bit**：`fuFormat = GGO_BITMAP(1)`（`0x46F3A4`/`0x47127B`）；只有 `Font+0x548 != 0` 才是
  GGO_GRAY4(5)/GRAY8(6)（`0x46F382..0x46F3A4`、`0x471259..0x47127B`；÷65/÷17 常数 `0x46DA9C/0x46DAAF`）。
  `Font+0x548` 建造 = 0（`0x46511A`），唯一写点 = 配置 `set:EnableAntiFont` + `message:UseAntiFont`
  （`0x417AF8`→`0x417B1B`→`0x4155C1`）。`lfQuality` 恒 0（`Font+0x4E8` 只写一次 `0x4653E4`；`0x4EA` 零访问）。
- **合成（不是 alpha-over）**：满覆盖 ⇒ **覆写**（`0x46DB72`/`0x46DB75`；32bpp `0x46DDC0`/`0x46DDC6`）；
  否则 `outA = max(dstA, srcA)`（`0x46DB8E`/`0x46DDDB`）、`outC = (srcC*srcA + dstC*(MAX-srcA))/MAX`
  （÷15 `0x46DBAF`，÷255 `0x46DE01`）。⇒ 同像素重复画**幂等**，永不累加。
- **两趟同一份缓存位图**：`0x4717BD`（每字位图）/`0x4717C0`（GLYPHMETRICS）；副色趟 `0x471A13..0x471A40`
  与主色趟 `0x471B01..0x471B20` 只差颜色（`+0x554`/`+0x550`）与 (+1,+1)（`0x4651BD/0x4651C3`）。
- **为什么真机只是变粗**：1-bit 硬掩码的两趟 = **几何膨胀**（右下各 1px），缝像素不会被半透明覆盖率相加；
  我们的旧实现是**灰度 AA + alpha-over**（`1-(1-a)(1-b)`），两趟在缝处**相加变亮** → 软边/粘连/重影。
- 实现：`text_raster.cpp` 默认 `FT_LOAD_TARGET_MONO`（1-bit）+ `compose_glyph_texel`（引擎的
  满覆盖覆写 / max / 颜色插值）；`EMULATOR_CXX_GLYPH_AA=1` 是对照用的灰度路径（同样 max 合成）。
  守卫：alpha 只有 0/255（1-bit 默认）；同像素重复画幂等（alpha 128 ≠ 192）；满覆盖覆写；部分覆盖公式。
- 仍未定：**GDI 的 GGO_BITMAP 掩码形状**（GDI 与 FreeType 的 hinting 差 1px；`EMULATOR_CXX_MONO_AUTOHINT`
  可对照）；真机 `SYS4REG.INI` 的 `[set] EnableAntiFont` / `[message] UseAntiFont` 实际值（决定 1-bit vs AA）。
