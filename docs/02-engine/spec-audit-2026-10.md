# 《天結いキャッスルマイスター》spec 审稿问题清单

只读范围：`data/spec/`（`spec.json`、`chapters/*.md`、`bindings.json`、`audit.json`、`format/*`、`core/README.md`）。未读 `apps/emulator*`、`.tmp` 既有内容、`corpus/`、`data/ledger/`、`data/shape/`；未改任何 spec 文件。

按严重度排列。每条只给“需要什么证据才能修”，不给结论。

---

## 一、严重（合同不可实现，或同一件事被写成两种互斥说法）

[自相矛盾] 00-overview（本版覆盖 / 本版不覆盖）
  · 现象：“对象模型、容器句柄、输入、表现边界、**文件装载的调度/搜索路径**、存档、配置、时间。”；同节又写“指令表里**逐条 opcode 的语义**……其余 opcode 的行为不在本版断言。”
  · 为什么是问题：manifest 已含 `config` / `ops` / `vm`，`55-config`、`60-ops`、`70-vm` 已成篇，`40-pools` 已有两条容器句柄规则；总览却把这三类全部列为“不覆盖”。
  · 影响：分发读者会按总览跳过配置、时间、逐 opcode 语义与容器句柄；实现者会认为这些不是合同。
  · 建议的“需要什么证据才能修”：逐条核对总览每个 bullet 与 manifest / `audit.chapters[]` / 章节规则标记的对应关系，确认总览是“范围声明”还是上一版残留。

[自相矛盾] 10-format（核验状态）
  · 现象：表格六行均写“**已核验**”，但每行“待核验什么”都非空，例如“`SYS3` 分支的头布局（语料无样本）”“30 条‘有编码、无处理函数’的表项来源”。
  · 为什么是问题：正文说“分成三类：已核验（引擎解码代码与语料两侧对账）、部分、观察值”，表里却没有任何“部分”行；且“已核验”与“语料无样本”不能同时成立。
  · 影响：读者把无样本分支当已验证合同；实现者无法判断哪一条能独立实现。
  · 建议的“需要什么证据才能修”：为每一行给出“引擎读取点 + 语料样本 / 无样本”的二分证据；再与 `format/verification.md` 的 `partial` / `unverified` 状态逐行对齐（该台账目前写 v5 签名 `SY`、v5 头长 `0x44`，正文却写“任何 UTF-16 签名变体……在本引擎的装载器里不存在”）。

[自相矛盾] 55-config（配置库）
  · 现象：“配置的**值**只有两类：整数与字符串。”；同一节写“值分整数、字符串与字符串列表三类”。
  · 为什么是问题：同一段对同一个库的值域给了两个互斥枚举；`format/config-keys.json` 的 `kind` 实际含 `list`，正文却没有对应的库语义（列表只追加、不能按元素覆盖）。
  · 影响：实现者会把两份列表键（例如 `VALIDFONTCHECKER` / `JUSTIFYCHAR`）当普通字符串覆盖，或直接不实现列表。
  · 建议的“需要什么证据才能修”：逐个 `kind` 对齐“默认表 / 玩家文件 / 保存”三条路径，确认列表键在库内是可覆盖还是只追加；以键表数据与装载点两边取证。

[自相矛盾] 40-pools（支持集合与不支持的组合）
  · 现象：“| 读整型 | 0–13；`0x8003`；`0x8009` | 8、14；…… |”；“| 读浮点 | 0–13；…… | 8、14；…… |”。
  · 为什么是问题：`0–13` 含 8，同一行又把 8 列为“明确不支持（抛）”；读整 / 读浮两行都如此。
  · 影响：实现者对 type 8 的读要么返回值，要么抛异常，两种都“符合”表格；后续 `0x1a3` / `0x1aa` 一类只用 type 8 的键路径会被写错。
  · 建议的“需要什么证据才能修”：核对五个原语跳转表里 type 8 的 case / default（`audit.pilot.sites` 已把 read-int case 8 标成 default），再决定表里该写 `0–7、9–13` 还是别的分段。

[自相矛盾] 40-pools（五种访问原语 / 五种访问原语的入口契约）
  · 现象：“| 读浮点 | 按浮点语义取值 | 32 位浮点数 |”；同章规则写“读浮点返回 64 位浮点”，后文又写“读浮得到该数（读原语返回 64 位浮点，值相同）”。
  · 为什么是问题：返回值宽度是入口契约的核心；32 与 64 不能同时成立。若“32 位存储在池里、64 位返回”是意图，正文没有一句话把两者分层。
  · 影响：跨语言实现会按 32 位返回（丢精度）或按 64 位存池（破坏槽宽），两边互不兼容。
  · 建议的“需要什么证据才能修”：取证读浮原语的返回类型 / 调用约定，以及调用方接收后如何截断；明确“池内表示”与“原语返回值”是两个量。

[自相矛盾] 15-frame（引擎里的脚本帧栈）与 60-ops（0x3 / 0x2）
  · 现象：“帧的数量上限是 **40**：第 40 层再要新帧就报错，报错文本是‘最大 40’。实现**不得小于 40**”；60-ops 写“帧号到 39 就不再进（引擎报「階層が深すぎます」）”。
  · 为什么是问题：同一个容量给了两种边界（第 40 层 vs 帧号 39）和两条不同的错误文本；“上限 40”与“实现不得小于 40”也互相拉扯（容量到底是合同 40，还是至少 40 的实现下限）。
  · 影响：off-by-one；实现者可能允许第 40 个帧或提前报错；错误文本不一致会让测试断言错。
  · 建议的“需要什么证据才能修”：在 39/40 两个边界做一次真实嵌套观测，记录实际错误文本与帧号；同时确认“父帧号 + 1”与“帧号 + 1”在父帧不是当前帧时是否同值。

[自相矛盾] 15-frame / 60-ops（换脚本与返回点）
  · 现象：15-frame 说“换脚本占用「父帧号 + 1」那个槽”；60-ops 的 `0x3` 步骤只写“帧号 +1……子脚本的指令指针 = 子代码区起点”，最后却说“父帧的指令指针停在调用点，子脚本结束后由父帧自己的长度槽推进到下一条”。
  · 为什么是问题：`0x3` 列出的三步没有任何一步写父帧的“长度槽”；`0x2` 却把父帧推进完全寄托在这个槽上。若父帧的长度槽保留旧值，返回后会跳错；若由处理函数自己写，正文没写。
  · 影响：父脚本返回后可能停在原地、跳过指令或死循环；这是“调用 / 返回”合同的核心缺口。
  · 建议的“需要什么证据才能修”：取证 `0x3` 是否在切换前写父帧长度槽、写的是 `1 + 2×argc` 还是别的；再与 `0x2` 的“父帧长度槽推进”逐条对上。

[自相矛盾] 50-engine-state（三条 handler 的公共前导）
  · 现象：“**引擎级**：属于引擎本身，不随当前帧变化”；规则却写“都先把当前帧记录的一个字段写成常量 **5**”。该规则还说“这个字段的**用途**（是否是指令推进计数）不在本版范围，交给 `CORE-VM`”；10-format 已写“由 opcode 对应的处理函数在运行时写进当前帧的‘操作数个数’槽”。
  · 为什么是问题：章节标题承诺“不随帧变化”，规则却写帧记录；同一字段在一章是“用途未定”，在另一章是“已定的操作数个数 / 推进计数”。
  · 影响：实现者会把该字段放进引擎全局，或不知道它是否参与 `ip` 推进；50 与 10 的读者得到相反结论。
  · 建议的“需要什么证据才能修”：取证该字段的读写点是否都在帧记录内、谁读它算 `ip`；确认 `5 = 2×2+1` 是“操作数记录数”还是另一个独立标志。

[自相矛盾] 55-config（配置库的键 / 脚本访问）
  · 现象：“键是 ASCII 名”；“**键不是操作数里的值**，而是 `（类型码, 表下标）` 拼成的 **12 字节键**”；“键的文本形式是类型码字节 + 8 位十六进制下标”。
  · 为什么是问题：同一库既说键是 ASCII 名，又说键是二进制 12 字节键；按后一句的组成（1 字节类型码 + 8 个十六进制字符）只有 9 字节，不是 12。`库里按字节精确匹配`、`命名空间`、`词表` 等规则只对 ASCII 名成立，对二进制键没有定义。
  · 影响：实现者无法决定键的宽度、比较方式、是否与窗口尺寸等命名键共表；`12` 与 `9` 必有一错。
  · 建议的“需要什么证据才能修”：取证脚本键的构造点（类型码字节、下标宽度、是否补零 / 对齐到 12）与比较函数；确认命名键与脚本键是否同一张表、是否有命名空间前缀。

[自相矛盾] 10-format（切分与操作数个数）与 format/opcode-table.md
  · 现象：“`argc` **不在脚本里、也不在任何数据表里**：它由 opcode 对应的处理函数在运行时写进当前帧的‘操作数个数’槽”；同节开头却写“分派一条指令之前，引擎先读一个 32 位整数作 opcode；随后按该 opcode 的 `argc` 把紧随其后的 `argc` 组 `(type, raw)` 原样切出来”。伴随数据却写“每条 `{opcode, argc, name, aliases}`”“`argc` 是决定指令边界的唯一字段”。
  · 为什么是问题：分派前需要 `argc` 切操作数，分派后才由 handler 写 `argc`，是循环依赖；同时“任何数据表里都没有 argc”与本规范自带的指令表直接冲突。
  · 影响：独立实现者会从 `opcode-table.json` 读 `argc`（被正文禁止），或实现成“先分派再回读长度”（无法切出操作数）。
  · 建议的“需要什么证据才能修”：取证真实分派器取操作数的时刻与长度槽的来源；确认 `opcode-table.json` 的 `argc` 是“规范合同”还是“handler 行为的静态投影”，并在两处统一表述。

[自相矛盾] 40-pools（引用族 / 容器句柄）
  · 现象：“指针槽本身**不参与编解码**：取址原语直接返回槽内容”；容器句柄规则写“池槽里装的是一个**容器对象指针**（与整型值一样编码存放）”。同章又说池访问“没有边界检查”，容器写路径却写“非空路径上的下标检查会抛‘容器下标越界’”。
  · 为什么是问题：若 handle 是“整型池的容器句柄”，它就在整型池的槽里；一处说指针不编码，一处说按整型编码存放，必有歧义。边界检查也一样：池说没有，容器说会抛。
  · 影响：实现者对 handle 槽做 / 不做 `DEC` 都可能“符合”；容器越界路径会被写成 clamp、静默或抛异常三种。
  · 建议的“需要什么证据才能修”：取证 handle 槽的读 / 写是否走整型 `ENC/DEC`、容器写路径的索引检查在哪个分支；区分“池下标检查”与“容器元素下标检查”两个域。

[自相矛盾] 40-pools（立即值 / 字符串引用）
  · 现象：“**0–2**……本版只登记‘接受’，**不规定**它们的值语义”；同章 `CORE-POOL-TAG-IMMEDIATE` 却逐条定义“**0**：raw 就是值本身……**1**：raw 的位模式就是一个 32 位 IEEE-754 浮点……**2**：raw 是一个文本偏移”。另一条写“本版**不规定**字符串引用的读语义”，支持集合表却把 type 8 的读写成“抛异常”。
  · 为什么是问题：同一标签同时处于“已规定”与“未规定”；“抛异常”是明确的可观察行为，不是“不规定”。
  · 影响：实现者可能跳过立即值语义，或把 type 8 读实现成“未定义 / 返回 0”而不是抛。
  · 建议的“需要什么证据才能修”：决定哪些标签是合同、哪些是缺口；把“不规定”和“抛类型异常”分列，不要在同一张表里混用。

[自相矛盾] 20-alf / 30-agf（LZSS）
  · 现象：20-alf 写“★ AGF 的 LZSS 参数不同（最短匹配 3），不能互相替代”；30-agf 写“AGF 使用与 ALF **不同参数**的 LZSS”，随后列出的窗口 `4096`、最长 `18`、最短 `3` 与 ALF 的“窗口 `4096`、最长 `18`、最短 `3`”完全相同，真正新增的只有“窗口初始位置 `4078`”。
  · 为什么是问题：用“最短匹配 3”作为“参数不同”的理由，但两边都写 3；读者无法知道真正的差异集合。
  · 影响：实现者可能复用 ALF 解压器（忽略初始位置 4078），得到错误输出；也可能以为两边只差最短匹配。
  · 建议的“需要什么证据才能修”：逐参数列出 ALF / AGF 的完整参数表（窗口、初始位置、flag 方向、位置 / 长度位分配），确认哪些真不同、哪些只是未写。

[自相矛盾] 70-vm（一次迭代只做一件事 / 场景计时窗）
  · 现象：“主循环的每次迭代按固定优先级**只做一件事**：回一次宿主消息、或者服务状态选择字里的**一个**位、或者**执行一条**指令”；计时窗规则却说“推进必须**每帧都跑**：帧首清标记、窗推进分支置标记”，而“门”非 0 时本迭代“只服务其中一个位”。
  · 为什么是问题：窗推进既不是“消息”、也不是“状态位”、也不是“执行一条指令”，在“一次迭代只做一件事”的枚举里没有位置；若它每帧都跑，就与“只做一件事”冲突。另“迭代”与“帧”在 70-vm 内混用。
  · 影响：实现者可能把窗推进塞进位服务分支（导致某些位被服务时窗不推进），或每帧多跑一件事（破坏“至多一条指令”）。
  · 建议的“需要什么证据才能修”：取证主循环里窗推进的实际位置与每次迭代次数；明确“帧”是否等于一次迭代，还是独立的呈现节拍。

[状态对应表与正文不一致] 60-ops（0x2f6）
  · 现象：状态对应表写“该组的 8 格被重置 | 语音对象 4 格（后端存在时）+ 引擎级 4 格（无条件）← 0”；正文却写“★ 这一整步只在**声音后端存在**时发生：后端不存在时，引擎连这 4 格也不清（那 4 格保持原值）”。
  · 为什么是问题：表格的“8 格被重置”对无后端路径不成立；括号里的条件只覆盖“语音对象 4 格”，却没有覆盖“8 格”这个总和。
  · 影响：实现者按表统一清 8 格，在无后端时多写 4 格；或按正文写，却与表的“8 格”断言冲突。
  · 建议的“需要什么证据才能修”：在无后端路径上观察那 4 格是否保持原值；把表改成“有条件重置”的两行，并与正文的条件逐字对齐。

[状态对应表与正文不一致] 40-pools（局部池 / 支持集合）
  · 现象：“指针族（12 / 13 / 14）的槽装地址；读 / 写都要经过一次解引用”；支持集合却把写整型的 13、14 列为“明确不支持（抛）”，把读整 / 读浮的 8、14 列为“明确不支持”。
  · 为什么是问题：正文把 14 当作可读写的指针族，表却对 14 的读写都抛；表的状态对应也只列了 12，没有 13 / 14。
  · 影响：实现者会对 type 14 做解引用，或把 13 的写实现成可用；两种都与表冲突。
  · 建议的“需要什么证据才能修”：逐个 type 核对 13 / 14 在五个原语里的 case / default；确认“指针族 12/13/14”是否只对取址成立。

## 二、数字 / 枚举：没有说明来源，也没说明是不是合同

[数字/枚举没有依据] 55-config（脚本访问）
  · 现象：“拼成的 **12 字节键**”；“类型码字节 + 8 位十六进制下标（不足 8 位左补 0）”。按组成是 1 + 8 = 9 字节。
  · 为什么是问题：`12` 不是由任何字段布局推出来的，正文也没说这 12 字节里除类型码 / 下标之外的 3 字节是什么。
  · 影响：键宽、对齐、比较、持久化都会写错；9 与 12 的差会让所有脚本键读不到。
  · 建议的“需要什么证据才能修”：取证键构造的字节布局（类型码宽度、下标宽度、填充 / 终止符），确认 12 是容器宽度还是键内容宽度。

[数字/枚举没有依据] 50-engine-state（0x30a）
  · 现象：“两条检查：**值 ≤ 31** 且 **索引 ≤ 7**；任一越界 ⇒ **抛异常**”；“带一个固定的异常码”。
  · 为什么是问题：表只有 8 格，值上界却是 31；31 是“值的合法范围”还是“类型标签 / 位宽”没有说明。异常码数值也没给。
  · 影响：实现者可能把值上界写成 7 或 255；异常码无法复现，测试无法断言。
  · 建议的“需要什么证据才能修”：取证 handler 里的比较常数与异常码；说明 31 是领域合同还是从别的机制借来的上界。

[数字/枚举没有依据] 60-ops（0x2f8）
  · 现象：“通道号 = 组号 + 一个固定偏移。**通道号 ≥ 15 一律拒绝**”；同章 0x2f6 又写“偏移属机器细节，本规范不规定”。
  · 为什么是问题：拒绝条件依赖一个被明确拒绝写出的偏移；不给偏移，读者无法计算“≥ 15”对应哪个组号。
  · 影响：组号 0/1/2 中哪些被拒会因实现者猜的偏移而不同；音量规则不可独立实现。
  · 建议的“需要什么证据才能修”：取证通道号偏移与 15 的来源（是否为后端通道总数）；要么把条件改写成可观察的组号范围，要么给出偏移合同。

[数字/枚举没有依据] 40-pools（字符串记录 / 容量与分配）
  · 现象：“容量小于 **16** 时，字符串字节内联在记录自己的缓冲区里”；“每个池按‘计数 + 一个**随机余量** + 1’分配”。
  · 为什么是问题：16 是内联 / 间接的分界，却没有说它是可观察合同、记录字段派生值还是实现常数；“随机余量”既不可复现，也被说成“不是语义容量”，读者不知道它对容量规则有没有影响。
  · 影响：SSO 判别阈值写错会让所有字符串记录走错分支；“随机余量”被实现成固定值或直接忽略，容量分配不可复现。
  · 建议的“需要什么证据才能修”：取证 16 是记录内的哪个字段、是否被读取比较；确认随机余量的实际作用（是否只影响分配大小，不影响合法下标）。

[数字/枚举没有依据] 10-format（opcode 域与缺省处理器）
  · 现象：“处理函数表固定 **1024 项**：先全部填成缺省，再逐项覆盖（本作覆盖 **544 项**）”；核验表又提“**30 条**‘有编码、无处理函数’”。
  · 为什么是问题：1024、544、30 的关系没有给出（544 + 30 = 574，既不是 1024 也不是 0x400）；读者不知道“覆盖”是相对 1024 还是相对有编码条目。
  · 影响：实现者会按 1024 建表却只填 544，或把 30 条“无 handler”误当覆盖；域边界与缺省判定会写错。
  · 建议的“需要什么证据才能修”：给出“域大小 / 有编码条目 / 有 handler 条目 / 缺省条目”的计数口径与来源，确认 544 是 handler 数还是“非缺省表项”数。

[数字/枚举没有依据] 20-alf（索引头）
  · 现象：表头列“头长 300 / 加装档段起点 268 / 归档记录 256 / 文件名 64 / 文件记录 80”；正文又说“头的前 240 字节是标题，后 60 字节是未知区”“段起点之后是 12 字节段头”。
  · 为什么是问题：同一张表混用了偏移（300、268）与宽度（256、64、80），没有列语义；`268 = 256 + 12` 之类的算术关系也没有说明，读者无法判断“加装档段起点提前”到底提前到哪个结构边界。
  · 影响：加装档（`AC` 签名）索引解析会从错误位置读段头；TOC 的 `archive_count` / `file_count` 起点随之错位。
  · 建议的“需要什么证据才能修”：把每个数字标成“偏移 / 宽度 / 元素数”，并给出 S4 与加装档两条布局的字段顺序；用一份 `AC` 样本核对 268 的实际语义。

## 六、其他歧义（正文无法唯一实现）

- **70-vm 计时窗**：“若‘现在’落在 `起点 + 延迟 + 持续时间` 之内”没有给下界、上界开闭和 clamp；“按 `(现在 − 起点 − 延迟) / 持续时间` 插值”没有定义 `持续时间 = 0`、进度 > 1、起点为 0 哨兵与真实时刻 0 撞车时的行为；“到期”也没有定义成可判定的不等式。
- **30-agf 像素 / alpha**：“若 meta 只有约 1024 字节且没有头，则取最后 1024 字节”——“约”和“没有头”都不是可判定条件；“alpha 的长度应等于 `width × height`；不等时实现不得把它当成完整 alpha 使用”——“不得当成完整”之后该做什么没有说（拒绝？部分使用？）。
- **20-alf / 30-agf 的 LZSS 位流**：只写“每个 flag 字节管 8 个单位”“`hi` / `lo`”“位置 12 位 / 长度 4 位 + 3”，没有定义 flag 的位序（MSB-first / LSB-first）、`hi` / `lo` 哪个字节在前、匹配距离是“窗口内偏移”还是“回退距离”。这些不定义，字节流无法唯一解码。
- **55-config 玩家文件**：“行缓冲有上限，超长行会被切开（不是错误）”——上限值、切开后是否保留剩余部分、切开是否算两条，都没有说；读者无法复现超长行行为。
- **55-config 默认表**：“条目**按文件顺序**处理，且处理前先把列表键清空”与“列表键：同名的多次出现**按顺序追加**，后出现的条目不会清掉先出现的条目”需要说明“清空”是一次性（整表处理前）还是逐条；否则两种实现都读得通。
- **55-config 收尾修补**：“若‘菜单保存开关’为 0、主版本为 1、次版本为 0，则把主 / 次版本改为 1 / 10”——“菜单保存开关”是哪个键没有给出（键表里有 `MENU_SAVE`、`NOSAVEDAT` 等候选）；`1/10` 也没有说明是“版本 1.10”的编码还是两个独立常量。
- **60-ops 0x1f9 颜色键**：“不透明黑 | (值 & 0xFFFFFF)”——“不透明黑”没有给出数值（是否为 `0xFF000000`）；类似地 0x202 的“现有颜色的高字节”没有说明是 `0xFF` 还是别的位段。
- **60-ops 0x73**：“`0x73` 有**十个**操作数（本版最长的一条）”——0x320 也有十个操作数，“最长”不唯一；若只是“最长之一”，措辞应改。
- **60-ops 0x70**：“三个字段对 ← (第 2 个, 第 3 个)”——一个源对写三个字段对，还是三个字段对分别对应不同操作数？表也只列两行，读者无法知道“三个字段对”与“两对值”的关系。
- **60-ops 0x88 / 0x101**：“状态选择字的**第 27 位**”没有说明位号从 0 还是 1 起；“清状态选择字里的**一个位**”没有说哪个位；这两个“位”都无法实现。
- **10-format 版本阈值**：“版本串 **≥ 阈值**（本作观测：4 字节 ASCII 的 `"080 "`）”——4 字节 ASCII 的“≥”是按字节字典序、按整数、还是按版本号解析？没有定义；`"080 "` 的尾随空格也属于阈值的一部分还是填充，没有说明。

### ★ handler 归属更正：`0x8` 不是 `sub_41C8D0`

判据是**分派表的表项偏移**（`opcode = (表项偏移 − 0xA509C)/4`）：

| 表项 | 赋值行 | opcode | 函数 |
|---|---|---|---|
| `0x0A50B4` | `mov dword ptr [esi+0A50B4h], offset sub_41C7C0` | **6** | 装载帧（长度槽 **5** = 2×2+1） |

| `0x0A50BC` | `mov dword ptr [esi+0A50BCh], offset sub_41C900` | **8** | 换帧（本文的主角） |

⇒ **"长度槽写 3" 不能用来认归属**：`0x7` 与 `0x8` 都写 3（argc 1）。上一轮把 `sub_41C8D0` 记成 `0x8`，
正是拿长度槽当判据的结果；`0x6` 的长度槽 5 只是**推翻**了"0x6 写 3"那条，并没有指出 0x8 是谁。

## 十四、参考实现（`apps/emulator-new`）的帧模型对齐（2026-10-21）

**问题**：`emulator-new` 的帧模型是 **LIFO 栈**（`frames: ScriptFrame[]` + `pushScriptFrame/pop`），
**根本没有"帧号"**：`0x3` 用"栈深"当深度、`0x2` 弹栈顶、`0x9` 清空栈。已有守卫全落在 LIFO 子集内
⇒ 绿是逃逸（缺陷单 `REQ-01M5D251ZJTZA4S6SX170RAXD2`）。

**改法**（与 `CORE-FRAME-STACK` / `CORE-OPS-FRAME-*` 对齐）：

- `frames` → **`slots: (ScriptFrame|null)[]` + `cur`**（根帧占 0 号槽；空槽是显式 `null`）。
  `body` / `ip` / `frame` / `operandCount` 变成**槽 `cur` 那条记录的访问器** —— 单一真源，不再有"副本 + 同步"。
- `ScriptFrame` = `{ body, ip, frame, parent, length }`：`parent` = 父帧号；`length` = **该帧自己**的长度槽
  （分派器写 `2·argc+1`、控制转移清 0 都落在当前帧那一格上）。
- `enterScript`（`0x3`）：`cur + 1` 号槽建子帧；**深度按槽号判**（`slot ≥ 40`）。
- `returnToCaller`（`0x2`）：当前帧号 ← **父帧号** + **有条件释放**（父号 + 1 == 当前号）+ **向下跳过空槽**。
- `loadFrameAt`（`0x6`）：任意槽写记录、**`cur` 不动**、父帧号 ← 装载者。
- `callFrameAt`（`0x8`）：切到已装载槽、父帧号 ← **切帧者**、`ip ← 0`、长度槽 ← 0；未装载 ⇒ 报错（文本含帧号）。
- `0x9`：释放全部帧，只留 0 号槽的根帧。

**守卫（会红的判据）** —— `tools/test/emulator-new-frame.test.mjs` 新增 6 条：
跨槽返回（父号 0 / 当前号 3）· 深度按帧号 · `0x6` 记录落在指定槽且 `cur` 不动（含槽复用）· `0x8` 切帧 + 跨槽返回 ·
父帧号 ← 切帧者（装载者 ≠ 切帧者）· `0x8` 未装载 ⇒ 报错且当前帧不变。
变异 6 条（`tools/mutate-check.mjs`，`--match` 各 **1/1 红**）：`0x2` 退化成 `cur -= 1` · 无条件释放 ·
不写父帧号 · 不拨回 `ip` · 装载顺手改 `cur` · 深度改按"已占用槽数"。

**边界**：两条新规则的 `bindings.evidence` 各自多挂一条 `emulator-new` 的守卫（"spec 驱动实现"的观察）；
引擎级事实仍以 `KN-01M5F56MPF2S5R1M4Q1V6E7M4T`（`0x8`）与既有 `0x6` 台账为准 —— 实现不是 spec 的真源。

## 十九、缺陷归因：三个案例（2026-10-23）

本节格式固定为四个字段：**错误类型 · 判据 · 本次处置 · 下次 review 要问什么**。
三个案例的共同点都不是"实现少写一行"，而是**归因**把观察导向了错的落点：
一个把 opcode 划出域、一个把哨兵写成值、一个把引擎决定划给平台。
判据是同一句：**先写可观察量，再问"这是谁做的决定"**。

### 案例 1：`0x23b` 被归进「ADV 文字未建模」白名单

- **可观察量**：TITLE 的 `Version 0.00.0000` 只剩两个小数点，七位数字没有画出来（像素层面：数字条位置空着）。
- **错误类型**：**误归类** —— 把"未成篇"当成"不属于本域"。`0x23b` 同时挂在 `audit.chapters.adv.residual.next`
  的"ADV 入口候选"与 `ops-unwritten` 的 0x200 段白名单里，两边都不再查它的真实消费者。
  它其实是**场景侧 CG 数字条**：外观来自 `0x2da` 登记的七格记录，逐位**建绘制项**（与 `0x1fb` 同表）。
- **判据**：白名单里的每个 opcode 都要至少回答一次"谁在什么条件下用它、它改哪些引擎数据"。
  `0x23b` 的消费者是 TITLE 自己，效果是建绘制项 —— 两条都答得出，就不该留在"ADV 文字"里。
- **本次处置**：`60-ops-scene` 新增 `CORE-OPS-SCENE-CG-NUMBER-23B`
  （两条返回路径 / 读序 / 清理 / 逐位 / 三种对齐 / 源矩形 / 键序），并把 `CORE-OPS-CG-SET` 的七格身份写成合同；
  `ops-unwritten` 的 0x200 段移出 `0x23b`；ADV 残差的 `next` 改成"别再拿它当 ADV 入口"；
  实现从 `unmodeledHandler` 换成真实 handler，守卫 `emulator-new-cg-digit.test.mjs`（几何单测）与
  `emulator-new-title.assets.test.mjs`（真实启动链上七位数字 / 两个小数点的源矩形），
  变异覆盖"源格子用错字段 / 丢前导零判据 / 退回未建模"。
- **下次 review 要问什么**：① 七格记录还有没有别的读者（存档 / ADV）？② 位数 < 0 时清理区间的上界低于下界，后果是什么？
  ③ 当初把它归进 ADV 白名单的依据是什么 —— 同一批白名单里还有哪些 opcode 没做过"真实消费者"这一问？

### 案例 2：`0x1f9` 的 `0` 是「无键」，比较是 32 位 ARGB

- **可观察量**：TITLE 的不透明黑描边被清成洞（像素层面：描边位置透出背景）。
- **错误类型**：**哨兵语义写反 + 比较位宽写窄**。旧正文写"负数 ⇒ 0"，并把 `0` 与 `0xFF000000` 都叫"黑键"；
  旧实现只比 RGB。实际是：负数 ⇒ 键 **0**（四段全 0 = **无键**）；非负 ⇒ `0xFF000000 | (操作数 & 0xFFFFFF)`
  （不透明黑键）；上传期按 **32 位像素值**比较，A 参与。
- **判据**：哨兵若表示"无"，必须写清它**为什么**不等于长得像的那个值（`0 ≠ 0xFF000000`，差在 A），
  并写出比较位宽与参与位段。可证伪观察：一张含不透明黑描边的图 + 负颜色键 ⇒ 只比 RGB 的实现会把描边清成洞。
- **本次处置**：`60-ops-texture` 的状态模型新增「颜色键」条；`CORE-OPS-TEXTURE-SET` 的归一化改成
  "负 ⇒ 无键 0 / 非负 ⇒ 不透明黑键"；`CORE-OPS-TEXTURE-LOAD` 的上传命中判据改成 **32 位像素值相等**
  （并写明调色板 / 24 位图先补 A=0xFF）；`RES-TEX-LOAD-KEY16` / `KEY-PIXEL` 收窄到 16bpp / 8bpp 的位模式；
  实现改为按 ARGB 全值比较，守卫 `emulator-new-agf.test.mjs` 新增
  "键 0 不清不透明黑 / 半透明黑不命中黑键 / 通道不许互换"，变异"只比 RGB"。
- **下次 review 要问什么**：① 16bpp 与 8bpp 命中后的目标位模式是否要升成合同？
  ② 还有哪些哨兵是"长得像值、其实是'无'"（空串 / `-1` / `0xFF000000` / 缺键）？
  ③ 归一化在别的指令里有没有第二份实现（重复定义会漂）？

### 案例 3：绘制顺序被推给平台边界

- **可观察量**：同屏条目的叠放顺序（谁盖住谁），以及引擎发出的绘制请求序列。
- **错误类型**：**把引擎决定的事推给平台边界**。原先的说法是"`present` 属平台，所以顺序不用规定"；
  实际引擎决定"谁先谁后"：两类可绘制条目按**条目键严格升序**发出，同键时**网格先于绘制项**，负键不参与。
  D3D 只执行。
- **判据**：说"归平台"之前先拆成**请求内容 / 请求顺序 / 请求之后的像素**；顺序由引擎选 ⇒ 顺序是边界契约的一部分。
  可证伪观察：同键放一条网格与一条绘制项，若绘制项先发出 ⇒ 规则错。
- **本次处置**：`60-ops-scene` 新增 `CORE-SCENE-DRAW-ORDER`（含 falsifier），章首与 `60-ops-render` 的 `0x20c`
  措辞改成"遍历 / 顺序是引擎行为，有命令记录的两档尚未成篇"；实现按同一序合成，
  守卫 `emulator-new-scene-order.test.mjs`，变异"退回先绘制项后网格 / 同键类别序写反"。
- **下次 review 要问什么**：① 有场景命令记录时的两档顺序（命令区间先 / 全键域收尾）何时成篇？
  ② 另两类可绘制条目的语义与同键位置？③ 平台侧还有没有别的"顺序"被默认成自由选择（多渲染目标、`present` 与提交的先后）？
