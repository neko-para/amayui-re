# 引擎 spec 的基建方案：精化范围审计的技术评审稿

> **评审问题**：在没有原项目总体设计、不能运行原引擎做内存差分的条件下，如何重建可独立实现的 spec，并查清每次精化处理了哪些机器行为、还留下什么？当前覆盖方案是否值得做，还是应换一种方法？
> **讨论状态**：问题与保证边界已明确；技术路线仍在讨论。不能把候选效果模型、指标、落点或检查策略当作已批准实现。
> 方法需求：[`REQ-01M5851Z51V1MTSWH414M7WN5Q`](../../data/requirements/01M5851Z51V1MTSWH414M7WN5Q.md)。
> 不变的项目口径：[`project-intent.md`](../00-origin/project-intent.md)（spec 是主交付物 · 两层本体 · 证据四类 · 不说“与引擎等价”）。
> **评审尺度**：先判断是否解决了下面的两个核心困难，再评估具体方法；不预设必须采用本方案，也不以字段设计代替方向评审。

## 1. 背景、问题与保证边界

### 1.1 两个核心困难

1. **没有原项目的总体设计可作为权威输入。** 只能从反汇编及其他可获得证据重建知识，不能先假定已有完整的领域设计，再把汇编当作事后验收材料。目标是形成有依据、能独立实现的领域模型，不是猜出原作者的设计意图。
2. **纯自顶向下的声明与实现会共享错误认识。** 用户报告旧项目反复陷入“发现问题 → 发现是实现错误”的循环；错误到集成行为异常时才暴露，难以区分理解、抽象、绑定与实现各层的问题。仅证明 emulator 遵守我们写的 spec，不能证明 spec 的解释有依据或没有遗漏。

因此需要双向约束：从机器观察提出并核验抽象候选；从领域模型提出待回答的问题；让 spec、机器绑定与实现合同彼此可追查。没有总体设计不是暂停抽象的理由，也不是把候选抽象直接登记为事实的理由。

### 1.2 覆盖系统为什么被提出

覆盖系统首先要回答：**接受一条 refine（精化）解释后，它处理、替换或明确舍弃了哪些代码上的行为义务？哪些尚未处理，需要补 spec、论证可省略，或继续研究？**

这不是“给研究进度加一个百分比”，也不是“把散文全部编译成脚本就能证明解释正确”。必须分开两件事：

* **精化依据**：为什么这个抽象可以解释相关机器行为，成立条件及证据是什么？
* **处理范围**：上述解释处理了什么、没有处理什么，剩余义务是否还在账上？

覆盖报告是第二项的摘要。**账闭合不等于解释正确；局部解释有依据也不等于范围完整。**

### 1.3 不增加“手工转写汇编”知识层

不要求先把整个函数完整转写为伪代码或散文，再从转写件生产 spec。那不会增加独立证据，却会增加一份需要维护与信任的语义副本。

像 shape 一样的分析支撑仍有意义：**类型、载体、视图等声明是待核验模型；扫描、CFG、数据流和报告是可重算的派生视图；语料是机器侧核验依据。** 派生视图辅助理解与计算，但不是独立证据，分析器的支持范围与未知必须显式化。

精化绑定只呈现抽象所需的最小论证：抽象合同、机器范围、状态对应关系、成立条件、检查或推导、剩余义务；不另造一份“完整函数行为转写”或并行替换台账。

### 1.4 必须保留的保证边界

* 目标是在可获得证据下可审计、可独立实现，不追求或宣称与原引擎等价。
* 本项目没有运行原引擎做内存差分 / trace 的条件；局部离线指令语义核验可另行试点，但不是现成能力或前置承诺。
* 自然语言到检查器存在忠实度风险。检查器是 spec 的**可执行投影**，通过只支持它明确检查的属性；不能自动覆盖正文中未形式化的内容。
* 机器范围、效果与调用摘要也可能未知；未知不能静默消失或被默认排除。内部一致性不替代真机观测、游戏数据、三方资料与第二实现这四类独立证据。
* 本轮只定方法、允许已有有效依据支撑的样例；不批量写入新的引擎语义，也不以全域语义清零作为方法单收口条件。

## 2. 候选方案的五条技术主张

| # | 候选主张 | 成立条件 | 不能由它推出什么 |
|---|---|---|---|
| 1 | **指令 / EA 适合作为可追溯的账本底数** | 固定语料、枚举口径与作用域；范围变化显式报告 | 不是唯一可能的指标，也不代表解释正确；函数区间被引用不等于其全部行为已处理 |
| 2 | **按指令上的行为义务登记精化范围，用守恒暴露残差** | 效果识别有支持边界；未知单列；同一义务统计去重，多条规则可以共同支持 | 守恒只检查归属完整性，不证明值、条件、对象身份或抽象语义正确；调用摘要不因目标已知而自动成立 |
| 3 | **规则存选择器，实例从语料重算** | 固定分析器、摘要、依赖状态与配置；检查器和适用域具有可审查依据 | 现算不等于算对；召回缺口需要独立的“应适用集合”，没有该集合就只能报告不可测 |
| 4 | **必要顺序可以局部静态检查，不可判单列** | 明确事件作用域与条件，相关控制流完整，采用与约束匹配的判据 | 支配关系不是通用运行时顺序证明；未知边、循环与异常不能默认通过 |
| 5 | **精化绑定与 spec 同处组织，引用 shape 与 ledger** | 机器布局和原子结论不复制；状态映射、组合语义有依据；依赖失效传到覆盖结果 | 单向引用不能证明抽象正确；`storage` 只回答“在哪里”，还需说明“如何表示抽象状态” |

这些是待验证的技术选择，不是从项目 intent 必然推出的实现。若某个自动判据不可行，应缩小能力或替换策略，不必连同精化范围审计的需求一起放弃。

## 3. 已有基础与尚需验证的能力

| 已有设施 | 能支撑什么 | 不能代替什么 |
|---|---|---|
| 反汇编语料 + EA 定位 + 调用目录 | 追溯机器站点、枚举候选范围 | 完整 CFG、未知调用目标与调用效果摘要；已知调用闭包只是下界 |
| opcode ↔ handler 桥 | 规则的候选已知集合 | 每个成员的语义与适用性核验 |
| shape 声明、扫描与独立复核 | 机器 context、绑定目标与结构债务 | 领域含义、计算关系、所有调用效果及语义闭合 |
| handler 体骨架 | 发现可共享规则的候选族 | 骨架相同不保证计算、参数、路径条件或领域合同相同 |
| ledger | 有效原子结论、证据与冲突 / 失效状态 | 新抽象及组合规则的自动背书 |
| emulator | 规范消费者、行为测试与缺项反馈 | 原引擎 oracle；与 spec 共享误解仍可能一致通过 |

**可行性待试点，而不是“机械件已在所以基本做得成”。** 新工作包括精化绑定、范围登记、残差审计与检查能力边界；若要核验计算关系，还需额外的局部语义分析。覆盖设施本身不创造独立证据，也不能自动补出领域知识。

**shape 闭合度是结构分析就绪度，不是 spec 覆盖率的数值上限。** L0 闭合不代表直接调用等语义已闭合；未闭合函数仍可能存在不受未知部分影响的局部解释。应检查具体规则的依赖与未知影响，不能整函数一刀切通过或作废。

设施与数量的复核入口见文末“怎么查”；本文不以未重新运行的快照数字证明可行性。

## 4. 四个关键取舍（仍待定案）

### 4.1 度量：先有处理账，再讨论覆盖率头条

**候选**：指令 / EA 做可枚举账本，行为义务做局部精化范围；报告从逐项处理记录派生，不反过来用百分比定义“已经理解”。

处理状态至少要能区分：

* **由 spec 处理 / 替换**：指向精化绑定，说明保留的行为及其依据；同一指令可只处理部分效果。
* **实现内部步骤可省略**：有依据表明不影响所声明的合同或边界行为；不能仅因寄存器计算、不在 DAG 里或未找到读取者就默认省略。
* **明确舍弃**：项目选择不保留的行为，有理由、范围与影响，和“已解释并保留”分列。
* **尚未处理 / 无法判定**：仍需补 spec、核验可省略性或继续研究；不能自动变为前三类。

指令粗覆盖与已解析效果的完整处理比例可以作为候选指标，但后者必须同时展示未知影响与舍弃项。未知调用不能因无法展开就移出分母、或被当成一个已知等权小效果。具体效果粒度、统计公式与“粗 / 严”命名待试点，不再把严覆盖解释为“真的搞懂”。

**替代**：若效果模型成本过高，先用指令及局部范围账加逐项残差；允许更粗的指标，但必须注明不能细分的行为，不能默认整段已闭合。

### 4.2 落点：精化绑定属于 spec，不另造转写或替换真源

**候选**：独立 spec 落点组织领域合同及其精化绑定。正文可保留自然语言；关键可检查部分明确为可执行投影，不要求先建设通用形式语言。

绑定呈现：抽象合同、适用上下文、机器范围、**机器—领域状态对应关系**、成立条件、证据 / 检查方式、处理范围与残差。`storage` 引用 shape 布局，原子结论引用 ledger；组合解释及模型选择仍需说明依据，不能因引用存在就被背书。

一条 spec 可跨多个函数，一个函数也可支持多条 spec；helper 的局部行为与调用上下文共同支持领域操作，不强求函数与抽象一一对应。

**替代**：先用结构化文档加可重算的局部绑定，或复用 ledger 当前模型投影。选择依据是能否维护单一语义出处与失效传播，不是“散文完全无用”或“多一个落点必然错误”。禁止再维护完整函数转写层；派生分析缓存可以存在，但必须可删可重建并保留来源。

### 4.3 顺序：合同要求的顺序才是义务

**候选**：只约束合同必须保留的事件关系，明确适用路径、事件作用域与重复事件含义。静态检查从相关控制流完整的局部范围开始；支配、后支配或路径判定依约束选择，不把支配关系作为通用判据。

违例、满足、不适用、无法判定分别报告；未知边不能证明不可达，互斥与循环也不能不看约束含义就统一判定。不在 DAG 里只是该合同未约束顺序，**不自动证明可交换、可省略或无副作用**。已知顺序违例应阻断相应处理结论；不确定性不得冒充通过。

**替代**：机械能力不足时保留带 EA 的人工核验与未判范围，不要求为获得覆盖率先完成通用顺序证明。

### 4.4 范围：局部闭环逐步扩，不让函数边界代替领域范围

**候选**：选一个有有效依据的局部规则，覆盖其相关调用、状态与失败路径；再按能力或 handler 族扩大。调用闭包只是已知可达下界，未知前沿必须在账上，共享 helper 的义务不能重复计数。

全语料可以先做定位与未归属普查，但当前验收域必须单列。换范围应解释新增 / 移出项，不能把范围缩小造成的残差下降当作精化进展。

**替代**：handler 集合作为初始工作域也可行，但不能只因为易枚举就忽略合同依赖的辅助函数；不预设 handler → 全域是唯一推进路线，也不把局部比例称为整个引擎覆盖率。

## 5. 预期收益与成本

**预期收益**：

* 每次精化能追查保留、替换、舍弃与未处理的机器行为，剩余项直接成为下一轮问题，而不是等 emulator 出错再补丁。
* 区分证据 / 解释问题、范围遗漏与实现违约，缩短错误暴露与定位链路；不承诺每个错误都能自动归因。
* 固定输入、分析版本、依赖与配置后可重算处理账；派生视图辅助阅读而不另造语义真源。
* 领域合同仍是主交付物，覆盖设施帮助发现漏项，不以指令注释或数字替代可独立实现的 spec。

**成本**：精化绑定的持续维护、派生分析器的可信度边界、效果粒度与调用摘要、局部检查和反例设计。若追求通用别名 / 异常 / 循环分析，成本可能显著扩大，不能视为一次性统计工程。

**不提供的保证**：不自动发现正确的领域抽象；不证明自然语言到检查器无失真；不因覆盖率高而证明语义或等价性；不消除共享误解；不替代外部证据。

## 6. 主要风险

| 风险 | 如何避免误读或假绿 | 剩余边界 |
|---|---|---|
| **把范围闭合当解释正确** | 精化依据与处理范围分别呈现；守恒只检查归属 | 全部义务有归属仍可能解释错 |
| **检查器弱于正文或空泛通过** | 列明可执行投影检查哪些属性；用有依据的正例与关键错误变体验证判别力 | 有限样例不能证明自然语言忠实度 |
| **自证与共享误解** | selector、适用域与语义核验分别交代来源；代码拆开不等于依据独立 | 多实现一致仍非原引擎 oracle |
| **未知或舍弃被洗成覆盖** | 未判、内部省略、明确舍弃分别列范围 / 依据 / 影响；未知调用与模型外效果不消失 | 是否可舍弃仍需裁决与证据 |
| **调范围或选择器刷数字** | 固定候选域并解释差异；错配与漏选分别检验；召回不可测就直说 | 没有独立适用集合时不能给完整召回结论 |
| **结构闭合或不在 DAG 被过度解读** | 按具体依赖核验；未知 CFG 边阻断相关证明；不约束顺序不等于可移动 | 静态模型与摘要仍有假设 |
| **语义副本漂移** | 不建手工转写层；引用 ledger / shape 的有效状态；精化随失效降级 | 状态映射与组合解释本身仍需审查 |
| **分析器成为新的主项目** | 先限定检查能力与试点，收益以真实残差和错误定位衡量 | 不保证每类义务都能自动判定 |

## 7. 试点与 Go / No-Go

**方向判断**：建立可追溯的精化范围与残差账，直接回应两个核心困难，值得讨论和试点；具体效果模型、覆盖指标、存储形态与自动核验能力尚未定案。不能把“方法值得验证”写成“技术路线已经成立”。

**P0 候选交付**：一个有限规则及其精化绑定、明确的机器候选域、可重算处理账、逐项残差、检查边界、一组会红的反例 / 变异。不以覆盖百分比或整个族语义清零为成功条件，也不要求先造通用证明器。

试点选已有有效依据的少量规则，不能从“族成员 / handler 守卫已在”推出全族语义已知。纯数值族可以提供候选，但其未知语义与特殊路径仍需保留；试点范围待选择。

**需要验证的收益**：

1. 能否双向追查“这条精化处理了哪些行为”与“这个机器站点由谁处理”，并点名所有未处理 / 未判项及后续问题？
2. 漏掉局部效果、放电越界、错误舍弃、依赖失效、选择器多选 / 漏选时，账与检查能否暴露相应问题？覆盖完整但语义错误的变体，能否被已有核验区分；不能时是否明确指出边界而不是冒充正确？
3. 是否在不建手工转写层、不靠缩范围洗绿的情况下，让领域合同更容易使用、机器遗漏更早暴露，收益值得维护成本？

方法域要求**未登记义务 = 0**，不是**未解释义务 = 0**：每一项都有处理记录或明确残差，未知可以非零。方法单不承担全域内容收口；后续内容批次在固定输入与范围下比较残差，分析变化或新发现单独解释，不能以降低未知数量为唯一目标。

若某一模块不成立，分别缩小检查范围、保留人工核验或替换技术路线；不因一个自动指标不可测就放弃范围审计，也不为了守住原方案强推覆盖率。

## 8. 需要继续裁决的问题

1. 哪种最小处理账能准确表达精化保留 / 替换 / 舍弃的范围与未知，而不是把引用代码区间误当解释完成？
2. 指令上的效果义务应细到什么程度才有收益？未知调用和多规则重叠如何登记且不重复统计？
3. 如何呈现状态对应关系、成立条件与证据，使抽象可审查而不复制布局或转写函数？
4. 哪些检查先做、哪些保持人工核验或未判？如何验证检查器对正文的投影没有被过度解读？
5. selector 适用域与必要顺序怎样核验？没有独立集合或完整控制流时如何报告？
6. 用哪条局部规则做 P0，什么结果足以支持扩大投入，什么结果应促使换策略？

## 9. 完整性判据与“定不了”的边界（2026-10-29 定案，回填技能 §0.5）

本节回应一个反复出现的误区：把**工程缺口**（还没枚举完 / 还没写进合同）说成**原则上的不可判定**。
本引擎是**单线程、确定性**代码；给定同一初始状态与同一输入 / 时钟序列，执行序列唯一。
因此“定不了”只有下面四种来源，且都不是“程序本身不确定”：

1. **观察 / 枚举未完成**：反编译视图会丢信息（间接调用、虚表、数据驱动分支），但字节级 `.lst` 可以静态补齐。
   例：记录标志位 2 的读者一直在 `0x4666B6`（`test [record+0x28],4`），只是按 C 视图扫会漏。
2. **抽象层选择**：同一可观察行为可以由不同的内部状态机实现。spec 只该规定到它选择的粒度；
   选择更细的粒度（如“每帧推进一格”）时，就要把该粒度对应的状态 / 触发也写全。
3. **环境是输入**：时钟、输入事件、宿主帧率、`Sleep(MessageSpeed)` 的实际执行不在二进制里。
   spec 要把它们写成**引擎 tick / 平台请求 + 参数**；像素与实际调度进 `discards`。这是边界选择。
4. **证据门槛**：结论必须绑可复核观察（EA / 语料区间 / 守卫用例）。“我复刻了全部状态”本身不是可验证的 spec 断言，
   除非状态枚举被证明完整。

**完整性判据（可执行）**：

> 独立实现者**只凭 `chapters/*.md` + `format/*`** 能写出唯一实现，不需要回看 `.lst`。
> 任何“必须回看 `.lst` 才能补”的字段 / 触发 / 转换 = **spec 缺口**，应写进正文，或登记 residual / gap 并写 `next`。

**与两层本体的关系**：领域状态（字段语义、谁写谁读、缺省 / 无效值、触发时机）属于 spec，必须写全；
机器布局（偏移 / 宽度 / 数组 / 池基点）属于 shape，spec 用 `storage` 指针引用。外置的是**布局**，不是**语义**。
若产品要求逐位复刻，把布局也写进合同同样合法，但只能有一份真源。

**静态优先**：

* 本引擎没有多线程 / 外部共享状态的竞争；“循环跑几次 / 什么时候跑”由**主循环 + 计时器 + 输入**决定，
  三者都可静态读。先读调用点与返回条件，把“两套入口 / 各自触发”写成合同。
* 只有静态读完后仍有两个**在 spec 的 tick 边界上不可区分**的模型，才登记“需要采样”；
  必须写清采什么（哪个输入、哪个时刻、看哪个请求 / 像素）以及采到后改哪条合同。
* 真机带壳不可 trace，采样只是“真机消费 / 人工目检”档证据，不是等价证明。

**实例（本轮）**：

* bit 2：读者已定（`0x4666B6`），写者未枚举完 ⇒ **spec 缺口**，补写者；不是“只能真机”。
* 第 29 位：`0x4096A9` 的每帧推进与 `0x406F90` 的置位后 drain 是两个入口，
  应先静态读 `sub_45BE20` 与两处调用点，把“每帧一格 / 抽干”写成两套触发；不是“只能真机”。

**与 emulator 的边界**：spec 写领域状态机（状态 + 触发 + 可观察请求）；emulator 是实现示范与第二实现证据，
⛔ 不是 spec 真源。把“复刻所有状态”当 spec，等于把规范写成参考实现：独立实现者没有二进制就写不出来，
且无法用行为合同验收。作为 **emulator 策略**它合法；作为 **spec** 它不合格。

## 附：职责地图、参考实践与怎么查

* **语料**：机器侧证据，EA 是锚；分析视图不成为第二证据源。
* **shape**：机器模型与可重算报告，辅助理解、绑定与结构缺口定位。
* **ledger**：原子结论及证据真源，读取时检查有效状态。
* **spec + 精化绑定**：领域合同、状态对应、成立条件与处理范围；声明单向引用机器布局与原子结论，不另建转写或替换真源。
* **覆盖报告**：从绑定与分析重算处理账和残差，不反向定义领域语义。
* **emulator**：规范消费者与第二实现证据，不作为 spec 真源。

### 参考实践（不是本项目已选工具）

* [NASA FRET](https://github.com/NASA-SW-VnV/fret/discussions/140)：受限表达、多种语义视图和样例辅助审查形式化表达；不自动证明真实意图正确。
