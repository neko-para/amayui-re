## 2. C 类逐条

### C1 `0x21c` 漏掉 `var_768`（场景对象 `&5==4`）——最严重

`apps/emulator-cxx/src/core/vm.cpp:470-472`
```cpp
if ((state_flags_ & (1u << 10)) != 0 && pending_glyphs_.empty() &&
    (state_flags_ & (1u << 29)) == 0) {
    state_flags_ &= ~(1u << 10);
}
```

语料的自然放行是**两**个谓词：

- `0x413221 call sub_407E20` → `0x413226 test eax,eax / jnz 0x413248`（消息/文本子系统仍有工作 ⇒ 不放行）；
- `0x41322A cmp [ebp+var_768], ebx / jnz 0x413248`（场景对象里仍有 `&5==4` 的对象 ⇒ 不放行）。

`var_768` 的来源在 `0x412648`：`0x4125AD cmp edi,3E8h` 扫 1000 槽，`0x41263F call sub_4050E0`，为真就 `0x412648 mov [ebp+var_768],1`；`sub_4050E0` 是 `(v1 & 5) == 4`（`this[265] ? this[268] : this[274]`）。

**判 C 理由**：spec（`60-ops-wait.md:31`）自己写了第二谓词，实现**一个都没有**；`pending_glyphs_` 只覆盖“字还没画完”，不覆盖“场景对象还在推进”。这不是“近似”，是**少了一个合取项**。旧实现 `!scene_animating_` 至少是“任何带 duration 的窗”的超集；本提交把它换成空集，等于把 `0x21c` 变成“字画完就走”。

### C2 `0x72` / 选项消费用**电平**代替“一次消费”

`apps/emulator-cxx/src/core/vm_ops_texture.cpp:902-916`
```cpp
const bool have = mouse_button_source_ && mouse_button_source_(mask);
if ((have && (mask & 1) != 0) || skip) {
    state_flags_ &= ~(1u << 31);
    state_flags_ &= ~(1u << 30);
}
```

语料输入字是**事件字**，不是“当前按着”：

- `0x477280`（`sub_478090` 的鼠标聚合）：`v5 = this[1158]`，命中一位就 `this[1158] = v5 & ~(1<<v3)` **清掉**，再 `*a2 |= 1 << (*v4 + 4)`；`v3` 是绑定按钮下标，`+4` 说明鼠标位从 bit 4 起（左键=bit 4=0x10）。
- `0x477130`：`*a2 |= this[1159]; this[1159] = 0`（键盘事件字同样读后清零）。

所以“按住”在一次刷新后就再没有 bit 0x10；实现用 `mask & 1` 的当前电平，脚本每次重新 `0x72` 都会**当拍放行**。这正是 ②。

### C3 选项消费用“光标命中 + 左键”而不是“确认位 + 选中项”

`apps/emulator-cxx/src/core/vm_ops_io.cpp:422-435`
```cpp
if (!choice_window_.input_gate || choices_.empty()) return;
if (!mouse_button_source_ || ... (mask & 1) == 0) return;
const auto hit = choice_hit_test();
...
frame_mut().ip = static_cast<std::uint32_t>(decide) * 4u;
```

`sub_4098E0` 的实际结构：

- `sub_478090` 刷新输入字；
- `sub_403DD0` / `sub_403E70`：光标**进出事件**（`this[7466]`、`this[959]` 的转移），命中时返回“进入/离开入口”并把条目压进 `[5D898]` 的向量，**不写 PC**；
- `0x4099A1 test byte ptr [edi],10h`：只有输入字 bit 0x10 才走确认支，`mov dword ptr [edi],0`（整字清）后 `sub_404120` 用 `this[7468]`（当前选中下标）取该条的**决定入口**（`[entry+1836]`），再 `PC ← [5D894] + entry*4`；
- `sub_404120` 内部先 `sub_403EF0`（七格清表）再返回 `[entry+1836]`；选中下标来自 `this[7468]`（上下键/悬停维护），不是现场矩形命中；
- 跳转后只清门字 bit23（`0x409991` / `0x4099DC` 的 `0FF7FFFFFh`），**没有**“置 latch”的写点。

**判 C 理由**：实现把“光标命中”当“选中”，把“左键电平”当“确认位”，还多写了一个 `latch = true`。后果：菜单一打开、光标恰在条目上且左键还按着 ⇒ `service_choice_click` 在下一拍立刻选中；长按会连选。语料不会：bit 0x10 已被 `0x4098E0` 那一支 `mov dword ptr [edi],0` 消费。

### C4 自动消息的**武装点**不在 `0x72`

`apps/emulator-cxx/src/core/vm_ops_texture.cpp:877-884`
```cpp
if (flag_y_ != 0) {
    const std::int32_t n = line_records_[resolved];
    ...
    auto_due_ms_ = scene_clock_ms_ + auto_interval_ms_;
    auto_armed_ = true;
}
```

语料的武装/重武装：

- `sub_4090F0`（由 `sub_4764E0` tail-call，后者是 `IAGEService` 虚表项 `0x526b78`）：先看 `[5EC70]`（`0x1b7` 开关）的锁存，非 0 就清掉返回；否则置 1，按“语音在播 / `AutoMessageOption` bit0”选组、算时长、`sub_453A60(a1+107545, 时长)`；
- `0x41204B` 起的帧服务：`cmp [esi+5EC70h],0` 之后按 `[77958]` 分派 —— `[77958]!=0` 走 `sub_453BC0`（置 `+10h` 挂起）；否则用同一 N/公式算时长并 `sub_453BD0`（只在 `[obj+10h] != 0` 时启动）；
- `0x72` handler 本身看不到这段公式。

**判 C 理由**：把“计时器武装”塞进 `0x72` 会改变可观察时序（从“点击/帧服务到期重武装”变成“脚本一到 0x72 就起算”），也丢掉了 `sub_453BD0` 的“pending 才重启”语义。公式对不等于触发器对。

### C5 `N` 是平行发明的计数器

`apps/emulator-cxx/src/core/vm_ops_text.cpp:645` / `:633`
```cpp
if (slot >= 0 && slot < 10) line_records_[slot] = 1;  // 清空后追加 1 条
...
if (slot >= 0 && slot < 10) ++line_records_[slot];     // 行结束 +1
```

语料 `N = ([eax+30h] − [eax+2Ch]) / 24 − 1`：`[+2C]`/`[+30]` 是**消息层记录向量**的 begin/end，`/24` 是记录数。实现没有维护这个向量，而是另记一个 `line_records_`：`0x71` 置 1、每个 `0x6f` +1。两者只有在“向量里每条记录恰为一行、且 `0x71` 恰追加一条”时才相等——这两点都没有证据；spec 自己的注释（`draw_text_layer_text`）说排版层在**每段结束**与**每次行结束**各追加记录，若一段里有多段，`N` 就会大于行数。

**判 C 理由**：这是“为了算公式而另造一个数”，不是从语料结构推出来的；`RES-AUTO-MSG-LINE-RECORD` 只承认领域名未定，没有承认“计数器可能与向量不一致”。

### C6 spec 把 `0x0B5B4` 叫计时器

`data/spec/chapters/60-ops-wait.md:38`
```
`0x0B5B4` 那个计时器的精确计数方式未取证
```

`sub_407E20` 的 `.lst`：

- `+0B5BCh` = duration（`edx`，非 0 才进入）
- `+0B5B8h` = start/elapsed
- `+0B5A4h` = now
- `+0B5B4h` = **返回值**（`mov eax,[ecx+0B5B4h]`）
- `+0B5C0h` = flags（bit 0x10000）

**判 C 理由**：把返回的忙闩当成计时器，会让读者去追一个不存在的“递减”；实际计时器是 `+0xB5BC` / `+0xB5B8` / `+0xB5A4`。这条也直接削弱了 `CORE-OPS-WAIT-TIMER` 残差的必要性——计时器其实是可读的。

### C7 spec 把输入字 bit 4 说成“确认键、不是鼠标左键”

`data/spec/chapters/60-ops-wait.md:34`
```
★ 这一路采样的是**确认键**（默认 Enter），**不是鼠标左键**
```

`0x477280` 的 `*a2 |= 1 << (*v4 + 4)` 与 `+0x1218` 的 consumed 位，说明 bit 4 是**绑定动作 0**（`code=0` 时）；默认绑定若是左键，它就是左键。`0x41330B` 清的是 `[edi] & ~0x10`。它不是“VK_LBUTTON 轮询”，而是“pressed 事件字”——所以“不轮询 VK_LBUTTON”成立，但“鼠标左键不构成放行”**至少未取证**，且与 ② 的实测相反。

**判 C 理由**：这条把“确认动作”与“物理键”混为一谈；如果默认绑定包含左键（本作 ADV 的常规操作），实现和后续守卫就会把左键从 `0x21c` 的跳过路径里排除。

### C8 `RES-AUTO-MSG-TIMER-PHASE` 与正文“1 个周期”矛盾

`data/spec/chapters/60-ops-list.md:422` 写“首次放行 = 1 个周期”；`:434` 写“首次放行的时刻是‘起点 + 2×时长’（机械后果）”。同一份 spec 两句话不能同时为真。

语料支持 1×：`sub_453A60` 起播 `[obj+8]=1`；`sub_453AF0` 在 `count×interval − elapsed < 5` 时进入到期支，`count=1` ⇒ 首次在 `1×interval`。**判 C 理由**：这是一条必须裁决的矛盾；实现跟了正文（1×），残差却留了一个会误导人的“2×”。

### C9 `0x32` 的模式 0 完全没建模

`apps/emulator-cxx/src/core/vm_ops_texture.cpp:770-860` 总是读 `ops[0]/ops[1]` 后走软件缩放；语料：

- `0x41E366 cmp dword ptr [esi+0A30D0h], 0`
- `jnz 0x41E3E0`（模式 ≠0）
- 模式 0 走 `0x41E372`：先读 1、再读 2，然后 `call [ebx+40h]` 的平台 blit（`0x41E3C3-0x41E3CD`）；
- 模式 ≠0 走 `0x41E3E0`：先读 2、再读 1，`sub_4A87A0`。

**判 C 理由**：spec 新写的“模式 0 = 平台位块传送”没有落到实现；而且读序在模式 ≠0 时是反的（`1→2` vs `2→1`），对非法操作数的抛出行为可观察。

### C10 `0x21c` 的输入跳过整条没实现

spec 写了“`system:EffectSkipOnClick` 非 0 + 输入字 bit 0x10 ⇒ 放行”，代码里 `service` 只检查 `pending_glyphs_` / 打字态，**没有**读 `system:EffectSkipOnClick`，也没有 bit 0x10 的跳过支。语料 `0x413248-0x4132A2` 与 `0x41330B-0x413357` 是完整的第二路。**判 C 理由**：spec 有、实现无，且这正是“淡入期间点一下能不能跳过”的行为。

### C11 spec 漏掉 `set:WheelKeyDown` 的第二跳过支

`0x4132A4-0x4132E3`：配置 `system:EffectSkipOnClick` 的 **bit 1** + `set:WheelKeyDown` 给出的按键下标，`test [edi], 1 << key` 命中同样走 `0x41330B`。spec 只写 bit 0 + bit 0x10，把“非 0”当成单一位。**判 C 理由**：配置值的位段写错，会让“只开滚轮跳过”的配置被当成“开左键跳过”。

### C12 `apps/emulator-new` 的等待门直接清位

`apps/emulator-new/src/core/machine.ts:1128-1133`
```ts
if ((this.flags & WAIT_BIT) !== 0) {
  this.flags &= ~WAIT_BIT;
  return null;
}
```

注释自己说“本参考实现没有建模文本子系统的待画格 ⇒ 这里等价于‘立即放行’”。**判 C 理由**：这是把“未建模”变成“永远没工作”，与 spec 的自然放行（计时器 + 场景对象状态）相反；用户如果在 Electron 窗口看到 ①/③，这里同责。

## 3. 四条可观测分歧

### ① TITLE 退回时按钮提前渲染

**最可能位置**：`apps/emulator-cxx/src/core/vm.cpp:470-472`（`0x21c` 放行）；`apps/emulator-new/src/core/machine.ts:1128-1133` 同责。

**证据**（本地只读解码 `TITLE.BIN`，id 21092，行号=指令下标）：

```
555 0x320 200000 9 13 17 1018952 1018956 21 25 4 0   // 建网格 200000
557 0x322 200000 0 0 0
558 0x323 200000 0 300 255 0                          // 300ms 颜色窗
560 0x322 200000 0 255 0
561 0x323 200000 0 300 0 0
563 0x21c                                             // 等这个窗
574 0x203 1038 0 255 16777215                          // 按钮当前色 ← 白
585 0x203 300 0 0 16777215
586 0x1fb 301 4 1282 0 156 156 1102 294                // 之后才建按钮纹理
```

语料 `0x41322A` 的 `var_768` 由 `0x412648` 扫 1000 槽、`sub_4050E0` 为 `(status&5)==4` 置起；TITLE 的网格 200000 有 300ms 窗，是最可能的对象。旧实现 `!scene_animating_` 会挡住；新实现只看 `pending_glyphs_`（TITLE 没有文本待画格）⇒ `0x21c` 当拍放行 ⇒ 574/586 的按钮写在 300ms 窗结束之前，表现为“按钮提前一整块出现”。★ 仍待一条 trace 确认 200000 这个键落在哪个对象槽（`0x320` 的键是句柄、槽号才是 `var_768` 扫的），但这不改变“第二谓词缺失”的结论。

**修复方向**：
1. 实现 `var_768`：扫场景对象槽（0..999），`(status & 5) == 4` 为真就挡住；状态字要从 `0x1fb`/`0x220`/`0x320` 的记录映射出来（先补一条 shape claim，确定是哪个字段）。
2. 实现 `sub_407E20` 的计时器：`+0xB5BC` 时长、`+0xB5B8` 起点、`+0xB5A4` now、`+0xB5B4` 忙闩；把 `pending_glyphs_` 作为它的**子集**，而不是替代。
3. ⛔ **不要**退回“任何带 duration 的窗都不放行”——那是 80 击 13 推进的坏法；正确判据是“场景对象状态”，不是“任意窗”。
4. 守卫：TITLE 退回时间线（`route-title` 之后注入一次返回），在网格 200000 的 300ms 窗未结束时，`0x1fb`/`0x203` 的按钮写**不许**发生；窗结束后才允许。

### ② ADV 长按鼠标持续推进

**最可能位置**：`apps/emulator-cxx/src/core/vm_ops_texture.cpp:902-916`（`service_advance_wait`）；`vm_ops_io.cpp:422-435`（选项消费同病）。

**证据**：`0x477280` 的鼠标 pressed 位 `this[1158]` 在刷新时被清（`v5 & ~(1<<v3)`），映射到 `1 << (code+4)`；`0x477130` 的键盘字同样 `*a2 |= this[1159]; this[1159] = 0`。`0x4098E0` 的确认支在 `test byte [edi],10h` 后 `mov dword ptr [edi],0`（整字清）。⇒ 引擎的输入是**一次消费**，不是电平。

**修复方向**：
1. 在 `Machine` 里建一个“输入字”，按 `sub_478090` 的次序刷新：键盘字 + 鼠标 pressed 位 → bit `code+4`，刷新时清 pressed 位；`service_advance_wait` 只在**新出现的 bit 0x10** 放行（或按“armed 之后的第一帧看到 bit”），放行后清该位。
2. 选项消费同样只认新 bit 0x10；菜单开窗那一拍不能消费同一个 press。
3. 守卫：`down` 一次、按住 2000ms、`up` ⇒ 只推进 **1** 次；`down`/`up` 80 次 ⇒ 推进 ≥ 60 次（现有 click-rate 保留）。

### ③ SN0000 遮罩渐变方向反

**最可能位置**：与 ① 同一个等待门（`vm.cpp:470`）；若遮罩走 `0x24d` 种类 1，则再加 `apps/emulator-cxx/src/core/scene_raster.cpp:510/527` 的极性。

**证据**（本地只读解码 `SN0000.BIN`，id 116）：

```
114 0x220 0 0 200 0 0 0       // key 0 场景记录/对象
120 0x202 0 0 200 0 1         // key 0 颜色窗：200ms，alpha → 0
121 0x21c
139 0x220 0 0 200 110 0 0
145 0x202 0 0 200 255 1       // key 0 颜色窗：200ms，alpha → 255（遮罩变实）
```

第一段 `0x202`（→0）后紧跟 `0x21c`；如果等待门当拍放行，第二段 `0x202`（→255）会在第一段 200ms 窗还没走完时**覆盖**它，屏幕上看到的就不是“先透明→再压暗”，而是“压暗先/无渐变/次序反”。`0x220` 的同步写（`item.flags |= 2`、`window_start=0`）让 key 0 同时是场景记录与绘制项，正好落在 `var_768` 的候选里。

另有一条独立候选：若遮罩来自 `0x24d`（种类 1，影片纹理遮罩），`record.mask_flag == 1 ? 0 : 255` 的极性在 spec 里是**显式未取证**的（`RES-SCENE-COMMAND-KIND1-FLAG`）；这也能单独造成“方向反”。

**修复方向**：
1. 先修 ① 的 `var_768` / 计时器，再看 SN0000 的两个 `0x202` 是否按 200ms 依次完成；这是最小改动。
2. 若仍反：在这段逐帧记录 key 0 的 `item.color` / `target_color` / `window_start`，确认是 `0x202` 覆盖还是 `0x24d` 极性；后者按 `RES-SCENE-COMMAND-KIND1-FLAG` 的 `next` 取证（截帧 255/0 两档）。
3. 守卫：key 0 的 alpha 必须从第一段结束值单调到 255；白字 `0x6e` 的绘制条目必须在 alpha=255 之后才出现。
