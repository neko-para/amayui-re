### 2.1 RES-SCENE3D-XFORM-INTFIELDS → `narrowed`

**判定**：narrowed（四个格的身份**已全部取到**；只剩 G3 的读者，而那条已在别的残差名下）。

**依据**（同一条辅助函数 `sub_4AD3C0`，`0x220` 的写体，逐字）：

| 格 | 写点 EA | 指令原文 | 读者 EA | 指令原文 |
|---|---|---|---|---|

| G3 = 记录 `+0x68` | `0x4AD453` | `mov dword ptr [eax+68h], 1` | 未取到（见 §4） | — |

G1/G2 的**时序判据**（`sub_49AA30`，与正文「场景计时窗」三档逐条对得上）：

```
0x49B577 mov edx,[ebx+58h]     ; G2
0x49B580 test edx,edx
0x49B582 jle loc_49BAE5        ; G2 ≤ 0 ⇒ 整段不做   ← 正文 70-vm.md:243「持续时间 ≤ 0 ⇒ 不插值」
0x49B588 mov eax,[ebx+44h]     ; G1
0x49B58B mov ecx,[ebx+34h]     ; 起点
0x49B594 mov esi,[esi+0B5A4h]  ; 场景时钟「现在」
0x49B59A lea edi,[eax+edx]     ; G1 + G2
0x49B59D add edi,ecx           ; 起点 + G1 + G2
0x49B59F cmp esi,edi
0x49B5A1 jnb loc_49B969        ; 现在 ≥ 起点+延迟+持续时间 ⇒ 到期
0x49B5B4 lea edi,[eax+ecx]     ; 起点 + G1
0x49B5BB cmp esi,edi
0x49B5BD jbe loc_49B953        ; 现在 ≤ 起点+延迟 ⇒ 延迟内
0x49B5C3 mov edi,esi / sub edi,eax / sub edi,ecx   ; 进度 = 现在 − 延迟 − 起点
```

⇒ **G1 = 延迟、G2 = 持续时间**，与 `0x202` 的窗（`0x4AD11E` `[eax+38h]`←延迟、`0x4AD136` `[eax+4Ch]`←持续时间）是**同一套三档语义、不同的一对格**（步长 0x14，**五对全部逐字核到**：颜色窗 `0x38`/`0x4C`（`0x202`）、缩放窗 `0x3C`/`0x50`（`0x21E`）、旋转窗 `0x40`/`0x54`（`0x21F`）、平移窗 `0x44`/`0x58`（`0x220`）、源矩形窗 `0x48`/`0x5C`（`0x239`））。
旁证（同族另外三对，全部逐字）：`0x21E` = `0x4AD1D2` `mov [eax+3Ch], edx` / `0x4AD1EA` `mov [eax+50h], ecx`；`0x21F` = `0x4AD2C5` `mov [eax+40h], edx` / `0x4AD2DD` `mov [eax+54h], ecx`；`0x239` = `0x4AD502` `mov [eax+48h], edx` / `0x4AD51A` `mov [eax+5Ch], ecx`。五对的写体都紧跟在 `or dword ptr [eax], 2`（`0x4AD0F3`/`0x4AD1A7`/`0x4AD29A`/`0x4AD3F7`/`0x4AD4D7`）与 `mov dword ptr [eax+34h], 0`（`0x4AD10F`/`0x4AD1C3`/`0x4AD2B6`/`0x4AD413`/`0x4AD4F3`）之后。

**处置**：
- **删** `RES-SCENE3D-XFORM-INTFIELDS`（"四个格的领域身份未定"这一问已被否证）。
- **补正文**（`0x220` 条，草案；建议插在「状态对应」前，并把 :908 那行的"两个整数属性"改掉）：

> 本条写的四个整数格属于**记录的一组窗字段**：`+0x34` 是**窗起点**（与 `0x202` 的起点同格，0 = 未盖章），`+0x44` 是本条所排**平移窗**的**延迟**，`+0x58` 是同一窗的**持续时间**，`+0x68` 是给其它矩阵写者共用的**重算标志**。

### 2.13 RES-SCENE3D-GETVEC-MISSING → `covered`

**判定**：covered（但理由与别的条不同：**这一问在引擎侧没有答案，因为它不是引擎问题**）。

**依据**：

- 引擎侧两支的输出**逐位相同**：记录不存在 ⇒ 三个 0；记录存在且三元向量恰为 (0,0,0) ⇒ 三个 0。**引擎没有第二种表示**（没有 NaN、没有 "无值" 位、没有单独的成功标志 —— 对比 `0x228` 才有失败标志，`:931`）。
- "找脚本侧对 0 的分支用法"考的是**游戏数据怎么写**（程序层），按 spec 的本体划分它不进引擎合同；而且它**不改变任何实现**：`0x218` 无论被怎么使用，写出的一样。

**处置**：**删**该残差 + **补正文一句**（草案，`GET-VEC1` 的「成立条件」）：

> 查不到时写出的三个 0 是**普通浮点值**，不是"无值"哨兵：引擎侧对「记录不存在」与「记录存在但三元向量为 (0,0,0)」**输出逐位相同**，不存在第三种表示。⛔ 不许为它加成功标志、NaN、或"空"枚举 —— 脚本若把 0 当哨兵，那是脚本的约定，引擎不参与。
> 可证伪：同一条脚本先后对「不存在的编号」与「存在且三元向量为 0 的编号」各调一次 `0x218` ⇒ 三个目标操作数收到的浮点位模式必须**逐位相同**；不同 ⇒ 引擎在"无值"上做了区分。

**`<待核>`**：若日后要做**数据侧**统计（发行脚本里 0 的出现频率与用法），那是一条需求单，不是 spec 残差。

## 3. 本轮真正的发现：正文有三处要动（不是残差问题）

按严重度排：

**A（写错）`0x220` 的两个整数格不是"两个整数属性"** —— 正文 `60-ops-scene.md:908` 与 :910 把它们记成"某场景对象的两个整数属性"，而 `0x49B577`/`0x49B582`（G2 ≤ 0 ⇒ 整段不插值）与 :917-:919 的三档判据证明它们是**时间量**（延迟 / 持续时间）。这是"把时间量写成属性"的典型误归类：独立实现者照现文写，会把变换窗做成"写死的两个整数"，插值整段丢失。

**B（缺口）第 1 位有四个名字，正文一个都没连起来** —— 见 §2.5。最硬的后果：`60-ops-scene.md:698-700` 的「修饰位」现在读起来像是**另一位**，而它是同一个位；`0x220` 置它等于**打开**②→① 回灌。独立实现者极可能实现成两个位。

**C（缺口）vec1 / vec2 的读者在正文里，但和写侧的名字没连起来** —— `0x217`/`0x219` 的条目只说"一组三个浮点"，而它们的读者分别在「场景对象的变换」（三个纯量 → T）与「绘制纹理 `0x1fb`」（三维位置）两条里。⇒ 本簇 3 条残差（VEC1-IDENTITY / VEC2-IDENTITY / VEC2-REL）都是这个"没连起来"的产物。

（附：**跨簇提示** —— `0x21e` 的两个整数格（`0x4AD1D2` 写 `+0x3C`、`0x4AD1EA` 写 `+0x50`）与 `0x21f` 的（`0x4AD2C5` 写 `+0x40`、`0x4AD2DD` 写 `+0x54`）**应当是同一族窗**的另一对对偶（步长同样是 0x14，五对已全部逐字核到、都紧跟 `or …,2` 与 `+34h ← 0`），直接冲击 `RES-SCENE3D-21E-ROLE` / `RES-SCENE3D-21F-ROLE`。本报告只给出写点与步长，**不**替那两条下裁决。）

## 4. 没取到的证据（逐条给原因）

1. **`+0x68`（G3 配置格）的读者** —— 没取到。原因：全语料 `+68h` 的命中上百处，横跨多个结构；要判"哪一处是 `T_Scene_460` 的记录基址"需要按基址归属（`shape access` 对"表查询返回值"这类基址目前归到 `unresolved`）。本轮只做到"写点全枚举"（7 处 `mov dword ptr [eax+68h], 1`：`0x4AC629`/`0x4AC6AB`/`0x4AC789`/`0x4ACC11`/`0x4AD203`/`0x4AD2F2`/`0x4AD453`；另 2 处写 0、2 处寄存器源写），**没做**读者归属。
2. **`+0x438` 条目表记录的 `+0x1F8` 读者** —— 没取到，原因同上，而且更糟：`+0x1F8` 的读点多数落在 `T_Scene_460` 上（`0x49B420`/`0x49B44D` 那一带是 ②→① 回灌），**同偏移不同结构**，不判基址就会张冠李戴。本轮明确**不**用它们当条目的读者。
3. **vec1 / vec2 的读者闭集** —— 没取到。只取到"已知读点"（`0x49ABF1` 系 / `0x4A2E14` 系），没做 `0x203` 条那种"值取址入口 36 个调用方 + 全语料同偏移扫描 + 反例排除"的闭集论证。
4. **`0x242` 第二张表是否就是 `0x23b` 所称的"辅助表 A"** —— 只取到"它在 +0x438、值宽 572、与 `0x344` 的 +0x448 不是同一张"；"另三条"到底是哪三条**没取到**。
5. **`loc_49BB8D` 之后的路径**（位 1 = 0 时跳去哪、`loc_49B953`/`loc_49B969`/`loc_49BAE5` 各自的出口）—— 没跟完。⇒ §2.5 的"位闸跳过整段"这句话**只对 `0x49AC04..0x49AC3D` 这一段成立**，写正文前要把出口读完。
6. **没有跑引擎**：本轮只有 `.cache/footprint/sn0000.jsonl` 的 opcode 计数（5 条都执行过），**没有 cell 级 / 像素级观测**。所以本报告里所有"可证伪"条目都是**待落地**的建议，不是已做过的观察。

## 5. 先做哪 3 条

1. **改 `0x220` 的 G1/G2（= §3 A）**：把"两个整数属性"改成「平移（变换）窗的延迟 / 持续时间」，并把 §2.1 的三档判据与 `0x49B582` 的 `持续时间 ≤ 0 ⇒ 整段不插值` 写进 `SET-TRANSFORM`。**理由**：这是本簇唯一一条"正文与指令正面矛盾"的地方，其余 12 条都只是缺名字；而且它顺手把 #1/#4 两条残差一起清掉。
2. **统一第 1 位的四个名字（= §3 B / #5）**：在 `0x202` 或 `SET-TRANSFORM` 加一段"同一位、四个名字"，并把 `0x49AC04`/`0x49AC3D` 的位闸写清楚。**理由**：会让独立实现者实现成两个位 —— 这是"闭合但错"的那类缺陷；先做它能防住后续一批残差反复冒出来。
3. **把 vec1 / vec2 的读者写回写侧条目（= §3 C）**：`SET-VEC1` 加"就是三个纯量 → T"，`SET-VEC2` 加"就是 `0x1fb` 的三维位置"，删 #6/#9/#10 三条（#6 只留闭集那半）。**理由**：一次改动清 3 条残差，且不引入新证据。
