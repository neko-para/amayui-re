# 复现：ADV 点击"丢失"（平均 2~3 下才推进一句）

对应缺陷：`REQ-01M665WGT6R9WH94F4QGTDYX7Y`（open）。

## 观测点

ADV 里连点左键，**大多数点击没有任何效果**：一句台词常常要点 2~3 下才推进；真机（以及本轮之前）
是一下一条。不是输入设备丢了——`0x108` 在那几次点击期间**根本没被读**。

## 复现（`links/install`，无窗口）

```bash
cd apps/emulator-cxx/out
./emulator-cxx --install ../../../links/install --skip-logo --play-headless \
  --input-script ../../../.tmp/verify/spam.txt --anchor-script 21092 \
  --tick-ms 16 --max-steps 4000000
```

`spam.txt` = 标题 → GameStart → 新游戏 → ADV，然后**每 300 ms 点一次（按住 100 ms）**、共 80 次
（时间线与 `apps/emulator-cxx/tests/input/route-newgame-chapter0.txt` 同前缀）。

## 实测（2026-10-30，`--tick-ms 16`）

- 80 次点击 ⇒ **只有 13 次推进**（`0x72` arm / release 各 13 次；`0x6e` 追加 34 次）。
- `0x108`（读鼠标按钮）**只在 clock 2216–4712 这段窗口里被轮询**；之后再没读过一次。
- 中间有 **≈18 s** 里 `state_flags_` 反复是 `0x400`（等待位 = 第 10 位）：
  `21544→23048`、`23048→25560`、`25608→27112`、`27128→29144`、`29160→32168`、
  `32184→35192`、`35576→37992`、`38008→39224`（每次 1.2–3 s）。这段时间**一条指令都不派发**
  ⇒ 既不会 arm `0x72`，也不会读 `0x108` ⇒ 落在这段时间里的点击**必然全丢**。
- `0x72` 的 arm→release 常常只隔 16 ms（点击还按着就放了）⇒ 一次点击可能推进一条，
  也可能整段落空。

## 假设（待核，⛔ 还没取证）

等待位的放行条件是 `!scene_animating_`（`vm.cpp` 的门服务），而 `scene_animating_` 是
"**场景里还有任何一个带 duration 的窗**"——背景色淡变这类长动画会把它拉长到秒级，
于是脚本被**别人的动画**卡住。引擎的等待位可能只等**本窗 / 本动画**（`0x21c` 的 handler
`sub_?` 要读 `.lst`：它等的是哪一格、什么时候清）。

## 下一步

1. `.lst` 读 `0x21c` 的 handler：等待位是哪一个字、清它的条件是什么（是"无动画"还是"本窗到期"）。
2. 若是"本窗"，把门服务改成按**发起等待的那个窗**到期放行；若不是，量一下引擎里这段动画该多长。
3. 判据（可入库）：同一段 ADV 时间线（80 次点击 / 100 ms 按住 / 300 ms 间隔）⇒ 推进次数
   必须 ≥ 点击次数的某个下界（例如 ≥ 70），否则红。当前值 13。
