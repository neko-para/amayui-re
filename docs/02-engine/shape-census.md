# 对象 shape 普查的工作流程（口径 / 判据 / 落点）

> 本文件回答"**怎么把'这个对象在内存里长什么样'变成可复核的数据**"——
> 即需求 `REQ-01M52F3ASMGWQXX64JSA18MP2N`（批 S1）的**做法与判据**。
> ⛔ 本文件**不写**进度、条数、比例、当前跑到哪一步：那些随每次干活而变
> ⇒ 一律现跑（口径见 `../../AGENTS.md` §10，命令见本文 §8）。
> ⛔ 也**不写**任何游戏语义（槽的含义、函数的用途）：语义走 `AGENTS.md` §6 的准入门，
> 进 `data/ledger/`；本层只产出**观察**（"哪个 EA 以什么形状碰了哪个偏移"）。

## 1. 为什么承重件是**复核器**，而不是扫描器

* 扫描器（助手）给的是一份**一次性产物**：它做前向符号执行、折叠链、链接分类，
  规则会随语料里新出现的编码形态而变 ⇒ 它**不可能**自带"我算对了"的证明。
* 复核器做的是另一件事：拿一条**声明**（witness EA + 形状）**回原始语料逐字重解**，
  产出 `verified` / `drifted` / `unverifiable` 三种话。
  产物能不能入库，取决于**每一条都过得了复核**，而不是取决于扫描器有多聪明。
* ⇒ 推论：**没有复核器的 shape 表不许入库**（它只是一份 Markdown）。

## 2. 两条实现的分工（"独立验证"的可执行判据）

"两个实现"不许是口号，判据必须写得能被检查：

| # | 判据 | 为什么 |
|---|---|---|
| 1 | 复核器**不 import** 助手的任何模块 | 共用一行解析代码 ⇒ "独立"当场失效 |
| 2 | 复核器**只读语料**（`.lst` / `.c`），不读助手的缓存 / 中间产物 | 读助手的产物 = 自证 |
| 3 | 两侧**方向相反**：助手 = 整个函数**前向**符号执行；复核器 = 从 witness EA **向后**做局部切片 | 同向同法 ⇒ 同一类错会在两侧同时出现而"一致通过" |
| 4 | 复核器的折叠识别是**闭集合的惯用法表**（每条都是语料里真实出现的形态）；表外 ⇒ `unverifiable` | 复核器宁可说"我复核不了"，也不拿不认识的形态硬套出一个数 |
| 5 | 复核器**逐个字段**判"证明 / 推断"，只有**证明**出的不一致才叫 `drifted` | 否则"复核器的近似"会被当成"声明的错"，红得没意义 |

★ 判据 3 的实测价值：助手侧把 `fld` / `fstp` / `idiv` 这类 x87 与除法指令的读写方向判错
（**两个实现同时判错时不会红**，因为它们在这一点上"一致"）——这正是为什么还要
**逐条列出读写族**、以及为什么 `drifted` 与 `verified` 都必须能被构造出来（见 §5）。

## 3. 记录模型（产物的一行是什么）

一行 = 一次观察，**必须带 witness EA**（唯一合法的锚；语料行号只是派生映射）：

```text
KIND   ∈ SLOT | ARRAY | LINK | HOLE
witness 二进制 EA（锚）           site   该 EA 的指令原文（给人看，不是锚）
obj     对象标识（`Engine` = 进来的对象根；`Engine+0x…` = 成员指针指向的对象）
origin  原点约定的名字（**必填**，见 §4）   off  相对 origin 的字节偏移
width   ∈ 1 | 2 | 4 | 8 | unknown（闭集合来自 defs.h，见 §6）
access  ∈ r | w | rw | a（a = 只取址的 lea，不算访问）
stride  数组元素步长（ARRAY 才有；按**索引量的单位**算成字节）
index   索引来源（`*(Engine+0xNNN)` 这样的**稳定身份**，不是语义名）
form    形态（字面位移 / 折叠位移 / 按索引 / 段前缀符号 …）—— 用于解释"为什么这么解"
```

* **`HOLE` = 未观察区间**：在某个 `(obj, origin)` 的窗口里，那些**没有任何 witness** 的偏移。
  它必须显式产出（"这里没有观察"与"这里没有东西"是两件事）。
* **两类地址要分开记**（它们看起来像同一个东西）：`ds:` 段前缀符号（进程全局 / 数据段对象，
  **没有**"对象根 + 位移"的形状）与 `[base+disp]` 形态（对象内偏移）。
  助手侧漏掉前者、复核器不认前者，都会让"访问总数"静默变小。
* **计数单位必须钉死**（否则同一个问题会得到不同的数）：需求里"非栈内存操作数"的口径 = 
  **函数体内、基址不是 `ebp`/`esp` 的 `[...]` 操作数出现次数**（按**操作数**计，不按指令计；
  `lea` 的取址也算一次，但 `access = 'a'`）。`ds:` 符号形态**另计一类**。

## 4. 原点约定：**不许静默选一个**

同一批字节有两套常见写法（先例：R1 的帧记录基址订正 `REQ-01M4H0Q2TQ…`）：
`0x5D880 + 0x78·cur` 与 `0x5D894 + 0x78·cur`。⇒ 每一条记录都要**同时**给出
"绝对位移"与"相对哪个原点"，并且原点表本身要能被复核器读到（复核器只做**算术自洽**校验：
`origin + off == 绝对位移`；原点表是**声明的约定**，不是语料事实）。

★ 推论：**"窗口式原点"（一族互不相关的标量）与"记录式原点"（基址 + 步长 + 条数）必须分开标**——
把 `0x5D884` 说成"`0x5D880` 那个对象的 `+4`"是错的：它们是**同族但无关**的两个 Engine 级标量。

### 4.1 落点：**`views`（声明的视图）= 模型的推测，工具只判算术与可证伪性**

"同一个数组、索引差 k"这种话**不是语料事实**，是**判断**。⇒ 它写成声明（`types` 成员的 `views`），
判定器只做两件能机械做的事，⛔ 语义**不由本层背书**：

| 判据 | 内容 |
|---|---|
| **算术自洽**（证明） | `成员.off + 步长 · elementDelta == 被解释的那段位移`（实测先例：`0x5d894 + 0x78·(−1) = 0x5d81c`） |
| **可证伪性**（不算通过） | 视图**零观察** ⇒ 单列"空话声明"；视图**多余**（字节范围已被 `delta 0` 覆盖）⇒ 也单列 |
| **分档**（守恒④） | 解释 = **观测档** + **视图推测档** —— 报告里视图解释标 `🧩 …**推断**`，分不开就审不出"哪条是猜的" |
| **不许吸走** | 裸位移（无索引）同时落在"标量成员"与"视图窗口"里 ⇒ 规则定**选标量**（⛔ 不靠声明顺序）；仍然选不出 ⇒ 单列 `ambiguous` |

★ 实测价值：`0x41A958`（`exit` 里的 `while (frames[*cur-1].f0 == edi) --*cur;` 展开）——
逐字是 `cmp [esi+edx*8+5D894h], edi`、`edx = 15·(cur−1)`，助手的归一化把它报成 `abs=0x5d81c`。
声明 `views:[{elementDelta:-1}]` 之后这一处被解释成"元素内 `0x0`"且**标为推断**（守恒④：观测 179 + 推测 1）。
⛔ 不声明就**如实进残差** —— 不许静默圆成"元素 0"（两条都有守卫钉着）。

### 4.2 `count: null`：**形态可说、边界不可说**

"条数未观察"的数组必须写成 `type` + `count:null` + `sweep:{stride,index}`：
形态（步长 + 索引身份）说得出来，边界说不出来。★ 为什么**必须**配 `sweep`：没有条数 ⇒ 窗口**无界**，
会把窗口外的偏移也"解释"掉 —— 实测形态是 `0x5ee04` 的无界窗口一路吞到 `0xa609c`（**假解释**）。
有了 `sweep`，"匹配"就只认**同一把索引、同一步长扫过**的站点，且仍受"元素内偏移"约束。

### 4.3 对象身份：**路径只管一跳**（更深交给局部载体）

**身份怎么表达**：

| 层 | 声明形态 | 意思 |
|---|---|---|
| 1 | 载体 `type: "T_Command*"` | `obj0` 本身 |
| 2 | `T_Command` 的成员 `{off, kind:"ptr", type:"TB"}` | `*(obj0+off)` 是 `TB` 的对象 —— **推导，一跳** |
| 内嵌（非指针） | 父类型的成员 `{off, type:"TX", count:1}` | `TX` **按值**嵌在这里（跨度 = `size(TX)`） |
| ≥3 | ⛔ **不声明多跳**：用 §4.4 的**局部类型载体** | "这个寄存器在这一段里是 `T*`" —— **断言** |

★ **为什么不做多跳**（2026-10 的结构简化的判决，不是口味）：把"深度"从校验里拿掉。实测代价表
（handler 子集，`pnpm tools shape census` 口径）：

| 层数 | 路径条数 | 站点数 | 若改用局部载体 |
|---|---|---|---|
| 1 跳 | **10** | **125** | 75 条（函数 × 基址寄存器） |
| 2 跳 | **2** | **8** | 同上那 75 条里的一部分 |

⇒ 一跳**划算**（10 条声明覆盖 125 处），两跳只覆盖 8 处却要带来"链遍历 + 下钻政策 + 按层级分桶"整套复杂度。
所以：**路径停在第一跳；跨两级以上一律进"跨两级以上（未判）"档（带 EA + 整条路径）**，
要判就写一条**局部类型载体**（实测：`sub_421450·edi` 一条声明判掉两处层级 3）。

★ 修掉的两个真错（都有守卫 + 变异）：
1. `lea eax,[<二级对象>+k]` 之后再解引用：`addr` 基址拿不到宿主偏移 ⇒ 早先报成层级 1、从所有桶里掉出去
   （守恒③ 上线当天因此对不上）。现在基址的**路径**跟着 `lea` 走 ⇒ 它是正常的一跳二级对象。
2. 三跳链早先报 `pointeeHost = 第二跳的偏移` ⇒ 拿它去对 `obj0` 的成员表 = **宿主认错层**（可能假解释）。
   现在这类**不判**，只单列整条路径。

★ 守恒②因此是四档：`二级对象 = 解释 + 不透明 + 拒绝/未声明 + **跨两级以上（未判）**`。
"未判"与"拒绝"**分开记账**：前者是"我们选择不看"，后者是"你声明的跟汇编对不上"。

### 4.4 第二条路：**局部类型载体**（寄存器 → 类型的断言）

路径只能表达"**从 `obj0` 的某个成员读出来的指针**"。指针还可能来自**参数 / 调用返回值 / 数据段 / 跨层级**——
那些位置上路径**没有任何东西可写**。于是有第二种声明：

```jsonc
{ "kind": "local", "fn": "sub_421450", "reg": "edi", "span": ["0x421544", "0x4215ca"], "type": "T_5c73c_0*" }
```

意思是"这个寄存器在**这一段**里装的是 `T_5c73c_0` 的对象"。它是**断言**（不是推导），所以 G10 有三条硬要求：

| 要求 | 为什么 |
|---|---|
| `span` 必须逐字等于 `regions` 的**活窗口** `[from..liveTo]`（⛔ 不许自己写） | 与 `roles` 同一条纪律；`liveTo` = 下一次写这个寄存器之前的最后一条指令（寄存器在最后一次写点之后**仍然持有那个值**） |
| 活窗口里被 `call` 打断的 **caller-saved** 寄存器不许用 | `eax/ecx/edx` 跨调用后值可能已被抹掉 ⇒ "它是 `T*`" 不成立（实测：`sub_4192F0` 的 `edx` 段就是这种，必须红） |
| 段落类别必须是 `load` / `ptr` / `other` | `const` / `init` 说明那是个常量，不能断言成指针 |

★ **两条路的取舍口径**（不是风格，是可判定的）：
**来源可表达 ⇒ 用路径**（推导，零声明，跟着对象图走）；**来源不可表达 ⇒ 用局部载体**（断言）。
两者对同一处并存 ⇒ G10 报一条 note（"同一事实有两套声明，建议只留一套"），⛔ 不许静默并存。
★ 那条 note **只在"路径本来就能判"时才报**（1 跳、且那一跳已声明成 `ptr → 本类型`）：
跨两级以上的站点路径**不判**，局部载体是**唯一**写法 —— 这时报"建议只留一套"是**错的建议**（会劝删唯一能判的那条）。
★ 实测：局部载体**跨得过**层级——`sub_421450` 的 `edi` 与 `sub_421690` 的 `edi`
（活窗口 `[0x421544..0x4215ca]` / `[0x421784..0x42180a]`，类别 `load`、未被 call 打断）
两条声明判掉了**四处层级 3** 的访问（`+0x20` / `+0x30`）。

★ **结构上判不了的一档（必须留着，⛔ 不许为清零去编）**：层级 3 的指针**只在 caller-saved 寄存器里**、
且活窗口被 `call` 打断 ⇒ 同一条断言会红两次（实测 `0x42165f` / `0x42189f`：`edx` 的活窗口
`[0x42165d..0x421689]` / `[0x42189d..0x4218ce]` 里各有 `call`，函数内也没有 callee-saved 持有它）。
这一档只出现在"跨两级以上（未判）"里，带 EA + 整条路径。

### 4.5 值传播的两个修法（"未解析基址"从 64 降到 41 的来路）

未解析基址一度是最大的一块。**其中 23 处不是"来源不可表达"，而是助手丢了两件事**——修法都在
`tools/lib/shape-access.mjs` 的值模型里，**不是**加声明：

| 修法 | 一句话 | 实测收益（控制流族） |
|---|---|---|
| **`noreturn` 之后没有 fall-through** | 闭集合只有 `__CxxThrowException@8`（语料 288 处）。若不切断，抛出路径上的写会**污染汇合点后面的块** | `sub_41C6A0` 9 处 + `sub_41C7C0` 3 处 ⇒ 回 obj0 桶（其中 8 处 +8 后**刚好落在已声明成员**） |
| **栈槽做值传播、不做站点** | `mov [ebp+x],reg` → 之后 `mov reg,[ebp+x]` 拿回同一个值（对象根经常被溢出到栈槽、在 catch/循环块里读回） | `sub_429460` 的 8 处 ⇒ 由 `l03`（`sub_429460·esi → T_Command*`）判掉；`sub_41AB80` 2 处回 obj0 |

前后对照（都在报告里现跑）：

| 口径 | 未解析基址 | obj0 相对 | 局部载体 |
|---|---|---|---|
| 控制流族（修前 → 修后） | **64 → 41** | 197 → **212**（残差 0） | 0 → **8**（解释 8） |
| 全表 handler 子集（修前 → 修后） | **752 → 711** | 3336 → 3368 | — |

★ **SEH `catch` 块是例外，而且只能靠声明**：`loc_429604` 这类块的唯一引用在 `.data` 的 SEH 表里
（`-868, offset loc_429604`）⇒ **静态没有入边**，块内寄存器状态解不出来。那里的正确写法是
**`{kind:"local", fn, reg, span, type:"T_Command*"}`**（"这个寄存器在这个块里就是 obj0"）——
⛔ **不是**编一个匿名类型（一轮提案曾为它发明 `T_429460_esi(0x8|0xa609c)`，那**就是 T_Command 的成员集**，
等于把 obj0 写成假类型）。

★ 两个修法各有守卫（`★⑪` noreturn / `★⑫` 栈槽），变异清单也各有一条 —— "改了会不会红"不靠声称。

## 5. 三档话，以及最危险的一类错

| 话 | 含义 | 判据 |
|---|---|---|
| `verified` | 声明与独立重解**逐字段相同** | 可入库 |
| `drifted` | 至少一个字段**被证明**不同 | 声明错 ⇒ 不许入库，报出来 |
| `unverifiable` | 重解不出来 | EA 不在语料 · 不是内存访问 · 基址证不出是对象根 · 折叠链落在惯用法表外 / 隔着 `call` / 超出窗口 · **不一致只落在被推断影响的字段上** |

★★ **最危险的是"假 verified"**：站点落在循环里、而它的索引是**循环变量**时，
"这一次访问落在哪个槽"**随迭代变化**——把它报成单个槽，复核会**通过**，而结论是错的。
实测形态：装载器里那个三轮循环（`xor edi,edi` → `lea ecx,[edi+edx*2]` → `[esi+ecx*4+…]`
→ `inc edi` / `cmp edi,3` / `jl`）三轮落在三个不同的槽上。
⇒ 判据：**循环变量必须单列一类**（"这一族槽由这个循环逐个写"），
复核器要把"索引依赖链里存在被回边区间改写的寄存器"判成 `unverifiable`，
**不允许**取"第一轮的值"当答案。

★ 这条也解释了 §2 判据 5 的必要性：复核器的局部切片天然会取"最近一次定义"，
在循环里那就是第一轮的初始化值 —— 它**看起来是对的**。

★ **第四档话 `unfalsifiable` 已落成 G7**（本文件原先只写了它"不算通过"）：成员声明 `kind:"ptr"`、
却在这个 claims 文件的**载体集里零解引用** ⇒ 单列"空话声明"。
**不判红**（类型是共享的：某个族文件里没看到解引用，只是说"这个族不这么用它"），
但它**绝不能被算成"已验证"**。实测反例：把 `{off:0x5d880,width:4}` 改成
`{…,kind:"ptr",type:"TB"}`、而该函数从不拿它当基址 ⇒ 旧版判定器一片绿、连一句提示都没有。

## 6. 宽度与折叠的闭集合来自 `defs.h`（已登记素材 `disasm/c-vocabulary`）

* 宽度闭集合：`_BYTE`=1 · `_WORD`=2 · `_DWORD`=4 · `_QWORD`=8 · `_UNKNOWN`=1。
* 语料里**大多数**内存操作数**没有**显式尺寸关键字 ⇒ 宽度要么由助记符 / 寄存器宽度推出，
  要么是 `unknown`。⛔ **`unknown` 不许当 4**。
* 折叠内在函数（`__ROL4__` / `WORD1` / `SLODWORD` …）以 `defs.h` 为准。
* ⛔ `engine.hpp` 之类前人推断**不得当底座**。

## 7. 未解析项必须报数（报数要报到能处置的粒度）

三类未解析各自报数，**不许静默丢**：

1. **base 未解析**（基址不是已知对象根 / 是别的对象 / 是参数或局部）——按**基址寄存器**分组报；
2. **index 未解析**（折叠链落在惯用法表外、隔着 `call`、超出窗口、循环变量）；
3. **width 未解析**（推不出宽度）。

★ **落地判据（守恒③：站点按基址分桶）**：这几类**不许从访问总数里消失** ——
`站点 = obj0 相对 + 位移不可用 + 二级对象 + 二级对象内嵌派生 + ds: 符号 + 未解析基址`。
其中"**位移不可用**"是**一个**判据下的两类（原因分开报）：`lea` 取址中间量（`abs` 只是位移项）、
**索引未解析**（报出来的 `absDisp` **少了索引那一项**）。★ 后者是最容易变成**假观察**的一档：
`mov [esi+edx*4], eax`（`edx` 未知）报成 `abs=0x0` —— 拿它当"偏移 0"的观察，轻则多一条残差、
重则**正好命中某个成员 ⇒ 假解释**。判据函数：`offsetUnusable()`（`lib/shape-claims.mjs`，普查与判定**共用同一份**）。
等式本身就是哨兵：漏掉任何一类，它立刻差数。★ 实测价值：守恒③**上线当天**就抓出了第三类 ——
`lea eax,[<二级对象>+0x10]` 之后再 `[eax+k]`（`addr` 基址拿不到宿主偏移 ⇒ `pointeeHost=null`）
**既不算 obj0、也不算二级对象、也不算 deep**，从所有桶里掉出去（某函数 128 个站点 ≠ 127）。
★ 这一类不是"推演出来的可能性"，是**分桶守恒逼出来的**：所以"先立守恒、再补桶"比"先想全再写判据"可靠。
★ **一条订正**（独立重测，见 `REQ-01M530BB8BY4XVP32E7Z2E6W5N`）：`index` 未解析**不是** `base` 未解析的子集 ——
handler 子集实测 `310 = 同时缺基址 128 + 基址已解出而索引没解出 175 + 其它基址 7`。
"三类未解析各自报数、**不许相加**"这条口径因此更要紧：把后一类并进"base 未解析"会让 175 处**假观察**看不见。

★ 一条纪律：**"我没走到"不等于"这里没有"**——控制流上不可达的指令也要按空状态参与普查
（全 UNK），否则漏掉的表现是"数字变小"，不是报错。

## 7.5 闭合度：**站点全绿 ≠ 函数分析完了**

这一节回答一个必须能机械回答的问题：**"这一轮分析完了吗？下一层能拿它用吗？"**

### 为什么需要它（实测教训）

`claims` 只数**站点**（带可解基址的内存操作数）。于是 `12/12 站点已判` 会被读成"函数分析完了"——
而 `sub_41C7C0` 的真实语义在**调用与异常**里：

```
sub_41C7C0  89 条指令 = 内存站点 14 · 栈 11 · 控制流 15 · 纯寄存器 49
            ❌ 未闭合 —— 0x41c7ec `call eax`（目标未知 ⇒ 副作用无界）
            L1：7 个直接调用逐个点名（含 3 次 __CxxThrowException@8），效果**不在本层**
```

⇒ 形状数据是**真的**，但"这个函数分析完成"是**假的**。判据必须把这两件事分开。

### 判据（三档，只有第一档可以由本层宣称）

| 档 | 含义 | 怎么判（机械） |
|---|---|---|
| **L0 形状闭合** | 函数的**形状**部分没留尾巴 | ①函数区间内没有"有内存操作数却没产生站点（且不是栈）"的行；②没有**目标未知**的间接调用/跳转；③没有基址未解析的站点 |
| **L1 副作用边界可数** | 调用/抛出**逐个点名**（改了 obj0 什么，⛔ 不在本层） | 直接调用带目标列出；抛出单独标 |
| **L2 语义** | 字段含义 / 函数用途 | 台账（`AGENTS.md` §6），本层永不自称 |

★ "**栈**"要在记账里单列：`[ebp+…]` 的读写**按口径不算站点**（"栈槽不是本单的对象形状"），
  它们是**设计上的排除**，不是漏分析。实测 `sub_41C7C0` 的 11 行"有内存操作数但没站点"全是这一类。
★ x87/SSE 内存操作数、字符串指令（`rep movsd` 这类）**在寄存器模型之外** ⇒ 单列点名，**不重复记**
  成"基址未解析"（否则同一个缺口被记两遍，判据会比实际更糟）。

### 现状（现跑，不在本文留数）

```bash
pnpm tools shape coverage sub_41C7C0        # 一个函数的指令级记账 + L0 判据
pnpm tools shape coverage --all --limit 60  # 全表抽样
pnpm tools shape claims data/shape/carriers.json   # 报告末尾自带「闭合度」一节
```

★ 每个具名 claims 文件的报告**末尾必须出现**这一节（`## 闭合度`）——没有它，"全绿"就只是个局部结论。

### 这条判据实际抓到了什么（第一次跑的结果）

* **数值族 19/19 L0 闭合** —— 那些 handler 是纯算术 + 记录槽，确实没有逃逸通道；
* **控制流族 4/12 闭合** —— 8 个未闭合：间接调用（目标未知）、间接跳转、基址未解析；
* 全表抽样 60 个函数：20 闭合 / 40 未闭合（原因分布：间接调用 28 · 未解析基址 25 · 间接跳转 11）。

⇒ **"下一层能不能用"从此有答案**：能用的是 L0 闭合的那些；其余是"形状已声明、语义未闭合"，
  下一层读它们时**必须知道**自己有未点名的副作用（间接调用 ⇒ 谁改了 obj0 说不清）。


## 7.6 调用链一致性：**A 传出去的、B 声明的是不是同一个类型**

`claims` 是**单模型、单函数**视角（"这个函数里 `ecx` 是什么"）。而"A 把 `ecx`/`esi` 传给 B，
B 说它的 `ecx` 是 `U*`"是**跨函数、跨族文件**的事实 —— 没有任何单一模型能看见它。
`pnpm tools shape calls` 就是这一层。

### 判据（三步，全部机械）

| 步 | 做什么 | 数据来源 |
|---|---|---|
| ① 调用方 | 调用点上该寄存器的**来源**（`this` / `addr(this+k)` / `load(路径)` / 值 / 未知） | 助手的不动点（`link.args`，6 个通用寄存器） |
| ② 解析成类型 | `this` ⇒ 调用方自己的载体类型；`load(path)` ⇒ 沿路径逐跳取成员的 `kind:"ptr"` + `type` | `types`（中心类型表） |
| ③ 对被调方 | 该函数在该槽位上的**载体声明** `kind:"arg"` 的 `type` | 所有族文件（跨文件建槽位索引） |

判定：都已知 ⇒ `same` / **`mismatch`**；只有一侧 ⇒ **单侧**（`calleeUntyped` / `callerUntyped`）；
两侧都未知 ⇒ 不入账（⛔ 不猜）。

### 口径边界（⛔ 不许越）

* **不拿"偏移相同"顶替类型**：`.lst` 与 `.c` 之间没有准确映射，同偏移≠同指令（这条也是"不要做 C 桥"的理由）。
* **栈上传参不覆盖**（本版）：要先证明 ABI 的"参数位 ↔ `push` 顺序"映射，属未证约定 ⇒ 如实留着。
* **间接调用**（`call eax` / `call [mem]`）不进对账：目标未知 ⇒ 连被调方是谁都不知道（这由**闭合度**那节点名）。

### 第一次跑的结果（现跑，不在本文留数）

```bash
pnpm tools shape calls          # 跨族对账（--json 给全量）
```

实测：**槽位对账 199 对，全部是"被调方没有类型"**（`✅ 一致 0 · ❌ 不一致 0 · ⚪ 被调方无类型 199`）。
典型：`0x41c6ff sub_41C6A0→sub_41BF50 ecx: 调用方 T_Command / 被调方 —`。

⇒ 这既是**好消息**（暂时没有互相矛盾的声明）也是**主要缺口**：被调方（`sub_41BF50`、`sub_40ED40`…）
一旦补上载体，这 199 对立刻会变成"能判一致/不一致"的**真检查**；在那之前，
"两侧引用同一个类型"这件事**只能算没被检查过**，⛔ 不能读成"检查通过"。


## 7.7 全语料建模的**批次机制**（谁是什么类、下一批是谁）

### 载体只有一个文件

`data/shape/carriers.json`（不分片、不记历史、直接更新）。**话题/族不是存储轴**：把载体按 topic 分族，
在"函数数以千计"时逼着人给每个函数编一个族名 —— 那是**没有答案的组织问题**。
"族/骨架组"是**查询**：`shape bodies`（骨架分组）· `shape census`（偏移聚类）。

### 下一批怎么挑：按**残差落点**分活，不是按函数大小排名

早期按"未标函数体量排名"派活（`sub_445D70` 233 条指令…），一批下来很难说清收益是什么。
现在改成**从残差反推**：把 `claims` 里每一行"访问 `0x…` 不落在任何已声明成员上"按**载体类型**聚合，
得到"哪个类型还有多少偏移没被声明、被谁碰"。这一步是机械的（`claims` 输出里已经带载体 id ⇒ 查
`carriers.json` 拿类型），而且**它同时给出证据**：热点偏移 × 访问它的那批函数，就是下一批要读的代码。

好处有三个：① 收益可度量（残差访问数下降，而不是"又标了几个函数"）；② 派活自带上下文（"这 25 处都在
`sub_45BE20`/`sub_45B2B0` 的同一簇偏移上"）；③ 它自己会**暴露模型缺陷**——例如按类型聚合后残差最大的两块
是 `T_Font` 的 `0x548..0x578` 与 `T_Command` 的 `0xa30d8`，而后者一读代码就发现是"1024 格掩码数组被写成
183 条离散槽"（见 §7.9「离散槽 vs 数组」）。

★ 但**不能只看残差**：残差为零也可能是因为**根本没人访问**（载体还没有）——所以另一半活是补载体
（`propagate` 报"已被传播确定类型、尚无载体"的候选，几百个）。两者交替推进：先补载体让站点"可判定"，
再按类型收残差让"可判定"变成"已解释"。

★★ **聚合必须从残差行自带的类型取，不能靠"块头状态"**（踩过）：`claims` 的每个载体块以
`c97 sub_412290 ecx→T_Command* 访问 …` 开头，看着像"接下来的残差都属于这个载体"。但块 id 不只有
`cNN` —— 还有 `b10cNN` / `b12cNN`（按批发的 id）。用 `^c\d+` 去认块头，`b12c*` 这些块就**认不出来**，
它们下面的残差会被记到**上一个**匹配到的载体名下：实测把 `T_Input`(8 偏移/8 访问) 与 `T_Sound`(4/5)
算成了 `T_Font`，于是派活清单里 `T_Font` 多算 12 个偏移（44/199 vs 真实 32/186），而 `T_CBunki`(7/14)、
`T_ReadTextDB`(1/4) 整块**没被派出去**。
**修法**：残差行本身就写着宿主 —— `⚪ 0x45be38 访问 0x548 不落在 *T_Font* 的任何已声明成员上` ⇒
类型从这一行取，块头只用来记"哪个载体"。块头正则若要认，就得写成 `[a-z]+\d+`。
★ 顺带一个结构性认识：这个"宿主类型"可能是**第二跳**的宿主（`[this+K] → 指针 → [eax+M]`），
即残差落在 `T_Input`/`T_Sound` 而不是发起访问的 `T_Font` —— 判活时要按**被访问的那个类型**去做，
否则会把 `T_Input+0x490` 写进 `T_Font` 的成员表（假声明）。

### 类判定只能靠**调用链传播**（⛔ 不许按偏移命中率猜）

`pnpm tools shape propagate`：从 `kind:"arg"` 载体出发，沿调用图 BFS 推导每个函数根寄存器的**类**。
规则只用已证明的：`this` / `interior(this+k)` ⇒ 同类；`member(path)` ⇒ 沿 `types` 解析出目标类；
`global(sym)` ⇒ 沿**全局载体**取类；`val` / `unknown` ⇒ **不传播**。

### 根对象只能从**数据段**进来（`kind:"global"` 载体，G13）

`T_Command` 就是引擎对象本身，而它**不是任何函数的参数**：`_WinMain@16`(0x4ba890) 里
`push 0AABC8h` → `operator new`(0x4baa11) → `call sub_415640`（构造器，0x4baa2e）→
`mov ds:dword_55E1BC, eax`(0x4baa3a)，全局才拿到它。⇒ 载体必须能表达"**这个数据段符号里装的是 `T*`**"，
否则从根**正向**爬树一步都走不了，只能继续从 op handler 倒着爬（那正是此前"每批只能推进 5 个函数"的成因）。

三条硬要求（缺一条就是编出来的声明）：`sym` 在语料里真实出现 · `witness` **至少一条 EA 是写该符号的 store** ·
`type` 已声明且同一符号不许两种类型。传播规则与 `member` 同级机械：调用点上 `ecx` 的来源是 `k:'global'`
且有声明 ⇒ 被调方根类型 = 该类型；**没声明的全局不传播**。

★ 被调方**必须真的收 `this`**（`__cdecl` 函数里的 `ecx` 是残留值）：不加这一条，`sub_40A160`(cdecl) 会被
同时推出两个类 ⇒ **假冲突**。

### 7.7b `+4` 那一族：**通用基类 `BaseObject`** 与全局输出对象

★ **同偏移不同类 = 基类相容，不是冲突**：`sub_4034C0`/`sub_4034D0`/`sub_4034E0` 是 `this->+0x4` 的**转发器** ——
`0x4034c3 mov ecx,[ecx+4]` + `jmp sub_497620`（追加字符串）· `0x4034d3` + `jmp sub_4976A0`（格式化）·
`0x4034e3 mov ecx,[ecx+4]; mov eax,[ecx]; mov eax,[eax+8]; jmp eax`（**虚调用**，vtable 槽 +8）。

它们被 `T_Command` 与内嵌子对象 `T_Sys3Draw`/`T_Scene`/`T_FileDB` 当 `this` 调用。**真相是基类**：`BaseObject`（RTTI 名
`??_7BaseObject@@6B@`）的构造器 `sub_4034A0` 只有两条写 —— `0x4034a2 [this] = ??_7BaseObject@@6B@`、
`0x4034a8 [this+4] = offset dword_55BF70`；而它有 **26 个调用方**，全是各类的构造器（含 `0x415640` 的
`sub_415640` = Command、`sub_403F40` = CBunki、`sub_477DD0` = Input、`sub_489970` = Music…）⇒ **子类在偏移 0 处
就是 `BaseObject`**，`this` 不需要调整 ⇒ 同一函数被多种"类"调用是**天然相容**。

★ `[this+4]` 指的东西 = **全局输出对象** `dword_55BF70`（`seg002:0055BF70 ; _DWORD dword_55BF70[266]` = `0x428` 字节）：
构造点 `0x4350c7 mov ecx, offset dword_55BF70` + `0x4350cc call sub_438C50`（另有 `0x51c140`/`0x51c2d0` 两处）。
它的方法：`sub_438CC0`（`WriteFile([this+4], …)` —— **`+4` 是文件句柄**）· `sub_497620`（读 `[+0x410]` 回调 /
`[+0x420]` 标志，否则写文件）· `sub_4976A0`（`sprintf_s` 格式化后转发；体内还读 `dword_55E1BC`）
⇒ 这是**游戏自己的输出/日志对象**，不是 CRT/STL 基建。

⇒ 处置：声明 `T_BaseObject`（`adapter:true` = 基类前缀：`+0x0` vtable · `+0x4` ptr→`T_out`）与 `T_out`
（`+0x0`/`+0x4`/`+0x410` 三个 ptr + `+0x420` 标志，`size` 来自那个全局数组 = `0x428`）。
三条硬要求仍成立：适配器**不许 `size`** · **不许 `complete`** · **至少一个成员**；调用点对账多一档 🔗（不是"不一致"）。

### 继承链：`BaseObject → Draw → DrawEffect → Sys3Draw`（全在 **+0x0**）

每一级构造器都 `mov esi,ecx` 之后**不改 ecx** 直接 `call` 上一级，然后在**同一个 `[esi]`** 覆盖自己的 vtable
（`0x43aab4` Draw · `0x44a823` DrawEffect · `0x4b7d93` Sys3Draw），**全链一处 `add ecx,K` 都没有** ⇒ 都是偏移 0 的基类。
⇒ `T_DrawEffect` 声明成 `adapter:true`（基类前缀），`sub_44A7F0` 写的 12 个成员归它、其余归 `T_Sys3Draw`。

### 用 RTTI 的**基类数组**判"有没有中间基类"（`??_R2<Class>@@8`）

MSVC 为每个多态类生成一张基类数组 `??_R2<Class>@@8`，**第一个 dword 是条目数**，其后每项指向一个
`RTTIBaseClassDescriptor`（末项为 0）。实测：

| 类 | `??_R2` EA | 条目数 | 内容 |
|---|---|---|---|
| `SE` | `0x53f40c` | **2** | `SE` + `BaseObject` |
| `Voice` | `0x53f6ac` | **2** | `Voice` + `BaseObject` |
| `Sound` | `0x53f4a0` | **3** | `Sound` > `SoundError` > `BaseObject`（校准） |

⇒ `Sound` 那条说明**中间基类会出现在数组里**；而 `SE`/`Voice` 都只有"自己 + BaseObject" ⇒ 它们**没有**共同中间基类。
这就把 `sub_4BB810` 的归属判成了"**布局适配器**"（只碰 `+0x408/0x40c/0x410` 三个 dword，两个类各自以相同顺序与值初始化），
载体用 `adapter:true` 的 `T_408_trio`（⛔ 不许硬记成 `T_SE` —— 那样冲突也能变 0，是**假绿**）。
### 指令文本里的位移 ≠ 折叠后的位移（踩过的陷阱）

`mov dword ptr [ecx+1FC4h], offset sub_418E30` 这行**看起来**是在「偏移 0x1fc4」上写，但 `ecx` 本身是
`0x41795A lea ecx,[esi+0A30D8h]` 之后的**表指针**（循环里 `0x4179CC add ecx,10h`、`0x4179CF dec ebx`，`ebx=0x100`）
⇒ 实际写的是 `Command + 0xa30d8 + 0x1fc4 + 16k = Command + 0xa509c + 16k`，也就是**op 分派表本身**。

★ 教训：判断「某个偏移属于谁」**必须看折叠后的站点**（`pnpm tools shape access` 的 `abs=`），
不能读指令文本里的位移 —— 一次误读把「派发表的条件复位」错记成了「T_Command+0x1fc4 有 4 条函数指针写」、
还顺带怀疑 `T_Sys3Draw` 的坐标不自洽（两条都是**假缺陷**，已撤回）。

### 离散槽 vs 数组：op 分派表的裁决

`Command+0xa509c` 原来是 **544 条离散内联成员**（543 条 `name:"fnptr"` + 1 条纯内联）。问题是三层的：
① 3 个读点全是**索引读**（`mov reg,[esi+eax*4+0A509Ch]`）⇒ 在 `shape access` 里是 `abs=0xa509c ⚠ index`
⇒ `offsetUnusable()` 判成 `index-unresolved` ⇒ 进「位移不可用」桶，**不比对成员、不产生残差/红**；
② 离散内联槽让 G4（数组边界）与 G3（步长）**永远没有 `type+count` 可查**；③ G7 只管 `kind:"ptr"`，内联槽不在其内。

⇒ 已改成 **1 条 `{off:"0xa509c", type:"T_fnptr4", count:1024}`**（`T_Command` 成员 965 → 422）。
★ 反事实实测：**只改表示法不改判据，`findings` 仍然 = 0** ⇒ 所以同时加了 **G15**
（索引访问落在非数组成员上 ⇒ 逐条点名；落在数组上 ⇒ note「形态已被数组承住」；两者都 ⛔ 不算通过）。

同族的 `Command+0xa30d8`（`lea ecx,[esi+0A30D8h]` 起、0x1000 字节、`sub_417800` 里按 16 字节步进 256 次、
每次处理 4 个 dword）**已裁决成 `{off:"0xa30d8", type:"T_el32", count:1024}`**（`T_Command` 成员 422 → 240）。
判据（两条独立，都可从 EA 复读）：
① 形状：`0x417341 push 1000h` + `0x417346 lea eax,[esi+0A30D8h]` + `0x41735F call _memset` ⇒ 整段 **0x1000 字节**被清零；
`0x41795A lea ecx,[esi+0A30D8h]` + `0x417960 mov ebx,100h` + `0x4179CC add ecx,10h` / `0x4179D0 jnz` ⇒
256 轮 × 每轮读 4 个 dword ⇒ **1024 个 dword 全被读**。
② 元素不是指针：读点是 `mov eax,[ecx]` → `test eax,eax` / `jle` → `mov edx,eax` → `and edx,[ebp+hFile]` → `cmp edx,eax` 三连，
**从不被解引用**（它是"所需能力位"掩码，配不上就把同下标的 handler 重置成 `sub_418E30`）。
★ 构造器往 `0xa3100+` 写的是**立即数 1**（`0x417364 mov eax,1` 之后连续 `mov [esi+0A310xh], eax`）、以及 `ebx`（0）——
不是 `&table`：`lea eax,[esi+0A30D8h]` 的结果只被 `push` 进 `memset`。
★ 紧随其后的 `Command+0xa40d8` 是**另一个独立标量**（`0x4142A6 mov eax,[esi+0A40D8h]` + `neg`/`sbb`/`and 0FFFFFFFEh`/`add 2`
= 布尔转 1/2，从不被解引用），原来漏声明 ⇒ 32 处站点一直是残差（残差 534 → 500 之后的两项之一）。
### 基址 / 索引分不清（新的一档，⛔ 不算通过）

`[ecx+eax]` 里**两个寄存器都是"从内存读出来的值"**时（实测 `0x448069 cmp byte ptr [ecx+eax], 0`：
`ecx=[esi+0x204c]`、`eax=[esi+0x2030]`），谁是指针、谁是游标**判不了**。判定器原先会要求"基址那个成员
声明成 `kind:"ptr"`"，而 0x204c 其实是**整数游标**（0x2030 才是图基址）—— 反事实实测：写成 ptr 会让 12 条红全消，
正是既往记录过的**假绿**。现在单列一档，守恒② 的等式把它算进去。
★ 传播因此遵守 **"声明 > 推断"**：被调方已有载体时，推断出的另一类只记 note（"调用方类在该偏移上相容"），
⛔ 不记冲突；冲突只发生在**两侧都是推断**时。`--propagate` 仍**按被调方分组**报（不按单条 EA 平铺）。

★ **被否掉的做法**：按"该函数的偏移落在 `T_Command` 已声明成员上的比例"判类。实测 1697 个未建模函数里
744 个"命中 ≤10%"，看着像"另一个类"——但低命中**也可能只是 T_Command 的成员表还没覆盖到**（T_Command 只有几十个成员，
全表 323 个偏移）。⇒ 这个判据**既不能证实也不能证伪**，只能靠调用链。

★ **踩过（已修，有守卫）**：`propagate` 早先把 `kind:"local"` 载体（"`sub_421450` 的 `edi` 装着 `T_5c73c_0`"）
也当成"这个函数的 `this` 是 `T_5c73c_0`" ⇒ 类型被污染成 `sub_41BF50` 同时收到两个类，报 5 处**假冲突**。
修法：**只有 `kind:"arg"` 能定根类型**。修后 115 个函数全部推出 `T_Command`、冲突 0；
那 6 个 5c73c 族函数**没有静态调用边**（走分派表）⇒ 类型推不出来是**诚实的未知**。

### 每批的验收（六条，缺一不过）

`claims types.json` / `claims carriers.json` 都 exit 0 · `calls` 无 `mismatch` · 变异全红预期 ·
`pnpm test` 全绿 · `requirements validate` 5/5 · **闭合度**不下降（下降必须写原因）。

### 闭合度的"未解析基址"要**分两档读**

`coverage`/`access` 同时报保守档 / 校准档。实测 `sub_41BF50`：保守档 64 · 校准档 35
⇒ **29 处只是"`call` 杀了 caller-saved"，不是模型缺口**。⛔ 派发任务书里必须写明这一点，
否则子代理会把这一大块当成"我解不出"。

### 补一批载体时，**未解析基址会上升**——那是"可判定化"，不是退步

实测（batch-14，一次并入 40 条载体）：载体 179 → 219，`未解析基址` 3710 → **5378**，
`obj0 相对` 6498 → **8370**，`解释` 6414 → **7892**。看着像变糟，其实是：

- 这 40 个函数**以前根本不在分母里**（没有载体 ⇒ 体内访问全记"未解析基址"）；
- 新纳入的 3054 个站点里 **1437（47%）转成 obj0 相对、1310（43%）直接解释**；
- 逐桶恒等式成立：`站点 = 改前 + 本批新纳入`（11391+3054=14445、6498+1437=7935、3710+1367=5077 一处不差）。

⇒ 读数字的铁律：**先看等式，再看比例**。`未解析基址 ↑` 与 `解释 ↑` 同时出现时，正确解读是
"可判定化"；只有**等式不等**或**已有站点的分桶变了**才是真退步。
★ 派发任务书里必须写明这一条，否则子代理会把"分母变大"当成自己搞坏了，进而去删声明换数字。

## 7.8 batch-01/02 的裁决记录（要点；逐条证据在需求树 S2a 与被合并的提案里）

### 结构：T_Command 是带内嵌子系统的大对象

`lea <reg>,[obj0+K]` 的频次就是判据（`0x4ed10` 210 次 / `0x408` 189 / `0x1ee8` 138 / `0xa609c` 121 /
`0x14d30` 94 / `0x55d8` 25 / `0xcac0` 17 / `0x511c` 14）。⇒ 这些槽**不是标量**：
`T_Command+K` 应声明成**内嵌子对象**（`{off, type:T_K, count:1}`），`this = &T_Command+K` 的函数用 `T_K*` 载体。
**已内嵌化**：`0x408` `0x5d860` `0x77960` `0x4ed10` `0x1ee8` `0xa609c` `0x14d30`（`0x55d8` 因 claims 变红回滚）。
效果：`--propagate` 从 51 → 89 个函数、分出 5 个类。

### 判据修正（都是实测打出来的）

| 原则 | 反例 |
|---|---|
| `interior(this+k)` **不是**"同类" | 11 个 interior 候选的根偏移签名各不相同；照同类会把它们全塞进 T_Command |
| **只取址（`lea`）的二级站点不是解引用** | 整数游标 `T_FileDB+0x2c24` 被 4 条 G5' 假红逼成 `ptr`（假绿） |
| **位移共现只是下界** | 曾据此把 `0x424/0x414/0x2c24` 判成 T_Command，被 G1 重叠推翻；改用调用点 `ecx` 来路才定案 |
| 判"某函数是不是 T_Command"看**仓内载体**，不看散文 | 散文里出现 `null`/`矛盾` 会把真 T_Command 的 98 条成员整批跳过 |

### 拒绝的声明（附理由）

`sub_408050`（printf 类通用函数，实参是 `(char*)T_Command+8`）· `sub_4E73EB`（CRT `/GS` cookie 桩）·
`sub_49E980`（异构：4 类来源）· `sub_455C60` 的 `esi`（整数文件 ID）· 12 条 lea-only 偏移（零标量读写）。

### 仍挂起（需要证据而不是猜测）

`T_Command+0x408/0x40c/0x414` 的归属（是否与 `T_Data`/`T_437440` 同一基类）· `T_rec50` vs `T_FileDB_elem` 是否同类 ·
`T_SE` vs `T_FileDB`（都有 `0x41c`）· `T_FileDB_elem` size 80 装不下步长 `0x54` 的数组 ·
**schema 缺口**：`T_Command` 里同一类型两个实例（`T_CBunki` @ `0x55d8`/`0xcac0`，跨度 `0x74e8`）。

### T_CBunki 的两个实例（更正：**可表达**）

`T_Command+0x55d8` 与 `T_Command+0xcac0` 是**两个相邻副本**（`0xcac0 − 0x55d8 = 0x74e8` = `size`）；
证据是同一组成员偏移在两处同时出现（`0xca78−0x55d8 = 0x13f60−0xcac0 = 0x74a0`，`+0x7498/+0x749c` 同理）。
曾判"schema 缺口"，实际是三条**建模伪影**：`size` 存成字符串 `"0x74e8"` · 缺 `+0x7498/+0x749c` 成员 ·
实例跨度内还有 **10 个重复的 T_Command 自声明成员**（G1 报"重叠"被误读成"schema 不支持"）。
修法：size 改数字 · 补两个成员 · 删重复的 T_Command 成员 · 两个实例都写 `{type:T_CBunki, count:1}`
⇒ G4 对两个末尾都给出引用（`0xcac0` 19 处、`0x13fa8` 5 处）。

### G4 的 oracle 曾经只认 4 位以上十六进制

`occurrences` 的正则写成 `[0-9A-F]{4,8}h` ⇒ `5F4h`/`65Ch` 这类 3 位位移完全看不见（全语料 112704 次被漏），
任何小于 0x1000 的"末尾地址"都会被判零引用 ⇒ 假红。同一个坑 `parseMem` 里早踩过（`44h`/`0Ch` 解不出）。
修成 `{1,8}` 后：`T_Font+0x5b0` 的末尾 0x5f4 由 0 处变 5 处 ⇒ `count:17` 站得住。

### 奇数跨度的末尾按定义不会被算出

u16×17=0x22、u16×289=0x242 都不是 4 的倍数 ⇒ 末尾地址非 4 对齐，编译器不会算出它 ⇒
"零引用"是**必然**。实测 6/6：零引用的 3 个末尾（0x5ae/0x616/0x89e）全 %4==2；有引用的 3 个（0x5f4/0x65c/0xd24）全 %4==0。
⇒ G4 改为：不对齐 4 且零引用 ⇒ **note**（"边界靠常量+写循环证明，⛔ 不是通过"），仍红的是对齐却零引用那种。

### 第三档：数组**正好填满对象**（末尾 == `size`）

`T_FileDB+0x3c48` 是 256 格表（`0x404A88 sar edi,18h` 索引取顶字节，`0x404A9C`/`0x404AC0` 两处 `[esi+edi*4+3C48h]`），
`0x3c48 + 0x400 = 0x4048` **恰好等于** `T_FileDB.size`。这时末地址落在**对象之外**，语料里零引用是必然 ——
旧 G4 只认"末地址被引用"，于是这条诚实的数组声明被判红，只能退化成"单槽 + note"（S2m）。
⇒ G4 加第三档：`end === size(容器)` ⇒ **note**（"数组正好填满对象"，⛔ **不是**"末尾有引用"那一档）。
它不是放行：等式**可证伪** —— ① `size` 大 4 而末尾不贴边 ⇒ 回落到红；
② count 写大一格 ⇒ 越过 `size`，由 G1（`成员 offN+ext > size`）当场红。
★ 顺序在"奇数跨度"那条**之前**：贴边的**且**不对齐的末尾（如 u16×…×恰好填满）也该走这一档。

### 命名棘轮（G14）：`T_<Name>` 是一个可证伪的断言

类型 id 改成 `T_Scene` / `T_Font` / `T_Command` 之后，"名字"本身就成了**结论**，可它原先没有任何守卫：
写错一个字母、换一次导出、note 过期，名字都会悄悄变成假话，而 G1–G13 一条都不会响。

判据（机械、可证伪）：

1. 把 id 的 `T_` 之后那段（`Scene`）拿去语料找 `??_7Scene@@6B@`；
   **找不到** ⇒ 这是**结构名**（`T_Queue_int` / `T_Scene_460` / `T_FileDB_3028`），不要求 RTTI 证据；
   **找得到** ⇒ 这是**RTTI 声明** ⇒ 必须有一条 `note` 把名字绑到那次 vtable 写入上。
2. `note` 里的 `??_7<Name>@@` 必须与 id 对得上（⛔ 不许 `T_Scene` 绑 `??_7Font@@`）。
3. `note` 里**至少一个 EA** 必须落在**写 vtable 的那条指令**上 —— 该行要逐字含 ``offset ??_7<Name>@@``。
   ★ 为什么是"至少一个"而不是"第一个"：note 里常同时给 ctor / dtor / `_atexit` 的 EA，
   要求第一个会逼人把有用的地址删掉。

实测这条一立起来就抓到一条真缺陷：`T_RemoteDebug` 的 note 里的 EA 是 `0x497570`（**函数起始行**，
`; Attributes: bp-based frame`），真正的 vtable 写入是 `0x4975A3`（`mov dword ptr [esi], offset ??_7RemoteDebug@@6B@`）。
其余 20 个 RTTI 类名的 note 全部一次通过。

### G3 比的是**最内层那个数组**的元素大小（`count:1` 不是数组）

`0x4116ba mov eax,[esi+eax*4+5D04h]`：`0x5d04` 落在 `T_Command+0x55d8` 那块 `T_CBunki(count:1)` 的跨度里，
元素内偏移 `0x72c` —— 而 `T_CBunki+0x72c` 本身是 `T_el32×100`。旧判据拿"步长 4"去比 `size(T_CBunki)=29928`
⇒ 假红。判据改成：

1. `leaf`（最终落到的成员）自己是数组 ⇒ 用 `leaf.type` 的元素大小；
2. 否则**只有当宿主是真数组**（`count == null || count > 1`）时才比 `size(host.type)` ——
   `count:1` 是**内嵌子对象**，与"步长"无关。

两个附带修正（同一处踩出来的）：
- **检查必须放在"元素内偏移 == 0 / ≠ 0"两个分支之外**：只写在 ≠0 那支里，`[esi+edi*4+2000h]`
  （第 0 个元素 + 真数组）**永远不校验**（合成用例实测零红）。
- **判红时也要记一条残差**：旧写法 `red(...); continue;` 把站点从 `explained + residue` 里弄丢，
  守恒① 当场破（实测 `7935 != 7581+353`）。判红 ≠ 可以从守恒等式里消失。

### 载体证据棘轮（G16）：`witness` 必须有一条落在**调用点**上

载体是模型的地基（"`F` 的 `ecx` 装着 `T_X*`"），可它原先**完全免检** —— 实测 174 条 `arg` 载体
**一条 `witness` 都没有**（`witness` 这个字段此前只有 `kind:"global"` 在用，见 G13 那条）。判据：

1. `arg` 载体的每个 witness 只能是两类：
   - **调用点**：那一行逐字是 `call <c.fn>`（证明"某个调用方把对象指针塞进 ecx"）；
   - **来路**：该行**出现 `ecx`**（实测形状 `mov ebx, ecx` = "这个寄存器就是对象根"、
     `lea ecx,[esi+14D30h]` = "传进去的是 obj0+K 的内嵌子对象"）。
   ⛔ 其它位置一律红。实测这样抓到 4 条坏 witness，其中两条是 `lea ebx,[ebx+0]`（**对齐填充**）——
   拿填充当证据等于没证据。
2. **至少一条必须是调用点**（只有来路证据证明不了"真的被这样调用过"）。
3. 语料里**确实没有** `call <fn>` 的载体（只经 op 分派表 / vtable 间接调用）不许编 witness，
   要声明 `indirectOnly: true`；而这个声明**也是可证伪的**：语料里若有 `call <fn>` ⇒ 当场红
   （把"可证伪的声明"与"随便少写一条 witness"分开，这是这一档的全部意义）。
4. 既无 witness 又没声明 `indirectOnly` ⇒ **note**（backlog），⛔ 不算通过。清完再翻红。

实测：214 条 `arg` 载体 → **179 条**的 witness 落在 `call` 上 · **34 条** `indirectOnly`（语料里确无直接调用点）·
**1 条** backlog（`c20 sub_401410` —— 唯一调用点 `0x455a62` 是 `push` 传参，`ecx` 来路不可读）。

要不要把上限推到层级 3（代价：对象身份从"名字"改成**路径**，且每一跳都要有声明）留给后续需求裁决；

## 9. 诚实项（已知局限，别当成"已解决"）

* 助手侧的 `call` 返回值模型是一个**开关**：保守档（按 ABI 杀 `eax/ecx/edx`）与校准档
  （`ecx` 跨调用保留，实测本语料的 callee 事实上保留它）。**两档的数都要报**，不许静默选一个。
* 助手的对象根判定依赖 `.c` 侧的调用约定（`__thiscall` / `__fastcall` / `__usercall`）。
  没有对象指针参数的函数，其 site 一律按"未解析 base"计入。
* 复核器解不了的形态**不猜**：它的能力边界由惯用法表显式给出 ⇒ "复核覆盖率"是**表**的函数，
  表长一点、比例就变一次。
* 两侧在**同一处**判错时不会红（它们"一致"）。⇒ 读写族 / 折叠形态这类**语义口径**
  必须写死在本文与 `defs.h` 里，不能只靠"两边跑出同一个数"。

## 10. 分层：**汇编层**与**引擎语义层**不许混（本文件的口径边界）

同一个函数体上其实叠着两套词汇，混起来会让校验器**拿引擎知识验证引擎知识**：

| 层 | 词汇 | 锚 | 谁拥有 | 准入 |
|---|---|---|---|---|
| **A 汇编层** | 函数符号 / EA · 指令 · `call <callee>` · 立即数实参 · 寄存器流 · 记录槽 / 位移 / 步长 / 宽度 / 访问方向 | **EA** | 语料观察（本文 §3 的记录模型） | 只有"观察到"这一档 |
| **B 引擎语义层** | **opcode** · **argc** · "第 k 个操作数" · `op1 ← op2+op3` · 长度字 `=2·argc+1` | **EA**（结论也要挂） | 知识台账 `data/ledger/` | `AGENTS.md` §6 准入门 |
| **A↔B 的桥** | "opcode `0xNN` 的 handler = `sub_XXXXXX`"（分派表本身是**语料事实**：`mov dword ptr [esi+0A50xxh], offset sub_…`） | EA | 可机械核 | **不属于** A 层，也不属于 B 层的结论 |

★ 判据（可执行）：**A 层的模型文件与校验器里不许出现 `opcode` / `argc` / 操作数序号 / 长度字公式**；
A 层的输入是**函数符号**，不是 opcode。表达"这个值从哪来"要用**汇编层的身份**——
"那次以立即数 `k` 为实参的调用的返回值"（字段 `callArgImm`），**不是**"第 k 个操作数"。

**A 层：从"义务表"改成"算出来的普查"**（原 A1–A6 的审计结论）

这张表原来列了六条**义务**（声明 + 校验）：记录槽立即数（A1）· 调用序列（A2）· 位置性观察（A3）·
算术与来源（A4）· 跨视图（A5）· 守恒（A6）。审计后**撤掉这张表**，理由是可执行的：

| 原项 | 审计结论 | 去向 |
|---|---|---|
| A1 记录槽立即数 | 声明的三元组 (EA, 立即数, 位移) **全部能从 EA + 语料机械读出** ⇒ 进产物就是第二份真源，必然与语料漂 | **算出来**（`bodies.recordWrites`） |
| A2 调用序列 | 同上（EA / callee / `push` 立即数 都是观察）；"同一 callee 的实参立即数集合"是**分组键**，不是声明 | **算出来**（`bodies.calls`） |
| A3 位置性观察 | 它本来就是**口径禁令**（"只观察立即数 1，别读成第 1 个操作数"），不是可判定的声明 | 留在 §10 的口径里；`calls` 里照样数得出 `(1)` |
| A4 算术与来源 | 左右序**由寄存器流定**（不需要声明）；"两个来源分别是哪次调用的返回值"也是观察 | **算出来**（骨架分组会把 `sub_41BF50(3)/sub_41BF50(2)` 的序记进签名） |
| A5 跨视图 | **不可机械化**（是"怎么对待 `.c`"的纪律），而且它的实质已由 §2 判据 1–3（两个独立实现）覆盖 | **删除**（§2 已经管了） |
| A6 守恒 | 纯守恒关系（每个 `call` 落桶）—— 观察 | **算出来**（`bodies.conservation`，会红） |

⇒ 落地：**`pnpm tools shape bodies`**（`tools/lib/shape-bodies.mjs`；守卫 `tools/test/shape-bodies.assets.test.mjs`）
按"**记录槽写法 + 调用序列完全相同**"把 handler 分组 —— 这正是 A 层唯一真正需要判断的东西：
**族边界**（而它是"看分组"得出的，不是拍出来的）。实测：543 个唯一 handler ⇒ 分组数远小于它
（数值手段器族共享同一个骨架：`记录槽 0x5d8f4/120/索引←7` + `call sub_41BF50(3)` / `call sub_41BF50(2)` / `call sub_42B4B0(1)`）。

★ **两条口径留下**（它们不是义务，是禁令）：
① 立即数 `k` 只许当"**以立即数 `k` 为实参的那次调用**"（字段 `callArgImm`），⛔ 不许读成"第 k 个操作数"；
② `.c` 只作**第二意见**，且它的实质由"两个独立实现"（§2）保证 —— 照 `.c` 抄会把 `-`/比较的左右序静默反掉。

★ B 层怎么长出来：桥（分派表）给 `opcode ↔ handler`，A 层给 `handler ↔ 体骨架`，
两条合起来**才**能说"某个 opcode 取几个操作数、算什么"；而"长度字 `=2·argc+1`""立即数就是操作数序号"
这类规则必须**显式登记为 B 层的结论**（挂 EA、过准入门），⛔ 不许让 A 层的工具替它背书。

## 负的二级偏移：MSVC `new[]` 的个数 cookie（⛔ 不是"折叠层算错"）

`[base-4]` 这种形态**不是**取址算术把基准折叠错了 —— 地址确实是 `p−4`，只是它指的**不是宿主对象的成员**：

MSVC 的 `new T[n]` 在元素数组前面塞一个**个数 cookie**（x86 上 4 字节）：

```
0x41529B  mov  [p], n       ; 写个数
0x41529D  add  p, 4         ; p 越过 cookie，返回给调用方的是 &elements[0]
...
0x40EAA2  mov  ecx, [p-4]   ; 读回个数（这里是 std::_Destroy/析构的规模参数）
```

⇒ 判定规则：**带二级路径但二级偏移为负 ⇒ "判不了"**（`shape-access` 把 `pointeeOff` 置 `null` 并打 `neg-off`；
`shape-claims` 的 G5' 单列一档，不记"某类型缺 0x-… 这个成员"）。
实测案例：`0x40EAA2`（`T_5d8bc` 那条长期挂着的 `0x-4` 残差）、守卫 `tools/test/shape-access.test.mjs#★access-01`。

## `0x5D7E8 .. 0x5D8BC` 这一段的角色表（S2ae 结论）

同一段字节里有**五类**东西，务必按这张表读，别再各自判一遍：

| 偏移 | 角色 | 判据 |
|---|---|---|
| `0x5D7E8/EC/F4/F8/FC`（+1） | 六个缓冲**条数** | `0x41513F..0x415189` 把 `0xAAB2C` 起的 6 个 dword **依次**复制到这里 |
| `0x5D800..0x5D830`（`8j+4i`，j∈{0,1}、i≤5） | **游标块**（6 格 × 2 翻转槽） | 初始化按 `0x5D800+8j+4i` 写；换槽 `0x41AAD9..0x41AB66` 只换前 6 格（到 `0x5D82C`）；析构只**释放**后 6 格、前 6 格只清零 |
| `0x5D830..0x5D860`（12 × 4B） | **分配基址块** | 与游标块按 `(j,i)` 配对；`0x40FF50` 的析构循环 2 轮 × 展开 6 次、基址每轮 +4 ⇒ 12 个 dword **逐个**释放；末尾 `0x5D860` 被引用 13 次 |
| `0x5D860` | 一个 `std::vector` 头（`T_stdvector`） | 三指针 + 步长 + 分配器槽；超长分支压 `"vector<T> too long"` 并调 `std::_Xlength_error` |
| `0x5D880` | 循环**游标**（单格） | `0x40F3A4 mov eax,[esi+5D880h]` 是索引来源 |
| `0x5D894..0x5EB54` | `T1 × 40`（元素 120 字节） | 末尾 `0x5EB54` 是下一个成员且被引用 |
| `0x5D8BC` | **`T1[i] + 0x28`**，不是独立表 | 强度削减：`0x40F3A4..0x40F3B1`（`shl edx,4` + `sub edx,eax` ⇒ ×15，再 `*8` ⇒ 120）；`0x5D8BC − 0x5D894 = 0x28` |

★ **`0x5D810` 是单格**（24 处访问全是裸 dword 读写、零索引），它指向的 28 字节对象与 `T_5d8bc`
**布局同形但不合并** —— 证据只支持"同形"，不支持"同一个类型"（可证伪条件见 `S2ae`）。
## `axis` 标注（S2ag）—— 什么能标、什么不能标

`member.axis = { stride, index, why }` 的含义是：**「这个成员的索引语义已判定」** —— 它是游标，
按 `stride` 步长索引到某个已声明的数组。

### 能标（这是**判断**，不是机械可读的事实）

| 例子 | 依据 |
|---|---|
| `T_Command+0x5D880`（stride 120） | `0x40F3A3..0x40F3B1`：`mov eax,[esi+5D880h]` → `shl edx,4` → `sub edx,eax` → `[esi+edx*8+5D8BCh]`；`15×8 = 0x78 = size(T1)` |
| `T_Command+0x5D7E8` / `+0x5D804` / `+0x5D82C`（stride 120） | 它们是游标块/条数块里按 `T1` 元素（120 字节）推进的槽；换槽 `0x41AAD9..0x41AB66` 与复制 `0x41513F..0x415189` 给出行程 |

**为什么这里必须靠标注**：`lea reg,[base+idx*S+disp]` 的索引项在折叠层会丢（132 处受影响），
而修折叠层要改 1213 处 `lea` 的抽象解释 —— 用判断换掉推理，代价小得多（见 `S2ag`）。

### 不能标（机械可读的事实，A 层明令禁止进产物）

- 「末尾地址有没有被引用」—— `G4` 用 `ABS` 换算绝对地址后自己查；
- 「成员宽度是多少」—— 从指令的 `dword ptr` 等读出；
- 「哪条指令访问了这个偏移」—— 那是 `shape access` 的输出，不进模型。

### 可证伪性（G17）

`axis.stride` **必须**等于同一容器里某个已声明数组的元素大小（`T_Command` 里是 `0x5d894 = T1×40`，`size(T1)=120`），
否则判红。⚠ 这条守卫的意思是：**标注不能自己给自己背书** —— 它必须落到一条独立的尺寸声明上。
