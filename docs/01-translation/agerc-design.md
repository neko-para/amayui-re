# 01 · AGERC.DLL 的汉化：旧做法实测 + 方案评估

> 本文件是**评估与设计**（记录"旧仓怎么做 / 实测到什么 / 有哪些选择"）。
> 可执行的工作项在需求树：`pnpm tools requirements show 1ENS6BN3090X8M`（节点「windows 资源重建」）。
> ★ 只写**工件与格式层**的事实；不做游戏语义结论（那些要走 `AGENTS.md` §6 的准入门）。
> ★ 标「实测」的是写本文件时**跑出来**的；标「旧仓记录」的是旧文档的原话（**未在本仓复核**）；标「待验」的是解释性假设。

## 0. 一句话结论（先看这个）

旧仓的成品是**两条互不相干的链叠出来的**：① 用 Resource Hacker 从 `.rc` 重建 DIALOG/MENU 资源；
② 用 `patch-menu.js` 按**硬编码偏移表**在字节层原位改写（改的是**代码里内嵌的菜单串**与**两个 API 的导入名**）。
两条链都必要（有些菜单项是引擎**运行时**插进去的，不在 MENU 资源里）。§4 由此给出三个可选方向。

> ★★ **当前取舍（2026-10-03 用户定案）**：**先用「可信产物」，重建留待以后。**
> 理由：菜单使用面小 + 16 个对话框**基本没汉化**（只 `DIALOG 3`）⇒ 自建链收益有限；
> 而重建要重写 11 个对话框过程 + 整条菜单状态同步（80 处 `CheckMenuItem`）、并**失去逐字节判据**。
> ⇒ 旧仓随包发布的那份已入库为 `corpus/assets/agerc/AGERC.DLL`（条目 `binary/agerc-dist`，LFS），
> "可信"由 `tools/test/agerc-artifact.test.mjs` 机械复核；
> **重建**归需求节点「AGERC.DLL 二进制重建（把可信产物换成自建链）」，本文件的 §4/§G 是它的设计输入。

## 1. 三份二进制与加壳实测

| 件 | 路径 | 大小 | 节 | 说明 |
|---|---|---|---|---|
| 根目录发布件 | `gameInstall:AGERC.DLL` | **335,872 B** | 8 个**无名**节、**全部 `0xE0000040`（RWX）**、另有 `.adata` | 加壳证据：节名被抹 + 全节可写可执行 + `rawSize(132,096) ≪ virtualSize(327,680)` |
| 脱壳件 | `oldRepo:raw-parts/DATA1/AGERC.DLL` | **849,408 B** | 7 个正常节（`.text` `.rdata` `.data` `.idata` `.rsrc` `.reloc` `.textbss`） | 旧仓把它当"原版"用（两条链的基线都是它） |
| **汉化产物** | `oldRepo:install/AGERC.DLL` = `oldRepo:patch/AGERC.DLL` | **848,896 B** | 同上（仅 `.rsrc` 小 512 B） | 发布包里就是这一份（sha256 `6241DE66…`） |

★ **实测 1 — 根目录那份不能被资源编辑器直接改**：它 40 条资源里有 **26 条的数据根本不在盘上**
（25 个叶子拿不到文件偏移 + 1 个越 EOF —— 都是 `MENU/110` `MENU/124` + 16 个 `DIALOG` + 几个 ICON/GROUP 项）；
只有 `.rsrc` 的**前 ~2148 B（资源目录本身）是明文**，且在盘的那几条内容也与脱壳版不同。
⇒ **必须用脱壳版做基、产出完整 DLL 去替换根目录文件**（旧仓正是如此）。
　这也解释了补丁包为何用 848,896 B 换掉玩家 335,872 B 的文件 —— **不是随便放大，是被迫的**。

### 1.1 它怎么被加载 / 谁读它的资源（**代码级**，来自只读反汇编侦查）

| 问题 | 事实 |
|---|---|
| 怎么加载 | **不是静态导入**：引擎 `LoadLibraryA("AGERC.DLL")`（硬编码字面量）+ `GetProcAddress` 取 3 个导出。`LoadLibraryA` 走 Win32 **按名字**搜索 ⇒ **加载的是游戏根目录那份**，`DATA1.ALF` 里那份同 id（21072）的副本**不参与加载** |
| 谁读资源 | **纯 Win32 资源 API，且显式传模块句柄**，**没有**自研 PE 资源解析器（exe 里 `FindResource/LoadResource/EnumResource/RT_MENU/RT_DIALOG` **0 命中**） |
| 具体调用点 | 引擎：`LoadMenuA(<AGERC 的 HINSTANCE>, 110)` + `SetMenu`（= 顶部主菜单栏本体）、`LoadIconA`、`GetFileVersionInfo*`；AGERC 自己：`LoadMenuA(hInstance, 124)`、**14×`DialogBoxParamA(hInstance,id)`**、**13×`CreateDialogParamA(hInstance,id)`**、`LoadIconA(hInstance,"IDI_ICON1")` |
| ★ 关键 | 这些是 **`…A`（ANSI）版本**，而且**每个调用点都写死了模块句柄** ⇒ ① 见 §2.5 的编码后果；② 任何"外部资源覆盖"方案都必须让**这些既有调用点**解析到译文，而 AGERC 还必须仍是**真 DLL**（3 个导出 + 脚本要的第 4 个 + 版本资源可读）⇒ **只放资源、不提供代码的卫星文件替代不了 DLL 本身** |

★ 顺带订正两处旧结论（**代码级**）：`_GetInstance@0` **不是空体**（它 `mov eax, hInstance` 返回自身模块句柄）；
"带壳 / 脱壳"这个提法本身**在旧仓文档里找不到**，是本仓新确立的（PE 指纹与 `raw/AGE.EXE` 逐项一致 + 脱壳件含 93,856 处 `0xCCCCCCCC` 与 `j___RTC_CheckEsp` ⇒ MSVC `/RTC1` **调试构建**）。

★ **实测 2 — 三份的资源清单完全一致（40 条）**：
`MENU=2 · DIALOG=16 · ICON=15 · GROUP_ICON=1 · CURSOR=2 · GROUP_CURSOR=2 · VERSION=1 · MANIFEST=1`，
语言几全是 `0x411`（日文）。

★ **实测 3 — 资源数据规模极小**：真正改动的只有 **`MENU/110`(1,900→1,576 B) · `MENU/124`(320→246 B) · `DIALOG/3`(358→328 B)**，
外加 3 个代码内嵌串槽与 2 个导入名（§2.3）。**整份改动 < 2.5 KB。**

## 2. 旧做法：两条链

### 2.1 内容真源（三处）

| 件 | 是什么 |
|---|---|
| `oldRepo:res/AGERC.DLL.rc`（UTF-16LE+BOM，49,522 B / 435 行） | **汉化**版的整份 DIALOG/MENU/CURSOR/ICON/VERSION/MANIFEST 资源源码；**人手改**；是**从汉化 DLL 反导出**的 ResHacker 全量脚本 |
| `oldRepo:res/AGERC_RAW.DLL.rc`（50,250 B） | 未汉化的对照快照 |
| `data/translations/subs-cn-jp.json`（3,002 条）+ `corpus/assets/fonts/Amayui-CN_cnjp.ttf` | **码位层**与**字体层**的真源（§2.5 解释为什么对话框离不开它们） |

★ **真源里混着构建残渣**：汉化 `.rc` 含 **196 个零宽字符**（`U+200B`，全在 MENU 字符串尾部），RAW 版 0 个。
`build-localized-agerc.ps1` 头部原话：
> 内容源：res/AGERC.DLL.rc（此前从汉化 DLL 导出的 .rc，**含 196 个零宽空格 U+200B**）
> 1) 去除 .rc 中**为保持字节长度而补的**零宽空格 … 现在用 Resource Hacker 重建资源，**不再受"等长"限制**

⇒ **旧仓换过一次方案**（等长就地改 → 重建资源），而**旧方案的产物留在了真源里**，每次构建都要再剥一遍。
`oldRepo:docs/translate/menu-patch-notes.md` 更直白地记了代价：
> 数据内容是**引擎自定义格式**，不是标准 `MENUITEMTEMPLATE` … 解析器依赖字符串终止符定位下一条结构。
> 因此译文必须保持原 UTF-16 单元数，不足用 U+200B 零宽空格补齐，`\0` 保持原位（**曾因"短文本+清零"导致整个菜单消失**）

### 2.2 链①：资源重建（`res/build-localized-agerc.ps1`）

```
① 剥掉 .rc 里全部零宽字符 → AGERC.clean.rc（UTF-16LE + BOM）
② Resource Hacker: compile .rc → .res
③ 对 DIALOG 与 MENU **各做一遍**：「先 delete 掉目标 DLL 里该类型的全部资源，再把 .res 里的整套 addoverwrite 进去」
   （脚本注释：addoverwrite 按 类型+名称+语言 匹配，语言一变会残留旧条目 ⇒ 必须先删整类）
④ 校验：PE 魔数 MZ · 零宽 = 0 · 探 4 个中文字串 · 若仍含日文菜单 ｹﾞｰﾑ(&G) 则警告
基线 install\DATA1\AGERC.dll（脱壳原版）→ 输出 install\AGERC.DLL；旧输出备份到 .tmp\agerc-backups\
```

* `LANGUAGE` 统计：汉化 `.rc` = 17×`LANG_JAPANESE,0x1` + **1×`LANG_CHINESE,0x2`** + 1×NEUTRAL；
  RAW = 18×JAPANESE + 1×NEUTRAL ⇒ **只有 `DIALOG/3` 的语言被改**（`0x411`→`0x804`）。
* 另有更早的形态 `res/inject-localized-agerc.rsh`（写死绝对路径的 ResHacker 脚本）。

### 2.3 链②：定点字节补丁（`oldRepo:scripts/patch-menu.js`）

**它完全不碰 PE 结构**（没有资源目录 / 节表 / RVA / 重定位处理），只按**硬编码偏移表**原位改写：

| 组 | 条数 | 改什么 |
|---|---|---|
| `EDITS` | 45 | 改 `MENU 110` / `MENU 124` 模板里的文字，**用 `U+200B` 补足 UTF-16 单元数** |
| `RUNTIME_MENU_EDITS` | 5 | ① 把 `0x66200` / `0x66328` / `0x66344` 三处 **SJIS(ANSI) 串槽**原位改成 UTF-16LE 中文；② 把导入名 `InsertMenuItemA` → `InsertMenuItemW`、`SetMenuItemInfoA` → `SetMenuItemInfoW`（**等长改名**，不用重建导入表） |

**为什么必须有这条链**（旧仓记录）：调试菜单的顶级项与消息窗口右键开关项**不在 MENU 模板里**，
是引擎**运行时**用 `InsertMenuItemA` / `SetMenuItemInfoA` 动态插入的 ⇒ 只改资源**够不着**它们；
而改成 UTF-16 串又必须换 `W` 版 API，所以连导入名一起改。

### 2.4 实测：产物到底改了什么（★ 把"不明差异"查清了）

**按节逐字节比对**（脱壳原版 → 汉化产物，**按节名对齐**、不是按文件偏移）：

| 节 | raw | 不同的字节 | 是什么 |
|---|---|---|---|
| `.text` | 413,184 → 413,184 | **0** | 代码一字未动 |
| `.data` | 6,144 → 6,144 | **0** | |
| `.reloc` | 23,552 → 23,552 | **0** | |
| `.rdata` | 72,704 → 72,704 | **58 B** | **= 链② 的三个 ANSI 串槽改成 UTF-16LE 中文** |
| `.idata` | 5,632 → 5,632 | **2 B** | **= 链② 的两个导入名 `A`→`W`（正好 2 字节）** |
| `.rsrc` | 327,168 → 326,656 | 尺寸变 | = 链① 重建资源 |
| PE 头 | — | 9 B | 节表里 `.rsrc` 的大小/指针 |

⇒ **"汉化不碰代码"是可复核的**（`.text` 逐字节相同），且此前看着"解释不了"的 58 B / 2 B **就是链②**。

**资源级**：

* 资源集合 40 条，**唯一的集合变化是 `DIALOG/3` 的语言 `0x411` → `0x804`**。
* **真正改内容的只有 3 条**：`MENU/110`、`MENU/124`、`DIALOG/3`。
* **另外 7 条 DIALOG**（2/4/5/6/10/105/134）**文字一字未改**，却被工具重写了、**每条正好 +2 字节** ——
  Resource Hacker 重新序列化模板的**纯工具产物**（实测：把两边 UTF-16 串抽出来逐条对比，完全相同）。
  ⇒ 这就是"只有 `DIALOG/3` 真中文化，其余 15 个 DIALOG 与 RAW 逐字相同"的那件事。
* 其余 30 条资源内容**逐字节相同**。

**内容举例（实测抽取）**：

```
MENU/110  原版：ｹﾞｰﾑ(&G) / ｾｰﾌﾞ(&S)... / 終了(&X) / 設定(&O) / ﾊﾞｰｼﾞｮﾝ情報(&V)...
          汉化：游戏     / 保存(&S)... / 结束游戏   / 设置(&O) / 版本信息(&V)...
DIALOG/3  原版：CAPTION "終了"、FONT "ＭＳ Ｐゴシック"、「次の方法で終了しますか？」「プログラムを終了する(&E)」「タイトルに戻る(&T)」「OK」「キャンセル」
          汉化：CAPTION ""、    FONT "Amayui CN"、   「要用以下方式俟束龜？」  「俟束程序(&E)」      「返回標題(&T)」    「確定」「取消」
```

★ 两处**行为变化**要人拍板（是改动，不一定是缺陷）：
① `MENU/110` 部分条目的**加速键消失**（`ｹﾞｰﾑ(&G)`→`游戏`、`終了(&X)`→`结束游戏`，而 `保存(&S)` 保留）；
② `DIALOG/3` 的 **CAPTION 从「終了」变成空**。

### 2.5 ★ 占位码位：对话框文本为什么必须是"**字体 + 字典**相关"的

`俟束龜` **不是乱码**，是**故意**的：`subs-cn-jp.json`（3,002 条）实测有
**`结→俟` · `吗→龜` · `标→標` · `确→確` · `题→題`**，而同一份 `DIALOG/3` 的 **FONT 被改成 `Amayui CN`**
（那份字体的 cmap 被替换过）。

**机制**（调用点是**代码级**的；下面是解释，逐条标强度）：

* **对话框走的是 `DialogBoxParamA` / `CreateDialogParamA`（ANSI 版）** —— 实测 AGERC 里有 14 + 13 处调用点（§1.1）。
  ANSI 版会把模板里的字符串**转成进程的 ANSI 码页**；游戏在 Locale Emulator 下按日语区域跑 ⇒ **码页 932**。
  ⇒ cp932 编不出的字（简体）会丢，所以只能写 **cp932 能编码的占位码位**，再由 `Amayui CN` 的 cmap 还原成简体字形。
  旧仓记录印证（未在本仓复核）：「直接写简体 + 微软雅黑 FONT ⇒ 控件文本**非 cp932 字符被引擎丢弃**（标题也丢）」。
* **标题栏**走系统字体、不做字形替换 ⇒ 占位码位会显示成它自己的日文汉字 ⇒ 只能 **CAPTION 留空**
  （旧仓记录；实测产物也是 `CAPTION ""`）。
* **菜单**走 `LoadMenuA`，可产物里是**真简体字**（实测 `游戏`/`保存`/`读取`）且补丁发布后菜单确实是中文
  ⇒ 这条路上没有发生有损转换（**解释**：`A` 影响的是按名字找资源那一步，取回的菜单对象本身是 Unicode —— 标「待验」）。
* 旧仓另有一条**对照实验**：**改 LANGUAGE 并不改变引擎编码行为**（同模板两种 LANGUAGE 的编译产物，
  仅目录语言 ID 不同、数据块逐字节一致）。

⇒ **同一份 DLL 里两种编码策略并存**（菜单真简体 / 对话框占位码位），不是随手写的。

★ 这条耦合**目前流水线里没有任何断言**：换一次字典，对话框里的中文会**静默**渲染错。
　对照：AGE 脚本侧的 `patch.json` 有 `subsSha` 指纹 —— **DLL 侧什么都没有**。

### 2.6 ★ 「效果怎么投射进 exe」= 两个宿主媒介（2026-10-03 新增，实测）

`AGERC` 自己**不直接改引擎状态**；它通过 `DllMain` 里
`GetProcAddress(GetModuleHandleA(0), "_GetClassObject@4")` 拿到宿主对象工厂，再懒加载**两个 COM 风格对象**：

| 媒介 | 槽位与签名（实测） | 用法计数 | 性质 |
|---|---|---|---|
| **`AGE:reg`**（配置存储） | `+4` `int Get(const char* key)` · `+8` `const char* GetString(key)` · `+12` `void Set(key, int)` · `+16` `void SetString(key, ...)` · `+28`（另有 1 处） | +4 **72×** · +12 **48×** · +8 **6×** · +16 **3×** | ★★ **归一化的键值存储** —— 键是**字符串**，值是 int 或 string |
| **`AGE:IAGEService`**（引擎服务） | `svc->slotN(args)`，vtable 偏移 `+4 … +236`（≈**60 个槽被用到**）；**每个槽有各自签名**：`()` / `(int)` / `(const char*)` / `(int,_DWORD)` … | 用得最多的是槽 5/6/8（各 10×）、9/10（各 8×）、11（6×） | **动作通道** —— "cmd + param" 的精神，但**不是单一签名** |

★ **`IAGEService+32` = `void(const char*)`** —— 就是"**让引擎去重载这支脚本**"：3 个 `CALLBACK_*.BIN`
（`CALLBACK_MESWINA.BIN` 消息窗透明度 / `CALLBACK_USEANTIFONT.BIN` 抗锯齿 / `CALLBACK_SETTING.BIN` 设置回写）
都走这一个槽。⇒ **AGERC 只负责发命令，脚本的加载与执行在引擎侧**。

#### ★★ 配置键是**带命名空间的字符串**（实测抠出 **59 个**）

```
set:     （15）GameName · GameVersion · Copyright · IsReggist · EnableAntiFont · NoSetMusic
              ScreenWarning · UseAppDataFolder · Menu_Message · Menu_MesSpeed · Menu_MesWinA
              Menu_RClick · Menu_Save · Menu_SoundONOFF · Menu_UseAntiFont
message: （11）MessageSpeed · MesWinAlpha · ReadTextSkip · RMouseEvent · UseAntiFont
              AdvanceMesOnWheel · AutoMessageOption · AutoMessagePitch0/1 · AutoMessageTime0/1
sound:   （10）Music · SE · Voice · Sound · Volume0..3 · MusicFadeOnVoicePlaying(+Volume)
display: （11）ScreenMode · FullScreenWidth/Height · VirtualFullScreen(Type) · AspectMode
              DeviceType · ForceScreen · MultiSample · PresentInterval · VertexProcessing
system:  （ 6）SaveBMPPath · UseMMX · LimitJoy · LimitTouch · EffectSkipOnClick · OutErrorLog
debug:   （ 6）DebugFlag · DebugRemote · DebugOutLabel · DebugOutVar · FunclstPath · DebugComputerName
```

（这是 `AGE:reg` 那 4 个槽的实参里抠出来的字符串字面量去重结果；原始 61 条里有 2 条是邻行误捕
——`Version %s` 与 `ｳｲﾝﾄﾞｳ(推奨)`，**不是键**。）

**⇒ 对"入库形态"的直接结论**：

1. **配置层可以真正归一化入库**：一条记录 = `(key, kind: int|string, value)`。
   键自带命名空间、可读、可 diff、**没有偏移**；`set:Menu_*` 那组就是菜单勾选状态。
   ⇒ 这是本方案里**唯一可以做成"像 `patch.json` 那种文本真源"的东西**。
2. **动作层不能归一成单一 `(cmd, param)`**：它是 **vtable 槽 + 逐槽签名**，
   要入库必须先把**每个槽的签名与语义**定下来 —— 而这份表现在**只有部分有一手证据**
   （文档自认；连"IAGEService ≈59 槽"这个数都标着"据说"）。
3. **效果的完整投射路径**（从命名空间能读出来）：
   `改设置 → reg->Set("message:MessageSpeed", v)`（持久化）
   `→ svc->slotN(...)`（立即生效）`→ 必要时 svc+32("CALLBACK_SETTING.BIN")`（让引擎重载逻辑）。
4. **对"重建"的含义（重要）**：要复现的效果面是**有限且可枚举**的 —— **59 个配置键 + ~60 个服务槽**。
   这把重建从"开放式"收窄成"一张表 + 一张表"；**瓶颈仍然在槽语义的证据**，而不在规模。

★ 与真机观察对齐：玩家真正看到的对话框就是**三组** ——
**退出确认**（`DIALOG 3`）+ **设置多 tab**（外壳 `DIALOG 9` + 页 `100/101/102/103/104/105/136`）+ **版本信息**（`DIALOG 2`）；
另有 `DIALOG 8`（存读档名）/`DIALOG 10`（注释编辑）在边缘，其余为 debug 用（`DIALOG 5` 甚至无调用点）。

#### ★★ 键的**初始值来自哪里**（旧仓已追到根 —— 出处 `旧仓 tickets/T-0196/evidence/sys4ini-tail-config.md`，含代码级锚点，**本仓未复核**）

`AGE:reg` 只是**读写口**；键的**发行默认值不住在 DLL 里**，而在**两个文件源**：

| 来源 | 形态 | 优先级 |
|---|---|---|
| **`SYS4INI.BIN` 的尾部配置块**（就是那个归档索引文件！） | `int count` + `count × (大写键名\0 值\0)` ⇒ 实测 **51 条** | 低（先加载） |
| **`SYS4REG.INI`**（玩家配置） | INI 的 `[set]` 等段（实测该文件 95 键、**没有 `[set]` 段**） | **高（覆盖索引）** |

引擎侧链路（旧仓记录）：`sub_414AC0` 读 `SYS4INI.BIN` → 尾部配置段 → `sub_405730`
→ 配置对象 `vtable+44`（"LoadFrom"）→ `sub_494220` **按大写键名逐个 `_stricmp` 匹配** → `atoi(值串)`
→ 写进 `set:<键>`。★ 键名表**在 exe 的 `.data` 里**（大写，如 `CONTROLDISIBLECURSOR` @`0x529E7C`），**但值不在 exe 里**。

⇒ **对"归一化入库"的结论（确认）**：这就是一张 **`大写键 = 字符串值` 的文本表**，
引擎内部统一成 `namespace:Name`，**两个来源 + 明确优先级**，**完全没有偏移/二进制结构**
⇒ 入库形态取 `(key, kind, value)` 是**天然合适**的（比 `cmd+param` 更归一，因为它连"命令"都不需要）。

★ 三条必须一起带上：

* `FONT` / `SAVEPATH` 是 **CP932 串** ⇒ 与汉化字典的**码位占位**直接相关
  （而 `message:Font` 的玩家值实测就是 **`Amayui CN`** —— 汉化安装说明里"把字体内分类指向 Amayui CN"那一步落的就是这个键）；
* 同名键在配置段里**可以重复出现**（`VALIDFONTCHECKER` / `JUSTIFYCHAR`）⇒ "取最后一次"还是"列表语义"**未定**；
* 配置段之后**还有可选段**（`raw 22147-22169` 的跳段循环）**未读**。

★ 对**重建**的含义：设置持久化这一层**不神秘** —— 我们只要照发 `reg->Set(key, value)`，
键名与格式已归一，且有旧仓那 51 条发行默认值表可直接对照。**风险不在这里**，仍在 `IAGEService` 的槽语义。

#### ★★ 两层要分清：**持久化走 `AGE:reg`、生效走 `IAGEService`**（实测，回答"是不是把非 INI 配置映射到 IAGEService"）

**不是。** `IAGEService` **不是配置存储，是动作/生效通道**。三条实测证据：

1. **菜单命令路径里一次 `reg->Set` 都没有** —— 38 个 `case` 里只有 `svc->[+N](…)` 串，
   有的后面还跟 `svc->[+32]("CALLBACK_*.BIN")` 让引擎**重载脚本**。抗锯齿是最干净的样本：
   ```c
   case 40029: svc->[+104](svc, 1); svc->[+32](svc, "CALLBACK_USEANTIFONT.BIN");   // 开
   case 40030: svc->[+104](svc, 0); svc->[+32](svc, "CALLBACK_USEANTIFONT.BIN");   // 关
   ```
2. **`reg->Set` 的 48 处全部集中在 4 个函数**里，其中两个是**对话框过程**
   （签名 `(HWND hDlg, UINT, WPARAM, LPARAM)`）：`sub_100427F0` **16** 处 · `sub_10041FE0` **16** 处（集中写入）·
   `sub_1003AD60` **11** 处（收 `hWndParent,hMenu`）· `sub_1003E440` **5** 处。⇒ **持久化确实走 `AGE:reg`**。
3. **形态上也不像**：`IAGEService` 多数槽**无参**（`+20/+24/+132/+136/+140/+172/+176`），
   而"设置值"必须带参数 ⇒ 它不是"逐键映射"。

★ **但你的直觉指向了一个真实存在的东西**：确实有一批**"不在 INI 里"的配置** ——
它们就是 **`SYS4INI.BIN` 尾部那 51 条**。它不是映射到 `IAGEService`，而是
**同一个 `AGE:reg` 接口的另一路来源**（索引先加载 → `SYS4REG.INI` 后加载并覆盖）。

⇒ 准确模型是两层：

| 层 | 媒介 | 形态 | 参与者 |
|---|---|---|---|
| **持久化** | `AGE:reg`（4 槽） | `(键, 值)` —— **归一化** | 来源 = `SYS4INI` 尾部（发行默认 51 条）+ `SYS4REG.INI`（玩家覆盖）。**设置对话框的 DialogProc 在这里写**（48 处） |
| **生效** | `IAGEService`（≈60 槽） | `slot(参数)` —— **异质签名，不归一** | 菜单命令 / 设置应用路径在这里发动作；`+32(脚本名)` = 让引擎重载 `CALLBACK_*.BIN` |

★★ **一个尚未闭合但方向明确的点**：`svc+32("CALLBACK_SETTING.BIN")` 之后，**是引擎侧那支脚本**去把设置真正落到
渲染/设备上 —— 旧仓文档自认 **`+32` 的引擎侧实现体未读**。
不过这同时说明：**"效果投射"的实现主体在游戏数据侧（脚本），不在 AGERC 里**。
⇒ 对**重建**是好消息：要复现的只是"**发命令 + 叫引擎重载脚本**"，不必理解每个效果怎么落地。
（代价：这条链的下半段**没有证据**，属于"别人替我实现"的那部分——它现在能跑，是因为原 DLL 与引擎的约定没变。）

### C 的判据（建议直接写进需求节点）

1. **资源集合不变**（type/name/lang 多重集与基线相等）—— 若确需改语言（E1），**显式声明**并只允许那一项；
2. **未列出的资源内容与基线逐字节相同**（含那 15 个没翻译的 DIALOG、30 条 ICON/CURSOR/VERSION/MANIFEST）；
3. **除被改写的字节外整文件逐字节相同** —— 具体是：`.rsrc` 里那 3 条资源的数据（+ 必要目录项）、
   `.rdata` 的 3 个串槽、`.idata` 的 2 个导入名；`.text` **必须 0 差异**；
4. **搬迁期证人**：产物的资源内容与旧仓 `install/AGERC.DLL` **逐资源对账相同**（对照 `resultSha` 的角色）；
5. ★ **必须带字典指纹**：真源里记 `subsSha`（= `data/translations/subs-cn-jp.json` 的 sha256）；
   与当前字典不一致 ⇒ **报出来**（对话框文本是占位码位，换字典必然改变渲染结果）。

### G. 「**凭空重建 DLL**」的评估（2026-10-03 追加）

设想：既然本作只用到 AGERC 的一小部分，**照反汇编 + 资源凭空重建一个 DLL**，只实现真正用到的部分，
从而摆脱"字节偏移 + 字符串替换"的脆弱方案。

**支持它的实测证据（比预期强）**

| 观测 | 数字 |
|---|---|
| 接口面**完全枚举** | 导出 **21 个，全部具名**（`_Name@N`，序号 1–21）；导入 **150 个 / 7 个 DLL**（含 `d3d9!Direct3DCreate9`、VERSION/WINMM/ADVAPI32/SHELL32） |
| **17/21 个导出是地图/碰撞族**，且语义**极简** | `_SetMap{Land,Wall,Ev}{PX,PY}` = 把入参数组拷进静态数组（10,000 或 100 个 int）；`_SetNameLenMax@20` = `dword_100A9000 = *a2; return 0;`；`_GetInstance@0` = 空体/极薄 |
| 它们**没有调用者** | AGE.EXE 反汇编里按名字只命中 `_GetInstance` / `_OperateMenu` / `_ShowDialog` **各 1 处**，17 个地图导出 **0 命中**；游戏脚本里只有 `_SetNameLenMax` 命中 **1 处** |
| 3D 是**单入口** | `Direct3DCreate9` 全库只有**一处**调用（`.text:1003E218`）⇒ 那一簇可整块丢 |
| 规模可控 | Hex-Rays 输出只有 **122 个函数**；AGERC 自己的代码集中在 0x10032xxx–0x10036xxx 与 0x1007Cxxx 两簇（其余多为静态链接的调试 CRT） |

**反对 / 风险（复杂度的真实所在）**

1. **省掉的是字节，不是行为**：剩下那 3 个导出恰好是**整个设置 UI**。`OperateMenu` 是 `a1 ∈ {0,1,2}` 的**分派器**
   （懒加载两个引擎服务 → `sub_10032924` / `sub_10032B04` / `sub_10032CBC`），其下是
   **38 条命令 ID**（`40003–40048` 去掉 8 个缺号）、**16 个对话框模板**（15 个有调用点，`DIALOG 5` 无；**现只汉化了 1 个**）、
   配置读写、截图/剪贴板、显示模式、计时器……**逐项对玩家可见**。
2. ★ **隐藏的硬依赖 = 引擎服务接口**：`GetClassObject("AGE:reg")` / `GetClassObject("AGE:IAGEService")`
   （后者据说 **59 个槽**）。重建必须**精确复现槽序/语义/结构体布局**，而旧仓对它的证据是**部分的**。
   ★ 这类错误**不会编译报错**，只在玩家点某个菜单时行为不对。
3. **判据退化**：本仓的纪律是"判据 = 逐字节"；重建之后**没有任何机械判据**能证明行为等价，
   只能人肉逐项验收，且失败模式是**静默**的（配置不保存 / 某菜单项无反应 / 切全屏后崩）。
4. **ABI 细节**：装饰名（stdcall 的 `@N` 后缀）必须**逐字一致**；`DllMain` 与初始化时机、两个服务的懒加载、
   `GetClassObject` 指针的来源都要复现。
5. **一条只验了一半的前提**："按**名字** 0 命中"**不等于**"按**序号**也没人调"——17 个桩是否安全，还差这一条。

**★ 重建唯一的真技术收益**：对话框可以由**我们**用 **`DialogBoxParamW`** 弹
⇒ §2.5 那条「**占位码位 + 字体 cmap**」的耦合**可以彻底去掉**（前提：`Amayui CN` 里真实简体字的字形仍在）。
**这是现方案做不到的** —— 现在弹框的是**原模块**的 A 版调用。

**★ 推荐的过渡形态：探针版（把"赌"变成"量"）**

在决定重写多少之前，先花很小的代价把**可达面**测出来：

1. 写一个**只含 21 个同名导出 + 资源**的 DLL：`_GetInstance` 返回**自己**（⇒ 引擎的 `LoadMenuA(HINSTANCE,110)` 会读到我们的菜单）、
   `_SetNameLenMax` 照抄那行、地图族照抄（它们本来就只有几行）、`_ShowDialog` / `_OperateMenu` **先转发**给**改名后的原模块**；
2. 在**游戏副本**里替换，实机跑；
3. 在转发点**记录实际被调用的 `a1` 值 / 菜单命令 ID / 对话框 ID**
   ⇒ 把"可达面"从**静态推断**变成**运行时清单**。★ 这份清单对**方案 C** 同样有用（知道哪些资源真被用到）。

这个探针同时验证三件事：导出名与初始化是否对（游戏能不能启动）、"资源 + `_GetInstance` 返回自己"这条路是否成立
（菜单栏是否变中文）、以及**真正需要重写的行为有多少**。

**结论**：**可行性成立、规模可控（122 个函数、接口已枚举），但"复杂度低"这个直觉只在"要重写的代码量"上成立**；
真正的成本与风险在 ① 引擎服务接口的语义复现、② 失去逐字节判据之后的行为验收。
⇒ 若目标只是**当前这份汉化**，方案 C 仍更划算；若动机是**摆脱脆弱 + 扩到 16 个对话框 + 去掉占位码位耦合**，
重建值得做，但应作为**独立项目**，并**先做上面那个探针**。

| ★ **菜单状态同步** | `CheckMenuItem` **80 处** · `EnableMenuItem` **21 处** · `ShowWindow` **23 处** | ❌ **要写出来**（每个命令的勾选/灰化/显隐都得自己维护） |
| ★ **非 COM 的效果** | 剪贴板截图（`OpenClipboard` + `WriteFile`）· 选目录（`SHBrowseForFolderA`）· 显示模式（`SetWindowPos`/`ShowWindow`）· `SetTimer` · `MessageBoxA` | ❌ **要写出来** |
| ★ **`IAGEService` ≈60 槽的语义** | 逐槽各自签名；**证据只有部分**（连槽数都标"据说"） | ⚠️ **"照抄"的前提是语义已知** —— 而这正是缺口；错了**不报错** |
| 出入口 / ABI | `DllMain` 的 `GetProcAddress(GetModuleHandleA(0),"_GetClassObject@4")` · 两个服务的懒加载时机 · 装饰名 `_Name@N`（4 个被用） · 版本资源（引擎查 `FileVersion`） · `MENU 110/124` | ❌ 要逐字复现 |

⇒ **一句话**：`AGERC` 的代码量不大（**122 个函数**），但它的内容是**界面与交互逻辑**，不是协议调用；
"照抄调用"能一次拿下**投射层 + 配置层 + 那 17 个导出**（这三块确实是大头里的"便宜部分"），
**剩下的是"把 11 个对话框过程和整条菜单状态同步重写一遍"**，外加补全 ~60 个槽的语义。

★ 由此也说明**探针版**的第二个用途：它能在运行时把**真实的 `(槽, 参数)` 序列**记下来 ——
那才是把"照抄"从**猜**变成**抄**的唯一办法。

## 5. 成本 / 收益：先问一句值不值得

实测下来，**对玩家真正可见的汉化只有两处**：**主菜单栏**（`MENU/110`）+ **退出确认框**（`DIALOG/3`）。
其余 15 个 DIALOG **是没翻译的日文**；`MENU/124` 是**调试菜单**，玩家看不到。

⇒ 收益面很窄，代价却是一条 **Windows-only、两条链叠加、不可复现**的构建链（§3）。
　两个方向都合理：

* 要"菜单栏也得是中文" ⇒ 走 **C**：因为只需处理 3 条资源 + 5 处字节，规模小到可以完全验干净；
* 只要"译文 / 剧情 / UI 图" ⇒ 走 **E**：把 AGERC 汉化降级为可选包，主包保持全链可复现。

★ **不建议 A**：缺陷 3/5/6 会在下一次改动里静默生效（而且它**现在已经跑不动了**）。

## 7. 怎么查（复现本文的实测）

本文数字来自两个**只读**探针（本次写在 `.tmp/` 里、**未入库**，用完即弃）：

1. **PE 结构 + 资源清单**：解析 DOS/PE 头 → 节表 → 资源目录树（type/name/lang 三层）→ 每条资源的 RVA 与大小；
   再用"RVA → 节内相对偏移 → 文件偏移"判断**该资源的数据是否真在盘上**（§1 实测 1 靠这步）。
2. **逐字节差异落点**：**按节名对齐**比较。

★ **两个取证坑**（都踩过，写下来省下一次）：

* **别按文件偏移逐字节比**：`.rsrc` 尺寸一变，后面所有节在文件里整体位移，
  按偏移比会得出"`.reloc` 有 17 KB 不同"的**假差异**；按**节名 + 节内相对偏移**比，真相是 **0**。
* **`.rc` 是 UTF-16LE**：本机 ripgrep 15.2.0 下 `rg --encoding utf-16le` 的**行首锚点 `^` 匹配不到**
  （`LANGUAGE` 能命中、`^LANGUAGE` 不能）⇒ 不转码就会得出"条目数为 0"的错误结论。要统计先转成 UTF-8 派生副本。

要看某个文件的现状，见 `corpus/assets.json` 的 `binary/agerc-*` 三条（只登记、不迁移）；
本文结论要落成实现时，**先**把它们写成需求节点里的可执行判据，再动代码。
