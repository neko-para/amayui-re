# 01 · 翻译 patch 方案（真源 = 叠加层；`data` / `src` 都是视图）

> 本文件是**评估与设计**：记录"为什么这么定"、以及支撑它的**观测**。
> 可执行的工作项在需求树：`pnpm tools requirements show 8SNRXKV`（节点「翻译 patch 方案」）。
> ★ 本文件只写**格式层与流程层**的事实与决定；**不写任何游戏语义结论**（那些归知识线 K1–K3）。

## 1. 三个词

| 词 | 含义 |
|---|---|
| **基线** | `gameInstall/` 里的**原版日文 BIN**。唯一不可变的东西（用 sha256 钉住） |
| **patch** | 相对基线的**变更叠加层**。★ **唯一入库物** |
| **视图** | 由基线（±patch）**实时算出**的文本：`data` = 基线的视图；`src` = 基线 + patch 的视图 |

⇒ 一句话：**`data` 与 `src` 都不入库**；"日文基线"不是一个目录，而是**原版 BIN 的一段只读视图**。

## 2. 支撑决定的关键观测（都可复核）

### 2.1 锚必须锚"基线指令序号"

| 观测 | 数字 |
|---|---|
| 在指令流中插入一条后，其余指令在原版里的**序号**是否仍能逐条对上 | **8/8 文件成立**（屏蔽 label 引用后逐条相同） |
| 插入一条 `set-string`（字符串表定义）后同样成立 | **6/6 文件成立** |
| 为什么不能用字节偏移 | 插入会改变后续所有偏移；**label 地址本身就是字节偏移的函数**（实测插入 12 字节后 `call label_0006d19c` → `label_0006d1a8`） |
| 为什么不能用 label | 它**就是**字节偏移：实测 `label_00000320` 处的指令字节偏移正是 `0x320`。两侧地址**只有 317 个交集**、同位置相同仅 **206 / 3362** |
| 为什么不能用字符串槽位 | 它是**产物空间**的地址，随产物变化 |

⇒ **锚 = 基线指令序号 + 内容摘要**（`opcode` 不必单列：整行里已经带了助记符）。
`delete` 只记序号与摘要就够 —— 被删的那条**本来就在基线里**（序号空间 = 基线），
所以它的原文随时可从基线现取；`sha8` 用来确认"取的还是当年那一条"。

**label 怎么处理**：patch 里**不记地址**，只保留"这里是一个 label 引用"这一**结构事实** ——
生成时把引用的地址**遮蔽成 `label_?`**（否则同一逻辑行在两侧因地址漂移而判成"不同"）。
重建时由汇编器按**符号**重算地址（它收集 label 的**值**作为符号、重写引用，所以漂移自动被吸收）。
替换行时**被替换指令身上的 label 定义必须跟着搬**（否则实测 115 处 label 悬空）。

★ 但**只靠遮蔽会漏掉一类真差异**：`jcc … label_00000390` 与 `jcc … label_000018fc` 遮蔽之后长得一样，
**字节却不同**。实测这一条会让重建出的 BIN 引到一个**已经被删掉的** label（悬空）。
⇒ 提取时对"匹配上的行"再做一次**按对齐关系解析 label** 的比较，不一致就**降级成 `replace-line`**。

★ 还有一类更硬的：产物**新增了跳转目标**，而那个目标落在"插入出来的行"上 —— 基线里**没有身份**。
⇒ patch 允许在 `replace-line` / `insert-after` 上带 `def`（**patch 局部 label 符号**，从 `0x800000` 起编号），
由控制脚本在重放时原样放出定义行。实测全量用到 **54 处降级 / 77 个 patch 局部 label**。

### 2.2 `src` 里的信息**全部可再算**（这是"src 能当视图"的前提）

| 信息 | 可重建性 | 依据 |
|---|---|---|
| `// FROM: <id> <名>` | **100.0000%**（30 271 / 30 271 页，全量） | 页前导区间里最近的 `mov (global-int 3f37) X`；`sub (global-int 3f37)…` 或 `call label_00071658` ⇒ `none`；`call` 递归进函数体（实测深度 1，限 4 富余，环 0） |
| `// 输入原文：` | **100% 冗余** | 55.1% 与同页正文完全相同，44.9% 仅折行差异 ⇒ 由 reflow 规则反向排版可得 |
| `// 页面结束` | **等价** | 不用任何注释，仅按"连续文本类指令段"切页 ⇒ **同页数、同取值（0 页分叉）** |
| 原文存档块（被译掉的日文） | **100%** | 逐字节能在原版 BIN 的反汇编里找到（30 145/30 145，抽查逐字节相同） |
| 存档块内的指令名 | **0 漂移** | 块内只有文本类指令（`show-text`/`display-furigana`），结构指令不进存档块 |
| `data/*.txt` | **100%** | 原版 BIN 的反汇编 |

★ 一条被推翻的旧说法：旧脚本头注释写"`wait-for-input 0` 为页间硬边界"，**代码里根本没实现**。
实测 30 067 条 `wait-for-input` 的**下一条 100% 是文本类指令**、是 ADV 的 **0%**；
"页前导区间里含 `wait-for-input`"的页数 = **0/30271**。⇒ 页边界只能由**文本类指令段**判。

### 2.3 BIN 落点（**三处，缺一不可**）

| 目录 | 是什么 | 角色 |
|---|---|---|
| `gameInstall/` 散装 | 本体原版 + **开发商的 patch 覆盖** | ★ **基线（优先）** |
| `gameInstall/` 的 `SYS4INI.BIN` / `APPEND0N.AAI` + `*.ALF` | 本体与资料片的归档 | ★ **基线（其次）**，见 §4 |
| 旧仓 `install/` | 本体**汉化产物树**（全量真拷贝 + 替换过的散装 BIN + 原样归档） | ★ **迁移期一次的提取源**（见 §4.2）；**运行时不再引用**（见 §5） |
| 旧仓 `raw-parts/` | ALF 的**解包派生**（且**与两边都不等**：`SC0000` 的字节既不等于基线也不等于产物） | ❌ **完全不引用** |
| 旧仓 `patch/BIN` · `gameInstall/_extracted/` | **overlay**（老汉化 / 新汉化的产物） | ❌ 排除：产物不是脚本来源 |

### 2.3 范围怎么定（**曾经在这里犯过一次错，留档**）

★ **patch 的范围不是按名字筛出来的**，而是：**基线根里全部能反汇编的 AGE 脚本，逐个抽差异，有变更才进 patch**。

为什么必须这样（实测教训）：译文存不存在**只能由"产物 ≠ 基线"判定**。任何名字过滤都会静默漏掉真译文 ——
曾经我拿旧仓 `scripts/annotate-speaker.js` 里的正则 `/^(SC|SP)/ || /^\$\d+\$(SC|SP)/`（共 223 支）当范围，
并把它叫成「官方集 = 翻译管线处理过的脚本」。**那两件事都不成立**：

| | 事实 |
|---|---|
| 那个正则是什么 | 旧仓 `annotate-speaker.js` 挑文件用的 —— 含义只有"旧管线给这批做过**页 / 说话人标注**" |
| 旧仓 `src/` 覆盖多少 | **941** 个文本（**全部**脚本，含 `SG*` / `SN*` / `CONFIG` / `PLINIT` / …） |
| 被那个正则挡在门外的 | **719** 支，其中 **247 支产物与基线不同**（= 有译文），且文本里有简体字 |
| 后果 | patch 只覆盖了 207 支，**漏掉 247 支真译文**；名字改对了才补回来 |

⇒ 现在（已修）：

| 口径 | 个数 |
|---|---|
| 基线根里的 `.BIN` | 942 |
| 其中能反汇编的 AGE 脚本（= **范围**） | **941**（唯一例外 `AGE.EXE__USERDATA.BIN`） |
| **产物 ≠ 基线 ⇒ 有条目** | **453** |
| 没有条目 | **488** ＝ 487 支两侧逐字节相同 ＋ 1 支**旧仓的坏文件**（见下） |

★ **旧仓有一处坏文件，迁移时没取它** —— 这是**旧仓的问题，不是本方案的机制**：
`install/$1$IMINIT.BIN` 是个 64 B 的空壳（基线 10 184 B / 367 条指令 → 只剩 `exit`，`local_vars` 也被重置）。
判据：① 它的文本树 `src/$1$IMINIT.txt` 367 行、与基线逐行相同、**0 行中文**（= 从未翻译）；
② 那 64 B 与**游戏自带的 `$4$IMINIT.BIN`**（原版就 64 B）**逐字节相同**；
③ 旧工程自己的 `tickets/T-0045/notes.md` 把 `$1$IMINIT`/`$1$SCINIT`/`$1$SCJUMP` 记成
"**opcode 改名后工具链重编的产物**"。
⇒ 迁移时**跳过**它，我们的构建保留**游戏原版**的完整脚本。记录见 `REQ-01M3YF5120V9WXB7NF36GVP52G`。

★ 这件事**不进数据模型、不进结构校验**（`patch.json` 里就是没有那一条）：迁移时用**通用的命令行开关**，
理由写在文档里而不是在代码里维护一张名单 ——

```bash
node tools/patch.mjs --extract --target <旧仓 install> --skip '$1$IMINIT.BIN' --write
node tools/patch.mjs --verify  --target <旧仓 install> --skip '$1$IMINIT.BIN'
```

★ 由此定了 `--verify` 的缺省口径：**产物根只是迁移期的一次性来源**（§5），所以缺省**不比产物**、
只做 `resultSha` 自证；要对产物复核就显式 `--target`。那一跑会如实报出 `$1$IMINIT.BIN（无条目）`
—— 那是**记录在说话**，不是机制在放行。

「说话人标注」这个口径仍然有用（它标出旧管线做过页/说话人标注的那 223 支），但它**只是那个任务的口径**，
**不是脚本的分类**，更不是 patch 的范围。代码里叫 `SPEAKER_FILTER`（说话人标注挑文件用）/ 字段 `annotated`。

### 2.4 `comment` 指令（0x1A7）——**不拿它存东西，但它必须被保留**

| 观测 | 结果 |
|---|---|
| 形态 | `comment` argc=1，**带一个字符串操作数**（`comment "ループ開始"`）；旧仓 opcode 表记 "nop（dev 注释，无副作用）" |
| 游戏是否已在用 | **是**：`comment "savemesskip q-load"` / `"loadmesskip advset"`，以及章节标记 `"▼G####　…"` |
| 注入我们自己的 comment 后 | 25/25 个 BIN **稳定**（原样往返仍逐字节相同，comment 数 +1） |
| ★ **把它从指令流里丢掉会怎样** | **重建结果不是逐字节相同**：6 个样本脚本共少 14 个字符串 / 472 B |

⇒ 它是一条**可行的自足通道**（把不可推导物嵌进 BIN），但本方案**选择不用**：入库物只有 patch，
发行物保持干净，且避免与 `▼G####` 之类既有标记撞车。
★ 但它是**数据不是注释**（带字符串载荷、占字节）—— 指令流的"注释"过滤规则**不得**把它滤掉。

### 2.5 BIN 里的字形不是中文 ⇒ **真源只能是中文**

| 观测 | 结果 |
|---|---|
| 旧仓写 BIN 的真实规则（`scripts/lib/sjis-encode.js`） | `canEncodeCp932(ch)` ⇒ **原样保留**；否则查简→日写法字典；字典缺 ⇒ 记问题并用**全角空格**兜底 |
| 为什么 BIN 不能反推回中文 | 同一个码位**既可能**来自"本来就编得进去的汉字"，**也可能**来自字典占位 ⇒ 两者在 BIN 里不可区分 |
| 字典规模 / 反查质量 | 字典 **3000 条**；反查基本唯一（整表只有 1 例冲突） |

⇒ patch 里存**中文**（真数据）；BIN 里的"日文写法"是它在**构建时**的机械派生
（`canEncodeCp932` 优先 → 字典 → 全角空格；顺序不能反）。这条决定同时解释了
patch 为什么必须带**字典指纹**（`subsSha`）：换字典 ⇒ 重建结果会变，必须报出来。

## 3. 设计（决定）

* **入库物 = patch**。`data` 与 `src` 由"基线 + patch"实时生成，**不落库**。
* **判据是"逐字节"**（不是"指令流逐条相同"）：基线 BIN → 反汇编 → 打 patch → 汇编 ⇒
  必须与目标 BIN **逐字节相同**。这条更强，且**顺带覆盖**了"指令流相同"。
  实测 6/6 样本脚本达成（修掉两处之后：label 遮蔽、`comment` 不丢）。
* **patch 的锚**：基线指令序号 + 内容摘要；带 `baseSha`（基线指纹）、`resultSha`（产物指纹）与
  `subsSha`（字典指纹）。三者都是**指纹关系**：任一变了就**显式报冲突**，不静默改写。
* **不叠加**：一条 patch 只对**基线**应用；要分层就显式写成 patch 链（后层以前层的产物为基线）。
* **`data` 视图**由基线 BIN 反汇编得到；**`src` 视图** = 基线 BIN → 指令流 → 应用 patch → 按规则重贴注释。
  ★ 落地的形态：`src` = **重建 BIN 的反汇编，但字符串取 patch 里的中文**（BIN 里只有占位写法，见 §2.5）；
  两份视图**同构**（同样的行数口径与**真实地址**）⇒ 可直接并排 diff。
* **编辑回路**：`view --kind src` → 人改中文 → `edit` 反解回 patch。
  反解走的是**同一条对齐/锚定路径**（`extractEntry`），所以锚永远在**基线行序**上、**不在旧 ops 上叠加**。
  实测往返：改一处中文 ⇒ 反解 ⇒ 重新生成 `src` ⇒ 与改过的那份逐字节相同；改回原样 ⇒ 操作集与 `resultSha` 都回到原值。
* **唯一需要旁挂的人工数据**：`NAME_OVERRIDES` **5 行**（`b`/`c`/`81`/`138`/`170`；实测 5 条全被用到）。

### 3.1 patch 用 JSON + 控制脚本（用户口径）

后续很多工具要**直接分析** patch（构建视图、比对、审计），所以：

* **数据** = JSON（不透明数据；字段语义只在控制脚本的自描述里）；
* **控制脚本** = 唯一写入口（`apply` / `extract` / `verify` / `--describe`），并**负责**：
  生成 `data` 视图、生成 `src` 视图、把"改过的 `src` 视图"反解回 patch、校验 patch 与基线是否仍匹配；
* **配套**：`data/translations/patch.json` + 同名说明书 `patch.md`（含「怎么查 / 怎么改」并指向 `--describe`）。

### 3.2 格式骨架（**已实施**；字段语义的真源是 `pnpm tools patch describe`）

```jsonc
{
  "schemaVersion": 1,
  "_doc": "本文件是不透明数据：字段语义 / 不变量 / 怎么查怎么改 见 `pnpm tools patch describe`。不要手改。",
  "subsSha": "简→日写法字典的 sha256（换字典 ⇒ 重建结果会变）",
  "scripts": {
    "SC0000.BIN": {
      "baseSha":   "该脚本**基线** BIN 的 sha256",
      "resultSha": "该脚本**产物** BIN 的 sha256（判据 2 的证人）",
      "ops": [
        { "op": "replace-line", "i": 431, "sha8": "3f9c1a2e", "line":  "…中文源行（整行，含助记符与操作数）…" },
        { "op": "delete",       "i": 512, "sha8": "a71b30c4" },
        { "op": "insert-after", "i": 700, "instr": "…中文源行…", "def": ["label_800001"] }
      ]
    }
  }
}
```

| 决定 | 为什么 |
|---|---|
| 三种操作 **`replace-line` / `delete` / `insert-after`** | 覆盖实测出现的全部差异；`insert-after i` 用 `i = -1` 表示"插在最前" |
| 可选 `def`（**patch 局部 label**） | 产物新增的跳转目标可能落在"插入出来的行"上，基线里没有身份 ⇒ 只能给它一个新符号 |
| **不存"原文"** | 它可由 `baseSha` 指到的基线 BIN 现算（`src` 视图的原文存档块要用）⇒ 省掉约一半体积 |
| **不存 `opcode`** | 整行里已经带了助记符；再存一份就是第二个真源 |
| **保留 `resultSha`** | 它是判据 2 的**证人**：旧仓消失后，"重建是否仍然逐字节对得上"只剩它能机械复核 |
| **`sha8` = 基线该条指令的摘要** | 基线一变即判冲突（与知识台账同构）；**不是**行号、不是地址 |
| **`line` 存中文** | BIN 里的日文写法是构建时的派生（§2.5）——存 BIN 形式就等于把真源存成派生物 |
| 顶层 `subsSha` | 字典是构建的一环；换字典 ⇒ 全量结果会变 |
| 一行一个 op（自定义行式序列化） | `git diff` / `git blame` 才有意义（`JSON.stringify(…, 1)` 会把一个 op 拆成 7 行） |

### 3.3 实测规模（全量 941 支脚本，453 支有变更）

| 口径 | 值 |
|---|---|
| patch JSON | **8.16 MB**（**453** 支脚本 / **77 198** 个操作：replace-line 49 196 · insert-after 21 766 · delete 6 236） |
| 其中 | 54 处"值相同但 label 目标变了 ⇒ 降级成 replace-line" · 77 个 patch 局部 label |
| 不进 patch | **487** 支无变更（`--verify --target` 的无条目复核断言）＋ **1** 支旧仓的坏文件（见 §2.3） |
| 对照 | 旧仓 `src` 文本树 **91.8 MB** ⇒ 小一个数量级；**且它才是唯一资产** |

⇒ 规模明确 ⇒ **单文件 `patch.json` 可行**；若将来并行编辑冲突变痛，再按脚本分片（纯物理切分，不改语义）。

★ **数字不手抄**：`pnpm tools patch status` 给当前值（脚本数 / 操作数 / 体积 / 按操作类型分布 / 基线解析来源）。

## 4. 基线与产物：**同一套解析层，两个根**

### 4.1 解析层（不依赖 `raw-parts`）

`raw-parts` 只是 ALF 的**解包派生**（实测它的字节甚至**两边都不等**），不该成为依赖。
按**引擎自己的优先级**解析：

```
① <根> 里的散装 BIN        ← 优先（对基线而言，它就是开发商给本体打的 patch）
② 否则进 ALF 归档：SYS4INI.BIN → DATA1..8.ALF ；APPEND0N.AAI → APPEND0N.ALF
```

* **基线根** = `gameInstall/`（清单 `roots.gameInstall`）；实测 **散装 35 · ALF 188 · 缺失 0**；
* **产物根** = 旧仓 `install/`（迁移期一次）；实测 **散装 209 · ALF 补齐 · 缺失 0**；
* 取条目时按**实际读到的字节数**：索引声明的 `length` 可能比实际长（实测 `PLINIT` 声明 52496、实际 52492）；
* 解包器用 `packages/age-format` 的 ALF 读取（M2 已交付）——**不复制一份 ALF 实现**。

### 4.2 迁移期：patch 从哪来

```
旧仓 install/  ──解析层① ②──▶  产物 BIN ─┐
                                          ├─ 逐指令对齐 ─▶ patch.json（唯一入库物）
gameInstall/   ──解析层① ②──▶  基线 BIN ─┘
```

⇒ 提取是**一次性**的：patch 落库之后，`install/` 与 `raw-parts/` 都**不再被任何东西引用**（见 §5）。

★ 端到端复验：**只靠安装目录解析基线** + patch ⇒ 与产物 BIN **逐字节相同**（样本 6/6；全量见 `pnpm tools patch verify`）。

## 5. 为什么旧仓 `install/` 必须停止被**运行时**引用

它**同时**含有原版数据与翻译产物（本体全量真拷贝 + 替换过的 BIN），且整体是**派生物**
（548 文件 / 7.5 GB）。把它当运行时来源会重现旧仓的核心症状：**同一份信息有多处副本且无唯一真源**。

⇒ **迁移期读一次**（`patch extract` 的产物根，见 §4.2）**之后**：
基线只认 `gameInstall/`；产物（汉化 BIN）只认**我们自己的构建输出**，不是旧树。
⇒ 唯一的长期真源是 `data/translations/patch.json`。

## 6. 怎么查

```bash
pnpm tools patch describe                 # ★ 字段 / 不变量 / 操作（schema 的唯一真源，本文件不复述）
pnpm tools patch status                   # 当前规模：脚本数 / 操作数 / 体积 / 基线解析来源分布
pnpm tools patch baseline [<脚本名>]       # 某个脚本的基线从哪来（散装 / 哪个 ALF 的哪一段）+ sha256
pnpm tools patch verify                   # 判据 2：基线 + patch ⇒ 逐字节相同（有产物根时比对产物；否则对 resultSha）
pnpm tools patch view --kind src --name SC0000.BIN --stdout   # 看 src 视图（生成物，不入库）
pnpm tools patch edit                     # ★ 改完 src 视图 ⇒ 反解回 patch（dry-run；--write 落盘）
pnpm tools requirements show 8SNRXKV       # 本方案的工作项、判据、非目标
pnpm tools requirements plan              # 进度树
pnpm tools corpus list                    # 素材的去向（`translation/patch-data` 一条）
```

★ **`data` / `src` 视图同构**：都是"某个 BIN 的反汇编"形状、都用**真实地址**；
差别只在字符串 —— `data` 是基线的日文，`src` 取 patch 里的**中文**
（不能拿"重建 BIN 的反汇编"当 `src`：BIN 里是**占位写法**，中文只存在于 patch 里，见 §2.5）。

## 7. 边界与坑（写规格时必须带上）

1. **`data/*.txt` 与 `src/*.txt` 用的是同一套旧命名**（如 `i20d`），与**当前指令表**（`set-render-target`）不同
   ⇒ **基线只能锚 BIN**，不能拿文本当指令流基线。
2. **分清楚"注释层的范围"与"patch 的范围"**（这两件事被我混过一次，代价是漏 247 支译文）：
   * **patch 的范围** = 全部能反汇编的脚本，**由"产物 ≠ 基线"定**，**不许按名字筛**（§2.3）；
   * **注释层（页 / `// FROM:` / 原文存档块）的范围** = 旧管线真正标注过的那批
     （`SG`/`SN`/`CONFIG`/`GAMECLEAR`/`BIINIT`/`HISTORY` **一条 `// FROM:` 都没有**）；
     按同一规则外推会凭空多出 180 个"页" ⇒ 视图层要照旧过滤器。
   ★ 一句话：**"没有 `// FROM:`" 只说明没做过页标注，不说明没有译文。**
3. **`_extracted/` 里 84 个 BIN 反汇编失败**：它们是**老汉化的 overlay**，不是脚本来源，**不在重建范围**。
4. **不可再生的集合是空的**（本文件 §2.2 逐项实测）——所以"没有 `src` 会丢东西"这个顾虑不成立；
   真正要小心的是**工具没做对**（视图算错）而不是**数据丢了**（patch 里都留着）。
5. 已知实现边界：`packages/age-format/src/asm/disassemble.mjs` 对 v5 头字段是有意修正（真实语料无 v5）。
6. **头部也能变**：反汇编的头部 4 行**通常**与基线相同，但**不是**不变量 ——
   唯一实测到的一例是 `$1$IMINIT.BIN` 的 `local_vars` 从 `{ 3 1 1 2 1 1 }` 变成 `{ 1 1 1 1 1 1 }`
   （而那一支是**旧仓的坏文件**、迁移时没取，见 §2.3）。
   ⇒ 条目保留了可选字段 `header`（只在**与基线不同**时出现），重放时用它替掉基线那 4 行；
   **当前发布物里 0 条用到它**，格式能力由 `tools/test/patch.test.mjs` 的合成用例钉住。
   ★ 这一条与 `--extract` 里"逐字段构造条目"是**成对的坑**：漏了 `header` 会表现为
   "提取时自证通过、落盘后 `--verify` 失败"（实测踩过）。
7. **patch 生成器必须"看懂"两件事**，否则结果静默错：`comment` 是数据（§2.4）、label 引用要遮蔽（§2.1）。
   两者都不会报错，只会让重建结果**差几百字节**。
8. **别把 BIN 当译文真源**（§2.5）：BIN→中文**不可逆**。要改文案就改 patch 里的中文，不要改产物再反推。
9. **`resultSha` 的比对对象是历史产物**，不是"上一次重建的结果" —— 否则就是自证循环。
   它由 `extract` 从旧仓产物写入；`verify` 只读不写。
10. **对齐算法不能省**：朴素的"窗口前瞻"会被**远处的巧合**骗到（实测 `$1$SCJUMP.BIN` 只动 3 行，
   却因 32 行外一行恰好相同而被判成"删 47 行 + 插 49 行"）。现在的实现是
   **剥公共前后缀 → patience 锚（两侧都唯一的行，取最长递增配对）→ 段内要求连上 3 行**。
   实测这一改让操作数从 78 082 降到 **65 465**，并让 `$1$SCJUMP.BIN` 从"表达不了"变成"逐字节相同"。
11. **`rowsOf` 认 label 定义行时不能要求 8 位 hex**：patch 放出的**符号**是 6~7 位
    （`0x100000 + id`）。要求 8 位会把符号行当成指令行 ⇒"打上 patch 的文本"再也解析不出 label 定义。
