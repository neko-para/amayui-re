## 0 摘要：三个读数 + 一句话结论

| # | 读数 | 值 | 怎么来的 |
|---|---|---|---|
| 1 | 10,254 个 `lift_cc_*` 的 **native 指令总数 / 代码字节** | **2,500,533 条 / 10,002,132 B**（B/insn=4.000 自检通过） | `llvm-objdump -d` 指令行数，8 份 `.obj` 合计（§2.1） |
| 2 | 闭包覆盖的 **静态 guest 指令数**（Σ`lift_tick` 的 i32 参数） | **348,208 条**（71,995 个 guest 块，平均块长 **4.84**） | IR 全量扫描 + 冻结口径块数严格对齐（§2.2） |
| 3 | **host native insn / guest insn** | **7.18**（块边界税 1.99 + body 5.19）；每 guest 块 **34.73 条** | §2.3 |

**结论（一句话）**：这 7.18 条里没有一个"单点大坏"的指令——损耗是**均匀摊在 71,995 个块的边界固定成本**（27.71%）与**每条 guest 指令的状态搬运/地址计算/取参**（mov 类合计 23.4%、地址计算 9.2%）上的；唯一接近两位数的单点是 `lift_tick`（静态 12.2%、动态量级约 1/3），而它的可改性在**内联**不在**删掉**。详见 §7。

**音频补充（2026-11-17 父级已核读数）**：静态「块/直线段」上界只有 µs 级，但**派发上界由 IR 循环决定、静态不可界**——`CTX.md` §E-5 实测「两次块边界间最长 5,900 万条 guest 指令」≈ **211 ms**，足以造成 dropout。详见 §6.3。

### 1.2 native 指令数口径

`llvm-objdump -d` 的**指令行数**（AGENTS.md §12.6），不是 `.ll` 行数。
- `-dr` 是必须的：未链接的 `.obj` 里 `bl` 是 `bl 0x0`，目标只在 `ARM64_RELOC_BRANCH26` 里
  （`_lift_tick` / `_lift_dyn` / `_lift_cc_*` / `___stack_chk_fail` …）。不带 `-r` 数不出调用类别。
- 函数范围用 `llvm-nm -n` 的 `T` 符号地址差定（`part00` 的 addr 0 同时是 local `ltmp0` 与 `_lift_cc_401000`，
  ⛔ 不能靠 objdump 的 label 认函数；同一地址的别名要去重，否则会丢 8 个函数 / 850 个块）。
- `objdump --start-address` 会从"包含该地址的符号"开始反汇编 ⇒ 逐函数复测时必须自己裁 `[start, stop)`；
  重定位行（`<16 hex>:  ARM64_RELOC_BRANCH26  _lift_tick`）也会被指令正则误吞 ⇒ 必须先挡掉。
  （这两条各踩过一次，修完后 23/23 个抽样函数的逐函数复测与 CSV **逐条相等**。）

### 1.3 指令分类（机械规则，不是猜语义）

`%st` / `%mem` / `%cpu` 在 prologue 被搬进 callee-saved 寄存器：**10,254/10,254 个函数都是 `x19 = %st`、`x20 = %mem`**
（`native_summary.json` 的 `stRegHistogram` 只有一个键）。据此：

| 判定 | 规则 |
|---|---|
| guest 寄存器 load/store | `ldr/str/ldp/stp …, [x19, #0..31]`（首次 call 之前也认 `x0`） |
| EFLAGS 物化落盘 | `str w, [x19, #0x20]`（`LiftRegs::eflags` 在 +32） |
| guest 内存 | `ldr/str …, [x20, wN, uxtw]`（首次 call 之前也认 `x1`） |
| 地址计算 | `add/sub wD, wS, #imm` 且 `wD` 被后面某条 `[x20, wD, uxtw]` 当 index |
| 入口区 / 派发 | 从函数首条到第一次触碰 `[st]`/`[mem]`/`call`/`ret` 之前；区内的 `cmp w2`、`sub w8,w2,#base`、`movz/movk w8`、`cmp w8,#` 算派发 |
| 调用 | 按**重定位目标**归类（`bl` 与尾调用 `b` 都算），不按 mnemonic |

★ 派发**不能**只数 `cmp w2`：clang 把 `switch i32 %ea` 降成**链式比较**，而且 `b.ne <trap/下一条链>` 的
**落空**才是 case 体、`b.eq` 的**目标**才是 case 体；只数 `cmp w2` 会把 39 块的函数数成 4 条。

桶是**互斥**的：Σ桶 = 2,500,533 = native 总指令（差 0，`agg_tables.md` 自检行）。

### 1.4 事实 / 推断 / 待核

- **【事实】**：能从产物机械读出、带命令可复算的数。
- **【推断】**：由事实推的（尤其"动态多少条/多少时间"），**不写成读数**。
- **<待核>**：本脚本证明不了、需要真机或另一份产物才能定的。

### 2.2 tick 参数求和 = 闭包覆盖的 guest 指令数；块数对账

```
node .tmp/insn-overhead/ir_scan.mjs            # → data/ir_funcs.csv · ir_blocks.csv · ir_summary.json
```

- **【事实】** Σ`lift_tick` 的 i32 参数 = **348,208**；tick 调用 **104,949**（IR）/ **101,765**（native，按重定位数 `bl`+尾调用 `b`）。
- **【事实】** `bb_` 标签 75,744 = **guest 块 71,995** + **`bb_exit_*` 3,749**。
  ★ 71,995 与冻结口径（"EFLAGS 活性：块=71995"）**严格相等** —— 之前的"75,744 vs 71,995 差 4.9%"不是矛盾，
  而是 `bb_exit_*` 这类**退出/中转块**（0 条 guest 指令，只把 EA 交回 trampoline）不属于 guest 基本块。
- **【事实】** 平均块长 = 348,208 / 71,995 = **4.84** guest 条/块；每块 tick = 104,949 / 71,995 = **1.458**（native 1.41）。
- **【事实】** guest 块里 2,638 个 `guestInsns=0`（被宿主调用切成两半的后半块 / 纯 shim 派发块，它们的 guest 指令计在前一块）；
  69,357 个有 tick。
- **【推断】** 静态 348,208 与动态 614M（FELLOW init）的比值 **≈1,764×**（每个静态 guest 指令平均被执行约 1.8k 次）。
  这个比值只说明"热面很集中"，⛔ 不能反推哪些 EA 热（没有动态块计数）。

## 4 C · 不合理 / 阻碍优化的形态（点名 + 次数 + 代表 EA）

### C1 「每条 guest 指令一次 `lift_tick`」——**不成立**，但站点密度确实高

- **【事实】** tick 调用 **104,949**，guest 块 **71,995**，guest 指令 **348,208**：
  **1.458 次/块、0.30 次/guest 指令**。**不是每条 guest 指令一次**，而是"块边界 + 宿主调用前"各一次。
- **【事实】** `-O2` 后仍是真调用：`bl _lift_tick`（101,765 个站点；按重定位数，含尾调用 `b`）。
  站点 3 条（`mov x0, x21` / `mov w1, #n` / `bl`），callee 热路径 5 条。
- **【事实】** `lift_tick` 无 `always_inline`、跨 TU（`runtime/lift_abi.cpp`），**不可能被内联**。
- **【事实】** 调用约定代价：`%cpu` 在 prologue 已进 `x21`（callee-saved），但每次调用仍要 `mov x0, x21`
  （ABI 要求 x0 传参）——**每次 1 条纯搬移**。
- **【推断】** 静态上 tick **站点级**（`bl` + 2 条取参）= 305,295 条（**12.2%**）；其中 `bl` 本身只占 101,765（4.07%），另 203,530 条是取参，其中可省的只有"取参 + `bl`"这 3 条的一部分；
  删不掉（`insns` 精确性靠它）。动态上一次 tick = 8 条执行 ⇒ 若动态块长 ≈ 静态 4.84，
  tick 约占**执行条数的 1/3**（1.48G / 4.4G，量级估算）<待核>。

### C2 guest 寄存器逐次 load/store（无跨块 SSA）

- **【事实】** `%st` 读写 **221,214**（**8.85%**）：load 111,198 / store 110,016，**2.92 条/guest 块**。
- **【事实】** 只有 **17.15%** 是 `ldp/stp` 成对（ld 13,449 / st 24,488），**82.85% 是单条 `ldr/str`**。
  原因之一是块尾 `flushRegs()` 按"槽位顺序"逐条 store，而不是把相邻槽位配对。
- **【事实】** 每个 `bb_` 开头清缓存（"缓存跨块作废"）、块尾 flush ⇒ **同一个寄存器在相邻两个块里各 load 一次**。
  代表：`lift_cc_401080`（part00，`bb_401000` 的 tick 前后各有一轮 `st+16/20/24` 的 load/store）。
- **【推断】** 这是"块边界税"的主体（221,214 / 693,001 = 32%）。

### C3 重复 `zext` / GEP 地址计算

- **【事实】** IR 里 `getelementptr` **715,263**、`zext i32→i64` **268,611**；native 侧 `zext` **不花钱**——
  它被折进寻址模式 `[x20, wN, uxtw]`（0 条额外指令）。★ 这条**不是**指令损耗。
- **【事实】** 真正的地址计算是 **229,844 条（9.19%）**：`add/sub wD, wS, #imm` 喂给 `[x20, wD, uxtw]`。
  典型来源：`push`/`pop`/局部栈访问（`ESP ± imm`）、结构体字段（`EBP + imm`）。
- **【事实】** 同一个 EA 常量常被重复算：如 `bb_435800` 里 `zext 5610088` / `zext 5377936` 各出现多次。
- **【推断】** GEP 的常量基址可以做 CSE（clang 已做一部分：`getelementptr %mem, i64 <const>` 被折成一条 `add`），
  但 `ESP` 变化后的重算是语义必需的。

### C4 `align 1` 的 4 字节 load/store

- **【事实】** IR 里 `align 1` 的 load/store **317,625** 处（占 842,837 条 load+store 的 **37.7%**）；
  `align 4` 369,858；其余是 `align 2/8/16`（浮点/SIMD）。
- **【事实】** arm64 的 unaligned `ldr/str` 单条就能做，**不额外花指令**。
- **【事实】** 但它**挡住成对化**：guest 内存访问**没有任何 `ldp/stp`**（`stPair` 只出现在 `%st` 上）。
- **【推断】** 这既是**正确性**要求（x86 允许非对齐），也是**优化上限**：若能把"可证明对齐"的
  （如 `ESP` 附近的 4 字节 push/pop、结构体字段）改成 `align 4`，相邻 guest 内存访问可合并成 `ldp/stp`（−2% ~ −4%）<待核：需要语义裁决>。

### C5 块尾 EFLAGS 逐位物化（190k 位）

- **【事实】** 冻结口径：物化调用 32,371 / 真发 IR 14,654 / 块尾物化位合计 **190,218**；
  `need_out=ALL` 的块 31,521、零 flags 块 38,222。
- **【事实】** 本扫描对账：IR 里带 flag 位权重的 `select` **85,540**、清位 `and -mask` **39,011**、`or` 89,371；
  native 侧 `[st+32]` **store 11,494 / load 11,422**（**15.2% 的 guest 块**写 flags），`csel` 系列 **47,484**，
  带 flag 位权重的逻辑运算 **24,058**。
- **【事实】** **不是每块都发生**：只有"后继要读 flags"的块才落盘（15.2%），与冻结口径的
  `need_out=∅`（53%）一致方向。
- **【推断】** flags 相关 native 指令 ≈ `11,422 + 11,494 + 47,484 + 24,058 = 94,458`（**3.78%**，上界偏宽）。
- **【事实】** `and i32 %x, %x`（恒等死运算）在 IR 里有 **5,854** 处，native 侧 **0** 处 —— 已被 `-O2` 折掉。
  ⇒ 它是**编译期/IR 体积**问题，**不是**指令损耗（但会拖慢 `clang -O2`，8 段共 120.7 s → 21.6 s 的那条线）。

### C6 函数入口的 switch / trap / 栈保护

- **【事实】** 入口区合计 **225,309**（**9.01%**），每函数平均 **22.0** 条（p50=19 / p90=25 / p99=34 / max=68）；
  其中"只比较 `%ea`"的派发 **58,521**（2.34%），`brk` **10,254**（每函数 1 条，switch default，冷路径）。
- **【事实】** **栈保护 = 0**：8 份 obj 里没有 `___stack_chk_fail` / `___stack_chk_guard` 重定位。

- **【事实】** **单块函数也付整套**：`42C74E`（1 块、2 条 guest）26 条 native 里，prologue/epilogue 6 + 派发 2 + tick 3 + 出口 2。

## 5 D · 与 `boundary` 29% 的关系

### 5.1 静态块边界税 = 27.71%

```
块边界税 = 入口区 225,309
         + tick 调用 101,765
         + 块首尾 %st 读写 111,198 + 110,016
         + EFLAGS 落盘 11,422 + 11,494
         + 块间分支/ret/间接 br 113,971 + 8,641 + 6
         − 入口区内的分支 821（避免重复计数）
       = 693,001  →  27.71% of 2,500,533
```

每 guest 指令的边界成本 = **1.99 条**；每 guest 块的边界成本 = **9.63 条**（693,001 / 71,995）。

### 5.2 与 profile 的关系：**同量级、同方向，但不是同一个量**

| | 静态（本报告） | 动态（win32 profile） |
|---|---|---|
| 量 | lift_cc **代码里**"因块边界而存在"的指令占比 | trampoline 里**花掉的时间**占 wall 的比例 |
| 值 | **27.71%** | **28.7–29.9%** |
| 分子包含 | 入口区（每次进 `lift_cc_*` 都要付）、每块 tick、块首尾 `%st` flush、flags 落盘、块间分支/ret | 闸门 / 定时器泵 / Present 泵 / **派发表查找**、以及 trampoline 自己的指令 |
| 分子不含 | trampoline 自身的全部工作 | `lift_cc_*` 内部的入口区与块首尾 flush（那部分在 profile 的 `lift` 50% 里） |

**【推断】** 两者数值接近是**结构性的巧合**：静态少算了 trampoline（29% 里的大头），
多算了"分支/ret/flags 落盘"这类**同时含语义**的指令。⇒ ⛔ **不能拿 27.71% 去复核 29% 的绝对值**，
只能说"块边界的固定成本确实是这个量级的大头"（方向一致）。

**差异来源（逐条）**
1. **采样口径**：静态 = 指令条数；动态 = 时间样本。两者只有在 IPC 恒定时才同序，而 `bl`/`ret`/分支的 IPC 明显低于算术。
2. **arm64 vs win x64**：后端不同（不同寄存器分配、不同派发实现、不同栈约定），本报告的 7.18 是 **arm64** 的；
   win x64 的 host/guest 可能不同 <待核>。
3. **boundary 还含派发表/泵**：那些是"块数/帧数"驱动、不在任何 `lift_cc_*` 里，静态上根本不计入。
4. **静态是均匀权重**：静态按"每条指令一次"计，动态按"热块多、冷块少"计。若热块偏长（>4.84），
   块边界的动态占比会**低于** 27.71%；反之偏高 <待核>。

### 6.2 静态上界：**块 / 直线段**只能到 µs 级

【事实】动态换算基准：FELLOW init = **614M guest insns / wall 2.2 s** ⇒ **3.58 ns / guest insn**（win32，RelWithDebInfo）。
【事实】静态 **7.18 host insn / guest insn**。

| 场景 | guest 条数 | 静态 host 条数（×7.18） | 按 3.58 ns/guest 的**线性外推** |
|---|---|---|---|
| 平均块 | 4.84 | 34.7 | **17 ns** |
| 单次 tick 间隙最长（`bb_44F8B8` 的 166 条） | 166 | 1,192 | **0.59 µs** |
| 最长块（`bb_435800`） | 475 | 3,410 | **1.7 µs** |
| 上述块 + 297 次 `lift_note_write` | — | +297 次调用（callee 另算） | <待核>：`_lift_note_write` 是薄转发，真正工作在 `lift::noteGuestWrite` |

**【推断】** 这些数只界住了**直线段**（一个块内、两次宿主调用之间）。一次派发是"从进入 `lift_cc_*`
到返回 trampoline 之间的全部执行"，中间可以走**块间回边（循环）任意圈** ⇒ **静态块上界 ≠ 派发上界**。
真正界住派发的是"最长循环"，见 §6.3。

### 6.3 动态派发上界：**IR 回边 / 循环**——静态不可界，`59M` 实测 ≈ 211 ms

【事实·父级已核】`CTX.md` §E-5（AOT 音频 S3 实测）：**两次块边界间最长 5,900 万条 guest 指令**
⇒ 单个超长派发期间音频**完全不推进**；S4 若欠料先看这条，⛔ **不是加大泵频**。

【事实】按同一条 3.58 ns/guest 的换算：**59M × 3.58 ns ≈ 211 ms / 次派发**——比 10 ms 的音频缓冲大 21 倍，
**足以**造成 dropout / 泵不推进。（这是**换算**，不是 arm64 读数；59M 本身是 win32 实测。）

**IR 侧循环普查**（`node .tmp/insn-overhead/loop_scan.mjs` → `data/loops.csv`；SCC = 循环，回边 = SCC 内部边）：

|---|---|---|---|---|---|
| `44F6B0` / `bb_44F8B8` | 1（自环） | **171**（4 次 tick/轮，最长间隙 166） | 1 | 1,101 | ≈ 345,000 圈 |
| `4D81B0` / `bb_4D82B0` | 17 | **128** | 21 | 3,913 | ≈ 461,000 圈 |

| `51033C` / `bb_510AF5` | 8 | 69 | 10 | 3,122 | ≈ 855,000 圈 |
| `401AF0` / `bb_401B04` | 1（自环） | **4**（1 次 tick/轮） | 1 | 220 | ≈ 14,750,000 圈 |

- **【事实】** 循环很稀（6.4% 的函数），但**一旦命中，派发时长由圈数决定**：同一个 `lift_cc_*` 调用
  内部可以把"块边界"重复上千万次而**一次都不返回 trampoline**。
- **【事实】** 自环占 44.7%（544/1,217），且多为"每轮 1–6 条 guest 指令"的**小循环**（
  `bb_401B04` 每轮 4 条 guest 指令（含一次 8 位 partial-register 读改写 + `inc` + 判零））。
- **【推断】** 按 `59M ÷ 每轮条数`，能跑出 59M 的循环形态从"每轮 4 条 × 1,475 万圈"到
  "每轮 171 条 × 34.5 万圈"都成立；**静态上无法点名是哪一个** <待核>（见 §8-7 的定位方法）。
- **【事实·口径】** `lift_tick` 在这些循环里**照常被调用**（`bb_401B04` 每轮 1 次、`bb_44F8B8` 每轮 4 次），
  所以 `insns` 计数是精确的、`lift_one`/shim 也能进；**唯独 trampoline 的泵不会被服务**——
  因为泵只在"返回 trampoline"时跑。这正是"59M 期间音频完全不推进"的机制。

**可复核线索（按可疑度排序）**
1. **单次派发内的长循环**（§6.3）：**唯一有实测支撑的项**（59M ≈ 211 ms）。静态可见 1,217 个循环、
   544 个自环。**【推断】** `bb_401B04`（4 条/轮）、`bb_401B40` 的 `bb_401B71/80/92/BC8`（4 条/轮）这类
   **小自环**是"千万圈"的首选形态（⛔ 不是"已确认就是它"）。
2. **`bb_435800` 的 297 连发 `lift_note_write`**（+ 298 次 tick = **595 次宿主调用**）：一个块、一次派发，
   每次 `noteGuestWrite` 都可能做页级/缓存级失效 <待核>；若命中热路径，这一条也能把一次派发拉到 ms 级。
3. **`lift_dyn` 落到阻塞 shim**（5,658 站点，最多 `490590` 59 次）：落到的 shim 若阻塞（DirectSound Lock /
   文件 I/O），那次派发就是毫秒级 <待核>。
4. ~~`bb_44F8B8` 的 166 条直线段~~：它其实是**自环**（§6.3 已收进第 1 条），单圈 171 条 ≈ **0.61 µs**
   （其中最长一次 tick 间隙 166 条 ≈ 0.59 µs），**单圈不构成 dropout**；
   基于「静态块上界 µs 级」的排除法**只对非循环块成立**。

⛔ 以上都**不是因果结论**；第 1 条有实测读数支撑，2–3 条是需要去 profile 里对号入座的线索。

## 7 F · 结论与下一刀建议（≤3 条）

### 7.0 总判断

**【事实】** 静态 7.18 host insn / guest insn 的构成里，**最大的单个桶是 `movImm` 14.0%**，
但它是"块尾 EA 常量 + tick/note 的立即数参数 + 地址常量"的混合体，**分散在 10,254 个函数、75,744 个块上**；
第二大的 `logicOp` 10.3% 里混着 flags 物化与位掩码。

**【结论】** **损耗均匀分布，没有单点可一刀砍掉 ≥10%（静态口径）。**
唯一接近两位数的是 `lift_tick`（静态 12.2% / 动态量级约 1/3），但它是**计数语义的必需品**，
可改性在"**内联**"（降动态、几乎不动静态）而不是"删掉"。

### 7.1 三条下一刀（按 静态证据 × 可改性 排序）

#### ① `lift_tick` 内联成 3 条 IR（`ldr/add/str` on `%cpu`）—— **动态收益最大，静态持平**

| 项 | 内容 |
|---|---|
| 改什么 | 生成器不再发 `call void @lift_tick`，改发 `%n = load i64, ptr (%cpu + insns_off)` / `add` / `store`；`%cpu` 的非空检查提到函数入口做一次 |
| 预期 | **静态**：站点 3 条 → 3 条（不变，甚至 +0）；**动态**：一次 tick 8 条 → 3~4 条（**−50% ~ −62%**）。按 §6.2 的 1.48G tick 执行条数估，**约 −10% ~ −14% 的执行指令** <待核：真实动态块长> |
| 守卫怎么红 | ① 形状断言：`llvm-objdump` 里 `bl _lift_tick` 计数 = **0**（新 CTest，注册在顶层）；② 语义指纹（`exit/frames/stop @EA/arena/table misses` 逐位相同）——现有 CTest 已覆盖；③ `insns` 精确性：现存"shim 调用处 insns 精确"的断言必须仍然绿 |
| 风险 | `lift_tick(cpu==nullptr)` 现在会**响亮退出**；内联后要保留等价检查（每函数一次），否则把编程错误变成静默。`insns` 是 `u64`（`[x0,#0x6d8]`），`add` 要用 64 位 |
| **边界（重要）** | 它降的是「**派发内**的指令数」，⛔ **不改变「一次派发最长 59M 条 guest、≈211 ms」这个泵粒度下界**。要修音频卡顿，得让长循环**周期性回到块边界**（生成侧按圈数切块）或让泵在派发内可重入——那是音频/派发形状，**不是**本报告的静态结论 |

#### ② tick 与 `lift_note_write` 合并成一次调用（同站点相邻时）—— **−3.2% ~ −4%（静态）**

| 项 | 内容 |
|---|---|
| 改什么 | 生成器在"tick 后紧接 note_write"的站点改发一个 `lift_tick_note(cpu, n, ea, len)`；`bb_435800` 那种连续写还可批量成一个 `(ea, len)` |
| 预期 | note 站点 38,535 个；若其中 ~70% 与 tick 相邻 ⇒ 省 ~27k 次调用 × 3 条 ≈ **81k（3.2%）静态**；再叠加"同块连续 note 批量成一个 `(ea,len)`"（5,769 个 tick 落在 >8-tick 的块里，每次省 3 条约 17k）⇒ 合计 ≈ **−3.2% ~ −4%** |
| 守卫怎么红 | ① IR 形状断言：`call @lift_note_write` 计数 ≤ 旧值且 `call @lift_tick` 相应减少（成对守恒）；② SMC 失效的**语义测试**（写代码段后取指必须看到新字节，现有 CTest）必须绿 |
| 风险 | `noteGuestWrite` 是按 `(ea,len)` 区间失效的，合并必须保证**区间内每一页都真的被写**；批量跨页时要按页拆 |

#### ③ 块尾 `%st` flush 按槽位排序成对化 —— **−2% ~ −3%（静态）**

| 项 | 内容 |
|---|---|
| 改什么 | `flushRegs()` 现在按"脏槽位顺序"逐条 `str`；改成先按 `r[0..7]` 升序收集，再让 clang 用 `stp` 合并（IR 里把相邻槽位的 store 放一起即可，语义不变） |
| 预期 | 目前 `%st` 只有 **17.15%** 成对（ld 13,449 / st 24,488 / 总 221,214 ⇒ 约 18,969 对）；若成对率提到 ~50%（≈55,304 对），净省 ≈ **36k 条（1.4%）**；块首 load 同理再省 ~20k ⇒ **−2% ~ −3%** |
| 守卫怎么红 | ① IR 形状断言：`bb_` 内 `store … ptr %st_<k>` 必须按 k 升序（生成期即可断言）；② 语义指纹不变；③ **flags 与寄存器的顺序**不能被这条改动打乱（`materialize` 必须在 `flushRegs` 之前，现有注释已钉） |
| 风险 | 低（store 之间无别名，`%st` 是 POD）；但要小心 `lift_stop`/`lift_one` 屏障点前的 flush 顺序 |

### 7.2 不建议动的

- **`align 1` → `align 4`**：guest 允许非对齐，这是**语义**不是优化项。若要做，只能"逐 EA 证明对齐"，风险远大于 2–4% 的收益。
- **把块间边从"回 trampoline"改成"直接 b"**：会把边界成本从 `lift` 搬到 `boundary`（已占 29%），并且要重做派发表，⛔ 不划算。
- **给某些热 EA 开特判**：AGENTS.md §12.5 明令禁止。
