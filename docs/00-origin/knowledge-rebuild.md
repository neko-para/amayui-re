# 知识层重建计划（**只有计划，没有任何结论**）

> ★ 本文件**不得含任何游戏 / 引擎语义结论**（字段含义、函数用途、opcode 语义、脚本角色……）——
> 那些属于**待重建的知识层**，必须按 §4 的准入规则、绑定可再校验的观察之后才准登记。
> 本文件只写：① 旧知识为什么不能直接搬（清理起点清单）；② 怎么分级；③ 准入门。
>
> ★ **本轮（骨架初始化）不执行本计划的任何一步**：K1/K2/K3 都不启动（用户口径：知识线本次先不做）。

## 1. 为什么不能直接搬 `[§1.10]`

用户口径：**现在所有历史知识都需要必要的清理、校验、重分类**，因此不把它们搬进新仓。

### 1.1 清理起点清单（旧仓实测，作为后续批次的输入）

| 缺陷类 | 实测 |
|---|---|
| **非法枚举** | `analysis/fields.json` 有 3 条 `status: "ANALYZED"`（那是 `functions.json` 的枚举，写串了） |
| **主键冲突** | `fields.json` 里 **2 组同 `scope+offset`** 且两边都标 `confirmed`（`Engine/0x5D880` = `cur_script` vs `frames`；`Engine/0x5D88C` = `dispatch_saved_effect_flags` vs `dispatch_saved_flags`） |
| **重名** | 9 组同名跨 scope（`flags` / `scene` / `width` / `height`……）⇒ **键必须是 `scope+offset`，绝不能是 name** |
| **写入缺陷** | `functions.json` 有 14 条 `fields_used` 是**字符串化的 JSON 数组** |
| **无 schema** | `fields.json` / `functions.json` 是**裸数组**，没有 `_doc` / `statusEnum` / `counts`，也没有 `--validate` |
| **记法混乱** | 字段引用至少 **6 种记法**并存（`Engine+0x5D8C8` / `Engine+82876` 十进制 / `Engine[93384]` / `this->cur_script` / `_this+4*cur+388612` / `MeshEntry.vbuffer`）；一条 `fields_used` 归一化后只有约 **1/4** 能回连 `fields.json` |
| **锚点失效** | 换反汇编后所有 `raw N` 行号锚全废（旧仓 611/625 个函数区间、139 条票据证据、180 条 `handlerBodyLine`） |
| **语料污染** | `engine/天结_unpacked.exe_utf8.c` 被 `sanitize_symbols.py` + `hexrays_prep.py` 改过（同一语料 raw 的 `::` 4754 / `this` 36753 → `_utf8` 只剩 **3** / **1**），据此得出的**字符串层结论**都不可信（详见 `decisions.md` §4） |
| **自述标签不可信** | `confirmed` / `tentative` 都是人工自述；`capabilities` 146 条里只有 79 条 `modeled-verified`（且这 79 条**都带可执行守卫**） |

### 1.2 涉及的知识资产（本轮一律**只登记、不复制**）

`analysis/*.json`(7) / `tickets/`(208 条，735 文件) / `docs-new/`(122 份) / `scripts/` 的台账生成器与逆向脚本 /
`DESIGN.md`。机器指向见 `corpus/assets.json` 的 `kind: "knowledge-source"` 条目。

**已确认缺失的数据源**：旧仓**不存在引擎函数级调用图**（`callers` / `callees`）⇒ 先不做，仅在 K1 的清单里记一笔；
真要它时须从语料重新生成（属 A 类：可机械再生成 ⇒ 生成器按"重建"处理，不迁旧脚本）。

## 2. 分级框架（后续批次执行；**本轮不执行**）

| 类 | 判据 | 处置 |
|---|---|---|
| **A 可机械再生成** | opcode 派发表、`raw_name → 起止行`、调用图、脚本骨架、各类生成视图 | **不是知识 ⇒ 数据丢弃**；生成器本身按"重建"处理，不迁旧脚本 |
| **B 被可执行守卫验证** | `capabilities` 的 `modeled-verified` + `guard`；票据的 `tests[]`；缺口台账的 `implemented` | **优先抢救**（这是旧仓唯一真正被验证过的部分） |
| **C 纯人工散文** | 字段语义 / 函数用途 / opcode 散文 / 脚本角色 | 默认**不采信**，逐条重做或按新准入规则重新登记 |

## 3. 批次划分与依赖 `[§6]`

两条线并行、互不阻塞：**素材线（M*，搬工件）** 与 **知识线（K\*，清理 / 校验 / 重分类）**。

| 批次 | 内容 | 前置 |
|---|---|---|
| K1 | **清理**（只读旧仓）：去沿革 / 修非法枚举（3 条 `ANALYZED`）/ 修主键冲突（2 组同 offset 双 `confirmed`）/ 统一 6 种字段记法 / 剔出 14 条字符串化 JSON ⇒ 产出**候选分级清单**供用户裁决 | 用户裁决；★ **清理的判据来自 M3 的 schema**（否则 K1 只能自己发明归一化口径，回头与台账打架） |
| K2 | **校验**：锚点从行号重挂到 **EA**；重跑幸存守卫；**B 类抢救** | K1 + **M4-1（无头核心）** |
| K3 | **重分类**：按 A/B/C 落位，逐条过准入规则，只有通过者进新仓台账 | K2（+ M3 的台账格式） |

★ **顺序纪律**：K1 可以立刻开始（纯静态、只读旧仓）；**K2/K3 必须等守卫能真跑** ——
因为"被守卫验证过"这一类要靠真正跑起来的测试来复核，而守卫现在还寄生在模拟器的 `test/` 里。
**任何知识条目在 K3 通过前，不得进新仓台账**（`kind=knowledge-source` 的素材在清单里只能 `external-only` / `deferred`，守卫 #8 会红）。

★ **但不是"等整个 M4"**（实测口径）：79 条 `modeled-verified` 的守卫文件**全部**落在 T0/T1 档
（T2 全仓只有 `e4-gamestart-shot.test.ts` 一个文件，且不进 `all`/`verify`）⇒
复核**不需要真窗口、不需要原生输入、不需要真游戏安装**，只要**无头核心 + fixture 驱动**。
因此硬前置是 **M4-1（无头核心）**；M4-2（表现层与窗口）与知识线无关。
★ 另：三个台账守卫（`journal` / `capability-ledger` / `script-ledger` / `ticket-ledger`）**只读台账、零 `../src` import**
⇒ 它们归**台账域**、随 **M3** 落地 —— 也就是说 **M3 先把"判据怎么机械执行"这件事做出来，K1 才有防退化的护栏**。
★ **分类轴（`system`）的机制已随台账落地，但域词汇表留空**：归一到哪 ~15 个域、旧仓两套词表
（`capabilities` 的 12 个中文粗标签 / `fields` 的 18 个英文细标识，实测**无法 join**）怎么合，**是 K1 的判据产出**。
⇒ K1 的候选分级清单里应包含"域归一表"这一项；它进台账要走 `kind=domain` 的处置记录（**要带锚**）。

## 4. 知识层的新准入规则（**本轮先立规矩，不落数据**）

1. 每条语义结论必须**绑定至少一条可再校验的观察**（二进制 EA / 语料行区间 + 内容摘要 / 可执行守卫用例 id）。
2. **锚点锚 EA，不锚语料行号**；换反汇编只重建 `EA → 行号` 映射，不改任何锚。
3. 读取时**重校验**绑定：观察失效（行内容变了、守卫用例没了）⇒ 该条自动降级为 `stale`，
   **不得再进 accepted**，但**不删除**。
4. 冲突**显式化**为产物，不允许静默改写已有结论。
5. **不需要人工审核全部历史结论** —— 靠上面的机械失效暴露问题，而不是靠人逐条看。

## 5. 与存储纪律的关系

知识台账将来落 `data/ledger/`（append-only 文本真源）+ `packages/ledger`（派生 SQLite 查询层，永不入库、可删可重建）。
本轮的落点只有两份 README（`data/ledger/README.md`），**没有任何条目**。
