# Amayui Spec（引擎规范：**绝对入口**）

> 本技能是"做 spec"的唯一入口：**判据 + 组织 + 计量 + 验证**都在这里。
> 它有意与其它技能重叠（`amayui-re-engine` 取证、`amayui-shape` 机器本体、`amayui-emulator` 落地、
> `amayui-requirements` 进度）——重叠是为了**不必先去发现**，不是让人二选一。

## 0. 三条最常踩的

1. **把「程序」写成规范**：bootstrap / INIT 顺序 / 场景流转 / 存档里的值，都是**游戏数据**（程序），
   不是引擎。spec 只回答"给定这份输入，引擎做什么"。
2. **把「机器」写进正文**：偏移 / 布局 / 宽度 / 池基点 / EA / `sub_XXXXXX` / 台账 id / 守卫路径
   → 一律进 marks / `storage` / 证据指针。正文只写领域行为。
3. **拿「闭合」当「正确」**：效果守恒只证明**归属记账**；投影一致只证明**内部不矛盾**。
   ⛔ 不许说"与真机等价"。

## 1. 什么时候用 + 先读什么

* 要**写/改**一条规范陈述，或判断"这句话该不该进 spec"；
* 要**开一个新主题**（新章），或质疑现在的分章对不对；
* 要给一条结论定**证据档位 / 处理状态 / 残差**；
* 要回答"这个 spec 做到哪算完""模拟器现在能不能开始"；
* 要复核 **spec 与 emulator 的边界**（谁是真源、谁验证谁）；
* 某个**表现不对**时，判它是 spec 缺失、spec 错还是实现偏（§9.2），而不是直接补实现。

先读（顺序不可颠倒）：

1. `docs/00-origin/project-intent.md` —— 交付物是什么、什么算做对、边界在哪；
2. 方法单 `REQ-01M5851Z51V1MTSWH414M7WN5Q`（`pnpm tools requirements show` 看现文）—— 口径与反模式；
3. 本技能的 §2–§7 —— 把上面的口径落成可判的决策；
4. `data/spec/README.md` + `pnpm tools spec describe` —— 落点与 schema（**只信 describe**）；
   机制怎么切、目录怎么放见 `data/spec/core/README.md`（**组织真源**）。

分工（本技能是入口，其余是下一层）：

| 要做的事 | 技能 |
|---|---|
| 判"算不算引擎"、定计量/证据/组织、写陈述 | **本技能** |
| 读某个 `sub_XXXXXX` 的逻辑（C 读 / lst 证） | `amayui-re-engine` |
| 判对象的偏移/载体/闭合度（机器本体） | `amayui-shape` |
| 把 spec 变成可跑的实现与守卫 | `amayui-emulator` |
| 开单、收口、看进度 | `amayui-requirements` |

## 2. 本体：**引擎 vs 程序**（最硬的一条）

| 属于 spec（引擎 = 代码） | 属于程序（数据） |
|---|---|
| 解码器（脚本头 / `argc` / 操作数编码）、容器读取（ALF / AGF） | 具体脚本的字节与内容 |
| VM：指令语义、帧、池与值、访问原语 | INIT 链、装载顺序、场景流转、入口选择 |
| 边界请求（平台 API 的请求 + 参数 + 时序） | 存档里的值、配置里的值 |
| 序列化原语（存档写 / 读） | 图像 / 音频素材 |

**判据一句话**：这段逻辑是**代码**，还是**数据驱动的流程**？

* 是代码 ⇒ 进 spec。**ASM 编码也算**——它对应 loader + dispatch，是真代码，不是"格式文档"。
* 顺序 / 选择 / 时机由数据决定 ⇒ 不进 spec，但可以当**测试程序**（见 §7）。
* 推论：spec 里**不许出现**"启动时要跑哪几个脚本"。

两层本体 + 一条边界（决定一句话写在哪）：

| 层 | 内容 | 落点 |
|---|---|---|
| 机器本体（shape） | 偏移 / 宽度 / 数组 / 载体 / 闭合度 | `data/shape/`；spec 只用 `storage` 指针引用 |
| 领域本体（spec） | 实体 / 状态 / 操作 / 规则 | `data/spec/chapters/*.md` |
| 边界契约 | 平台 API 的请求 + 参数 + 时序 | spec 的正文；⛔ 不写 Win32/D3D 细节 |
| 表现层 | 像素 / 混音的逐位一致 | 明确进 `discards`（不在正文） |

## 3. 组织轴：**提问域 + 闭集**

主题不是按文件、也不是按子系统名切，而是按**引擎必须回答的问题**切；每个域**必须有一个可枚举的闭集**。

| 域 | 引擎侧回答 | 闭集（现查） |
|---|---|---|
| 输入解码 | 字节 → 结构 | 容器与文件类型（`pnpm tools corpus list`）+ 指令表条目（`pnpm tools opcodes report`） |
| 存储与值 | 槽 / 原语 / 编码 / 容量 | 操作数类型标签（五个访问原语的 case + 容器句柄分支，`pnpm tools disasm-at cases`） |
| 指令语义 | 每条 opcode 改变什么 | 有 handler 的 opcode 与缺省（`pnpm tools opcodes handlers`） |
| 边界 | 向平台发出的请求 | IAT 导入 + 调用点（`pnpm tools disasm-fn data` / `globals`） |
| 持久化 | 存档读写的原语与格式 | 存档样本（`pnpm tools fixtures list`） |

规则：

* **能不能成域，判据 = 有没有闭集**。没有闭集的话题只能进残差 / gaps，不能当章。
* **章节是视图**（阅读顺序），不是单位；`00/10/20` 编号**不是**依赖顺序 ⇒ 依赖用**偏序边**表达。
* 现有 6 章是一次**先行构造**：`10/20/30` = 输入解码，`40` = 存储与值，`50` = 指令语义的第一块。
  ⛔ 不要把它当最终分区；也不要因为它"看起来完整"就停止问"闭集还剩哪些元素没被回答"。

## 4. 一条规范陈述（条目）长什么样

| 字段 | 内容 | 约束 |
|---|---|---|
| 合同 | 领域行为（可独立实现的那句话） | 不写偏移 / EA / 台账 id / 守卫 |
| 上下文与条件 | 何时适用、成立条件、自由度 | 条件不许写成"通常" |
| 状态对应 | 领域状态 ↔ 机器状态 | 机器侧只给 `storage` 指针，不内联布局 |
| marks | 这条陈述处理了**哪些指令的哪些效果** | 见 §5；局部 / 绝对两种 |
| 证据 | `KN:<ULID>` / `guard:<path>#<用例>` | 锚只能是 EA 或守卫用例 id |
| 残差 | 未处理的部分 + **下一步问题** | 残差不是"算了" |
| 处理状态 | 已处理 / 替换 / 内部省略 / 明确舍弃 / 未处理 | 五者不许混（方法单 §6） |

* **替换 = 数据精化**：必须声明 `preserves / discards / chosen` **与覆盖范围**；越界即红。
* ⛔ 不另建"替换台账"（那会变成第二份 spec）；替换只落在条目字段 + 机器绑定 + 证据指针上。

## 5. 计量：指令是**底数**，不是正确性分母

* **mark = 局部**：声明处理的效果子集 + 未处理的原因；**mark = 绝对**：完整效果集
  （只有在效果模型明确时才能用"绝对"，否则它只是"我以为的完整"）。
* **守恒**：`E(insn) = ⊎ marks ⊎ 残差`，**按义务去重**；多条陈述可以共同解释同一义务
  ⇒ **重叠合法，重复计数非法**。
* ⛔ **不要求唯一归属**。⛔ 更不许"一个函数 = 一个机制"——函数与领域操作是**多对多**
  （大函数内部可以驱动多个机制；一个操作也可以散在多个函数里）。
* `unknown`（未判）与 `discarded`（明确舍弃）**分列**，不许并进"已解释"；舍弃要带理由 / 范围 / 影响。
* **样本域必须由数据算**（§7 的脚本足迹 / 闭集），不许手挑：手挑的样本只证明"这个样本自洽"。

## 6. 验证：**oracle 强度阶梯**（写状态之前先给自己定档）

| 档 | 能声称什么 | 典型来源 |
|---|---|---|
| **精确** | "这条机械判据成立" | 区域算术 / 跳转落在指令边界 / 重编码逐字节相同 |
| **不矛盾** | "与所有可获得的数据不矛盾" | 引用闭合、越界为 0、初始化后槽非空 |
| **真机消费** | "真机接受了这个产物" | 我们写出的存档/配置/脚本被真机载入 |
| **人工目检** | "人看到的行为是这样" | 一处采样，不是证明 |

* 独立证据只有四类：**真机观测 / 游戏数据 / 三方文档·版本 / 第二实现**；
  多路推导只能发现内部矛盾与遗漏 —— **投影一致 ≠ 与引擎一致**。
* ⛔ **助记符是编造的名字**，没有任何证据支持它真的叫这个名 ⇒ 不作判据。
  能作判据的只有：opcode 编号、长度（`argc`）、字节、操作数 `(type, raw)`、槽号、文本值。
* **存档是产物**（引擎选择持久化的那部分状态），不是状态快照；差分能证伪、不能定位，
  也不能证明"状态相等"。要整档相等，得先能把 bootstrap 跑通（那是程序，见 §2）。
* `patch.json` 是**差分**：只作"行号 + `(type, raw)` + 文本值"的语义断言用；原数据永远是主语料。
* spec 与 emulator 冲突时**按证据裁决**；⛔ 不许改 emulator 去迎合 spec（第二实现必须独立）。

## 7. 渐进：spec 必须能**部分**落地

不需要"等覆盖率"，因为**程序与引擎正交**，任意真实脚本都能当测试程序。

1. **静态足迹**：解码脚本 → 它用到的 opcode / `type` 集合（不需要任何语义）。
2. **已实现集合 S** ⇒ **可完整执行的脚本集合** = `{脚本 | 足迹 ⊆ S}`；进度 = 这个集合，
   且**未实现即抛错**（⛔ 不许 no-op，否则"跑通"是假的）。
3. **切片 = 引擎子集 + 测试程序 + oracle**。⛔ 不用章节、也不用场景当切片单位；
   程序（INIT 链、场景）只是固定输入。
4. 一个切片只有"不矛盾"档 oracle 时，条目状态**不许**写"已核验"。

## 8. 决策清单（写一条之前逐条过）

* **D1** 这是代码还是数据？→ §2
* **D2** 它属于哪个域？闭集里有哪些元素被它回答、哪些还没有？→ §3
* **D3** mark 是局部还是绝对？未处理的部分写进哪条残差（带 `next`）？→ §5
* **D4** 有别的陈述也在解释同一义务吗？去重之后还缺哪些？→ §5
* **D5** 证据是哪一档？够不够升状态（`reviewed` 需要强证据 + falsifier）？→ §6
* **D6** 判不了时三选一：未规定 / 残差 / 明确舍弃（理由+范围+影响）——⛔ 不许沉默。→ §4
* **D7** 依赖边：实现 B 之前必须先实现 A 的哪条行为？（偏序，不是编号）→ §3
* **D8** 它能不能被某个"足迹 ⊆ S"的程序验证？→ §7
* **D9** 落哪个文件、跑哪条门禁？→ §9
* **D10** 这条改动来自哪个缺陷？归因是 spec 缺失 / spec 错 / 实现偏？→ §9.2

## 9. 落点与门禁

```bash
pnpm tools spec validate      # 不变量（含正文自包含 / 跨文件一一对应）
pnpm tools spec report        # 审计账：覆盖 / 内部省略 / 残差 / 未登记
pnpm tools spec chapters      # 章节骨架（每章规则与残差）
pnpm tools spec show <id>     # 一条条目：正文 + 证据有效状态
pnpm tools spec effects       # 从语料机械枚举 effect（`--pilot` 现算）
pnpm tools spec describe      # 字段 / 枚举 / 不变量 / 操作（schema 唯一真源）
```

* 落点：`data/spec/`（manifest + `chapters/*.md` + 内部 `bindings` / `audit` + `format/opcode-table.json`）。
* **现状口径**：`pilot` 是**单域样本**，不是全域；报告里的"未登记 0"**只对该样本成立**；
  正文目前是两个先行主题，其余域只有骨架与残差（`pnpm tools spec chapters` 现查）。
* 复核信息的落点是 `bindings` / `audit`，**绝不进正文**（不变量会红）。

### 9.1 编辑后：独立复审（**强制**）

1. **改完就要复审**：任何对 `chapters/*.md` / `bindings.json` / `audit.json` / `format/*` 的改动，**必须**在收口前
   让一个 **subagent** 独立复审**这次变更**（不是自我检查）。给它变更清单（`git diff --stat` + 规则 id），
   要求它逐条判"改得对不对、有没有引入新矛盾"。
2. **用户说「完整review」时复审全部**：subagent 要读**全部**内容（`spec.json` + 所有 `chapters/*.md` +
   `bindings.json` + `audit.json` + `format/*`），**不是只看 diff**。判据：一个独立实现者只凭
   `chapters/*.md` + `format/*` 能不能写出**唯一**实现。
3. **复审 agent 的只读边界**：只看 `data/spec/`；⛔ 不读 `apps/emulator*`、`corpus/`、`data/ledger/`、
   `data/shape/`、`docs/` —— 避免被实现与旧结论带偏；它若需要证据，由你回 `.lst` 取。
4. **产出是清单，不是"通过/不通过"**：每条给 `文件:行` + 引文（≤40 字）+ 为什么是问题 + 需要什么证据 / 决定；
   处置只有两种 —— 改正文（带 EA）或进 `audit` 残差（带 `next`）；⛔ 不许沉默删掉。归因判据见 §9.2。
5. **不复用自己**：复审不能由本次编辑的执行者完成 —— 那只是把同一套假设再读一遍。
6. **记录与棘轮**：结论落 `docs/02-engine/spec-audit-<年月>.md` 的新一节 + 需求单；
   同一缺陷**不得重复出现**（修过的不能再被指出，否则说明没修对）。

### 9.2 缺陷后的 spec 归因（**先归因，再改**）

一个"表现不对"（数字没画出来 / 描边被清成洞 / 顺序反了）**不是**"补实现"的指令。
**归因错会让 spec 与实现一起错，而且一起变绿**。按下面五步走，每步都有可执行判据。

#### 第 1 步：先写可观察量，不先读实现

- 可观察量只有三类：**像素**（哪块画面不对）、**状态**（哪个字段 / 记录 / 槽变了）、**请求顺序**（引擎向平台发出的请求 + 参数 + 时序）。
- 写成一行可复现的话：**输入**（哪支脚本 / 哪份数据 / 哪个配置）+ **观测点** + **期望 vs 实际**。
- 判据：这句话**不引用函数名 / 偏移**也读得懂。opcode 只能当**定位**（"TITLE 的三条 `0x23b`"），
  不能当**解释**（"`0x23b` 是 ADV 数字绘制"）—— 后者正是要判的东西。
- ⛔ 先读 handler / emulator ⇒ 你会把"实现现在的行为"当成"引擎的行为"，缺陷会被写成"实现细节"或"未成篇"。

#### 第 2 步：找到对应规则，四选一

| 归因 | 判据 | 处置 |
|---|---|---|
| **A. spec 没有规则** | 按可观察量（像素 / 字段 / 请求）在 `chapters/*.md` 找不到合同；`audit` 的 `gaps` / 残差也没登记 | 补规则（带可证伪条件）；证据不够就先登记残差 |
| **B. spec 明说"未规定 / 未成篇"** | 命中「本版不规定」「尚未成篇」「见残差」；且该措辞不是"证据不足"，而是**归属判错**（把引擎决定的事划到域外） | 重新归属；把"不规定"改成"未取证"或直接写成合同 |
| **C. spec 有规则但错** | 规则的可观察后果与第 1 步的可观察量**矛盾** | 改规则；旧规则写错的点必须变成新规则的 falsifier（同一个观察能推翻它） |
| **D. spec 对、实现偏** | 可观察后果在规则里成立，**独立实现**与它不符 | 只改实现；⛔ 不许改 spec 去迎合实现；配会红的守卫 + 变异 |

★ B 最容易骗人：**"不规定"是结论，不是发现**。先问"这是引擎没做决定，还是我们没看？"——答不出就退回 A。

#### 第 3 步：四类高发错误，逐条过

1. **把引擎决定的事推给平台边界**：绘制顺序、提交顺序、状态机、请求参数。
   判据：说"这归平台 / D3D / present"之前，先拆成**请求内容 / 请求顺序 / 请求之后的像素**。
   引擎选了顺序或参数 ⇒ 它是边界契约，必须进 spec；平台只负责位模式、批次合并、光栅化。
   反例：由"`present` 属平台"推出"绘制顺序不用规定" ⇒ 顺序是引擎按键升序发出的，已写成 `CORE-SCENE-DRAW-ORDER`。
2. **哨兵 / 归一化没有逐字核对**：`0`、`-1`、`0xFF000000`、空串、负值、缺键。
   判据：每个哨兵写清**它是值还是"无"**，并写出比较的**位宽与参与位段**；长得像不等于相等
   （`0` 与 `0xFF000000` 在 32 位 ARGB 里差在 A）。
   反例：`0x1f9` 的 `0` 是**无键**不是黑键；旧文写"负数归一化成 0，RGB 黑键"并把比较写成 RGB
   ⇒ 不透明黑描边被清成洞。
3. **误归类进"未建模子系统"后再不查真实消费者**：一个 opcode 被塞进白名单（ADV / audio / text / input）后，
   它的读者 / 效果不再被枚举。
   判据：白名单里每个 opcode 至少回答一次"**谁**在什么条件下用它、它改哪些引擎数据"；
   答不出就不许留在白名单，答得出就移出并归因。
   反例：`0x23b` 被当成 ADV 文字入口 ⇒ TITLE 的七位数字没人画，只剩两个小数点；它其实是场景侧 CG 数字条（建绘制项）。
4. **状态 / 记录字段没有枚举消费者**：字段写了进去，但没有 reader 合同 ⇒ 字段语义是猜的。
   判据：每条记录的每个字段，要么有 reader 的合同（谁读、读来做什么、缺省 / 无效值怎么判），要么显式进残差。
   ⛔ "写进去了"不是语义。

#### 第 4 步：处置二选一（不许沉默）

- **归因 A / B / C 的处置二选一**：补 / 改规则（必须带**可证伪条件** —— 一个具体观察能让它变红）
  或登记 audit residual（必须带 `next`，`kind` 选对：`unknown` / `unhandled` / `discarded` 不许混）。
- **归因 D 的处置**：spec 不动，只改实现。
- **任何 emulator 修复**（D，或规则改完后的落地）**必须**配一条**会红的守卫** + `mutate-check` 一条变异；
  ⛔ "实现能跑 / 游戏能跑"不是证据（§6、§10）。
- ⛔ 不许删掉发现、不许静默改实现；没有 falsifier 的规则只是"一段话"。

#### 第 5 步：复审必须同时给两面（规则面 + 实现面）

| 面 | 问题 | 输入 | 判据 |
|---|---|---|---|
| **规则面** | 规则**唯一可实现**吗？ | 只读 `data/spec/`（§9.1 的边界） | 独立实现者只凭正文能否写出唯一行为；falsifier 是否真能推翻它 |
| **实现面** | 实现是否只是**迎合**规则？ | 第 1 步的可观察量 + 独立实现（emulator）；⛔ 不把 emulator 当 spec 真源 | 守卫断言的行为能否从可观察量独立推出；变异改一处关键常量是否真红 |

- 两面**必须都由复审给出**（可以是分工的两轮），但**输入必须分开**：规则面守 §9.1 的只读边界（只读 `data/spec/`），
  实现面由**能读实现**的一方给出（不是编辑者自证）；⛔ 不许拿"实现与规则一致"当规则面的证据，
  也不许拿"规则这么写"当实现面的证据。
- ⛔ **"实现能跑" ≠ spec 正确**；⛔ **"规则与实现一致" ≠ 规则对** —— 第二实现会重复同一误解（§6、`AGENTS.md` §11）。
- 结论落 `docs/02-engine/spec-audit-<年月>.md` 的新一节，格式固定为：
  **错误类型 · 判据 · 本次处置 · 下次 review 要问什么**。

## 10. 常踩的坑（都有出处）

* **把助记符当事实**：名字是编造的，`patch.json` 的行文本也用它渲染 ⇒ 拿它比"解码一致"是循环论证。
* **用"游戏能跑"证明 spec 对**：那是"程序被接受"，不是"语义被证明"。
* **把 bootstrap / 装载顺序写进 spec**：那是数据；写进去就把程序当成了引擎。
* **给函数区间贴"完成"**：函数的全部效果不会因此被处理（方法单反模式）。
* **手挑站点当分母**：样本自洽 ≠ 全域覆盖。
* **把未知塞进"舍弃"**：未知与舍弃必须分列。
* **用覆盖率 / 守恒 / 第二实现一致当等价证明**：三者都只到"不矛盾 / 归属"。
* **在正文里写 EA / 偏移 / 台账 id / 守卫**：自包含不变量会红，且分发物会带出内部材料。
* **把缺陷归因成"未成篇"或"平台的事"**：误归类会静默吃掉功能；按 §9.2 归因，⛔ 不许拿"不规定"当发现。
