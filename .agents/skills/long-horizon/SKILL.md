# Long-horizon（长程无人值守）

## 0. 激活意味着什么（先读这五条）

1. **用户在一段时间内不会回应。** 所以 `ask_user_question` 一次都不要用 —— 问了也没人答，
   而工具会**阻塞在问题上**，那等于把整段无人值守时间浪费掉。
2. **不能提权。** 不要带 `sandbox_permissions` 重试被拒的操作（那是一个必须被批准的请求，
   没有批准者时它**失败关闭**）。被拒 ⇒ 这是"需要人的一步"，登记后绕开。
3. **所以唯一能推进的手段是**：`create_goal`（跨轮撑住目标）+ `todo_write`（管当前轮）+
   `subagent` / `subagent_fork`（把独立的重活并行掉）+ 仓库里的命令与守卫。
4. **不在对话里留结论。** 没人会读你这段上下文 ⇒
   一切**进度进需求树**（`pnpm tools requirements plan`）、**结论进 `docs/` 或 `data/ledger/`**、
   **变更进 git**（但**不要** `git add` / `git commit` —— 提交时机仍由用户决定）。
5. **"停下来"是正常结局，不是失败。** 每轮结束时你必须能回答三件事：
   做完了什么（有守卫为证）· 还剩什么（在树里）· 什么被卡住且**为什么只有人能解**。

## 1. 启动（只在第一轮做一次）

```bash
pnpm tools requirements plan     # ① 目标树：还要做什么、哪一支现在能动
pnpm tools requirements validate # ② 树是否自洽（红了先修它，别在坏地基上开工）
pnpm tools corpus validate       # ③ 素材清单守卫（同 ②）
pnpm test                        # ④ 默认门禁（= @env pure，~14 s；`pnpm test:list` 看分级）
```

**目标必须是"能独立判定的交付物"，不是"努力方向"。** 判定标准：收口时能挂上
`verify: <文件>#<用例名>` 或写清 `done_reason`。

```
✅ "把 M3 的派生 DB 判据做成守卫，`pnpm tools ledger validate` 7 条全绿"
❌ "继续完善台账"
```

★ **先声明停止线**：`create_goal` 时给 `max_goal_rounds`，并在第一轮里写下"到什么状态我就停"
（例：某个可交付物落地 + 门禁绿 / 或者某分支真的卡在需要人裁决）。
没有停止线的长程任务会退化成无限循环 —— 那比不做更糟。

## 2. 每轮的形状

```
① 从树里挑**一个**最小可判定单元（别同时开三条）
② 读它要求的东西（判据 / 相关 docs / 相关守卫），别凭记忆
③ 做 → 立刻跑它的门禁：
     pnpm test · pnpm tools requirements validate · pnpm tools corpus validate
     pnpm tools ledger validate · node packages/age-format/cli.mjs verify
   ⇒ **红了就修**，不要把红的留在树里过夜
④ 收口：能挂守卫就 `--verify`，不能就 `--done_reason`，并 `validate` 一次
⑤ 下一步：更新 todo_write，继续 ① —— 直到触到停止线
```

**一轮只落一个"可判定"的改动**：守卫绿 + 树自洽 + 工作区没有半成品文件。
宁可多轮，也不要在同一轮里改三个子系统、最后一个都没验完。

## 3. 什么时候用 goal / todo / subagent

| 工具 | 什么时候 | 不许怎么用 |
|---|---|---|
| `create_goal` | **开场一次**：目标 + `max_goal_rounds`（按 ① 的停止线估；宁少勿多） | 不要每轮重开；不要拿它当 todo |
| `update_goal` | 真的达成 ⇒ `complete`；连续 ≥3 轮同一处卡死 ⇒ `blocked` + **具体**理由 | `blocked` 不是"难"，是"`X` 这个前提在这台机器上不存在" |
| `todo_write` | 每轮开头重排（一条 = 一个可判定动作） | 不要把"思考 / 调研"当条目 |
| `subagent` | **独立、无需本对话上下文**的重活：大范围检索、读一批文件做分类、跑一遍对照实验 | 不要拿它做"我该做什么决定"（那没有上下文） |
| `subagent_fork` | 需要**本对话上下文**的活（接续分析、评审我的改动） | 不要用它替代自己去读手上的文件 |

★ **并行要真并行**：独立的委派在**同一条消息里**一起发，然后自己继续做别的事 ——
不要在委派上忙等（`list_agents` 有通知，不需要轮询）。

## 4. 卡住了怎么办（本模式里最要紧的一节）

**没有人的时候，"需要人"的判定标准只有一条**：

> 这一步**要么**要一个批准（提权 / 询问 / 网络 / 装依赖），
> **要么**要一台不具备的机器状态（真机、真游戏安装、旧仓不在本机、headless Chrome），
> **要么**要在两个都成立的方案里做**产品取舍**（例如"域怎么分"这种，本仓要求由证据喂养、不许 agent 拍板）。

判句一旦成立 ⇒ **三件事，按顺序做**：

1. **在需求树里留痕**（不是留遗憾）：`--status blocked` + `blocked_by`，或开一张明确的小单；
   把"卡在哪、要人做什么决定、为什么 agent 不能替"写进正文。
2. **绕开**：同一目标下换一条不依赖它的路（本仓几乎总有：先做判据、先写守卫、先补文档、
   先做另一个可独立验收的分支）。
3. **继续下一轮**。★ **不要**重试被拒的操作，**不要**换个写法再赌一次沙箱，
   **不要**为了"看起来有进展"去改无关文件。

**本轮确实无事可做**（整个目标都被人的决定挡住）⇒ 结束轮次，输出 §5，并（按停止线）考虑
`update_goal … blocked`（理由必须具体到"缺哪台机器 / 缺哪次裁决"）。

## 5. 交回给用户时必须给的四段（每轮结束或最后）

```markdown
## 做完的
- <一条一行> —— 附**可复核凭据**（守卫命令 / 用例名 / 文件路径），不要写"已处理"

## 验证
<逐条贴退出码：pnpm test / requirements validate / 其它域守卫>

## 卡住的（需要你）
- <在哪一步> · 需要你做什么决定 · 为什么 agent 不能替 · 我先绕到哪去了

## 下一轮我会从哪起
<一个具体动作，不是方向>
```

★ **把"我以为的对"和"测得的事实"分开写**。长程模式最容易出的错不是做错，而是
**把自己上一轮的推测当成本轮的事实**（这条在本仓有先例：`script-dsl` 的"前置"是读 README 推出来的，
实测旧仓模拟器根本不依赖它）。凡是"我印象中 / 应该是"，要么去测，要么标成**待核**。

## 6. 本仓特有的五条硬约束（长程时最容易踩）

1. **旧仓 `E:\Games\Eushully\天結` 只读**：不改 / 不删 / 不移。
2. **`git add` / `git commit` 一律不做** —— 提交时机由用户定（长程模式**不改变**这条）。
3. **不凭记忆写游戏 / 引擎语义结论**：那些是知识层，必须绑可再校验观察、过准入门
   （`AGENTS.md` §6）；`data/ledger/` 里现在**一条都没有**，这是有意为之。
4. **测试分级**（`AGENTS.md` §5）：默认只跑 `@env pure`；`assets`/`external` 档**显式**跑
   （`pnpm test:assets` / `pnpm test:all`），并把结论里"哪档没跑"写清楚 —— 别把"没跑"说成"绿"。
5. **改动前先看有没有守卫**：本仓的规矩是"没有守卫的清单等于一份 Markdown" ——
   你要新立一条约定，就顺手给它一条**会红的**守卫（红了指向真实不一致，而不是"不许出现某字符串"）。

## 7. 反模式（本模式专属）

* ❌ 用 `ask_user_question`（没人答 ⇒ 阻塞）。
* ❌ 带 `sandbox_permissions` 重试（失败关闭 ⇒ 白等）。
* ❌ 没有停止线就开始"无限推进"。
* ❌ 把"我读了 README 推断的依赖关系"当事实写进结论（先测）。
* ❌ 一轮改太多、门禁跑不完，把红留给下一轮。
* ❌ 收尾只说"已完成 / 进行中"，不给**命令 + 退出码 + 用例名**。
* ❌ 为了让轮次"看起来有产出"去动无关文件（那是把噪声当进展）。
