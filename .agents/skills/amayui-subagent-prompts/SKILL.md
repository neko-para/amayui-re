# Amayui Subagent Prompts（派活：五类场景的 prompt 规格）

★ 先说清一件事：**这个文件不教"怎么逆向"**。取证口径在 `amayui-re-engine`，spec 口径在 `amayui-spec`，
实现口径在 `amayui-emulator`，排期在 `amayui-requirements`。本文件只回答**派活时怎么写**，
以及**哪一类活必须由另一个 agent 做**。

## 0. 三条最常踩的（都踩过）

1. **断言没有归宿。** 写了一句"这没有引擎对应物"，却没说子代理该**解决**它、**登记残差**、还是**移交**。
   ⇒ 子代理只能猜；猜对了也是运气，且**没有人记账**。
   判据：prompt 里每一条断言都要能回答 §3 的三件套（证据 / 处置 / 落点）。
2. **把子代理的推断当事实转发。** 上一轮的报告写着「引擎是 盖章→立刻到期→**清窗位**」，
   我照抄进了下一轮的 prompt —— 其中"清窗位"在报告自己的诚实项里写着**未取证**。
   ⇒ 下游按假事实改了实现，还得再花一轮回退。
   **转发前必须把"已核事实（带 EA）"与"待核假设"分开写**，假设要标 `<待核>`。
3. **让子代理自己裁决。** 「你觉得阈值该不该改成 30」「你看要不要动 shape」这类问句，
   子代理会给一个**看起来合理**的答案并顺手改掉。裁决是父级的活。
   ⇒ prompt 里写「**已裁决，不要重新裁决；发现硬反证就停下来报告**」。

## 1. 动手前先定三个变量（定不下来就别发 prompt）

| 变量 | 取值 | 它决定了什么 |
|---|---|---|
| **场景** | 五类之一（§4.1–§4.5） | 输入边界、判据、输出格式 |
| **输入边界** | 能读哪些目录 | 结论能有多硬。⛔ 边界越松，越容易被实现/旧结论带偏 |
| **落点** | 报告 / 清单 / 直接改工作树 | 并行安全性、是否需要单独一轮复审 |

★ **输入边界是五类场景的唯一实质区别**，不是"任务描述不同"：

| 场景 | 只许读 | 一句话判据 |
|---|---|---|
| 4.1 取证 → spec 草案 | `corpus/`（+ 只读 `data/shape/`） | 每条结论有 `EA → 指令原文 → 结论` |
| 4.2 实现 / 修复 | `data/spec/`（+ 要改的 `apps/`、`tools/`） | 每条规范条款都有落点，门禁全绿 |
| 4.3 spec 内部一致性 | **只有 `data/spec/`** | 独立实现者只凭正文能写出**唯一**实现 |
| 4.4 spec ↔ lst 忠实性 | `data/spec/` + `corpus/` | 正文每个可判的"必须/只/总"都能在 EA 上复核 |
| 4.5 C++ ↔ spec 符合性 | `apps/` + `tools/` + `data/spec/` | 实现与正文逐条对上，且**改坏一处守卫会红** |

## 2. 一条 prompt 的六段骨架（顺序固定）

1. **角色 + 场景 + 一句话目标**（"你是本仓的取证 subagent…"）。
2. **输入边界**（"只许读 X；⛔ 不许读 Y"）+ 开工前要先 `skill` 加载哪几个技能。
3. **已核事实 / 已裁决**（带 EA 或引文）与 **`<待核>` 假设**分开写。
4. **必须回答的问题**（编号，一条一问，可验收）。
5. **硬纪律**（锚只有 EA / 不许 `git add` / 不许改历史件 / 不许绕过门禁 ……）。
6. **交付物 + 失败分支**（写到哪、什么格式、做不动怎么办）。

★ 第 3 段最容易写坏：把"我上轮读到的"当"事实"。规则是——**凡是没写 EA 的，一律标 `<待核>`**。

## 3. 每条断言都要有三件套

| 要素 | 写法 | 缺了会怎样 |
|---|---|---|
| **证据** | EA（指令行首地址）+ 指令原文；或守卫用例 id | 子代理无法复核，只能信你 |
| **处置** | 闭集：①补/改正文 ②登记残差（`kind` + `next`）③改实现 + 会红的守卫 ④只报告不动 | 变成 §0.1 的无归宿断言 |
| **落点** | `文件:行` / `.tmp/…md` / 需求单 id | 干完了没人找得到 |

**否定式断言**（"没有引擎对应物""引擎不这么做""没人读它"）额外要两样：

- **证伪条件**：什么观察能推翻它；
- **回退动作**："若被证伪就恢复 X / 改哪条合同"。

★ 否定式断言是**存在量词的否命题**，最贵也最容易错。能给出"引擎某处**就是**这么做的"（结构性证据）就别用否定式。

```
## 必须回答
1. 这条在**领域层**是什么（可观察行为，不写偏移）。
2. 它改的每一格：**谁写、谁读、初值/缺省、无效值**（含经寄存器基址的别名访问——字面 grep 为空**不等于**没人读）。
3. 第 <N> 位 / 第 <M> 位 的分工与消费者。
4. 与相邻指令（<列出>）的先后 / 互斥关系。
5. 新规则 id 建议（仓内风格：`CORE-OPS-…-<opcode>`）、落点章节、要改的交叉引用（`rg` 给 `文件:行`）。
6. 新正文草案（合同 / 上下文 / 状态对应 / **可证伪** / 残差）。正文⛔不许出现 EA/偏移/函数名/守卫路径。
7. bindings / audit 草案（JSON 片段）。⚠ `storage` 只许挂 `data/shape/types.json` 里**已登记**的成员；没登记就用领域措辞 + 残差。

## 硬纪律
- 锚只锚 EA；⛔ `.c` 行号与文本不许当锚；⛔ 助记符不算事实。
- 每条结论写 `EA → 指令原文 → 结论`，别人照着重跑能得到同样结果。
- 不确定就写「未取证」，不许凭记忆补。
- ⛔ 你不能开 subagent；不要承诺做复审。

## 交付
报告写到 `.tmp/<批>/report-<主题>.md`：覆盖上面 7 项 + 末尾「这次没能证明的事」。
最后 `send_message` 回 ≤40 行摘要 + 报告路径。
```

**常见失败**：把 handler 的"做了什么"直接写成"领域语义"（`把 [x] 清 0` ≠ `重置相位`）；漏别名访问；
把"我没 grep 到"当成"没有读者"。

**输入边界**：`data/spec/chapters/*.md`（合同）+ 要改的 `apps/emulator-cxx/**`、`apps/emulator-new/**`、`tools/**`。
⛔ 不许动 `corpus/`、`data/shape/`、`docs/`（历史件）、`git add/commit`。

```

## 已裁决（⛔ 不要重新裁决；发现硬反证就停下来报告）
1. <行为条款 A>
2. <行为条款 B>
<每条附 EA 或正文引文>

## 要落地的清单
1. 正文：<文件:行> —— <改什么>。⛔ 正文不许出现 EA/偏移/`shape:`/守卫路径；标题保留 `opcode 0x…`（gaps 覆盖从标题机械派生）。
2. bindings / audit：<id> —— <增删改>；`storage` 只挂已登记成员；`evidence` 的用例标题必须与 `test('<标题>')` **逐字一致**。
3. 实现：<文件> —— <语义>。⛔ 不许只改注释就说改完了。
4. 守卫（必须**会红**）：加进 <CTest 顶层注册 / pure 档 JS 用例> + `tools/mutate-check.mjs` 一条变异。
5. 需求台账：<节点 id> —— <状态 / 结论>。

## 硬纪律
- 只改上面点名的文件；⛔ 不动 `corpus/` `data/shape/` `docs/`。
- ⛔ 不许为了让门禁变绿去改输入时间线 / 放宽阈值 / 删断言；要重定基线就**说明实测值 + 为什么是程序侧基线**。
- ⛔ 不许 `git add` / `git commit`。
- ⛔ 你不能开 subagent；复审由父级另派。

## 门禁（逐条报结果，不要只说"全绿"）
`pnpm tools spec validate` · `pnpm tools requirements validate` · `pnpm test` · `pnpm typecheck`
· `cmake --build apps/emulator-cxx/out` · `ctest --test-dir apps/emulator-cxx/out --output-on-failure` · `git diff --check`
★ 并**实测一次会红**：临时施加变异 → 跑对应守卫 → 必须红 → **还原并比对全文** → 再跑一次确认绿。

## 失败分支（重要）
- 某条做不动（缺钩子 / 缺数据 / 会连带破坏无关测试）⇒ **先停下报告**，不要偷偷降级成"只改名"。
- 门禁红且**不是你改动引起的** ⇒ 报出来，不要顺手改无关文件。

## 交付
`send_message`：改动文件清单（含关键行）、门禁逐条结果（ctest 给计数）、**没落地/保留的部分 + 原因**、新增/删除的规则与残差 id。
```

**常见失败**：把"改名"当"改语义"；实现比正文**多**（加了正文没写的 clamp / 兜底）；
测试断言了某份脚本的实测数字（那是**程序**，不是引擎不变量）。

### 4.3 复审：spec 内部一致性

**输入边界（硬）**：**只有 `data/spec/`**（`spec.json` + `chapters/*.md` + `bindings.json` + `audit.json` + `format/*`）。
⛔ 不许读 `apps/` `corpus/` `data/ledger/` `data/shape/` `docs/` `data/requirements/` ——
它要像一个**只拿到 spec 的独立实现者**那样判"照这份正文能不能写出唯一实现"。

```
你是独立复审 subagent（规则面）。只许读 data/spec/；⛔ 不许读 apps/ corpus/ docs/ data/shape/ data/requirements/。
开工前 `skill` 加载 `amayui-spec`（§4 条目结构 / §5 计量 / §9.1）。

## 被审变更（规则 id + 一句话）
- <id>：<改了什么>

## 判据（每条给结论，不给"通过"）
1. 唯一可实现？未定义术语 / 自相矛盾 / 缺"谁写谁读·缺省·无效值" / 把两套计时写成一个。
2. falsifier 能不能真推翻？是不是"输入 + 观测点 + 期望"；观测点在 spec 里有没有定义（没有 ⇒ 不可观测）。
3. 残差名副其实？`next` 是不是具体下一步；有没有把已写进正文的又列成残差（重复计数）。
4. 跨章一致？与 <相关章节> 有没有同一件事两种说法；**同一术语指两个格**（如"状态字"）。
5. 自包含？（无 EA / 偏移 / 函数名 / `shape:` / 台账 id / 本仓路径）
6. 章首计数（规则数 / opcode 数）与实测是否一致。
7. 有没有"与真机等价""已验证"这类过强措辞。

## 输出（格式固定）
每条一行块：`文件:行 | 引文（≤40 字） | 为什么是问题 | 需要什么证据/决定（改正文 / 进残差 + next）`
按严重度排：硬矛盾·不可实现 → 歧义 → 措辞。**没有就写"没有"**，不许凑数。
末尾附「我认为这次改对了的 3 件事」（防把对的也当错的）。

⛔ 不改任何文件。完成后 `send_message` 回清单（≤60 行）。
```

### 4.4 复审：spec 是否符合 lst（忠实性）

**输入边界**：`data/spec/` + `corpus/disasm/files/*.lst`（只读）+ `data/shape/`（只读）。
⛔ 不许读 `apps/emulator*`（不许拿实现证 spec）。

```
你是独立复审 subagent（忠实性面）。任务：逐条判 spec 正文的断言能不能在 .lst 上复核。
可读 data/spec/ + corpus/ + data/shape/；⛔ 不许读 apps/emulator*（那是第二实现，不是真源）。

## 抽检规则
- 每条规则抽 **3–6 条**可判陈述（优先："只/总/必须/不得/相等/不等"、边界、位宽、符号性、顺序）。
- 对每条：`bindings` 里找到站点 EA → 用 `pnpm tools disasm-at at --ea <EA> --lines N` 重读 →
  判定 **一致 / 过强（正文说得比指令多）/ 过弱 / 无锚**。

## 必查的五类（都在本仓出过错）
1. **符号性与相等**：`ja`（相等仍窗内）vs `jge`（相等已到期）；32 位有符号 vs 无符号。
2. **别名**：`Engine+4ED10` 当 `this` 时 `+B5B0/B5B8/B5BC` == `Engine+5A2C0/5A2C8/5A2CC` —— 字面 grep 抓不到。
3. **"谁写谁读"**：正文说"有读者/无读者/无取址"，必须给出读点 EA；`lea` 取址也算读者入口。
4. **否定式断言**："不复位/不清位/不投递"—— 要有结构性证据（没有该写点的**穷举**口径）。
5. **`.c` 是改写**：HEx-Rays 的 `__ROL4__` / `this[…+383220]`（十进制！）不能当锚；跨侧比偏移要归一化。

## 输出
每条：`规则 id | 正文引文（≤40 字） | EA + 指令原文 | 判定 | 处置（改正文 / 补残差 / 只报告）`。
末尾：`<待核>` 清单（你没法证的）+ 「哪些断言被证明是过强的」。

⛔ 不改文件。`send_message` 回清单（≤60 行）。
```

### 4.5 复审：C++ 是否符合 spec（实现面）

**输入边界**：`apps/emulator-cxx/**`、`apps/emulator-new/**`、`tools/**` + `data/spec/chapters/*.md`（只为对照条款）。

```
你是独立复审 subagent（实现面）。判：实现是否**只是迎合**正文、守卫是否**真能红**。
可读 apps/ + tools/ + data/spec/chapters/；⛔ 不改文件（除 §变异 的临时改动，且必须还原）。

## 逐条判
1. **实现了没有**：把正文拆成可判子句，逐句在代码里找落点。找出"没实现 / 比声称多 / 比声称少"。
2. **守卫真能红**：对每条不变量问"改坏哪一行会让它红？"，并**实测至少 3 条**：
   临时 `edit` 改一处 → 重建 → 跑对应 `ctest -R …` → **必须红** → 还原（`git diff` 比对全文）→ 再跑确认绿。
   ★ 一次只改一处，改完立刻还原；结束前 `git diff --check` 必须干净。
3. **测试断言的是引擎还是程序**：有没有把某份脚本的实测数字（条数 / 毫秒 / 阈值）写成引擎不变量。
4. **旧语义残留**：`rg` 改名前的标识符 / 被删函数 / 被否证的近似判据，列出来。
5. **改动是否自洽**：被改的判据有没有别的依赖路径（`keep_window` / `dirty` / `active` 之类）没跟上。

## 输出
每条：`文件:行 | 问题 | 判据（哪个断言会红 / 哪条路径不再自洽）| 建议处置`。
末尾附「我实测施加过的变异及结果」（改了哪行、哪条 ctest 红、是否已还原）。
⛔ 收工前必须恢复原样：`git diff --check` 干净 + 相关 ctest 全绿。
```

## 5. 并行还是串行

| 情形 | 结论 |
|---|---|
| 两轮**取证**、写不同报告 | ✅ 可并行（各自写 `.tmp/<批>/report-*.md`） |
| 两轮**编辑** | ❌ 串行。尤其**同一份 `bindings.json` / `audit.json`** —— 并发 `edit` 会互相覆盖（读-改-写竞态） |
| 编辑 + 复审 | ❌ 串行。复审要在"工作树定稿"之后 |
| 两轮**复审**（规则面 / 实现面） | ✅ 可并行（输入边界不同，正好互补）。⚠ 但实现面会**临时改源码重建**，此时**不要**在父级跑 `pnpm test` / `ctest`（结果会串） |

★ 取证的产出落 `.tmp/`，**不要**让它直接改 `data/spec/` —— 那是并行冲突的主要来源，也让"改"和"判"混在一轮。

## 6. 复审纪律（比模板更重要）

1. **不复用编辑者。** 谁改的谁不能复审 —— 那只是把同一套假设再读一遍。
   ⚠ subagent **开不了 subagent**（深度限制）⇒ "编辑 + 自我复审"一轮里做不到，必须父级分两轮。
   prompt 里要写「你不能开 subagent」，否则它会**承诺**做复审却做不了。
2. **两面分开、输入分开。** 规则面（只读 spec）与实现面（读实现）**不能互相作证**：
   ⛔ 不许拿"实现与正文一致"当规则面证据；⛔ 不许拿"正文这么写"当实现面证据。
3. **产出是清单，不是判决。** 每条要 `文件:行 + 引文 + 判据 + 处置`；没有就写"没有"。
4. **父级要抽检被告。** 复审说的"硬矛盾"可能也是错的 —— 父级用 EA 抽检 1–2 条再决定改不改。
5. **落点**：结论进 `docs/02-engine/spec-audit-<年月>.md` 的新一节（格式：错误类型 · 判据 · 本次处置 ·
   下次 review 要问什么）+ 需求单。同一缺陷**不得重复出现**（棘轮）。

## 7. 回执格式（要求子代理这么回，父级好验收）

```
## 结论（≤5 行）
## 改动/发现（文件:行）
## 门禁（逐条：命令 → 结果；ctest 给 N/N）
## 没做 / 保留 / 需要父级决定（一条一行，带理由）
## 我实测过的变异（改了哪行 → 哪条守卫红 → 是否还原）
```

★ 要求它**贴命令与计数**，不接受"全绿"三个字。★ 要求它单列"没做"——这一栏最容易空着，也最关键。

## 8. 失败分支（都要写进 prompt，否则子代理会自己发明）

- **做不动**（缺钩子 / 缺数据 / 会连带破坏无关测试）⇒ **停下报告**，⛔ 不许降级成"只改注释/只改名"。
- **门禁红但不是它引起的** ⇒ 报出来，⛔ 不许顺手改无关文件。
- **发现我给的事实是错的** ⇒ 停下报告，⛔ 不许照着错的做（否则一轮下去要回退两处）。
- **需要裁决**（阈值 / 基线 / 要不要动 shape / 要不要改名）⇒ 报上来，⛔ 不许自己定。

## 9. 发出去之前的 10 秒检查单

1. 场景是五类里的哪一个？**输入边界**写了吗（尤其 4.3 的"只读 data/spec"）？
2. 每条断言都有 **证据 / 处置 / 落点**？否定式断言有**证伪条件 + 回退动作**？
3. "已核事实"与 `<待核>` 假设**分开了**吗（有没有把上一轮的报告当事实转发）？
4. 裁决写死了吗（"已裁决，不要重新裁决"），失败分支写了吗？
5. 说了"⛔ 你不能开 subagent"吗？说了"复审由父级另派"吗？
6. 交付格式要了**门禁逐条 + 没做清单**吗？
7. 这轮会不会和另一轮**写同一个 JSON**？会 ⇒ 改成串行。
8. 有没有"你觉得要不要…"这种把裁决推给子代理的句子？删掉。
