# Subagent 编排（父级 / 子代理）

> 来源：2026-11-09 用户的明确要求 ——「**总是使用 subagent 执行任务**，subagent 仍可再启动一层 subagent，
> 因此可以把分析工作下放；请提示使用 subagent 来 review 变更和设计」。
>
> 本文件只管**谁做什么、按什么顺序、父级验收什么**；单条 prompt 的措辞见 `amayui-subagent-prompts`。
> ★ 它**不是只给"多单批次"用的**：单条、发现型、长程都走这里，只是流水线不同（§3）。

## 0. 三条最常踩的

1. **父级自己上手**：一旦父级开始改产品代码，就没有带宽验收了，而且"谁改的谁复审"的独立性也没了。
2. **编辑并行**：同一工作树 + 同一 build dir + `tools/mutate-check.mjs` 会临时改文件 ⇒ 两个编辑者并发 =
   构建失败、变异互相踩、`git status` 分不清谁改的。**只有只读能并行**。
3. **写代码的人给自己发合格证**：实现者自审只会把同一套假设再读一遍。

## 1. 三种输入形状（先认形状，再选流水线）

| 形状 | 用户长什么样 | 父级第一步 | 产物 |
|---|---|---|---|
| ① **已有单** | "把 X 下面的子单逐个处理" / 直接给单号 | `pnpm tools requirements show <id>` | 每单 analysis → 改 → report |
| ② **发现型** | "梳理 X 缺失的能力并逐个修" / "这里为什么不对" | **切面**（按文件面，不按单号） | 缺口清单 → **新建单** → 转 ① |
| ③ **长程无人值守** | "我一段时间不回 / 你自己往下做" | 按 `long-horizon` 立 goal + 停止线 | 每轮一个可判定单元 |

★ **形状②最容易漏**：任务开始时**一张单都没有**，所以 `pnpm tools requirements plan` 帮不上忙 ——
这时父级的产出不是代码，而是**能立的单**。切面规则：
- 按**子系统 / 文件面**切（例：设备状态面 / 绘制与流水线面 / 资源与上传面），⛔ 不按"想法"切；
- 每个面一个只读普查 agent（3–6 个并行），文件集**互不重叠** —— 否则同一处缺口被报三遍，还互相矛盾；
- 每条产出的验收格式固定：`文件:行 / 现在做什么 / 语义要求 / 缺口类别 / 引擎是否用到（证据） / 影响 / 最小修法 / 守卫怎么红`。
  **没有"怎么红"的条目不许立单**（那是"我觉得该补"，不是判据）。

## 2. 角色分工

| 角色 | 谁 | 只做什么 | 明确不做 |
|---|---|---|---|
| **父级（你）** | 当前会话 | 拆活 / 写 prompt / 抽检 / 跑最终门禁 / 改需求树 / 裁决 | 不把活干了 |
| **普查者** | subagent（只读） | 取证 / 枚举缺口 / 给出可立单的条目；写 `.tmp/<主题>/<面>.md`；可跑**只读**诊断命令 | 不改文件、不构建、不跑会写盘的用例 |
| **实现者** | subagent（可写） | 实现 + 守卫 + 变异 + 自测 + 写 `report.md` | 不改需求树、不 commit、不自己裁决 |
| **设计复审** | 另一个 subagent（**不是实现者**） | 动手前判"修法对不对 / 守卫能不能红 / 有没有更小方案" | 不替实现者改代码 |
| **变更复审** | **又一个**不同的 subagent | 读 `git diff`、跑守卫、**实测变异**、还原 | 不动产品代码 |

★ **父级读到哪里为止**：原则不是"不读源码"，而是**不把活干了**。父级至少要读三样，否则判不了子代理说的是真是假：
① 被改文件的**关键 hunk**；② **守卫用例本身**；③ **一条命令的读数**（自己复跑）。
需要再读第四个文件才能判断 ⇒ 派一个只读 agent 去读，而不是父级继续读。

★ **父级裁决、子代理执行**：凡是"要不要新增停机原因 / 目标定多少 / 判据算不算满足 / 要不要动 guest ABI"这类，
父级写死"已裁决，⛔ 不要重新裁决；发现硬反证就停下报告"。子代理擅长干活，不擅长替产品做取舍。

## 3. 流水线（按形状选，别拿一条流水线套所有任务）

### 3.1 形状① 已有单

```
① 盘点（父级）    requirements plan / show <id> → 活节点 + 每单判据
② 前置只读分析    每单一个只读 agent → .tmp/reveq/<id>/analysis.md（可并行）
③ 编辑（串行）    每单一个编辑 agent（内部：设计复审 → 实现 → 变更复审）
④ 父级验收 + 收口 门禁 + 抽检 + requirements set --status/--verify/--body --write
```
- 不必等所有分析回来：**下一单只要它的 analysis 到了就开工**。
- **变更复审一定在编辑之后**：工作树定稿再派，否则复审看到的是半成品。
- 编辑运行期间**父级不要跑** `pnpm test` / `ctest`（会与它自己的验证串）。

### 3.2 形状② 发现型（先有清单，才有一批单）

```
① 切面（父级，≤10 分钟）  按文件面切，每个面写死"读哪些文件 / 回答哪几个问题 / 产出什么"
② 并行普查（3–6 个只读）  各自写 .tmp/<主题>/<面>.md，互不重叠
③ 父级裁决 + 立单        合并去重 → requirements add（每单只收一类失效方式）→ 排优先级
④ 转 3.1                 一次只开一单的编辑，做完再下一单
```
- 排序口径：**屏幕/行为影响 × 风险**，不是"哪个好修"。
- 已知的根因单（例："纹理 α 整张为 0"）**先做**：它通常是别的现象单（渐变、覆盖层）的共同前置。
- 合并时**保留分歧**：两个 agent 对同一处给出不同结论 ⇒ 不选一个，标 `<待核>` 并派第三个 agent 证伪。

### 3.3 形状③ 长程无人值守

按 `long-horizon` 的激活纪律（不提问、不提权、登记 + 绕开）；本文件只管"这一轮的那个单元交给谁、父级怎么收"。

## 4. 并发与槽位

* 活跃子代理有**运行时上限**（实测出现过全树 8，depth 1 与 depth 2 合计）—— **以运行时告警为准**，别把 8 当预算。
* 被拒时**不要让子代理无限重试**：降到"实现者自审 + 父级另派一个全新 subagent 做变更复审"，
  并在报告里如实写"独立复核未成行 / 由父级另派"。
* 普查者要再开一层复审时，先告诉它"槽位满就自审并如实标注"。

## 5. 复审按风险定档（省仪式，不省独立性）

| 档 | 什么时候 | 谁复审 |
|---|---|---|
| **两层** | 改语义 / 改判据 / 动 guest 可见行为 / 碰别人单的 hunk | 设计复审（动手前）+ 变更复审（另一个 agent，实测 ≥2 处变异） |
| **一层** | 纯守卫补强 / 测试夹具 / 不改语义的重构 | 变更复审（**非实现者**） |
| **父级抽检** | 单行修复 / 文档 / 生成物 | 父级读 diff + 自己跑守卫 |

★ 不可省的只有一条：**写这段代码的人不给自己发合格证**。

## 6. 每单的 prompt 骨架（父级写给实现者）

1. **角色 + 场景 + 一句话目标**（单号 + 标题；发现型任务写"面 + 要回答的问题"）。
2. **先读** `.tmp/reveq/<id>/analysis.md`（或 `.tmp/<主题>/<面>.md`）——别让它从零取证。
3. **输入边界**：只许改哪些文件；⛔ 不动 `corpus/` `data/spec/` `data/shape/` `docs/` `data/requirements/`（按需放宽）。
4. **已核事实 / 已裁决**（带 `文件:符号` 或 EA）与 `<待核>` 假设**分开写**。
5. **必须做到**：实现范围、守卫（必须能红）、变异条目、`verify:` 锚建议。
6. **复审档位**：按 §5 写死"本单要几层、谁做"；变更复审要实测 ≥2–3 处变异。
7. **硬纪律**：不 commit、不改别人的 hunk、按内容定位而不是行号、工作树只多该改的文件。
8. **门禁逐条贴命令与计数**（不接受"全绿"三个字）+ **没做清单**。
9. **失败分支**：做不动就停；门禁红但不是它引起的就报；发现 `已核事实` 有错就停下报告。

## 7. 父级验收清单

```bash
# 本仓 win32 优先（AGENTS.md §2）；macOS / Linux 换对应 preset，⛔ 不要照抄别人平台的值
cd apps/emulator-lift && cmake --build --preset windows-x64
ctest --test-dir out --output-on-failure          # 记录 N/N（skip 要说明环境原因）
cd <repo> && pnpm test                            # 合同档
pnpm verify                                       # 工具链档
pnpm tools requirements validate
pnpm tools lift check
git diff --check && git status --porcelain         # 只多该改的文件
```

* **抽检最小集**：① 自己跑一次 build + 对应 CTest；② 看 diff 的关键 hunk（不要全读）；③ **复跑一条**子代理报的读数。
* **守卫真实存在**：`verify:` 的 `路径#用例名` 要在文件里逐字找得到（C++ 看 `g_current_case` / `TEST` 名）。
* **不是"挂空守卫"**：合成/夹具类用例要能在改动前红（让实现者报"修前 N 条红"的输出）。
* **不接受**：只贴"全绿"、只贴耗时、把当前数字写成断言、改了测试换绿。

## 8. 需求树收口（父级独占）

* 写入口只有 `pnpm tools requirements set <id> --status … --verify … --body <md> --write`
  （**不要手改** `data/requirements/*.md`）。
* **需求**：`done` + `verify: 路径#用例名`；没有守卫 ⇒ `done_reason` 写裁决本身。
  **缺陷**：`done` + `verify` 或保留 `repro`；`dropped` 要写"不是缺陷 / 不修"的理由。
* **判据要写实**：子代理报"按单的 repro 不通过"时，父级要么改判据并写明裁决，要么保持 open ——
  ⛔ 不许不动判据统计 `done`（实测踩过：`verify` 挂的路径与 `repro` 不是同一条路径）。
* **新发现立刻开单**（同一棵树下，或最该负责的父下），每张单只收一类失效方式；
  被裁"边界外"的东西写进单的 `## 未做`，不要留在对话里。
* **预算**：单节点 ≤ 80 行、活节点 ≤ 100；超了先拆层 / 移进知识台账，⛔ 不放宽预算。

## 9. 实测过的坑（都发生过）

| 坑 | 现象 | 处置 |
|---|---|---|
| 父级"先自己看看" | 读着读着开始改，验收带宽归零 | 读完"能写 prompt"就停；再要读就派 agent |
| 普查按"想法"切面 | 三个 agent 的文件集重叠，同一处给三种结论 | 按文件面切，prompt 里写死"只读这些文件" |
| 子代理报"29 处"复跑是"28 处" | 报告里的数字没贴命令 | 要求"命令 + 读数"；父级抽检一条 |
| 用例把"合法时序被拒"写成期望 | 锁死了实现限制，下一步修不了 | 标"已知偏离 + 跟踪单号 + 修好后必须翻面" |
| 子代理顺手改了别人的 hunk | `git status` 分不清 / 单独编译不过 | prompt 列明"工作树已有 N 张单的未提交改动，不要改回去" |
| 子代理自己"裁决" | 阈值被悄悄改掉 | prompt 写"已裁决，不要重新裁决" |
| 分析者开工太晚 | 编辑者等 analysis | 先并行发分析，再按到达顺序开工编辑 |
| 变异用 `if (false)` | `/W4 /WX` 下 C4127 让构建失败，工具记"无法判定" | 用"运行时恒真"或等价改写 |
| 守卫断当前数字 | 换实现就红，且红得没意义 | 只断言不变量（口径 / 关系 / 存在性） |
| 照抄示例命令 / 示例 preset | 平台不对，门禁根本没跑 | 判据从 AGENTS.md 的口径来，不从"上一次成功的命令"来 |
| 图脚本追加的 `profile_begin` 不 arm | 静默全 0 表，A/B 假成立 | 这是真实缺陷，已开单；分析时把"仪器真的开了"当判据之一 |

## 10. 收工检查单

- [ ] **形状判断对了吗**（① 已有单 / ② 发现型 / ③ 长程）？发现型有没有**先立单**再改代码？
- [ ] 父级没改产品代码；抽检三样（build + diff hunk + 复跑一条读数）都做了
- [ ] 编辑是串行的；出现过的并发只发生在只读
- [ ] 每单的复审档位按 §5 定了；变更复审由**非实现者**做过（或如实记录"未成行 + 父级另派"）
- [ ] 每单的守卫能在改动前红（有输出为证）
- [ ] 门禁逐条有命令与计数；`git status` 只多该改的文件；没有 commit
- [ ] 需求树：能收口的都写了实判据；新发现都开了单；预算没超
- [ ] 没做的、裁掉的、边界外的，都在对应单的 `## 未做` 里有位置
- [ ] 产出可追溯：批量在 `.tmp/reveq/<id>/`，发现型在 `.tmp/<主题>/<面>.md`（**小修复不强制两份文档**）
