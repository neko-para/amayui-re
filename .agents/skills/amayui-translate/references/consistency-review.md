# 全库一致性 / 命名复核（C 模式的配方）

> 场景：**要推翻的是既有定稿**（"XX 这套译法丢了原义，评估能否优化"），或旧文档里挂着一条"活冲突 / 待定"要核实。
> 与 B 模式的分岔只有一条：**C 的先手不是"改哪句"，而是"当年定了什么、现在全库长什么样"**。
> ★ 本文件只写**怎么查、怎么判、候选怎么写**；**不记任何裁决** —— 裁决后的真源是 patch 的中文 + 需求树节点。

## 1. 清点（只读；全库、两侧配对）

```bash
pnpm tools patch find '<词形1>' '<词形2>' …        # 日文 ↔ 当前中文 配对明细（人读）
pnpm tools patch find --regex '<词根>|<变体>' --count   # 先看规模与分布（先跑这条）
pnpm tools patch find --regex '<现有写法 A>|<现有写法 B>'   # 中文侧的"活冲突"各在哪
pnpm tools patch find '<词根>' --kind data          # 只看日文侧（含 src 侧同样保留的 comment 标记）
pnpm tools patch find '<词根>' --json               # 机器可读（配后处理统计）
```

读输出：

* **两侧配对**：`data` 行是日文原文、`src` 行是当前中文或 op 载荷；只有 `src` 有行 = **新增**的那一行（`insert-after`），
  只有 `data` 有行 = **被删**或本就是原文标记。行键 `i=<锚>` = **基线行序**（= patch 自己的键空间），
  编辑就用它；`data` 那侧另给**文件行号**（`L123`），要读上下文按它 `Select-Object -Skip` 即可。
* **语域（决定"改得起改不起"）**，看行形状就够：
  | 形状 | 是什么 | 约束 |
  |---|---|---|
  | `set-string (global-string …) "…"` | **UI / 数据表项**（物品名 · 设施名 · 地图名 · 单位/种族名） | 受控件宽度约束；`【设施：…】`/`【装飾：…】`/`１Ｆ` 这类是**组合串** |
  | `show-text 0 "…"` | **剧情正文**（ADV 视觉行） | ≤25 中文字/视觉行（见 `conventions.md` §1） |
  | `draw-string … "…"` | **控件文本** | 只有尾参是字面量才可译；受绘制宽度约束 |
  | `comment "▼G####…"` | **分节标记（原文，不是译文）** | 两侧都一样，**不算活冲突**、也不译 |
* **词形要穷举**：片假名 / 平假名 / 汉字三种写法、以及**同根家族**（一个专名往往带一串派生名）。
  只搜一个词形就下结论是这类复核最常见的错。
* **宽度**：改名前**先数字数**（ASCII 按半字）。UI 表项按**同组最宽的那条**看（地图名列表、物品名列表）。
* 基线索引不在 / 陈旧 ⇒ `find` 会**现反汇编**（慢一点但一样全）；先 `pnpm tools patch index --write` + `patch view`
  可以省下这部分（索引只依赖不可变的东西，建一次就不用再管）。**不要**绕过 `find` 用裸 `rg`：`src` 根本不落盘。

## 2. 决策史（"当年提过什么"）

```bash
Expand-Archive docs\01-translation\ref\archive.zip -DestinationPath .tmp\ref-archive   # 或 unzip -d
rg -n '<词根>|<现行译法>' .tmp/ref-archive
rg -n '<词根>' docs/01-translation/ref/assets
```

* 先看 **`archive/prob/prob-决策清单.md`**（跨文件决策的**主清单**：已定稿 / 待定稿 / 活冲突 + 回改范围）；
* 再看相关 `archive/prob/prob-<脚本>.md` 与专题件（`prob-追加包系统.md`、`prob-SG追加包.md` …）；
  §「处理约定」里常写着**分流规则**（哪一类词按语义译、哪一类保持音译）与"待 X 定稿"的尾巴；
* ★ 这些是**历史工作单**：结论 / 计数 / 日期一律**不采信**，只回答"当时提过什么、理由是什么"。
* ★ `assets/**` 里的「待定 / 已确认 / 出现 N 处」同理；实测过它**与既成译文不一致**
  （文档写"待定"，译文其实早已定稿落地）⇒ 它给的是**线索**，不是现状。

## 3. 评估：候选 + 代价（★ 只给，不写）

* 候选**必须**字母编号，并标「**主推 X**」；每个候选附一句取舍 + **代价**。
* 代价至少写清这五项：① 涉及**几支脚本几处**（来自 §1 的清单，不靠记忆）；② 涉及哪些**语域**（UI / 正文 / 两者）；
  ③ **宽度**变化（UI 表项尤其）；④ 会不会**拆散同根词**（日文同根 ⇒ 中文也该同根，这是这类问题的本质）；
  ⑤ 需要**连带回改**什么（同一家族的其它词形、旧文档的"待定"尾巴、其它已定稿用法）。
* 常见的四种候选形态（按"动了多少"排）：
  | | 形态 | 典型代价 |
  |---|---|---|
  | A | **维持现状**（音译 / 既有写法） | 零改动；语义/双关继续丢 |
  | B | **全语义化**（连专名一起意译） | 语义回来，但"名"的形态没了；生僻派生名可能**无从意译**；改动面最大 |
  | C | **音义折中**（保留名字后缀，把词根换成语义） | 语义可见、字数常与现状持平；名字读起来偏"梗"（若原本就是玩笑命名，这反而是对的） |
  | D | 只改**部分语域**（如只改地名、留物品名） | ❌ 默认不推荐：会造出**新的混用**，除非有明确判据（如"UI 宽度只允许这一处变"） |
* ★ **"维持现状"也是合法裁决** —— 那时按 A 处理：**什么都不写**，把结论记进需求树节点。
* ★ 候选的**波及面可以直接量**：`patch find '<旧>' --edits e.txt --to '<候选>'` 是**只读**的
  （只写那份清单文件），它逐条给出「日文原文 / 现在 / 改后」并汇总"命中 N 条 / M 支脚本" —— 这就是候选的代价。
  ★ 但它**只是机械填空**：同形词会被误伤（实测 `赫塔→废柴雷斯` 得到"废柴雷斯雷斯"）⇒ 这份清单是**草稿**，不是结论。

## 4. 裁决之后（才动笔）

1. **回改 = 生成清单 + 逐条确认 + 按锚直改**（不是逐支手改，也不是"一条命令全库替换"）：
   ```bash
   pnpm tools patch find '<旧写法>' --edits e.txt --to '<新写法>'   # ① 机械生成清单（只写 e.txt）
   #  ── ② 逐条审 e.txt：一条记录 = 头行 `<脚本> <锚>[+<k>]` + `- 现在` + `+ 改后`
   #        同形词会被误伤 ⇒ 该删的删、该改的改（锚 = 基线行序，不是文件行号）
   pnpm tools patch set --edits e.txt            # ③ dry-run：逐条打「- 现在 / + 改后」
   pnpm tools patch set --edits e.txt --write    # ④ 一次写盘（判据：重建行空间逐行 == 独立算出的期望）
   pnpm tools patch verify                       # ⑤ 判据：逐字节
   ```
   * `-` 行必须与现场**逐字相同**：锚写错 / 位置漂了 ⇒ 当场报错，不会"按锚硬套"；
   * `set` 只接受**改一行字面量 / 插一行 / 删一行**三种形态；**折行拆分 / 合并（行数变化）**要走
     `patch view --kind src --name <脚本> --out dist/views` → 编辑器改 → `patch edit --name <脚本> --write`；
   * 只想改某一处 ⇒ 在清单里**只留那一条**、其余删掉（这就是"逐个确认"的落地形态）。
2. **判据**：`patch find --regex '<日文词形>|<中文写法 A>|<中文写法 B>' --kind src` 里**同一日语词根只剩一种中文写法**（活冲突清零）+ `patch verify` 全绿；
3. **收口**：需求树节点写 `verify` 或 `done_reason`（裁决内容 + 范围）；**玩家可见**的改动补 `release/CHANGELOG.md` 一条；
4. ❌ **不要回写** `docs/01-translation/ref/assets/**`（只读快照，守卫钉字节保真）；❌ 不要新建第二份术语台账。

## 5. 踩过的坑（这类复核的误判来源）

* **拿裸 `rg dist/views/src` 当"全库"**：视图可能只覆盖一部分脚本、或比 patch 旧 ⇒ **少报且不报错**；
* **拿"文档说已改完 / 待定"当证据**：唯一证据是刚跑出来的那次检索；
* **只搜一个词形**（片假名 vs 平假名 vs 汉字；同根家族的派生名）；
* **把 `comment "▼G####…"` 与 `display-furigana` 的第二参当竞争译名**（前者是原文标记，后者是注音/释义）；
* **组合串漏改**：`【施設：X】　結陣なし`、`一般属／X種`、`X迷宮１Ｆ` 这类是**另一条文本行**，
  按词搜得到、但只改"裸词"那条就会漏；
* **只改一半语域**（UI 改了、剧情没改）⇒ 立刻造出一处新的活冲突。

## 示例（只演示"怎么查"，不含任何裁决）

`ヘタレ` 词根（普通词与专名同根）的复核在 `REQ-01M43Y8D8CKMW32EHB2XQE7NT3`，2026-10 当时的清点形状是：

```bash
pnpm tools patch find --regex 'ヘタレ|へタレ|ヘタテット|ヘタボウ' --count
# → 20+ 行、十来支脚本；普通词（难度档 / 称号 / 攻击名 / 设施）走一个译法，
#   专名家族（ヘタレス / ヘタテット / ヘタボウ / ヘタレン / ヘタレ種）走另一个
pnpm tools patch find --regex 'ヘタレ|へタレ|ヘタテット|ヘタボウ'
# → 两侧配对：能看到同一 UI 列表里（$1$PLINIT 264/265）两种写法**并排**
```

★ 计数是**当时的下界**（随时会变）：复核时**重跑命令**，不要引用上面的形状当结论。
