# Amayui Requirements（需求台账：开单 / 收口 / 裁决）

## 0. 三条最常踩的

1. **不许手改 `data/requirements/*.md`**（改参数区、重命名、新建文件都算）：写路径**只有一条** ——
   领域模型里的 `planAdd` / `saveNode`，两个调用方（CLI `--add/--set`、工作台 `POST /api/nodes`）共用它。
   手改会被 `validate` 判红，且失去"写后回读复验、不绿回滚"的保护。
2. **不许 `git add` / `git commit`** —— 提交时机由用户决定（沿用旧仓长期要求）。
3. **进度只写在树里**：`release/CHANGELOG.md` 是**玩家**的更新记录、README **不许**写状态 / 进度 / 计数
   （`AGENTS.md` §10）。发现"该做的事没人 track"时的正确动作是**开单**，不是写进散文。

## 1. 什么时候该动用它

* 用户问**进度 / 还剩什么 / 某支到哪一步**；
* 用户问**某节点（或它的子树）能不能收口**，或要你**废弃 / 降级**某个节点；
* 用户要求**登记**一件事（缺陷、待办、可能性、投资方向）；
* 用户在做别的任务时**你自己发现**了"这属于还要做什么"的东西：判据写不实、守卫缺了、
  能力做了但没人记、某个"以后可能做"被硬塞进当前节点 —— ★ 这时**主动开单**并说清放在哪个父下，
  不要留在对话里或写进 README。
* 反过来：**"知道什么"（逆向结论 / 观察）不进这棵树** —— 那是知识台账 `data/ledger/`；
  长调查 / 设计 / 沿革进 `docs/` 或 `git log`。一条记录只能进一个地方。

## 2. 四步工作流

```bash
pnpm tools requirements plan                 # ① 全局：树 + 聚合状态（先看**活节点**预算，别撞 ≤40）
pnpm tools requirements show <引用>          # ② 一个节点：字段 + 子树 + 正文（正文里才有"判据"）
pnpm tools requirements add … / set … --write # ③ 动作（缺省 dry-run；★ 只在确认后才 --write）
pnpm tools requirements validate             # ④ 改完必跑：5 条不变量，红 = 退出码 1
```

★ `<引用>` 认完整 id / 裸 ULID / **唯一前缀** / **唯一后缀**：ULID 以时间开头，**同批节点的前缀全都一样**
⇒ 日常用**后缀**（例：`show 1CTKKQFC4`）。
★ CLI 与工作台是同一个写入口的两个前端；网页那边只有"新建"（`POST /api/nodes`），改状态仍走 CLI。

## 3. 收口的三种凭据（怎么选 —— 这是最容易做错的一步）

| 局面 | 凭据 | 判据 |
|---|---|---|
| 节点锚的是**能力**（做完了） | `verify: <文件>#<测试名>` | 文件与用例名**必须真实存在**（挂空守卫 = 假收口） |
| 节点锚的是**分歧/缺陷** | `verify` **或** `repro` | `repro` 同时是**重开条件**；缺陷的"重复"用 `dropped` + 理由指向那条，**不许用 `superseded`** |
| **文档 / 裁决类**（无守卫可挂） | `done_reason` | 例：本仓「ヘタレ 命名复核」就是裁决类收口 |
| **不做了 / 不是缺陷** | `status: dropped` + `dropped_reason` | **禁静默关单**：理由要写"为什么不做"，不是"做完了" |

★ **守卫要红得有意义**：挂上去之前先问"它会不会因为这个能力坏了而红"。
★ 收口凭据**一起写实**，不要让节点停在"判据（待写）"——那等于没有收口标准。

## 4. 两条硬不变量 + 预算（agent 最常撞的两堵墙）

* **父不先于子**：`父 done ⇒ 子树里不许还有 open / doing / blocked`。
  ⇒ "父能不能关"永远先看 `plan` 那一行的聚合状态（形如 `[10/12]`）。
* **预算**：单节点 ≤ 80 行、**活节点**（`open`/`doing`/`blocked`）≤ 40。超了**不要放宽**，先问：
  "这一层是不是塞了本该更低层、或本该进知识台账的东西？"⇒ 往下拆新节点。
  （两个数都在 `--describe` 里，改预算＝改模型里的 `BUDGET`。）
  ★ **收口的 `done`/`dropped`/`superseded` 不占预算** —— 预算是给"还要人读它才能推进"的待办表设的；
  若把历史也数进去，树会因为"做过的事变多"而爆预算、逼人删掉**已经交付的**记录
  ⇒ 所以"拆一个节点出来"不该先付两个已完成节点的代价。

## 5. 五种常见局面的处置（都附本仓真实先例）

1. **想关但子树还有活的** ⇒ 逐个子节点判断：
   * 还该做的 ⇒ 补判据 / 挂守卫做完；
   * "将来可能做"的 ⇒ ★ **降级**：把它 drop 掉，另开一个**轻量跟踪单**放在正确的父下，理由指向新节点
     （先例：`AGERC.DLL 自建链` 工程节点 → dropped，改由挂在「翻译更新」下的**可能性跟踪单**接管）；
   * 纯阅读便利、不构成交付物的 ⇒ drop 并写明"它为什么不再需要"
     （先例：**旧式注释层** —— 新模型下原文/说话人/页边界都由视图现算，判据里 3 条已失去意义）。
2. **判据是「待写」** ⇒ 先把判据写实（能力 → 落点 → 守卫 一张表），再谈收口；
   四件能力各自有守卫时，父的 `verify` 挂其中最关键的那条，其余写进判据表正文。
3. **"无守卫可挂"** ⇒ `done_reason` 写**裁决本身**（含依据与边界），不要写进散文。
4. **发现守卫名不副实**（挂了个不会红的用例、或断言的是当前数据取值）⇒ 开 **`bug`** 单，
   `repro` 写成**反例**（能证明分歧还在的那个用例 / 命令）。
5. **一件事横跨多个父** ⇒ 别复制节点：放在**最该负责的那个父**下，在别处只在正文里写"由 X 跟踪"
   （先例：AGERC 的可能性跟踪单挂在「翻译更新」下，工程节点已 drop）。

## 6. 不许做的事

* ❌ 手改 `data/requirements/*.md` / 改 ULID / 改文件名（写路径只有模型那一条）；
* ❌ 把 `repro` / `severity` 写到 `req` / `spike` 上（缺陷专属字段，守卫会红）；
* ❌ 用 `superseded` 表示"重复"；
* ❌ 把进度 / 完成清单写进 README / CHANGELOG / 散文；
* ❌ 用"放宽预算"或"删节点"来解决超预算（先拆层，或滚去知识台账）；
* ❌ 静默关单（`dropped` 无理由、`done` 无凭据）。
