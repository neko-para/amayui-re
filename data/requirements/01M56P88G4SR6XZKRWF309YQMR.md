# S2r · 函数指针 may-set 调研结论 + **G15**（索引访问↔非数组成员）+ 分派表数组化 + 3 处模型缺陷

## 一、调研结论（只读，产物 `.tmp/shape/fnptr/`）

1. **may-set 能机械求，但写侧/读侧不同**：全语料 2,374 行含 `offset sub_`，其中代码写入/传值点 **629**
   （549 `imm-store` + 73 `push` + 2 reg-load + 3 栈槽 + 1 fill-init + 1 `rep stosd`），**索引形式写入 = 0**，
   其余 1,746 条是数据段静态初值（280 个 vtable）。落进容器的只有 549 条 imm-store + 1 次 1024 元素 fill
   ⇒ **(容器,K) 组 550，may-set 唯一 1024/1024（元素级）、多值 0、空 0**；544 槽被写两次（打底+覆写），按写序合成仍 1 值
   ⇒ **多态在索引，不在目标集**。
   读侧：6,293 处间接转移只有 2,953 落到槽、705 有类型；150 个被 `call` 的槽（38 个是 vtable 指针槽）里
   **只有 2 个有立即数静态写**，110 个没有，其中 **45 个是"值来自寄存器"**（例：`T_Command+0x5ec98` ← `GetProcAddress` @`0x415a88`）。
2. **op 分派表 1024 项全部解出（`unknown = 0`）**：544 `immediate` + 480 `loop`（默认 `sub_418E30`）；
   544 个不同 handler，`sub_419690` 占 opcode **175 与 424**；覆写是 **12 段连续区间（1..850）**。
   下标来源分两类：544 条**逐条字面位移**（最高可信），480 条来自 `rep stosd` + `mov ecx,400h`（次一档，
   被 3 处 `cmp reg,400h` 与端点 `0xa609c` 交叉验证）。**无一项来自寄存器**。
3. **为什么漏审（三层叠加）**：3 个索引读 `abs=0xa509c ⚠ index` ⇒ `index-unresolved` ⇒ 全进「位移不可用」桶，
   **0 红 · 0 残差 · 0 成员解释**。★ **(a) 与 (b) 同时成立**：`0x411a66` 的 `sub_411900` **零载体**（连桶都不进）；
   `0x412843/0x413464` 的 `sub_412290` 有载体 c97，进的是 `indexUnusableEAs`（24 处之一），不在 `residue`（41 处）。
   **该管却管不到**：G2 在入口就被剔、G3/G4 因离散内联成员永无 `type+count`、G7 只管 `kind:"ptr"`
   ⇒ **是"索引未解析"这个桶把它藏的**，表示法是结构性帮凶。
   ★ 反事实：**只把 `0xa509c` 改成数组，`findings` 仍然 = 0** ⇒ 光改表示法不够。
4. **4 条 local 载体**：`reg` 一次都没被 `call reg` / `call [reg+K]` 用过（**0/4**）⇒ may-set = **可证空集 ∅**（不是"未知"）；
   但 l01/l02 的 pointee 有 `T_5c73c_0+0x20` / `+0x30` 两槽被 call 且**零立即数写** ⇒ 那两槽只能到"未知"。
5. **表示法裁决**：**形态进模型，取值是派生视图**。
   · `targets:[...]` 进成员字段 ⇒ **两道守卫都不响**（违反口径却不会红 ⇒ 最危险的写法）；顶层 `opcodeMap` 被词汇守卫红；
     `kind:"fnptr"` 被 G8 红。
   · `opcode → handler` 只作**派生视图**（`.tmp` 或 B 层 `data/ledger/`），**永不进 `types.json`**。

## 二、本轮落地（工具 + 类型）

1. **新义务 G15**（`shape claims`）：对每个"带未解析索引"的站点，
   · 落在**数组**成员上 ⇒ note（"索引本身不可判，但形态已被数组承住"，⛔ 不算通过）；
   · 落在**非数组**成员上 ⇒ **逐条点名 EA**（"这些成员应当声明成数组"），当前 **note 级**（⛔ 不算通过）；
   · 位移 0 + 未解析索引 / 未声明偏移 ⇒ 跳过（留在「位移不可用」桶）。
   ★ 当前它是 **note 级**而不是红：全模型 100+ 处命中、多数是还没建完的类型表；先"可见"、后"翻红"（见本单"重开条件"）。
   守卫 ★㉒ + 变异 1 条（拆掉 G15 ⇒ 当场红）。
2. **分派表数组化**：`T_Command+0xa509c` 的 **544 条离散内联槽** ⇒ 改 **1 条 `{off:"0xa509c", type:"T_fnptr4", count:1024}`**
   （`T_Command` 成员 965 → **422**）。G15 现在对 `c97` 报"24 处索引访问落在**数组**成员上"。
3. **G15 的命中分布**（24 条 note）：大部分是"索引 + 未声明偏移"，其余点名的是真缺口（如 `T_FileDB+0x3c48`
   —— 它正是 S2m 那条被 G4 挡住数组化的成员）。

## 三、调研发现、**只登记未改**的 3 处模型缺陷

| # | 事实 | 影响 |
|---|---|---|
| ① | `T_Command+0xa537c` 是 544 条覆写里**唯一没标 `name:"fnptr"`** 的纯内联成员，却**被 call**（`0x4165ce` 写、`0x428a6a→0x428a71` 读调） | 它现在落在新数组窗口 `[0xa509c,0xa609c)` 内 ⇒ **被数组吸收**；数组化后需确认"它能被解释" |
| ② | `T_Command+0x1fc4..0x1fd0` 有 4 条**条件**代码地址写（`sub_417800`），而 `T_Command` 在这 4 个偏移上**没有任何成员** | 这 4 处现在是 `c113` 的残差（`sub_417800` 的 this = `T_Command`） |
| ③ | `T_Sys3Draw` 成员坐标（`0x1f7c..0x29f4`）与它内嵌在 `T_Command+0x1ee8` 的声明**不自洽**（`0x1fc4` 应为 `T_Sys3Draw+0xdc`，而 `0xdc` 不是成员） | ②③ 必有一处错框：要么那 4 个偏移属于 `T_Sys3Draw`，要么 `sub_417800` 的 `this` 不是 `T_Command` |

## 四、重开条件（G15 从 note 翻成红）

1. 把 G15 的"落在非数组成员上"从 note 改成 **red**；前置：上面 3 处缺陷 + `T_FileDB+0x3c48`
   （G4 挡住的数组化）与其余点名项都有裁决。
2. 索引解析能力提升后（例如给 opcode 寄存器加 `local` 载体），G15 应能进一步比**索引范围**与 `count`。
