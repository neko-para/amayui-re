# spec 证据去 emulator-new 化：把只挂冻结参考实现的规则重锚到 emulator-cxx

## 背景

`apps/emulator-new` 已按用户口径废弃（与 `apps/emulator` 同级只读遗产，见 `AGENTS.md` §11）。
但 spec 侧有一个遗留依赖：`data/spec/bindings.json` 里有 **103 条规则**的 `evidence` 挂着
`guard:tools/test/emulator-new-*.test.mjs`，其中**多数没有第二条证据**。

## 为什么这是个问题

冻结件仍可执行（`pnpm test` 照跑），所以这些证据**形式上仍解析得到**、`pnpm tools spec validate` 也绿。
但它们锚的是一个**不再维护的实现**：

- 规则演进时，这些测试会红 —— 而红在冻结件上，两条路都难受：改冻结件（解冻）或删证据（掉档）；
- "第二实现能证伪第一条"的价值，前提是第二实现**独立**。两套实现都必须跟着 spec 走时，它只是第二份要改的代码。

## 判据

- **新规则**：`evidence` 优先挂 `apps/emulator-cxx` 的**顶层 CTest**；`emulator-new` 的用例只能当辅助、不许当唯一。
- **既有规则**：保持原样（不因为这条单去批量删证据、也不批量改测试）。
- 迁移完成一条 = 该规则有**至少一条** `apps/emulator-cxx` 的顶层 CTest（或 accepted 台账）证据 ⇒ 才可摘掉 `emulator-new` 那条。

## 下一步

1. 先只统计（不猜）：按 `evidence` 里"是否只有 emulator-new"分组，给出条数与规则 id 清单。
2. 挑**已被 C++ 实现覆盖**的族先迁（`CORE-OPS-TEXTURE-*` / `CORE-OPS-SCENE-*` / `CORE-VM-*` / `CORE-TIMING-*` 这几族最可能已有 CTest）。
3. 每迁一条：加/确认 CTest 断言 → `pnpm tools spec validate` → 再改 `evidence`。⛔ 不许先删证据再补测试。

## 不要做

- ⛔ 不改 `apps/emulator-new/**` 与 `tools/test/emulator-new-*.test.mjs`（它们是冻结件）。
- ⛔ 不为了让 `validate` 绿而删 `evidence`（那是掉档，不是迁移）。
- ⛔ 不把这条单当成"必须马上做完"：它不影响当前 spec 的正确性，只影响**将来改 spec 时的手感**。
