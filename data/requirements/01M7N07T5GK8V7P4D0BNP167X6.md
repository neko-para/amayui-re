## 一句话

真 feeder 线程落地后**平均能跟上**（90 s 转场 run：186 刀 fill、`underruns=2`），但**最坏一刀 1.0 s**
（`fill_max_ms=1016.04`、`fill_slow=1`）⇒ 那两处各插入 ~0.32 s 静音（`underrun_silence_bytes=124672`）。
⇒ 需要按 EA 归因这一刀，再决定优化什么；⛔ 不要先优化再找证据。

## 读数（2026-11-17 / mac arm64 M3 / `links/raw` / `prefix27` / `LIFT_D3D9_PS_VERSION=0x200` / `--audio sdl --sound` / 90 s）

```
fills=186  fill_bytes=15561900  pushed=17304320  played=17285120  notify=186
underruns=2  underrun_silence_events=2  underrun_silence_bytes=124672
fill_max_ms=1016.04  fill_slow=1  fill_overlapped=5  fill_wait_timeouts=0
audio-pump: calls=0 fills=186 … feeder=host-thread lead=19200 dev_frames=1024
```

- 平均：90 s / 186 刀 ≈ **484 ms 一刀**（≈ 每刀 0.5 s 音频 ⇒ 平均利用率 ~95–100%，没有余量）。
- 最坏：**1.0 s 一刀**（≈ 实时 2×）⇒ 那两刀就 underrun。
- 对照：解释器时代的旧读数 **200–250 ms/刀**（含 per-EA native override，已退役，`REQ-01M75PTEGCR1Y91FKKJ1CWPNH2` 是 dropped）。

## 要做什么（先测量）

1. **按 EA 归因那一刀**：feeder 线程上的 guest 执行没有 per-thread profile（AOT 的 `--profile` 是整跑聚合，且只给主线程）。
   两条便宜的路：① 用 `t_shim_token_wait_ns` / `fill_max_ms` 的现有读数先确认"是不是卡在 shim 令牌"；
   ② 给 feeder 的 fill 加一条 opt-in 的"分段计时 + 最贵 3 个 EA"（工具改动，缺省关）——另开或并入 profile 工具单。
2. **区分两种原因**：① 这一刀本身 decode 重（Vorbis IMDCT/floor/`__ftol2_sse`）；② 主线程同时在重计算（转场段）⇒
   feeder 与主线程抢核 / 抢 guest 令牌（`fill_overlapped=5` 是线索）。
3. **判据**：120 s 转场 run `underruns=0`，或至少 `fill_max_ms < 500`（= 单刀不超过它要产出的音频长度）。

## 未做
