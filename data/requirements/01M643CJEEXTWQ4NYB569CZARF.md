# 纹理记录与纹理槽在模型里合成一张表（0x1fa 删记录，spec 说保留记录只清槽对象）

- parent: REQ-01M5BK8QMQYK7XQG707YVMQ202

## 分歧（实现 ≠ spec，可观察面恰好等价）

spec 的 `0x1fa`（「释放纹理：opcode 0x1fa」）说得很具体：

- 先清**共享对象槽**里该 id 的对象（不受释放守卫影响）；
- 释放守卫为 0 时：把**纹理记录的来源文件写成"无"**、清**纹理槽里的对象**（释放平台纹理）；
- ★ 记录本身**保留**（颜色键等字段不动），所以「空槽 ≠ 空白纹理」是两种状态。

我们的模型把「纹理记录」与「纹理槽」**合成一张 `textures_` 表**，`0x1fa` 直接
`textures_.erase(id)` 把记录整个删掉。

## 为什么现在才发现

可观察面上这一步恰好等价：`0x208`（查询尺寸）在"槽为空"时就返回 `0/0`，记录在不在都一样；
`0x1f9` 重载会整体替换记录。所以语料侧与现有 CTest 都看不出差别。

## 它导致的真实缺陷

删记录 ⇒ 同一编号重建时版本号从 **1** 重来 ⇒ 窗口路径的 GPU 纹理缓存按 `(id, revision)` 命中，
把上一条记录的纹理当成当前纹理 ⇒ **设置界面 ↔ 初始配置界面互相污染 / 整张美术图不画**
（缺陷单 `REQ-01M642804D7FRDHYFFRZ03C9ZH`，已修：加了"每个编号的版本号下限"）。

## 还要做什么

1. **把记录与纹理槽对象拆开**（或至少让 `0x1fa` 保留记录字段：来源文件改成"无"、像素/对象清空，
   `color_key` / 空白标记等按 spec 保持原值），否则下面这条会错：
   `0x1fa` 释放 id → `0x1f8` 空白创建：spec 要求**颜色键与记录里其它字段保持原值**，我们删过记录 ⇒ 全丢。
2. 拆开后重新核 `0x208` 的"槽空 ⇒ 0/0"（记录在但槽空），并补一条守卫。
3. 版本号下限的守卫已在 `core_selftest` 里（`0x1f8`→`0x1fa`→`0x1f8` 断言 `revision > 1`），
   拆表后要保证它仍然成立。
