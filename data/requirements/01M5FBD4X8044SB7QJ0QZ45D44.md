# spec：未成篇 opcode（约 489）的义务落点与 report 计数必须一致（现在"缺口 0"是假象）

## 问题

`60-ops.md:7` 说"其余指令尚未成篇"、`audit.json` 的章级残差 `RES-OPS-UNWRITTEN`（`kind=unhandled`）也承认"指令表里仍有处理函数的 opcode 尚未成篇"。按指令表口径：**544 个**有 handler 的 opcode 里只有 **55 个**出现在规则里 ⇒ **约 489 个未成篇**。但：

- `pnpm tools spec report` 打印「残差 unknown=115 · **unhandled=0**」「审计缺口 **0** 个」，`audit.gaps = []`；
- 三处文档对"未成篇的义务该落哪里"说法不一：`data/spec/README.md:74` 说 `gaps[]`、`audit.md:38` 说 `pilot.residuals`、而实际只记在章级残差。

⇒ "缺口 0"读起来像"做完了"，而真实未成篇义务是**数百条**。

## 要裁决/要做的

1. 定**唯一落点**（推荐 `audit.gaps[]`：一条一个 opcode 族/条，`note` 写为什么没写 —— 它本来就是"尚无规范条目的义务"表），删掉另外两处说法。
2. 让 `spec report` 把这类义务计入（`unhandled` 计数或单独的"未成篇 opcode"计数），使"缺口 0"名副其实；或把报告改为显式打印两项。
3. 生成初始 `gaps[]`（可从 `format/opcode-table.json` 的 544 条 hasHandler 减去已写规则自动派生；**派生不是手写**）。
4. 判据：`spec validate` 13/13 + 新增一条会红的守卫（例：`hasHandler` 数 − 已写 opcode 数 ≠ gaps 条数 ⇒ 红）。

## 出处

第四轮 spec 复核 S1-⑤；数字与坐标见 `docs/02-engine/spec-review-4.md`。
