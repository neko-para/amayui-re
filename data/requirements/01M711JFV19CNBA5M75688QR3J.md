## 判据（存在性 + 观测）

`REQ-01M6XVZG4T9WY8SQ1WS7P8RNW9`（令牌等待）收口时用 31 遍实测给出的**新基线**：

| 工况 | `--audio off`（默认口径） | `--audio sdl`（feeder 在跑） |
|---|---|---|
| 空转（295 帧） | `waits 0 / wait 0.0 ms`（6/6 遍） | `wait/wall = 5.06 / 5.15%` |
| 进房间（300M 条） | `waits 0 / wait 0.0 ms`（8/8 遍） | **16.6 / 17.5 / 19.8%** |
| 出房间（480M 条） | `waits 0 / wait 0.0 ms`（7/7 遍） | `11.5 / 12.1%` |

- 默认口径的 0 是**结构性**的：令牌只有"主线程块边界 + 音频 feeder"两条取用路径 ⇒ 音频关掉就没有竞争（未竞争连时钟都不读）。
- 开音频时等待真的存在，且**进房间那一段最重（≈1/5 墙钟）**；但 `avg` 在 324–2017 µs 之间跳、样本 N=2–3 ⇒ **要知道它值不值得修，先得 N≥8**。
- ⚠ 载荷帧本身的主成本**不是** shim：`guest 50.4% + interp 31.1%`（解释执行 81.5%）vs `shim 1.06%`（`fr110-111` 窗口，wall 5022.3 ms）。
  ⇒ 本单的收益上限是"墙钟的 5–20%"，**不是**把装载帧从 5 s 拉到 1 s。

## 要回答的三件事

1. **把等待归到帧**：`tokenwait` 今天是**整轮一档**（进程级 `GuestToken`）⇒ 只能按块边界比例推断。要排序"三类阻塞型宿主等待"
   （Present / 音频 `mutex_` / 文件 IO `fread`）必须新增**按窗口的等待账**（与 `WindowProfiler` 同生共死，口径照 M1）。
2. **N≥8 排序**：拿窗口级等待账排三类；⛔ 不要用整轮数字排序。
3. **只对排在首位的那一类做让出**（`yield` 前必须复核 `guest_token.h` 自己的取/放规则；先例是 OBS-15 的 shim 边界令牌）。
   ⛔ 不改并发契约（那会回到堆损坏）；⛔ 不动音频线程模型。

## 判据（若开做）

- A/B：同一脚本、同一窗口、N≥8，`wait/wall` 下降且**其余分桶不变**；`--assert-guest-token` 仍 `violations=0`、`guest_token.cpp` 全绿、
  进出房间的终态像素不变。
- ⛔ 不许用"放宽令牌"换速度；⛔ 不许把等待记进别人的桶（口径一致性是 M1 已经修好的东西，别弄回去）。
