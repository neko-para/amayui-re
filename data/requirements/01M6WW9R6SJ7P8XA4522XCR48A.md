## 表 2 · 原因 → 进程退出码（`main.cpp` 的出口顺序）

| 顺序 | 条件 | 退出码 |
|---|---|---|
| 1 | guest 令牌违规 | 4 |
| 2 | `--gpu-strict` 且 `!ok()` | 2 |
| 3 | GPU 无后端 / fallback | 3 |
| 4 | 交互任务未 `task done` / `InteractionFailed` | 5 |
| 5 | `exitCodeForRun(r)` = `ok() ? 0 : 2` | 0 / 2 |

⇒ 资源耗尽与 `Trap` 今天都是 **2**（改动前都是 `Stopped` ⇒ **0**）；交互图下仍是 5（该闸门更早）。

## 表 3 · 裁决（2026-11-09：**要**，B 案）

- 判据成立：两族都在 `stop_why` 里写了真因，只有 `RunResult.ok()` 不知道 ⇒ 任何"只看 exit code"的流水线会把
  我方容量失败 / 槽没实现当成成功。**不合并**成一个原因：两者修法不同（容量 vs 补实现），合并会接回 BUG-02 刚分开的误诊链。
- 改动只落在「枚举 + 置位点 + 汇入点 + 名字 + 退出码映射」；⛔ 未动 `GuestLayout` / `heap_.init` 尺寸 / arena 容量 /
  shim 返回值与参数语义 / guest 可见地址。
- 消费者实测：读退出码的 4 个 CTest + gpu-strict `WILL_FAIL` + smoke **期望一处未改**（它们不在这些场景期待 0）；
  进程内断言改了 6 处（`Stopped` → `Trap` + `!ok()`）。
