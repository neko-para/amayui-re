# emulator-lift · TITLE 往返后的一次性 +2 surfaces / +1.3 MB：判「预期缓存」还是「真残留」（两种结局都落结论）

## 已知（父级验收实测）

进 OPTION → 右键回 TITLE 之后，相对 TITLE 静止态多 **+2 surfaces / +1,299,856 B**；而 1 / 2 / 3 轮往返的
读数**完全相同** ⇒ 这个增量**不随轮数增长**，与刚修好的那条泄漏（每轮 18,077,080 B）不是同一件事。

## 判据：给结论，两种结局都写

**观测法**（同一份安装 + 同一份 appdata，三次**独立子进程**，脚本终点都是"回到 TITLE 之后"）：

| 跑法 | 目的 |
|---|---|
| 0 轮：进 TITLE 后原地等到同一帧再 `quit` | **基线** = TITLE 静止态 |
| 1 轮往返 | 一次往返后的增量 |
| 2 轮 / 3 轮往返 | 增量**还长不长** |

- 比的是 run summary 的 `arena     : surfaces N in_use U peak P largest-free F` 行，逐字段。
  基线 → 1 轮 = 那 +2 / +1.3 MB；1 → 2 → 3 = 增长项。
- ★ 现在**没有 0 轮基线**：既有用例 `repo:apps/emulator-lift/tests/option_roundtrip.cpp` 只让 1/2/3 轮互比，
  所以它证明的是"不增长"，**证明不了**"第一轮的 +2 是一次性缓存"。这两句话必须分开说。
- **结局 A（一次性缓存 / 惰性装载）**：若 2 轮 == 3 轮 == 1 轮，且能点名那两张 surface 属于哪个对象 /
  哪次装载（候选：TITLE 惰性装载、跨屏缓存）⇒ 把它写成**预期行为**，落点 = 那条用例的文件头
  （"一次往返后基线多 2 面 / 约 1.3 MB，之后每轮 +0"）+ 本单 `done_reason`。
  ⛔ **不要**把它修成 0 —— 那是改引擎的缓存策略，不是在修缺陷。
- **结局 B（真残留）**：若 2 → 3 轮仍在涨，或那两张面所属对象**引用已归零却没有回收** ⇒ 转一条 `bug`
  （`repro` 挂那条能红的用例），并把面 / 对象点名到具体分配点。

## 为什么现在不做

它是**观测结论未定**，不是已确认缺陷：每轮 18 MB 那条已经归零，剩下的 1.3 MB 不随轮数增长、也不妨碍
继续进 OPTION（同一组实测 3 轮都跑完了）。现在把它写成缺陷，等于让下一个人去"修 1.3 MB"，
而它很可能正是引擎本来就会做的事。

## 现在绕到了哪里

- 门禁只看"不增长"：1/2/3 轮互比 + 1 MiB 容差（那条用例的判据 ④）⇒ 一次性项**被容差吸收**，
  既不会假红，也不会被发现。
- 所以本单的产出**不是代码**，而是一段能复跑的观测 + 一句写进用例文件头的"预期"。

## 边界

- ⛔ 不用"调大容差"或"调大 arena"把它盖掉。
- 终点必须都是"回到 TITLE 之后"：终点不同就没法比（TITLE 静止态与 OPTION 屏的工作集本来就不同）。
