# emulator-lift · sub_48B090 native override 破坏纹理/渲染

## 现象

用户实测：启用全部 native override 后**渲染坏掉**；只关掉 `sub_48B090` 就恢复正常。
已复现为可观测分歧，不是视觉错觉：同一 boot、同一虚拟时钟、300 帧：

- 关闭 `sub_48B090`：300/300 帧 hash 与 no-override 基线完全一致。
- 注册 `sub_48B090` 的 native 8bpp→32bpp fast path：第 **2** 帧起出现 hash 分歧
  （`0x765FC242A26FBA6B` vs `0x0C41812AF9164191`；后续 49/300 帧不同）。
- 另一次启用 8/24bpp 的变体在第 **47** 帧出现 RGB `max=1` 的 698,877 像素差异
  （BMP 的 RGB 只差 1，但 `Present` hash 不同，说明纹理/alpha 状态被改写）。

## 当前处置

- `sub_48B090` **已从 known 表撤下**，不再能被 `--native-overrides all` / 显式名字启用；
  `--native-overrides _memcpy,...,sub_436A80` 的 300 帧与基线 0 差异。
- 原型代码（`nativeUpload48B090`、嵌套 `Create`、`convertPal8To32`/`convert24To32`）保留但**未注册**。
- 因此 boot 加速回到 LZSS/CRT 档（首帧 12.68 s），不是 7.67 s。

## 已知线索

- 第 1 帧 hash 完全一致，说明 Create/读回/基本格式没崩；分歧在后续帧的纹理内容。
- 8bpp alpha=0、key=0 的最小路径也会在第 2 帧分歧（1 native call / 6 fallback）。
- 24bpp 变体在第 47 帧只差 RGB 1 LSB；更像 alpha/调色板/行序/字节序的细节，
  不是“整张图错位”。
- 需要逐像素比较 **纹理 arena**（不是 BMP；BMP 丢掉 alpha）以及 `TextureInfo` 的
  pitch/format/alpha 语义，再决定修 8bpp 还是直接弃用该 override。

## 重开/验收

1. 重新注册后，300 帧 CPU vs override hash 0 差异（或按 SCOPE 登记的可接受预算）。
2. 至少覆盖 8bpp（alpha 0/非 0）和 24bpp 的纯 fixture。
3. 修复前保持 known 表不注册；默认关闭。
