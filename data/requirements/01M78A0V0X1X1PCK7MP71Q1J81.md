## 现象

手工跑 `graphs/sn0000-quit.graph` 3 次，**1 次**在 step3 `await script GAMESTART` 处超时红：

```
node     : step3（node 行 7 = await script GAMESTART）
window   : frame 1..49   样本 48   timeout=5000ms(default)
detail   : 条件在窗口内一次都没成立
```

点击（`click 1186 373`）发生在 **frame 0**；窗口内**帧在推进**（到 49），只是 `GAMESTART` 一次都没出现。
CTest 的 4 臂（`quit-graph` a/b × 2 遍）**未复现**。

## 判断（不是"慢"）

不是时间不够：帧在动、GAMESTART 完全没出现 ⇒ 更像**首次点击丢失**（frame 0 时窗口 / 输入队列 / 消息泵尚未就绪）。
⚠ 因此**⛔ 不许用加大 step3 超时来变绿** —— 那会把偶发输入竞态藏成"慢机"，与 `REQ-01M786CQP4JT8D7CSJ64NG6KYC` 里
"`save-graph`/`quit-graph` 是超时不足"的裁决**不是同一类**（那两条已用 trace 的 guest_ms 差证明是有限长活）。

## 要做

1. 取证"frame 0 的 click 被谁丢了"：`InputScript` 的排队/落点、窗口是否在 frame 0 已建、消息泵是否已起；
   给"点击被记录但没人消费"与"点击压根没记录"的**判别证据**。
2. 按取证结果修（可能是"frame 0 的输入延到首个 Present 之后再投递"，也可能是图脚本不该在 frame 0 点）。

## 判据

- 同一图**连跑 10 次 0 次红**（`ctest -R quit-graph` 或直接跑 exe，记录每次结果）；
- ⛔ `step3` 的超时**仍是缺省值**（不许借超时变绿）；
- 若取证结论是"图脚本写法问题" ⇒ 改图并说明为什么这是脚本侧而非引擎侧。

## 反证条件

- 若在 frame ≥ 1 点击也复现 ⇒ 改判为交互图 tick / 输入注入的竞态，不是"首次点击"。
