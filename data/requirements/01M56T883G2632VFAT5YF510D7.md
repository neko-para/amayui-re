# S2z · G3 比"最内层那个数组"的元素大小 + 判红时守恒① 仍自洽 —— 已落

## 踩到了什么

新并入 30 条载体后冒出一条红：

```
- G3 b14-20 @0x4116ba：数组形态步长 4 != size(T_CBunki)=29928
- 守恒①：7935 != 7581+353
```

两件事同源。站点是 `0x4116ba mov eax,[esi+eax*4+5D04h]`：`0x5d04` 落在 `T_Command+0x55d8` 那块
`T_CBunki(count:1)` 的跨度里，元素内偏移 `0x72c` —— 而 `T_CBunki+0x72c` 本身是 `T_el32×100`。
旧判据拿"步长 4"去比 `size(T_CBunki)=29928` ⇒ 假红；而那条 `red(...); continue;` 又把站点从
**守恒①** 的等式里弄丢了（`explained + residue` 少一个，等式当场不成立）。

第二个坑：G3 的检查原来写在 `elemOff !== 0` 那支里 ⇒ **第 0 个元素 + 真数组**（`[esi+edi*4+2000h]`）
永远不校验（合成用例实测：一条红都没有）。

## 修法

1. G3 比的是**最内层那个数组的元素大小**：
   `innerArray`（`leaf` 自己是数组时用 `leaf.type` 的 size）优先，
   否则**只有当 host 是真数组**（`count == null || count > 1`）时才比 `size(host.type)` ——
   `count:1` 是**内嵌子对象**，与"步长"无关。
2. 检查移到 `elemOff === 0 / !== 0` 两个分支**之外**。
3. 判红时**照样记一条残差**（`数组步长与元素大小不匹配（见 G3）`），守恒① 因此恒成立；
   G2 的"宽度超声明"同理。

## 守卫

- 用例：`tools/test/shape-claims-guards.test.mjs#★㉗`（两个分支都覆盖：内嵌子对象里的索引访问要**解释** ·
  真数组步长不符要**红** · 且断言 `守恒①: obj0Acc === obj0Explained + obj0Residue`）
- 变异：`G3 不再对"真数组"校验元素大小`（113 → 114 条，全红）
