# 0x82 的颜色看起来是「借用后归还」，spec 与模拟器都写成永久写

## 分歧（待逐支确认）

`0x82`（`sub_41F720` 的 handler）调用 `sub_466000`；后者在 **`0x46643C`（主色）/ `0x466460`（副色）**
把第 4、5 个操作数（字节反转后）写进字体对象的两格颜色，并在**同一次调用内**、尾部
（`0x467371` 写 `+0x554`、`0x4673E1` 写 `+0x550`，每次写后 `call sub_459F40` 重建字体）
把**保存下来的旧值写回去**；是否恢复由两件事之一触发：`var_FC != var_134`（旧值 ≠ 当前值）
**或** `var_C0 != 0`。而 `var_C0` 就是在 `0x46641D` 记下的"本次调用要覆盖颜色"那个标志
（同一个 `jz` 跳过 0x46643C/0x466460 的写入）。

⇒ 二进制的样子是"**借用颜色 → 画 → 归还**"，不是"永久改字体颜色"。

## 现状

- spec `CORE-OPS-TEXT-SPAN`（`data/spec/chapters/60-ops-text.md:113` 的状态对应表）写的是
  「两格色格 ← 字节反转后的操作数（仅当第 3 个操作数位 1）」，**没有"借用/归还"**；bindings 也只绑了
  两个写点（`0x46643c` / `0x466460`），没有绑恢复点。
- 模拟器（`apps/emulator-cxx/src/core/vm_ops_engine.cpp` 的 `op_82`）照 spec 实现 ⇒ **永久写**。
- 可观察分歧：一条带颜色的 `0x82` 之后，任何"不吃颜色实参"的绘制（例如 `0x204`，它的颜色来自字体对象）
  会用**残留**的颜色画 —— 真机不会。

## 为什么先开单不改

要改就得同时定三件事，缺一个就会写出第二个错实现：
1. 恢复**无条件**还是"旧值 ≠ 当前值 / 借用标志"两条件之一（`0x4673C8` 那段的两个判据到底哪个是主判据）；
2. 恢复发生在**绘制请求之后**还是**之前**（我们这条路径是"追加绘制命令、稍后消费"，颜色要在追加时就定死；
   真机是同步画完再归还）；
3. `var_C0` 之外还有 `var_F8` / `var_F0` / `var_F4` / `var_FC` / `var_134` 一组保存值 —— 它们是同一批字段的
   旧值快照，逐支读完才能确认"哪些字段被借用、哪些是永久写"（`+0x558` / `+0x55C` 也在这一组里）。

## 下一步（可判定）

1. 逐支读 `sub_466000`（起点 `0x466000`）里 `var_C0` 的置值与所有 `[ebp+var_F*]` 的比较，给出一张
   "字段 → 借用/永久"表。
2. 按那张表改 spec（状态对应表加"临时覆盖并在本条返回前恢复"），bindings 补恢复点 EA。
3. 实现：`op_82` 在追加绘制命令时把颜色**快照**进命令（不依赖字体对象后续状态），并恢复两格；
   守卫：一条带颜色的 `0x82` 之后紧跟一条 `0x204`，断言后者的颜色 = 覆盖前的值（现在是残留值 ⇒ 红）。
