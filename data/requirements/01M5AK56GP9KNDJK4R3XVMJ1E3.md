## 目标

`CORE-VM` 复杂度高（主循环是**多层嵌套 while** + 引擎上有大量状态标记），若直接写条目会堆成一大坨。
本单只做**浅层扫描**，产出"怎么拆"的依据；⛔ 不写规范条目、不改 `data/spec`。

## 扫描范围（只读，不落规范）

1. **主循环骨架**：嵌套层数、每层的退出条件、每层的输入（帧? 场景? 输入? 计时?）；
   每层的判据字段各是哪个（EA + 字段偏移）。
2. **状态标记清单**：主循环里读 / 写的引擎标志位（`Engine+X` 或帧字段）；
   每个标记：谁写、谁读、控制哪条分支。这是"状态机"的候选边界。
3. **等待门 / 帧推进**：主循环里"等一帧"的机制（等待条件、超时、输入事件是否参与）。
4. **入口到主循环**：谁调主循环、主循环怎么退出（EA）。
5. **建议拆分**：把 VM 拆成 2–5 个子机制（例：主循环骨架 / 等待门 / 状态标记 / 控制流原语），
   每个子机制给出：回答什么、闭集是什么、依赖谁、预计条目数。

## 产出（只写 `.tmp/spec-draft/core-vm-scan/`）

- `README.md`：扫描结论 + 建议拆分（子机制表）
- `structure.md`：主循环骨架（层级 / 判据 / EA），配一段可复述的伪结构（**不含语义结论**）
- `flags.md`：状态标记清单（名字 / 偏移 / 写点 EA / 读点 EA / 控制的分支）
- `feedback.md`（可选）：对机制地图 / 技能的质疑

## 判据

- 每个"主循环层"都有 EA；每个状态标记都有至少一个写点与一个读点（或明确"只写不读/只读不写"）
- 拆分建议能回答：**为什么这样拆**（按控制流层？按状态？），以及"条目会不会又堆成一坨"
