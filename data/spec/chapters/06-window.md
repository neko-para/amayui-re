## 启动期的平台请求：窗口、图形设备与事件入口

本章规定启动阶段（引擎取得控制权 → 主循环被调用）围绕**窗口**向平台发出的请求。它只记录**请求、参数、次序与失败后果**；Win32 / D3D 的内部实现与像素结果不在本章。窗口过程**大多数**消息的逐条处置也不在本章；本章只规定与启动、退出、定时器、输入转发、绘制、光标与系统菜单有关的少数类别（见「事件入口与消息泵」）。

窗口类注册之前，引擎还做三件不单独立条的事：创建**命名单实例信号**、装载**辅助宿主模块**、初始化 **COM**。它们属于启动前段；本章只在用到其结果的地方引用（图标 / 菜单资源来自辅助宿主模块，窗口类的实例仍是入口参数；见「窗口类注册」的残差）。

本章的请求顺序是：注册窗口类 → 创建窗口 → 首次显示 / 重绘 → 解绑输入法 →（仅窗口态）交接菜单并重画菜单栏 → 记录服务窗口 → 图形设备初始化 → 建立周期定时器 → 进入消息泵。
索引装载发生在**窗口创建之前**（见「启动入口」），根脚本装载夹在「图形设备初始化」与「周期定时器」之间；两者都不在本章重复。

### 窗口类注册

<!-- rule: CORE-BOOT-WINDOW-CLASS -->

引擎注册**一个**窗口类（ANSI 变体），不注册子类或工具窗口类。引擎选定的参数：

| 参数 | 值 |
|---|---|
| 类名 | 固定字符串 `ARCGameEngine` |
| 窗口过程 | 引擎**唯一**的事件入口（见「事件入口与消息泵」） |
| 实例 | **入口参数给的进程实例** |
| 大图标 / 小图标 | 同一个图标资源，按资源名 `IDI_ICON1` 从**辅助宿主模块**给出的资源实例取 |
| 光标 | 系统预定义的标准箭头（引擎传 `0x7F00`） |
| 背景刷 | 系统预定义的黑色实心刷（引擎传 `4`） |
| 菜单名 | 空（`0`） |
| 类附加 / 窗口附加 | `0` / `0` |
| 类风格 | 一个固定值（引擎传 `0x40`；位含义属平台侧，本规范不解释） |

- **注册失败**（返回 `0`）⇒ 走共享出口：**不显示任何消息**、不建窗口、不装载索引之后的任何东西。
- 类名同时是**创建窗口**时要用的类名（同一个固定字符串）；窗口标题与类名分开（见「窗口创建」）。
- 图标资源名与菜单资源号都是**引擎内建的常量**，不来自配置、也不来自脚本。
- 失败分支**没有**用户可见输出：这是与**索引失败**的区别（后者有消息；辅助模块的失败形状见残差）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 窗口类已注册 | 类名 → 窗口过程的映射已建立 |
| 未注册 | 无映射；启动结束 |

**成立条件**

- "一个类"是合同：本作只注册一个窗口类。
- 图标与光标都是**资源 / 系统项**，不是引擎自绘的位图：引擎不产生任何像素。
- 窗口类的实例与窗口的实例都来自入口参数（同一个进程实例）；图标 / 菜单资源来自辅助模块给出的资源实例：**两类实例不是同一个句柄来源**。

**残差**

- `RES-BOOT-CLASS-STYLE`（unknown）：类风格那一位（`0x40`）在平台侧选中的具体行为没有取证，本版只登记数值。下一步：真机对比该位取 0 / 取 `0x40` 时的重绘行为（若可观测）。
- `RES-BOOT-CLASS-ICON-FALLBACK`（unknown）：图标资源缺失时平台返回空句柄，引擎**不检查**；此后窗口图标处于未规定状态。下一步：真机替换 / 删除图标资源后观测窗口图标。
- `RES-BOOT-RESOURCE-INSTANCE`（unknown）：辅助宿主模块给出的资源实例（图标 / 菜单）从哪来、模块装载失败怎样处置，本版不规定；本版只把它当作一个外部输入句柄。下一步：把辅助模块的装载 / 三个导出作为「启动前段」单独立条。
- `RES-BOOT-CLASS-MODULE`（unknown）：辅助宿主模块的装载判据（固定文件名 + 三个导出都非空）与失败文本本版不规定；本版只用到它给出的资源实例。下一步：把该模块的装载 / 失败分支作为「启动前段」单独立条。

### 窗口创建

<!-- rule: CORE-BOOT-WINDOW-CREATE -->

引擎创建**一个**顶层窗口（类名 = 上一则的固定类名），随后**立即**请求"按入口给的显示方式显示"与"立即重绘"。

**形态判据**：屏幕形态字 `S` = 配置的屏幕形态值（`display:ScreenMode`；该键只在玩家文件词表里，缺键时按「配置」的配置库规则读成 **0**）；若配置的"强制屏幕"键（`display:ForceScreen`）恰为 1，则 `S := 1`，并把 `display:ScreenMode` **写成 1**（一次引擎级的配置写入，先于建窗）。然后 `S ≠ 0` 走**窗口态**，`S = 0` 走**占满屏态**。

**窗口态**（`S ≠ 0`）：

| 参数 | 值 |
|---|---|
| 客户区尺寸 | 引擎级缓存里的**客户区宽 / 高**（来源见「成立条件」：配置的 `set:WinX` / `set:WinY`，发行默认表里的 `SCREENX` / `SCREENY`） |
| 窗口尺寸 | 宽 = **客户区宽 + 2 × 边框宽**；高 = **客户区高 + 2 × 边框高 + 标题高 + 菜单高**（四类量都由**平台报告**，见下） |
| 位置 | 配置 `set:SaveWinPos` 非 0 ⇒（`set:WinPosLeft`, `set:WinPosTop`；两个**整数运行期命名键**（见「配置」的配置库：类型由写入方给出，缺键读 0））；为 0 ⇒ 平台的"使用默认位置"哨兵（`0x80000000`） |
| 风格字 | 固定值 `0x90CB0000`（位含义属平台侧） |
| 扩展风格字 | `0` |
| 菜单 | 从辅助宿主模块实例装载的**菜单资源**（资源号 110） |
| 父窗口 / 参数 | 空 / 空 |

**外框的四个量与两个公式**（仅窗口态）：窗口态向平台查询**四类**量 —— **边框宽**、**边框高**、**标题高**、**菜单高**。平台报告的边框宽 / 边框高是**单边厚度**；引擎按"左右对称、上下对称"的假设计算：

```
窗口宽 = 客户区宽 + 2 × 边框宽
窗口高 = 客户区高 + 2 × 边框高 + 标题高 + 菜单高
```

- **边框宽只进宽，边框高 / 标题高 / 菜单高只进高**：四类量各有各的落点，互不替代（把边框高当边框宽会得到不同的窗口）。
- 对称假设是**引擎的**：每类量只查一次，边框宽 / 边框高各乘 2；**不存在由平台自动换算外框的请求** —— 引擎不把客户区矩形交给平台、由平台换回窗口矩形。⛔ 若实现成"交给平台换算"，这四类量就一次也不会被查，与本条不符。
- 标题高**必须**进高：漏掉它，窗口（连同客户区）会比预期**矮**一条标题栏。
- 菜单高只在**有菜单的形态**下有意义：占满屏态不查任何一类量。

**占满屏态**（`S = 0`）：

| 参数 | 值 |
|---|---|
| 尺寸 | 平台报告的**屏幕宽 / 屏幕高**（不查边框 / 标题 / 菜单，也不做任何加算） |
| 位置 | `(0, 0)` |
| 风格字 | 固定值 `0x90000000`（位含义属平台侧） |
| 扩展风格字 | 固定值 `0x8`（位含义属平台侧） |
| 菜单 | 空 |
| 父窗口 / 参数 | 空 / 空 |

- 两个形态的**尺寸来源不同**：窗口态 = 客户区 + 外框；占满屏态 = 屏幕尺寸本身。⛔ 不要用"屏幕尺寸"去算窗口态，也不要用"客户区 + 外框"去占满屏。
- **标题**：引擎把一个自己的标题缓冲按字符串格式化成窗口标题串（上限 `0x100` 字节）。建窗**当时**标题缓冲的实际内容本版不规定（见残差）。
- 两个分支的**实例参数**都是入口给的进程实例（与图标 / 菜单所在的实例不同）。
- 扩展风格在**窗口态恒为 0**、在**占满屏态是一个固定非 0 值**：它由形态决定，不是由配置逐位拼出来的。

**显示**：建窗成功之后，引擎**无条件**请求 `ShowWindow(窗口, 入口给的显示方式)` 与 `UpdateWindow(窗口)`。显示方式**原样转发**入口参数（引擎不覆盖它）；两件请求的返回值都**不检查**。

**失败**：窗口句柄为空 ⇒ 走共享出口（先释放引擎对象，再退出）；**不显示消息**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 有窗口 | 一个顶层窗口句柄被记录为"引擎的窗口" |
| 无窗口 | 建窗失败 ⇒ 启动结束 |

**成立条件**

- 窗口创建时配置库已建立（发行默认表 + 玩家文件；见「配置」「启动入口」）。客户区尺寸**只**来自发行默认表（这两个键不在玩家文件可覆盖的词表里）；玩家配置改不了启动时的客户区尺寸。
- **客户区尺寸来自缓存，不是建窗时现读配置**：索引装载时，`set:WinX` / `set:WinY` 被抄进引擎级的**客户区宽 / 高**两格；建窗读这两格。推论（都是合同）：
  - 建窗**之后**再改这两个键**不改变已建窗口的尺寸**；缓存只在索引装载时抄入。改键之后是否还有「重新抄入缓存」的路径（从而影响重设窗口）本版不规定（见残差）。
  - 值为 **0** 时**原样使用**：客户区宽 = 0 ⇒ 窗口宽 = 2 × 边框宽。**没有**"缺键 / 为 0 就换成屏幕尺寸"的兜底。
  - **640 / 480 只是构造期初值**（引擎对象建立时写进这两格），只在默认表块缺失、那两个键从未被抄入时保留；⛔ 它不是"屏幕尺寸"，也不是兜底常量。
- "窗口尺寸 = 客户区 + 外框"是引擎算的，不是平台自动换算的：引擎**显式**向平台查询四类外框尺寸、把边框宽 / 边框高各乘 2 再相加；**不存在由平台自动换算的请求**。
- 两个分支的菜单不同：窗口态有菜单（并因此把菜单高度算进窗口高度），占满屏态没有菜单。
- **窗口态的菜单是建窗实参**：菜单资源在这一步就被交给建窗请求，作为"该窗口的菜单"挂上；本章的「窗口附加请求」只是**取回**它、交给辅助入口并重画。建窗路径**不发送**"设置菜单"的请求；引擎另有重设窗口路径（挂菜单）与切模式路径（传空菜单清空）两处，都**不在本章**。
- 标题、类名、资源名 / 号都是**引擎内建常量**；标题**不是**窗口类名。

**残差**

- `RES-BOOT-WINDOW-TITLE`（unknown）：建窗**当时**标题缓冲里是否已有内容未证实：把游戏名字串读进该缓冲的读取发生在**建窗之后**，且该键不在发行默认表 / 玩家文件的词表里。⇒ 建窗时窗口标题的**实际内容**本版不规定。下一步：真机观测启动时窗口标题；或找出建窗之前对该缓冲的写入点。
- `RES-BOOT-WINDOW-CLIENT-VS-SCREEN`（unknown）：同一套"客户区 + 2 × 边框宽 / 2 × 边框高 + 标题高 + 菜单高"的算法在**重设窗口**路径上被**重复一次**，且那里读的是**同一对客户区缓存**（不是配置键）；本版只规定建窗这一条路径。下一步：把重设窗口路径也写成条目；并确认"建窗后改 `set:WinX` / `set:WinY`"是否还有重新抄入缓存的路径，若有则补时序。
- `RES-BOOT-WINDOW-STYLE`（unknown）：两个风格字的位含义（是否有边框、是否可缩放、是否有系统菜单）本版只登记数值，不解释。下一步：真机对比风格字改动后的窗口外观（可观测项：能否拖边缩放、是否有最大化按钮）。
- `RES-BOOT-WINDOW-AERO`（unknown）：建窗之后还有一个"限制窗口装饰"的请求（一个布尔参数），由配置的"限制装饰"键的两位与"虚拟全屏"键共同决定；它调用的辅助对象的语义未取证。下一步：读该辅助对象的实现，确认它对应哪一类平台请求。

### 窗口附加请求：输入法解绑、菜单交接与窗口记录

<!-- rule: CORE-BOOT-WINDOW-ATTACH -->

建窗成功后，引擎**依次**做三件事：

1. **解绑输入法上下文**：把窗口的输入法上下文设为**空**（请求 `ImmAssociateContext(窗口, 0)`），即"该窗口不接输入法"。返回值不检查。
2. **菜单交接**（**仅当**配置的屏幕形态非 0，即窗口态）：
   1. 取该窗口**已经挂着的**菜单（请求 `GetMenu(窗口)`）；
   2. 把它交给辅助宿主模块的「操作菜单」入口 —— 四个实参**依次**是：**类别号 1**、窗口、菜单、**恒为 0 的第 4 参**；
   3. 请求**重画菜单栏**（`DrawMenuBar(窗口)`）。

   占满屏态**不**做这一步（那一支没有菜单）。
3. **记录窗口**：把窗口句柄写进引擎级的"服务窗口"槽 —— 此后启动期与运行期的一切"服务窗口"引用都用它。窗口态与占满屏态在这一步汇合。

- **启动期没有"设置菜单"的请求**：窗口态的菜单是**建窗时作为建窗实参挂上的**（菜单资源从辅助宿主模块装载，见「窗口创建」）；本阶段只做"取回已挂上的菜单 → 交给辅助入口 → 重画"。建窗路径不发送设置菜单的请求；另有重设窗口路径（挂菜单）与切模式路径（传空菜单清空）两处，都不在本章。⛔ 不要把"把菜单挂到窗口上"实现成本阶段的第四件事。
- **实参位置是合同**：类别号是辅助入口的**第 1 个实参**（不是第 4 个）；第 4 个实参在本阶段**恒为 0**，它的语义本版不规定。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 输入法已断 | 该窗口的输入法上下文为空 |
| 菜单已交接（仅窗口态） | 辅助入口已按类别 1 被调用；菜单栏已重画 |
| 窗口已接入引擎 | 服务窗口槽 = 该窗口 |

**成立条件**

- 三件事的**次序**是合同：解绑 → 菜单交接 → 记录。⛔ 不许先记录后解绑，也不许把菜单交接移到记录之后。
- "解绑"是**显式**请求（第二参数 0），不是"不设置"。
- 解绑与记录发生在**所有**形态下；菜单交接只发生在窗口态。
- 菜单的**内容**不是引擎建的：引擎装载的是辅助模块里的菜单资源，这里只是把它交给辅助入口并重画。
- 菜单在启动期**只由建窗实参提供**；本阶段不发送任何"设置菜单"的请求。

**残差**

- `RES-BOOT-ATTACH-IME`（unknown）：解绑之后引擎是否在别处重新绑定输入法（例如脚本要求输入时）本版不规定。下一步：在输入相关路径里找 `ImmAssociateContext` / 输入法窗口的其它调用点。
- `RES-BOOT-ATTACH-MENU-CATEGORY`（unknown）：「操作菜单」入口的**类别号**（第 1 个实参）语义本版不规定；启动期只观察到取 1，菜单切换 / 重建时另取 0 与 2。第 4 个实参恒为 0 的语义同样不规定。下一步：核对菜单切换 / 重建时各个类别号的用法，以及第 4 参在两处的取值。

### 图形设备初始化

<!-- rule: CORE-BOOT-GRAPHICS-INIT -->

窗口存在之后、根脚本装载之前，引擎请求**图形设备初始化**。它有**两条路线**，由配置的"创建对象"键（`set:CreateObject`）的**两个独立位**分别触发：位 0（值 1）= 旧式绘制；位 1（值 2）= 三维设备。两个位是**独立判断**，不是 if/else：键为 3 时两条路线都会跑。

| 路线 | 选择条件 | 引擎发出的请求 |
|---|---|---|
| 旧式绘制 | 键的位 0 = 1（值 1 / 3） | 建立旧式绘制对象（实参见下表）；失败发给用户一条错误消息并结束启动 |
| 三维设备 | 键的位 1 = 1（值 2 / 3） | 见下 |

**三维设备路线**的请求顺序：

1. 创建 **Direct3D 9** 对象（请求参数是 SDK 版本号 32）。
2. 查询**适配器显示模式**（适配器 0）—— 拿当前桌面的宽、高、格式。
3. **校验分辨率**：只在"虚拟全屏键 = 0"的分支里做。引擎枚举该适配器（0）可用的显示模式，对每个模式写一行诊断并作判定，
   最后挑一档**写回请求的宽 / 高**或失败（见「失败后果」）。窗口化时这个写回**不影响**后缓冲尺寸（后缓冲取客户区宽 / 高）。

   **请求对**：默认是**客户区宽 / 高**；若 `display:FullScreenWidth` **或** `display:FullScreenHeight` **任一非 0**，
   则请求对**整对**改成这两个键的值 —— ⛔ 不做逐分量回退（一个为 0 时它就是 0）。

   **判定的量**：模式自己的**高宽比** `r = 高 / 宽`（诊断里印成 `16 : 16r`）；请求的高宽比 `R = 请求高 / 请求宽`。

   逐模式（每行：宽、高、比率、**一个**分类符号）：

   1. **尺寸闸**：`模式宽 < 请求宽` **或** `模式高 < 请求高` ⇒ 符号 `×`，出局。
   2. **分流**（按**模式自己**的比值）：`r ≥ 0.7` ⇒ **窄档池**；`r < 0.7` ⇒ **宽档池**。
   3. **比值闸**：`r < R`（模式更宽）⇒ `×`（宽档）/ `■`（窄档），出局；`r = R` ⇒ `○` / `●`，进池；`r > R`（模式更窄）⇒ `△` / `▲`，进池。
   4. **池的替换**：每个池只留**一档**；新模式只有宽与高都**不大于**池里现档时才替换，否则记 `―`。
      ⇒ 池里是"过闸的**最小一档**"，⛔ 不是"比值最接近"。
   5. **收口**：`R ≥ 0.7` ⇒ 先取宽档池；若窄档池的宽**严格更小**则改取窄档池。`R < 0.7` ⇒ 宽档池非空就取它（忽略窄档池），空才取窄档池。
   6. **失败**：收口后仍无任何一档 ⇒ 写一行"该请求分辨率不被支持"的诊断、**请求宽 / 高保持原值（不写回）**、结束启动。
   7. **写回**：把选中档的（宽, 高）写回请求宽 / 高，并写一行"判定结果（宽 × 高）"的诊断。写回值用于绘制区域与**全屏**后缓冲。

   ```text
   pick(modes, W, H):
     R = H / W; A = B = NONE
     for m in modes:
       r = m.h / m.w
       if m.w < W or m.h < H: sym = "×"
       else if r >= 0.7:
         if r == R:
           if B != NONE and (B.w < m.w or B.h < m.h): sym = "―"
           else: B = m; sym = "●"
         else if r > R:
           if B != NONE and (B.w < m.w or B.h < m.h): sym = "―"
           else: B = m; sym = "▲"
         else: sym = "■"
       else:
         if r == R:
           if A != NONE and (A.w < m.w or A.h < m.h): sym = "―"
           else: A = m; sym = "○"
         else if r > R:
           if A != NONE and (A.w < m.w or A.h < m.h): sym = "―"
           else: A = m; sym = "△"
         else: sym = "×"
     if R >= 0.7: if B != NONE and (A == NONE or B.w < A.w): A = B
     else: if A == NONE: A = B
     if A == NONE: return FAIL(不写回)
     return ACCEPT(A.w, A.h)
   ```
   - 逐档符号是**诊断专属**的：规范只钉"每档一个符号、集合是这七个、与判定的对应关系"，⛔ 不钉字节与排版。
4. **创建设备**：请求携带**焦点窗口**与一组**呈现参数**，参数来源见「设备创建请求的实参」。
   设备类型或顶点处理取 0（"未指定"）时按**固定顺序多次尝试**，任一成功即停（序列见下）。

**尝试序列**（`display:DeviceType` 与 `display:VertexProcessing` 谁为 0，就枚举谁）：

| 两个键 | 尝试次数 | 序列（设备类型, 顶点处理） |
|---|---|---|
| 都为 0 | **6** | (1,1) → (1,2) → (1,3) → (2,1) → (2,2) → (2,3) |
| 只有设备类型 = 0 | 2 | (1,v) → (2,v)　`v` = 键值 |
| 只有顶点处理 = 0 | 3 | (d,1) → (d,2) → (d,3)　`d` = 键值 |
| 都不为 0 | 1 | (d,v) |

- **设备类型是外层、顶点处理是内层**；**每个新的设备类型都把顶点处理重置为 1**（不是接着上一轮继续）。
- 停止条件只有一个：**某次尝试成功**（返回 0）。枚举耗尽（设备类型 > 2 或顶点处理 > 3）仍是失败。
- 每次尝试只有这两个取值在变：**呈现参数只构造一次**，不随尝试重建；适配器恒为 0、Direct3D 9 对象恒为同一个。
- 枚举上界只到"参考设备"与"混合顶点处理"：设备类型键 > 2 也按参考设备发请求、顶点处理键 > 3 也按混合发请求。
5. 设备建成之后，依次：请求**对话框绘制模式**（参数 = 开）→ 查询**设备能力**（最大纹理宽 / 高）
   并与 `set:TexWidth` / `set:TexHeight` 比较（不足即失败，见「失败后果」）→ 做一次**32 位纹理格式可用性检查**
   （不可用只写一条警告文本，**不**结束启动）→ **清一次渲染目标** → 按 `display:TextureBit` 与
   `display:PixelShader` 建立上层的绘制对象。

**旧式绘制路线的实参**（这条路线**没有**设备 / 呈现参数，只有一次"建立绘制对象"的请求）：

| 请求里的参数 | 来源 | 取值规则 |
|---|---|---|
| 窗口 | 建窗得到的窗口句柄 | — |
| 客户区宽 / 高 | 引擎级缓存（与三维路线第 3 / 4 实参**同一个来源**） | — |
| 全屏位 | `display:FullScreenBit` | 原值直传，**不**与任何键做或 |
| 行为位 | `display:UseDirectDrawEmuration` 与 `display:ScreenMode` | **该键原值** 或上 `形态字 ≠ 0 ⇒ 2 / 形态字 = 0 ⇒ 0`；即位 1 = "窗口化请求" |

**这条路线下"窗口 / 占屏"只看 `display:ScreenMode`**：形态字 ≠ 0 ⇒ 行为位带 2（窗口化）、形态字 = 0 ⇒ 不带（全屏）。`display:VirtualFullScreen` 在旧式路线上**没有**作用（"虚拟全屏非 0 ⇒ 一律窗口化"是三维路线独有的规则）。

建立成功后，引擎还按形态字分两路：窗口态清一个引擎格；**占满屏态把鼠标光标移到客户区中心**。`set:AlwaysBackupSurface` **不是**这条请求的实参（它只写进引擎自己的一个格子）。

**旧式绘制对象内部的"窗口化"降级**（只规定后果，不规定对象内部结构）：行为位的位 1 是"窗口化请求"。对象内部会判两次，两次都可能把这一位清掉（窗口化请求**退回全屏**）：

1. **桌面色深 < 16**：先**问用户**（"本程序需要高彩以上显示"，带确定 / 取消）。**确定** ⇒ 清位（退回全屏）；**取消** ⇒ **整个对象的建立失败**（走旧式路线自己的失败出口）。⚠ 不是"不确认就降级"。
2. **桌面高 ≤ 客户区高**（**相等**也算装不下）：**直接**清位、**不询问**，并置一个"已降级"标志。

- 次序：条件 1 先判；两者清同一位；**只在该位为 1 时**才判（全屏请求不会被"升级"成窗口化）。
- 清位影响三件事：**重排窗口装饰**、是否把位深刷成桌面位深、交给"建表面"的行为位。
- **重排窗口装饰的请求序列**（只在清位时执行；固定五条、固定次序）：
  1. 把窗口样式改成**占满屏**那一套；
  2. 取屏幕的宽 / 高；
  3. 把窗口**移动并调整**到 `(0, 0, 屏宽, 屏高)`（置顶，不改尺寸标志）；
  4. **摘掉菜单**；
  5. 再置顶一次（只改置顶，不动位置 / 尺寸）。
  之后把"当前位深"改成**配置的全屏位深**。
- **"已降级"标志**：构造时清 0；**只在第二个条件**（桌面高 ≤ 客户区高）置 1，第一个条件（色深 < 16 且用户确定）清位但**不置**。本版**不规定**这个标志影响什么（全镜像只观察到两处写、没有读点 —— 有界负结论，不排除整块复制或外部模块按同偏移读）。
- **引擎的形态字不跟着改（合同）**：降级是对象内部的事，不回写任何引擎级形态字；调用方成功之后仍按**配置的形态字**处理（窗口态清一格 / 占满屏态移光标）。⇒ 一次内部降级之后，引擎仍按窗口化做这两件事。

**设备创建请求的实参**（键名见「配置」的键词表）：

| 请求里的参数 | 来源 | 取值规则 |
|---|---|---|
| 适配器序号 | 固定 | 0 |
| 设备类型 | `display:DeviceType` | 1 ⇒ 硬件设备；其它非 0 ⇒ 参考设备；**0 ⇒ 依次试 1、2**（成功即停，见「尝试序列」）。请求里只区分"硬件 / 参考"两种：键 > 2 一律按参考设备 |
| 顶点处理 | `display:VertexProcessing` | 1 ⇒ 硬件、2 ⇒ 软件、3 ⇒ 混合；**0 ⇒ 依次试 1、2、3**（成功即停）。键 > 3 按混合。无论取哪个，请求里**都再带一个恒开的"多线程"位** |
| 焦点窗口 | 建窗得到的窗口句柄（见「窗口创建」） | — |
| 是否窗口化 | `display:ScreenMode`（形态字 `S`，见「窗口创建」）与 `display:VirtualFullScreen` | `S ≠ 0` 或 `display:VirtualFullScreen ≠ 0` ⇒ 窗口化；两者都为 0 ⇒ 全屏（占满屏）。★ 这是**呈现参数**，不是「后缓冲尺寸」的判据（后者按形态字分档，见下） |
| 后缓冲宽 / 高 | 见下「后缓冲尺寸」 | — |
| 后缓冲格式 | **适配器显示模式的格式** | 不来自配置 |
| 后缓冲个数 | 固定 | 1 |
| 多重采样类型 | `display:MultiSample` | 原值作为类型（0 ⇒ 不启用）。启用时另强制"交换效果 = 丢弃"，并**关掉**"后缓冲可锁定"标志 |
| 交换效果 | 上表的"是否窗口化" | 窗口化 ⇒ 复制；全屏 ⇒ 丢弃；**多重采样启用时强制丢弃** |
| 呈现间隔 | `display:PresentInterval` | 0 ⇒ 立即呈现（不等待垂直回扫）；1 / 2 / 3 / 4 ⇒ 等待 1 / 2 / 3 / 4 个回扫；**其它值 ⇒ 平台默认**（键缺 ⇒ 读 0 ⇒ 立即） |
| 自动深度缓冲 | 固定 | 开；格式 = 24 位深度 + 8 位模板 |
| 后缓冲可锁定 | 固定 | 开（多重采样启用时关，见上） |
| 全屏刷新率 | 固定 | 不指定（平台默认） |

**后缓冲尺寸**（三条互斥，按顺序取第一条成立的）：

1. **屏幕形态字 ≠ 0（窗口形态）** ⇒ **客户区宽 / 高**（引擎级缓存，来源见「窗口创建」的成立条件）；
2. **屏幕形态字 = 0** 且 `display:VirtualFullScreen` 非 0 且 `display:VirtualFullScreenType` = 1 ⇒ **桌面宽 / 高**（第 2 步查到的显示模式）；
3. 其余（形态字 = 0 且不满足第 2 档）⇒ **全屏宽 / 高** = **分辨率校验后的请求宽 / 高**（校验已把选中的模式写回；未走校验时 = 请求对；请求对为 0 时退回客户区宽 / 高）。

**这两个键不是设备参数**：

- `set:TexWidth` / `set:TexHeight` 是**能力下限**（与设备报告的最大纹理宽 / 高比较，不足即失败），不是请求参数；
- `display:TextureBit`（纹理位深）与 `display:PixelShader`（像素着色器版本）在设备**建成之后**才读，用来配置上层的绘制对象 —— ⛔ 不要把它们的值当成设备创建请求的参数。

**失败后果：两个通道，分工不同。**

- **日志通道**（引擎自己的日志）承载**步骤特异性**的文本，三类前缀：`错误` / `警告` / 无前缀（诊断、信息）。**旧式路线的三处失败例外**：它们不写日志，只把文本直接送给用户。
- **用户可见的错误消息**：**三维路线**只有**一条通用文本**（标题固定为"错误"），不区分是哪一步失败；**旧式路线**的三处失败各自给自己的一条专用文本。两者都与日志里的文本不是同一句。

**逐步骤的类别与后果**：

| 步骤 | 日志文本类别 | 用户可见 | 后果 |
|---|---|---|---|
| 创建 Direct3D 9 对象 | 错误 + 专用文本 | 通用错误消息 | **结束启动** |
| 取显示模式 | 错误 + 专用文本 + 平台错误码文本 | 通用错误消息 | **结束启动** |
| 创建设备（重试穷尽） | **复用"取显示模式"的文本**（错误码取最后一次尝试） | 通用错误消息 | **结束启动** |
| 分辨率校验 | **诊断**（无"错误"前缀）+ 一行"请求的分辨率不可接受" | 通用错误消息 | **结束启动** |
| 对话框绘制模式 | 错误 + 专用文本 + 平台错误码文本 | （无） | **不结束启动** |
| 纹理能力不足 | 错误 + 专用文本（含期望的宽 / 高两个数） | 通用错误消息 | **结束启动** |
| 32 位纹理格式不可用 | **警告** + 专用文本 | （无） | **仅警告**，继续 |
| 旧式绘制路线（3 处：装载图形库 / 建立对象 / 建表） | **不写日志**（文本直送消息） | **步骤特异性**的错误消息 ×3 | **结束启动** |
| 上层绘制对象（设备之后） | 无 | **通用错误消息**（与前三步同一个出口） | **结束启动** |

**这条不可省**：对话框绘制模式失败**写的是"错误"类文本，但不结束启动**——它是唯一一处"错误文本 + 继续"。因此"文本前缀 = 致命性"是**错的**；实现必须按上表的**后果**列决定是否中止，⛔ 不许因为"写了错误文本"就中止。

- 两条路线任一步**结束启动** ⇒ 不建主循环、不装载根脚本；**任何失败都不得静默**：三维路线**有日志文本的步骤**写日志通道（"上层绘制对象"那一步没有日志文本，只有用户消息），旧式路线的三处只发用户消息（上表已注明）。

**日志通道的落点与丢弃**

- 引擎的日志文本写到**一个**由配置键 `system:OutErrorLog` 决定的文件，文件名固定；打开是**覆盖**语义（每次启动从空文件开始，不追加）。
- **路径展开**：`配置根 [+分隔符] + set:RegFilePath [+分隔符] + 固定文件名`。两个分隔符**只在"拼到此处的结果非空"时**补：
  根与相对目录都空 ⇒ 裸文件名；根非空、相对目录空 ⇒ **连续两个分隔符**（⛔ 不许用"折叠重复分隔符"的路径拼接）。整条路径上限 256 字节。
- **配置根**：`set:UseAppDataFolder` **恰为 1** ⇒ 平台"用户**本地**应用数据目录"（不是漫游）；其它值（含 2）⇒ **空串**，路径相对**安装目录**。
- 拼好后先**探存在性**：不存在 ⇒ 剥掉文件名、补分隔符、**递归建目录**；文件本身由**打开点**创建。
- 该键**非 0** ⇒ 打开文件，此后每条文本都进这个文件；该键为 **0** ⇒ **不打开**；**打开失败** ⇒ 句柄同样**无效**。
  ⚠ **缺键不是静默的**：读一个不存在的配置键会返回 0，但**先弹一次模态错误框**（键名 + "不正なキー"）——这条对本规则读的所有键都成立。
- **时机**：日志文件在**窗口附加之后、图形设备初始化之前**打开一次（每次启动一次）；窗口阶段的文本没有落点。
- **句柄无效时整条文本被丢弃**，且是**静默**的：不写第二个地方、不弹框、**不影响启动是否继续**。
  ⇒ "写了日志文本"与"日志文件里能看到"**不是同一件事**。
- 引擎另有"把一条文本交给外部接收者"的入口（结构上在文件之前），本版**不规定**其行为（见残差）；但可以钉一条否定式合同：**不存在"文件写不进去就改写到别处"的兜底** —— 文件是最后一个落点。
- 文本的**具体字面**属表现层（可替换），本规范钉的是**类别 + 是否中止**。

- 设备建立之后，引擎按"虚拟全屏"键决定是取**客户区矩形**还是用屏幕矩形作为绘制区域；绘制区域本身不是本规则规定的内容（属表现层）。
- 本规则只到"请求 + 参数来源"为止：**设备 / 表面 / 交换链的内部结构、像素格式选择、呈现结果不在本规范**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 图形后端就绪 | 三维设备对象或旧式绘制对象已建立 |
| 图形后端不可用 | 一条错误文本；启动结束 |

**成立条件**

- 路线选择是**配置位**决定的引擎行为，不是"先试一个再退回另一个"：本版没有观察到任何自动回退。
- 屏幕形态字（`display:ScreenMode`）与"是否窗口化呈现"**不是**同一个量：后者是形态字与虚拟全屏键的组合（见上表）。后缓冲尺寸只看形态字（第 1 / 2 档），与呈现参数不是同一个判据。
- **"错误"前缀不等于致命**：对话框绘制模式失败时引擎写了"错误"类文本却继续启动，函数最终仍返回成功（见「失败后果」）。⚠ 不要用"有没有错误文本"推断"启动是否结束"。
- **旧式路线的窗口 / 占屏判据与三维路线不同**：旧式只看 `display:ScreenMode`（形态字），不看虚拟全屏键；三维的"虚拟全屏非 0 ⇒ 一律窗口化"在旧式路线上不存在。
- 旧式对象内部的降级**不**回写引擎形态字：⛔ 不要实现成"降级后引擎形态字也变窗口 / 全屏"（见上面"内部的窗口化降级"）。

**残差**

- `RES-BOOT-GFX-RESOLUTION-CACHE`（unknown）：校验壳有一个"复用上一次选定值"的短路，但从唯一调用点观察不到命中。本版不规定该短路。下一步：复查调用方 + 真机改分辨率后重建设备。
- `RES-BOOT-GFX-EX`（unknown）：另一条 `Direct3D 9 Ex` 的创建路径存在于引擎的另一个模块（有一个版本探测 + 临界区），它**不在**本启动阶段被调用。下一步：确认该模块的调用者与用途（影片 / 截图 / 另一渲染后端）。
- `RES-BOOT-GFX-DEVICE-LOST`（unknown）：设备丢失后的重建请求本版不规定（属运行期）。
- `RES-BOOT-GFX-LOGSINK-PATH-DATA`（unknown）：`set:UseAppDataFolder` / `set:RegFilePath` 的**发行默认值**不在语料 ⇒ 具体落地目录算不死；正文只钉展开规则与"恰为 1"的判据。下一步：读发行配置数据。
- `RES-BOOT-GFX-LOGSINK-SINK2`（unknown）：写手有"先交给外部接收者、它认领就不再落文件"的结构，但该接收者在本镜像里从未被启用。本版不规定其行为。下一步：查是否存在启用它的导出 / 插件入口。

### 事件入口与消息泵

<!-- rule: CORE-BOOT-EVENT-LOOP -->

引擎只有**一个**窗口事件入口（注册窗口类时指定的那个窗口过程），消息泵**在主循环内部**。两者分工：

- **泵**（主循环内，按节流在泵点；节流见「执行与时间」）：先**窥视**（`PeekMessage`，不移除）队列 —— **没有**消息 ⇒ 本趟继续做引擎工作；**有**消息 ⇒ 用**取消息**（`GetMessage`）取**一条**，然后 `TranslateMessage` + `DispatchMessage`，并**回到窥视**，直到队列空。
- 泵的另一处（等待 / 睡眠之后）：先按需**睡眠**一段，再**窥视**一次；有消息就回到**窥视**那一步（窥视不移除，随后照常取一条 → 翻译 → 派发），没有就继续本轮。
- **退出信号**：`GetMessage` 报告“取到退出消息”（返回 0）⇒ 抛出**引擎级退出异常**；该异常在**主循环内部**被捕获，汇入**唯一出口段**；出口段跑完后主循环**正常返回**（void），入口拿到的是一次正常返回，随后进入退出清理。出口触发**不止退出消息**：错误对话框选“终止”也汇入同一段（见 `CORE-BOOT-LOOP-EXC`）；**主循环自身**的返回点只有 **1 个**（见 `CORE-BOOT-LOOP-EXIT`）。`0x2` 的根帧结束抛引擎退出异常；主循环捕获后，在窗口存在时向窗口发送关闭消息（与 `CORE-CONFIG-EXIT-SAVE` 的关闭收尾同一入口），无窗口时不发送（见 `RES-FRAME-EXIT-BOOT`）。
- **销毁**：窗口过程收到“窗口已销毁”消息时，先请求隐藏窗口，再请求**投递退出消息**（`PostQuitMessage(0)`）—— 这是正常退出的触发方式**之一**；对话框终止也汇入同一出口段（见 `CORE-BOOT-LOOP-EXC`）。
- **关闭**：窗口过程收到"关闭"消息时，先做引擎自己的收尾（配置保存见 `CORE-CONFIG-EXIT-SAVE`；其它释放见残差），并**杀掉那个周期定时器**，再请求**销毁窗口**。
- **定时器**：
  - 主循环即将被调用之前，引擎建立**周期定时器**：标识 2、周期 10000 毫秒、无回调函数。
  - 该定时器到期的处理：刷新一次"禁止系统空闲"请求（`SetThreadExecutionState(3)`）；若状态选择字里的一个位在效、另一个引擎级格为 0，且窗口是前台窗口，则向自己发一条应用激活消息（`WM_ACTIVATEAPP`）。
  - 另有**鼠标悬停定时器**：窗口过程收到"鼠标移动"消息且光标在客户区内时建立（标识 1、周期 100 毫秒）；光标离开或按下键时杀掉。
  - "禁止系统空闲"在启动期还**直接**请求过一次（设备初始化之后、根脚本之前）。
- **窗口过程的其他职责**（本版只列与引擎状态 / 生命周期有关的）：激活 / 失活（转发给引擎的激活处理）、设置光标、最小 / 最大跟踪尺寸（客户区 + 外框尺寸，与「窗口创建」同一套算法）、系统菜单项、按键 / 鼠标 / 滚轮（转发给引擎的输入处理）、绘制（转发给绘制请求）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 主循环在跑 | 泵在窥视 / 取消息；事件入口在派发 |
| 主循环经退出消息结束（已证路径） | 一条退出消息已被取到；一个退出异常已被抛出 |
| 其他结束路径 | 本版不规定（见残差） |
| 周期定时器在效 | 标识 2 的定时器存在 |

**成立条件**

- "窥视 + 取一条"是**结合**用法：窥视只用来判"有没有"，取消息用阻塞式 —— 但因为之前已窥视到有消息，实际上不会阻塞。⛔ 不要把它实现成"纯轮询"或"纯阻塞"。
- 定时器周期（10000 / 100 毫秒）是**引擎常量**，不是仿真参数。
- 本节只登记平台侧“退出消息 → 异常”；主循环的**唯一出口段**与入口清理见 `CORE-BOOT-LOOP-EXIT` / `CORE-BOOT-EXIT-CLEANUP`。⛔ 不许把“退出消息”推广成“主循环必然不返回”。`0x2` 的根帧结束抛引擎退出异常；主循环捕获后，在窗口存在时向窗口发送关闭消息（与 `CORE-CONFIG-EXIT-SAVE` 的关闭收尾同一入口），无窗口时不发送（见 `RES-FRAME-EXIT-BOOT`）。这不等于“进程一定退出”——入口之后是否再回到宿主本版不规定。

**残差**

- `RES-FRAME-EXIT-BOOT`（unknown，属 `0x2` 条）：根帧结束已确认抛异常并由主循环捕获后发送关闭消息；无窗口分支与服务窗口清理未取证。下一步：读无窗口分支与清理调用点。
- `RES-BOOT-EXIT-CLEANUP`（unknown）：退出异常被兜住后的清理项与顺序只到"释放引擎对象 → 释放单实例信号 → 睡眠 → 清指针 → COM 反初始化 → 释放运行时库 → 辅助模块析构"这一串观察；各项的语义未逐条取证。下一步：按清理调用点逐项成条。
- `RES-BOOT-CLOSE-CLEANUP`（unknown）：窗口过程在关闭消息里做的**除配置保存外**的收尾没有逐项取证；配置保存见 `CORE-CONFIG-EXIT-SAVE`。本版只规定收尾发生在杀掉周期定时器与销毁窗口之前。下一步：按关闭分支的调用点枚举释放操作。
- `RES-BOOT-TIMER-CONDITION`（unknown）：周期定时器到期时检查的"另一个引擎级格"的身份本版不规定（"状态选择字里的一个位"已有机器绑定）；本版只规定三者的合取。下一步：补另一个格的位号 / 身份。
- `RES-BOOT-WNDPROC-CLOSURE`（unknown）：窗口过程处理的**全部**消息类别没有逐条登记；本版只列了与生命周期、定时器、尺寸计算、输入转发、绘制有关的那几类。下一步：按消息号枚举窗口过程的 switch，逐类给出"转发给谁 / 是否改引擎数据"。
- `RES-BOOT-TIMER-PURPOSE`（unknown）：标识 2 的定时器为什么是 10 秒、除"刷新空闲抑制 + 补发激活消息"之外还有没有别的消费者，未取证。下一步：查该定时器标识的其它读取点。
- `RES-BOOT-PUMP-SECOND-PATH`（unknown）：泵的第二处（睡眠 + 窥视）的**睡眠时长来源**本版不规定（可能与帧率 / 等待门有关，属《执行与时间》）。下一步：把该睡眠点与等待门的规则对齐。
