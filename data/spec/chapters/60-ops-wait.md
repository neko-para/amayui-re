## 等待、影片与空操作

本章的规则逐条点名它覆盖的 opcode（见各小节标题）；未列出的 opcode 本版不作断言。

### 等待（opcode 0x21c）

<!-- rule: CORE-OPS-WAIT -->

`0x21c` 没有操作数。它只做两件事：把当前帧的**推进格数**写成 1（= `2 × 0 + 1`），并**置起等待位** —— 等待位是状态选择字的**第 10 位**（位号从 0 起数）。

- 阻塞**不发生在处理器体内**：置位后门立刻关上，之后由门的服务分支决定何时放行（见「执行与时间」）。
- 本条不读操作数、不写别的引擎状态。
- 等待位（第 10 位）与 `0x71` 置的第 27 位**不是同一位**：⛔ 不许把"置位后门关上"的机制实现成一条共用位。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 脚本在等待 | 状态选择字的第 10 位 = 1 |
| 本条指令的长度 | 当前帧的推进格数 ← 1 |

**成立条件**

- 实现不许在处理器里循环 / 睡眠等待；那是把门的语义搬成一条指令。
- **自然放行 = 两个谓词同时为假**（都在门的服务分支里）：
  - **谓词 A（消息子系统）**：它自己的**定时器**在窗内，**或** 它有一个**等待谓词的待处理闩**。
    定时器就是 `0x238` 写的那一对格：**起点**（0 = 未盖章，首次检查时盖章为"现在"）与
    **时长**；`0x243`、以及 `0x305` 的**揭示支**，把这一对连同"中止位"写死成 `(1, 0, 0)`。
    判据（无符号比较，**相等仍算窗内**）：时长 = 0 ⇒ 只看**等待谓词的待处理闩**；
    否则起点未盖章 ⇒ 盖章；中止位置起 **或** 现在 > 起点 + 时长 ⇒ 起点 / 时长清 0、退回看**等待谓词的待处理闩**；
    都不是 ⇒ **还在窗内**（不放行）。
    ★ **计时器支的副作用**：时长 ≠ 0 的**每一次**调用都会把**场景脏**置 1（含本次就到期的那一次；时长 = 0 的那一支不置）⇒ 等待期间门前「需要重绘」恒成立、每迭代都会请求渲染步。⚠ **脏 ≠ 待处理闩**：它们是场景上的**两个不同的格**，⛔ 不许合并（合并之后"等待期间不请求渲染"或"窗走完仍挡门"必错其一）。
    ★ **待处理闩的写点分两类**（实数 29 个写点、5 个读点）：**清 0 五处** —— 引擎构造、**渲染步入口**（唯一的按迭代清点）、渲染步内部两处、`0x222` 的收尾；**置 1 二十四处** —— **场景 / 网格 / 纹理命令写入器**的尾部（由 17 个 opcode 驱动），加**渲染步内部**推进窗时的 3 处再置，加 4 处**不驱动任何 opcode** 的内部再置（都在渲染步 / 场景更新内部）。逐 opcode 清单属**复核数据**；正文只给分类与"非 0 即未完成"的合同。⇒ 置 1 的来源**不含**消息窗口 / 文本方法的独立写者。
    ★ **5 个读点也分两类**：**两个在等待谓词内部**（一个是计时器到期 / 中止之后的收尾判据，一个就是谓词的**返回值**本身）；**三个在渲染步收尾**（两处形状相同：闩 = 0 才走一次后续调用；一处把闩与相邻的那个待处理格**按位或**起来，非 0 ⇒ 把**场景脏**置 1）。五处**都只读不写**（⛔ 不许把它们当成写点）；逐处清单属**复核数据**。
  - **谓词 B（影片 / 场景对象）**：遍历影片对象表的 1000 个槽；任一非空槽的
    "生效参数"满足 `(参数 & 5) == 4` ⇒ 还有对象在等（不放行）。
    **生效参数**本版**只规定**这一个取值来源：该对象**最近一次真正启动**时收到的那份**选项字**
    （= `0x20f` 的第 3 个操作数；启动路径把它**整字**存进对象，并把第 0 位单独抽成循环位 ⇒ 引擎不解释其余位）。
    ★ **「有延时启动待办」这一支的读侧本版仍未成篇**：**写者已定** —— 种类 1 的影片覆盖命令在配置之后把对象置成待办启动（待办标志置起、**待办参数 = 固定 6**，见「场景 / 颜色族」的影片覆盖命令）；仍缺**何时清 / 缺省 / 它在哪一拍的判定里出现**（见残差 `RES-WAIT-MOVIE-PENDING`）。⇒ 本版**不**把这一支写成通用判据；但种类 1 的待办参数（6）被当生效参数读时与 `(参数 & 5) == 4` 一致 ⇒ 那条对象在待办被消费之前也**挡门**。⛔ 不许把"待办参数"编成通用合同，也⛔ 不许给它编字段名。
    ★ **第 2 位与第 0 位是两个位，⛔ 不许合并**：第 0 位是**循环**位，判据要求它**为 0**；第 2 位是独立的一位，判据要求它**置起**。
    - 发行数据里带第 2 位的两支影片**同时也都是非循环的** ⇒ 在发行数据上"第 2 位置起"与"非循环"**观测上不可区分**。⛔ 不许因此把判据简化成"非循环" —— 那会把"非循环但不带第 2 位"的影片也当成挡门的对象（原引擎会放行）。
    - ⛔ 也不许给第 2 位编一个领域名（"等它播完"只是旁证，见残差 `RES-WAIT-MOVIE-BIT2`）。
- **输入跳过**：配置 `system:EffectSkipOnClick` 非 0、主循环模式字的**第 0 位为 0**、
  且输入事件锁存的**第 4 位**命中 ⇒ 放行（这一路还会清输入位、发一次渲染步、并取消场景对象）。
  另有一条同形的滚轮支（配置 `set:WheelKeyDown`，见残差）。
- **颜色窗会挡住本条**：给一个绘制项排颜色窗（`0x202`）时，引擎同时把**场景待处理标记**置 1。
  该标记的生命周期是（它就是**等待谓词的待处理闩** —— 同一个标记，两个视角：场景推进写它、等待谓词读它）：**每个渲染步的开头清 0**，随后在**同一渲染步内部更早的子步**里推进该绘制项的窗时，
  只要“窗还在走”就重新置 1（**例外**：该项设了「不参与场景动画」位 ⇒ 推进**不置**这个标记，它的窗因此**不挡本条**，「脏」照置 —— 见「场景计时窗」）。窗还在走 = `现在 < 起点 + 延迟 + 持续时间` 且未中止；
  起点在本窗被第一次推进的那一步盖成“现在”（未盖章的哨兵是 0）。⇒ 窗没走完之前本条不放行。
  ★ 那个渲染步若被整段跳过：窗不前进、两个标记也不重算，但等待计时器**只要该跳过点没有同时跳过时钟盖章就照常前进** —— 跳过点、它们的分类以及"被持续跳过"的后果，见「场景计时窗」的「暂停时」那一条（本版**只在那一处**列清单）。
- **所有排窗的绘制项都参与，不按种类**：窗的种类只决定推进时插值的是颜色还是四条边，
  不决定“挡不挡门”（唯一的“不挡门”来源是上一条那个位）；**未到期时**，延迟段（`现在 ≤ 起点 + 延迟`）**也算窗内**。
  ⛔ 不要说“颜色窗不在判据里”（那是错的）；它正是通过**场景待处理标记**（= 等待谓词的待处理闩）进判据的。
- **两种计时的到期边界不同**：本条自己的消息等待计时器在 `现在 > 起点 + 时长` 才到期（**相等仍算窗内**）；
  颜色窗 / 源矩形窗在 `现在 ≥ 起点 + 延迟 + 持续时间` 那一刻就**已到期**。
  ⛔ 不许把两者实现成同一个比较，也不许把延迟段当成“还没开始所以不挡”。
- **本条不含任何“每句时长”的引擎常量**：一句要停多久、一次淡入多久，都由脚本的操作数给出
  （`0x238` 的时长格、`0x202` 的延迟 / 持续时间），每字多久由配置键的每字间隔给出。
  那些是**程序**的性质，⛔ 不是本条的合同，也⛔ 不许为了“节奏像真机”改本条的判据。
- ⛔ 也不要反过来把本条简化成"没有待画格就放行"——谓词 A 的定时器 / **等待谓词的待处理闩**、
  谓词 B 的影片对象扫描都是判据的一部分。

**可证伪**

- 先 `0x238` 写时长 200、再 `0x21c`：从现在起 **199 ms 不许放行、200 ms（相等）仍不许放行、201 ms 必须放行**。
  只看"有没有待画格"、不看这对格 ⇒ 本条错。
- 先 `0x238` 写时长 5000、再 `0x243`（把三格写成 `(1,0,0)`）再 `0x21c`：下一拍就必须放行（中止位优先于窗）。
- 影片对象表里放一个"参数 `& 5 == 4`"的对象、再 `0x21c`：这个对象还在表里时不许放行；它被销毁后下一拍放行。
- 给一个绘制项排 `0x202`（`delay = 0`、`duration = 200`）后立刻 `0x21c`：从**第一个时钟 ≥ 起点 + 200 的渲染步**起，
  **场景待处理标记**不再被重新置起 ⇒ 它之后的那一拍门必须放行。把它写成“200 ms（相等）仍不许放行、201 ms 才放行”是错的
  （颜色窗在相等处已到期，与上一条计时器的边界**不是同一个比较**）。第一拍就放行 ⇒ “颜色窗经场景待处理标记进判据”这条错。
- 给一个绘制项排 `0x202`（`delay = 200`、`duration = 0`）后立刻 `0x21c`：**起点 + 199 不许放行**（未到期时延迟段算窗内），
  **起点 + 200（相等）必须放行**（`≥` 的到期判据先于延迟段的 `≤`）⇒ 延迟段就是窗的一部分，不是“还没开始所以不挡”。
- 给一个绘制项排 `0x202`（`delay = 0`、`duration = 0`）后立刻 `0x21c`：置标记那一步之后，**下一个渲染步**就必须让它到期；
  永不放行 ⇒ 把“未盖章”当成了“还在走”。
- 只置等待位（不写时长、也不排任何窗）：待处理闩为 0 ⇒ 下一迭代必须放行；若不放行 ⇒ 把**脏**当成了**待处理闩**（两者是两个格）。
- 写时长 200 后等待：**等待期间每一迭代都必须请求渲染步**（计时器支每迭代把**脏**置 1）；若等待期间一次渲染步都不请求 ⇒ 漏了"计时器支顺手置脏"。
- ★ **在影片位不挡门的前提下**（该前提本身是残差 `RES-WAIT-MOVIE-BIT2` 的待查项），放一支**非循环且第 2 位为 0** 的影片再执行本条：**必须放行**。若不放行 ⇒ 要么判据被退化成了"非循环"（第 2 位被丢掉），要么挡门来自影片位（此时这条可证伪不成立，要先查影片位服务）。

**残差**

- `RES-WAIT-MOVIE-PENDING`（unknown）：谓词 B 的**「延时启动待办」读侧本版仍未成篇**。**写者已定**：种类 1 的影片覆盖命令在配置之后把对象置成待办启动 —— **待办标志置起、待办参数 = 固定 6**（见「场景 / 颜色族」的影片覆盖命令「其后各步（与『播影片』对照）」）；另有**两处**写同一组待办格（本版不展开）。**仍缺**：待办的**清除时机**、**缺省值**、以及消费待办的那一支出现在哪个时机。⇒ 已证并保留的是**第 2 位 ≠ 第 0 位**（第 0 位 = 循环、要求为 0；第 2 位 = 要求置起）与判据式 `(生效参数 & 5) == 4`。下一步：读消费待办的启动例程（每拍逐对象被调用的那一支）与它那两处写者，定**清除时机与缺省**；读到就补进正文，读不到就把本残差收窄到只剩清除 / 缺省。
- `RES-WAIT-MOVIE-BIT2`（unknown）：第 2 位的**领域名**仍未取证，但**判据已钉死** = `(生效参数 & 5) == 4`（生效参数 = **最近一次真正启动时收到的那份选项字**；"延时启动待办"那一支见 `RES-WAIT-MOVIE-PENDING`，本版不规定）。三条来源已排除：① **引擎内没有第二个读者**（选项字只被本条谓词与影片收尾的「(选项字 & 3) != 2」读，后者只碰第 0 / 1 位）；② **引擎不解释它**（启动路径只把选项字整字存进对象，并把第 0 位单独抽成循环位）；③ **发行数据不可区分**（两支带第 2 位的影片**同时也都非循环**）。⇒ 位名只能来自引擎之外，而外部后端不在本版。★ **采样发行数据永远分不开这两个模型**，必须用自造输入。⚠ 还有一个**混淆项没排除**：「影片位」对任何已启动影片都可能挡门，它与第 2 位的可观察后果重叠 ⇒ 分离实验必须先读影片位服务。下一步：① 读「影片位服务」与置位的关系 —— 它对**非循环**影片是否也一直挡门、什么时候清；若对任何已启动影片都挡门 ⇒ 第 2 位在发行数据 + 可写脚本里无法分离，只把「它只被本条谓词读」写成合同、位名按"无第二个可观察消费者"处置；若它只在特定条件下维持 ⇒ 用**同一支影片的「选项字 0 vs 4」对照**做探针，观察点放在**影片位已清之后**。② 第二条路：若脚本能设「延时启动待办」，待办期间影片位还没置起（谓词读的是待办参数）⇒ 同样的对照。⚠ 真机只接受自己的数据 ⇒ 真机不可用就保持 unknown，不要再派采样。

## 外部请求

### 播影片（opcode 0x20f）

<!-- rule: CORE-OPS-MOVIE -->

`0x20f` 有三个操作数：**1 = 资源 id**、**2 = 对象表槽号**、**3 = 选项字**；读取顺序是 **2 → 1 → 1 → 3**。资源 id 使用《总览与约定》的**统一文件 id**；影片字节从该 id 对应的文件取。

- 按第 2 个操作数查**对象表**（0..999）；该槽为空 ⇒ 新建一个影片对象放进去；同槽已有影片对象 ⇒ **不重建**，只改配置与启动。
  ★ 这里的**对象表**与「纹理族」的「共享对象槽」是**同一张表**（同一批槽位、同一套编号：按整数 id 索引，每格装一个对象引用）；两章各自从自己的用途称呼它，⛔ 不是两张表。
- 用第 1 个操作数取文件名并初始化播放后端（**外部请求**）；后端初始化失败 ⇒ 抛**显示消息型异常**，已建对象留在槽里。
- **纹理绑定**：按**同一个槽号**索引的**纹理槽表**里的一项；它与对象表里的影片对象**不是同一个东西**（对象表空只是建对象，纹理槽空则抛异常）。本条**只读**它，不建立、也不清除；播放期间该槽被 `0x1f8` / `0x1f9` / `0x1fa` 重建或释放时，影片绑定是否还有效本版不规定（见残差）。
- **绑定门**：纹理槽为空 ⇒ 抛**显示消息型异常**；不会继续打开 / 配置。
- 次序固定：建对象（仅当槽空）→ 初始化播放后端 → **绑定门** → 取文件并配置播放后端 → 读选项字 → 应用音轨类别 / 音量 → 启动 → 置影片位。
- **失败**：后端初始化 / 取文件打开失败、或绑定为空 ⇒ **已建的影片对象留在对象表里**，影片位**尚未**置，启动不做。**打开成功后的配置返回值不被检查**：配置返回 0 仍会启动并置位；若后端没有可用流，可能在下一迭代立即收尾。
- 第 3 个操作数是**选项字**：第 0 位 = 循环；`(选项字 & 3) == 2` ⇒ 收尾时**不发出**“填纹理”请求；其余位（含音频类别）的位段与语义未完全取证，本版只登记“对象音量被配置”，不规定键位与合成公式，也不把“可跳过”当成合同。
- 最后**置起影片位**，并把“有活动对象”写 1。
- 处理器体内**不等待**：建对象、配置、启动之后立即返回；阻塞由**门之前的影片对象表服务**与门上的影片位服务共同维持（见「执行与时间」的「影片对象表的服务」）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某个槽上有影片在播 | 对象表该槽非空、对象已启动 |
| 影片占用主循环 | 影片位 = 1（由门上的影片位服务维持；循环分支保持置起） |
| 有活动对象 | “有活动对象”标记 = 1（仅成功启动后写 1；失败残留对象不参与服务） |

**成立条件**

- 影片时长、解码、声音呈现都属于外部模块；本条只规定请求 / 对象状态 / 选项字分流。
- 本版**不要求**实现音频输出；忽略音频不得改变影片位、对象生命周期或阻塞。
- 资源 id 的统一性只到“取文件”为止；文件名 / 容器识别属外部模块。
- 失败残留对象没有“已启动”；本版规定它不进入播完判据、也不维持影片位（避免从未播放的对象把门永久关住）。这是本版对未取证失败路径的**显式边界**，见残差。

## 空操作

### 退出清理：影片 / 场景槽（opcode 0x23d）

<!-- rule: CORE-OPS-MOVIE-CLEAR-23D -->

`0x23d` 没有操作数。

- 遍历槽号 **42..999**：槽里若有影片对象，关闭 / 释放该对象并清空槽（外部释放请求）。槽号与 `0x20f` 的对象表槽号同一套；槽里不是影片对象 ⇒ 跳过。
- 对每个 42..999 的槽，若该槽的**释放守卫为 0**，把纹理记录的**来源文件格**写 **-1**（`0x216` 可观察；无论槽里有没有影片对象），并释放该槽的纹理槽对象（槽 ← 空；纹理记录保留）；守卫非 0 ⇒ 只跳过这两项（影片对象仍然清）。0..41 不变。**不删除纹理记录 / 绘制项 / 网格**。
- 不写脚本变量、不置门位、**不切换当前帧**；推进格数 = 1；没有返回值。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 槽 42..999 的影片对象被清掉 | 这些槽的影片对象 ← 空 |
| 槽 0..41 的影片对象 | **不变** |
| 槽 42..999 的纹理记录来源文件格 | 释放守卫为 0 ⇒ -1；守卫非 0 ⇒ 不变（槽 0..41 不变） |
| 该槽的纹理槽对象 | 释放守卫为 0 ⇒ 槽 ← 空；守卫非 0 ⇒ 不变 |
| 场景脏标记 | 清掉至少一个**影片对象** ⇒ 1；没清掉 ⇒ 不变 |
| 场景"有动画"标记 | **不变** |

**成立条件**

- 范围是**左闭右开**的槽号 `[42, 1000)`；槽 41 不在范围内；对象表只到 999。
- 只要真的清掉至少一个影片对象 ⇒ 场景标脏；没有清掉 ⇒ 脏标记不动。
- 它清影片对象、来源文件格与纹理槽对象，**不删纹理记录 / 绘制项 / 网格**。
- 空槽 / 非影片对象静默跳过，不报错。

**残差**

- `RES-23D-IMAGE-OBJECT`（omitted）：纹理槽对象（图像对象）的**内部资源**释放不建模；纹理槽清空与来源文件 -1 是合同，由守卫固定。
- 释放守卫的写者问题与 `0x1fa` 共用 `RES-TEX-GUARD-WRITER`（unknown）：只有读点，没有写者，观察上恒 0。

### 注释（opcode 0x1a7）

<!-- rule: CORE-OPS-NOOP-COMMENT -->

`0x1a7` 带**一个**操作数，但**不读它**：处理器只写"操作数个数"槽（3 = 2×1+1），然后返回。

- 不读操作数 ⇒ 即使载荷的类型标签不受支持，也**不抛异常**。
- 不写任何池、标量或场景状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 无 | 只有分派协议的操作数个数槽 |

**成立条件**

- 这条的合同是"**什么都不做**"：把它实现成 no-op 不是偷懒，而是规范结论。
- 操作数载荷（注释文本）只存在于指令流里，不进入任何状态。

### 未使用（opcode 0x1a8）

<!-- rule: CORE-OPS-NOOP-DEV -->

`0x1a8` **没有**操作数：处理器只写"操作数个数"槽（1 = 2×0+1），然后返回。

- 不读操作数、不写任何引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 无 | 只有分派协议的操作数个数槽 |

**成立条件**

- 与 `0x1a7` 的区别只在操作数个数（一条带载荷、一条不带）；语义都是 no-op。

### 睡眠：opcode 0x0c8

<!-- rule: CORE-OPS-SLEEP-C8 -->

`0x0c8` 有一个操作数。推进格数 ← **3**（= 2 × 1 + 1），然后按四步：

1. **前置**：走「共用前置」的「宿主环境检查」那一关 —— 宿主报告存在调试器 ⇒ 抛**退出型异常**，不睡、一个字节都不改。前置失败路径**不改**推进格数（它已经写了 3）。同一前置里还有两项启动期随机化的内部不变量，本版按**实现内部省略**处置（见该条，不是"待核实"）。
2. 状态选择字**第 27 位**（位号从 0 起数）为 1 ⇒ 除推进格数外**什么都不做**。★ 第 27 位的服务体把控制交回迭代头（见「执行与时间」的服务链位序表）⇒ 它置起时本迭代**不派发**，这一支是**防御性分支**，本版不把它当可观察路径。
3. 否则读整型(第 1 个) = **n**：
   - **n ≥ 10**：置状态选择字**第 0 位**；把 n 交给**引擎计时器对象**（时长 = n）。本条**不阻塞** —— 门由第 0 位关住，放行由那一位的服务分支决定（见下条「何时放行」）。
   - **n < 10**：**在处理器体内**请求宿主睡眠 n 毫秒（**阻塞**）。这一支不置任何位。
4. **何时放行**（第 0 位的服务分支，每迭代一次）：查一次计时器 —— **未到期 ⇒ 本迭代不派发**（第 0 位保持）；**到期 ⇒ 清第 0 位并交回迭代头**。清位那一拍**不派发**，所以下一条指令在**下一迭代**才执行。服务分支**自己**不阻塞、不 Sleep、不改别的位、不写脚本数据。

**计时器（长睡眠那一路用的那个）**

- 它是「**计数 × 单位**」的倒计时：单位是**毫秒**，长睡眠把**计数**置 1、把**单位**置 n（n = 0 时按 1 处理）⇒ 实际时长就是脚本给的 n 毫秒。
- 到期判据是「**已过的宿主毫秒数 ≥ 计数 × 单位**」（**相等即到期**），到期与否是派生量，不落在脚本可读的数据上；到期的服务分支按上一条清第 0 位。
- 它读**宿主毫秒时钟**，与场景时钟**同源但不同格**：它**不经过**场景的「现在 / 上一次读数」那一对 ⇒ **场景时钟停走（画面暂停 / 场景绘制模式 ≠ 1）不影响它**。这是它与「消息等待计时器」（那条走场景时钟）的**关键差别**，⛔ 不许把两者实现成同一个计时器。
- 读计时器时若剩余 ≤ 4 毫秒，引擎会**阻塞至多 4 毫秒**再重读（它的**唯一**短睡眠就在这里；第 0 位的服务分支自己不阻塞）。这是引擎自己的节流，不是平台细节。
- 计时器有一个「**停表格**」：非 0 时到期判据**恒返回未到期**（永不结束）。它是**布尔**语义（只与 0 比较），写者只写 0 / 1。
- **停表格的写者只有一对操作「停表 / 重开」**（停表置起、重开清除），此外只有计时器**构造**把它清 0。这对操作**只被一个子系统调用**：**自动消息（自动翻页）的节拍** —— 自动翻页开着 ⇒ 用配置里的两个键算出节拍并**重开**那个计时器；关着 ⇒ **停表**。它作用在**另一个**计时器实例上，**不是**睡眠用的那一个。
- ⇒ **睡眠计时器的停表格恒为 0**：长睡眠一定会到期。⛔ 不许把「暂停时睡眠也停」写进本条 —— 被暂停的是自动消息的节拍，不是睡眠。
- **重开是「整段重新计时」，不是「接着剩余继续」**（将来复现自动消息节拍时必须照做）：重开 = 清停表 + 计数回 1 + 起始时刻 ← 现在 + 单位 ← 新给的时长 ⇒ 暂停期间流逝的时间**不**计入。
- 停表格是**布尔**语义（只判"与 0 比较"），不是计数值；到期判据读它**先于**读时钟 —— 停着时**不**读时钟、不盖章、不节流睡眠。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 长睡眠（n ≥ 10） | 状态选择字第 0 位 = 1；计时器 ←（计数 1、单位 n） |
| 这段睡眠还剩多久 | 派生量：已过毫秒与"计数 × 单位"之差（不落在脚本可读的数据上） |
| 短睡眠（n < 10） | 处理器内阻塞 n 毫秒；状态选择字不变 |
| 跳过（第 27 位为 1） | 只有推进格数 |
| 前置失败 | 退出型异常；引擎数据不变 |

**成立条件**

- 判据是 **n ≥ 10**（含 10），不是 n > 10。
- **第 27 位不是等待位**（等待位是第 10 位）：第 27 位即「消息逐帧推进门位」（又称「跳过位」），`0x88` 在值为 0 时清它（见「引擎级标量」的成对写）。
- 短睡眠搬进了处理器体：⛔ 不许把它改成"置位 + 门"（那样短睡眠会变成一次迭代，而不是一次 n 毫秒的阻塞）。
- ⛔ **短睡眠不得变成 no-op**：实现可以用虚拟时钟代替真实阻塞，但必须让**时间前进 n 毫秒**、并保持次序（同一次迭代内不得提前执行下一条指令）。把 `sleep 1` 当作"什么都不做"会让轮询循环以 CPU 全速空转，属于违反本条，不是仿真参数。
- 负值**没有范围检查**：n < 10 这一支把值交给宿主睡眠（按无符号解释 ⇒ 极长阻塞）。这是可观察行为，不是"夹到 0"。
- 前置里那个入口是**宿主库**按名字取得的（平台边界）：判据、留空处置与同组两项内部不变量的定位见「共用前置」的「宿主环境检查」。
- **放行与置位不在同一拍**：置位是处理器体内的事，放行是服务分支的事；⚠ 清位那一拍不派发 ⇒ 至少隔一拍才执行下一条指令。
- 睡眠计时器**不随场景时钟停走**：它的格与场景时钟那一对**不是同一对**（见上）。

**可证伪**

- `sleep 10`：从置位那一拍到清位那一拍之间**至少有一拍**是"不派发"的；清位之后**必须再隔一拍**才执行下一条（若清位与派发同拍 ⇒ 服务分支写成了"清位后直接派发"）。
- `sleep 10`：**9 毫秒时必须仍不放行、10 毫秒（相等）必须放行**（若 11 毫秒才放行 ⇒ 比较式用了 `>`）。
- 把场景绘制模式设成 ≠ 1 再 `sleep 10`：**仍然 10 毫秒放行**（若与场景时钟一起停走 ⇒ 把两个计时器混成了一个）。
- 长睡眠期间观察第 27 位与等待位：两者都不得被这条指令改动（置位的是第 0 位）。
- 长睡眠期间遍历所有引擎状态（配置 / 场景 / 消息 / 输入）：**找不到任何**能让它永不到期的状态。若某个"暂停"把睡眠冻住 ⇒ 它把停表格接到了**错误的计时器**上（停表格属于自动消息节拍）。
- 自动消息开着时观察节拍计时器 ⇒ 必须处于「未停」；把它关掉 ⇒ 必须变「停」（这是停表格**唯一**的可观察来源）。
- 自动消息关掉后再开 ⇒ 节拍必须**从零重新数一整段**，而不是接着上次剩余；接着剩余 ⇒ 重开被写成了"恢复"。

### 读系统毫秒时钟：opcode 0x0d0

<!-- rule: CORE-OPS-CLOCK-D0 -->

`0x0d0` 有一个操作数。推进格数 ← **3**（= 2 × 1 + 1）；读一次宿主的系统毫秒时钟；把读数经**写整型**写进第 1 个操作数。

- 本条请求**一次**时钟读数；它是否与主循环迭代头那次读数是同一次，本版不规定（见残差）。
- 单位毫秒、宽度 32 位、会回绕（与「时钟」一章同口径）。
- 不归一、不夹取；除第 1 个操作数与操作数访问原语的缓存外，不改其它引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数 = "现在" | ← 本处理器自己的一次毫秒读数 |

**成立条件**

- 值经过**写整型**原语（要编码）：落点的接受集就是「数据池」写整型原语的接受集；不受支持的类型 ⇒ 操作数类型异常。
- ⛔ 不许把它实现成"读一个常量"；是否复用迭代头读数属未定（见残差）。
- 回绕比较由**读它的人**负责（本条只给 32 位读数）。
