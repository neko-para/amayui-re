## 引擎级标量与事件

本章 17 条规则 / 33 个 opcode。

## 引擎级标量写（opcode 0x149 / 0x21b / 0x252 / 0x88）

这一族把操作数的值写进**引擎里固定的格**（不是池、也不是按索引的表；一条指令可以写一个或多个格）：格的身份属机器细节，本版只规定「读什么、写成什么形态、有没有归一、有没有分支」。

### 薄标量写：opcode 0x149 / 0x21b / 0x252

<!-- rule: CORE-OPS-SCALAR-THIN -->

三条各有一个操作数，各写**一个固定格**：

- `0x149` 与 `0x252` 把操作数按整型语义读出、**原样**写进各自的格（不归一、不夹取）。
- `0x21b` 把同一个值**归一成 0 / 1**：值为 0 ⇒ 写 0；任何非 0（含负数）⇒ 写 1。
- 三条都：只读**一个**操作数、不调用别的引擎函数、**不把返回值写回操作数**（返回值由分派器丢弃）。
- 写进去的是**解码后**的整数值：池里的编码位模式不参与本规则。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该指令负责的那个引擎级格 | ← 读整型（第 1 个操作数）或它的 0/1 归一 |

**成立条件**

- `0x21b` 的归一不可省：写原值看起来「也能跑」，只有读它的人才会发现区别。
- 三条都不是「写回操作数」：操作数所在池的内容不变。
- **三格都有读者，因此写它们会改变之后的判据**（三格的角色就是从这些读者上读出来的）：
  - `0x149` 的格：`0x148` 把它**原样读回**第 1 个操作数；窗口定时器路径把「距上次取时的毫秒数」与它比较，**超过**它才继续做后面的事 ⇒ 它是一段以毫秒计的间隔。
  - `0x21b` 的格：一个**布尔量**（只有 0 / 1 两个值，由本条的归一保证），**两个**读者 ——
    ① `0x247` 把它**归一成 0 / 1** 读进第 1 个操作数；
    ② **门前的渲染步判据**：它非 0 ⇒ 本迭代照常发出门前渲染步请求；它 = 0 ⇒ 再看**状态选择字**的**等待位（第 10 位）与影片位（第 13 位）**：两位都为 0 ⇒ 本迭代**不**发门前渲染步（并跳过那一次盖场景时钟），任一位为 1 ⇒ 照常发（见「执行与时间」的「暂停时」）。
    ★ 这两处就是它的**全部**读者；"它 = 0 时再看另一格的状态位"说的正是第 ② 处，⛔ 不要把它记成第三个读者。
    ★ 它是**粘滞**的：`0x21b` 写完就保持，直到本条再写一次或复位清 0；两个读者都**只读**（读它既不清它、也不改任何其它格）。缺省 = 0（建立 / 复位时清 0）。
  - `0x252` 的格：场景更新路径按**第 0 位**与**第 1 位**分别测试它（各是一处判据），另有一条路径也整格写它 ⇒ 它是一段**按位**读的标志字，脚本写进去的是位模式。

### 成对写：opcode 0x88

<!-- rule: CORE-OPS-SCALAR-PAIR-88 -->

`0x88` 有一个操作数，读成整型值，然后：

1. 把**同一个值**写进**两个固定格**（两个都写，不看值）；
2. 按值分支：**非 0** ⇒ 把第三个固定格写成**常量 1**；**等于 0** ⇒ 把**状态选择字**（门读的那一个字，见「执行与时间」）的**第 27 位（位号从 0 起数）清 0**（读-改-写，其它位不变）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 两个引擎级格（= 「引擎级模式位」的 **C / D** 两格，见「引擎级模式位」的字母表） | ← 读整型（第 1 个操作数） |
| 非 0 支 | 第三个格（= 该字母表的 **G**）← 常量 1 |
| 为 0 支 | 状态选择字的第 27 位 ← 0 |

**成立条件**

- 两支**互斥**：非 0 时不碰**状态选择字**；为 0 时不写第三个格。
- 清位是**读-改-写**：其它位原样保留（把它写成「整字 = 0」会踩掉别的位）。
- **第 27 位是「消息逐帧推进门位」**（名字与位序见「执行与时间」的服务链位序表第 16 行）：
  `0x71` 在文本子系统返回非 0 时**置**它，本条在值为 0 时**清**它；`0x19b` 无条件清它；`0x19c` **不是无条件清**：三个判据格（`C` / `E` / `F`）里 `C ≠ 0` 或 `E ≠ 0` ⇒ **置**它、`F ≠ 0` ⇒ **不动**它，只有 `C = 0 ∧ E = 0 ∧ F = 0` 才清 0（**按该条分岔的先后**读：先判 `C`，`C = 0` 时才判 `E`、再判 `F`；`E` 支与 `F` 支的差别是"不动 `D`"与"连位都不碰"，见「引擎级模式位」）；除上述之外引擎自己另有置点。⛔ 不许把 `0x19c` 列进"清 0 者"—— 那会把"置门"当"放行"。
- **置起 ⇒ 门被这一位挡住**：扫描到它时，它的服务体**进入一次消息处理**（读一条消息并派发；它与迭代头那个按节流周期触发的泵**不是同一处**，也不受那个计数器约束），
  再让出一拍，然后**交回迭代头** ⇒ **本迭代不派发脚本指令**；同时它还会让 `0x71` 不再置打字位（第 29 位）。
  **清 0 ⇒ 门不再被这一位挡住**：本迭代的扫描从它继续往下走（下一个检查点是第 29 位），
  没有任何服务体交回迭代头时就走到表尾**派发一条指令** —— 这就是「清了之后放行什么」：**放行脚本继续执行**。
- **它不是"等消息"的等待位**（等待位是第 10 位，见「等待（opcode 0x21c）」）：等待位由等待谓词清，这一位由消息处理 / 脚本指令清。
- 本条写的**两个固定格是「引擎级模式位」的 C 与 D，非 0 支写的第三个格是 G**（字母表与这三格的其它写者见「引擎级模式位」的 `0x19b` / `0x19c` / `0x1c7`）：
  ⇒ `0x88` 是这套模式里唯一**一次写两格 + 按值选"清位 / 置 G"**的入口；⛔ 不许把它实现成"只清一位"。

### 薄标量写：启动前段五条（opcode 0xfe / 0x10f / 0x248 / 0x261 / 0x8b）

<!-- rule: CORE-OPS-SCALAR-THIN-PROLOGUE -->

五条各读**一个**操作数、各写**一个**固定格；都**不调用别的引擎函数**、**不把返回值写回操作数**（返回值由分派器丢弃）。写进去的都是**解码后**的整数值（池里的编码位模式不参与）。

| opcode | 落点 | 形态 | 检查 |
|---|---|---|---|
| `0xfe` | 引擎级的**键总数**格（角色见「输入」） | 原样 | **值 ≤ 31**（无符号比较），否则**抛显示消息型异常**、该格不变 |
| `0x10f` | 引擎级的另一格 | 原样 | 无 |
| `0x248` | **进程级**的一格（不属于引擎对象） | 原样 | 无 |
| `0x261` | 引擎级"五格连续段"的**最低一格** | 原样 | 无 |
| `0x8b` | **字体对象**的一格 | 原样 | 无 |

- `0xfe` 的范围检查是**引擎自己抛的异常**（显示消息型；见「异常与错误通道」），不是静默截断、也不是夹取：越界时该格保持原值。★ 这个上界与「引擎级状态」的标量表**不同源**：那里 31 也是字面常数（表宽只约束索引 8），这里同样是写死的常数。
- `0xfe` 的落点是**键总数**：它的读点与角色在「输入」的 `0x100` 里；本条只规定**写入形态与越界**，不重复键总数的扫描语义。
- `0x248` 写的是**进程级全局**，不是引擎对象的字段：重建引擎对象**不会**复位它。⛔ 不许把它与引擎级那几条合并成"同一个标量表的相邻格"。
- `0x261` 与 `0x260` 的四格是**同一段连续五格**：`0x261` 是最低一格、`0x260` 是从它上面一格起的四格（见「成对与四格写：opcode 0x1a4 / 0x260」）。⛔ 两条落点不同，不许互换。
- `0x8b` 写的是那个**字体对象**（`0x75` / `0x76` / `0x77` / `0x1a4` / `0x197` / `0x1a5` / `0x2bd` / `0x2fe` 共用的接收者）的一格；其余四条写的是引擎对象顶层的格。⛔ 不许把这一族当成"引擎对象的连续字段"。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该指令负责的那个格 | ← 读整型（第 1 个操作数）；`0xfe` 另加上界 31 |

**成立条件**

- 只有 `0xfe` 有范围检查：把它推广到同族其它四条，会让本该写入的值被拒。
- 五条都**不归一**（不像 `0x21b` 那样归成 0 / 1）：写进去的可以是任意整数。
- **三个格的角色由它们的读者定出**：
  - `0x10f` 的格：窗口层按**第 0 位**与**第 9 位**分别测试它（各是一处判据）⇒ 它是一段**按位**读的标志字；值由脚本整格写入。
  - `0x248` 的格：另一族代码在把矩形坐标换算成块下标时把它当**除数**（除不尽向上取整）⇒ 它是一段进程级的换算除数；进程级 ⇒ 重建引擎不复位。
  - `0x8b` 的格：字体对象自己的方法读它、并把它加进一处位置换算，另有方法把常量 6 写进它 ⇒ 它随字体对象走，不是引擎对象顶层的格。

### 成对与四格写：opcode 0x1a4 / 0x260

<!-- rule: CORE-OPS-SCALAR-PAIR-PROLOGUE -->

两条把**多个操作数**一次写进**相邻的格**，都不调用别的引擎函数、不归一、不写回操作数：

- `0x1a4`（两个操作数）：第 1 个 → 字体对象的一格；第 2 个 → **紧邻的下一格**。读序 **先第 2、再第 1**。⛔ 两个落点不许交换（交换后两个值整体错位，而写入本身不报错）。
- `0x260`（四个操作数）：第 1、2、3、4 个依次写进**四格连续**（第 1 个最低、第 4 个最高）。读序是 **先第 4、再第 3、第 2、第 1**（倒序读、正序写）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| `0x1a4` 的两个格 | ←（第 1 个, 第 2 个） |
| `0x260` 的四格连续段 | ←（第 1 个, 第 2 个, 第 3 个, 第 4 个），按地址从低到高 |

**成立条件**

- `0x260` 的"第 1 个进最低格"是合同的一部分：把读序当写序（倒着写）会让四格整体反过来。
- `0x1a4` 的两格与 `0x76` / `0x77` / `0x78` 写的格在**同一块字段**里但是不同的格。
- 两条都不检查、不建记录：写不进去只有操作数类型异常一条路。

### 带变换的格写：opcode 0x76 / 0x77 / 0x2bd

<!-- rule: CORE-OPS-SCALAR-VARIANT-PROLOGUE -->

三条各读**一个**操作数，写进**字体对象**的格，并且写完都请求**重建字体**（外部请求：字体对象据此重建它持有的字体）；**重建的内部过程属实现侧**（引擎内部怎么重建它持有的字体、平台怎么建字形、逐位结果怎样）不在本版。可观察的是**请求发生**与**本条写下的那几格**，⛔ 不许把"内部不建模"写成"没有写"。三条的**写值形态各不相同**：

| opcode | 落点 | 写进去的值 | 写完之后 |
|---|---|---|---|
| `0x76` | 字体对象的**主色** | **低 24 位的字节倒序**（第 0 字节与第 2 字节互换、第 1 字节留在中间，高 8 位丢弃） | **调用**重建入口（会返回） |
| `0x77` | 字体对象的**副色**（与主色相邻的另一格） | 同上 | **调用**重建入口（会返回） |
| `0x2bd` | 字体对象的**两格** | **二选一常量**：操作数 ≠ 0 ⇒ 两格都写 **700**；操作数 = 0 ⇒ 两格都写 **0** | **尾跳**进重建入口（本条不再返回分派器） |

- `0x76` / `0x77` 写的是**倒序后的字节模式**，不是操作数原值：写成原值不报错，只是那两格承载的**主色 / 副色**整体错位。⛔ 两条只差落点，不许共用一个格。
- `0x2bd` **不写操作数本身**：它把操作数当**开关**，写的是 700 或 0。⛔ 不许实现成"写操作数原值"（那会同时丢掉 700 与"二选一"）。
- 调用与尾跳的区别是**可观察的**：尾跳之后，本条之后的指令不会被执行（控制流已经交给重建入口）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| `0x76` / `0x77` 的主色 / 副色 | ← `bswap24(读整型(第 1 个))`（低 24 位字节倒序） |
| `0x2bd` 的两格 | ← 700 / 0（由操作数是否为 0 决定） |
| 重建请求 | 一次对字体重建入口的调用（`0x76` / `0x77`）或尾跳（`0x2bd`） |

**成立条件**

- 三者的落点都在那个字体对象里；⛔ 不许把它们写进引擎对象顶层。
- `0x2bd` 的 700 是一个**引擎写死的常量**，不是从操作数算出来的。
- `0x2bd` 的两格相距很远、不在同一段字段里：它们同属那个字体对象，但不是"相邻两格"。

## 键位映射表（opcode 0xfd / 0x10c）

这一组两条不是"把值写进某个固定格"，而是**改键位映射表本身**：它们按二级索引落一格，并且是**运行期唯一**能改这三张表的脚本指令（配置不写这些表，见「输入」的章首）。两条的读者在「输入」的采样里。

### 按表索引写一格：opcode 0xfd / 0x10c

<!-- rule: CORE-OPS-SCALAR-TABLE-10C -->

两条都改写**键位映射**里的三张表（这三张表怎么参与采样、以及"键码表一格只存一个位号"的后果见「输入」的「输入字与键总数」）：

| 表 | 下标 | 格里的值 |
|---|---|---|
| **A** 槽 → 逻辑键 | 槽号 `0..31` | 逻辑键号（构造时槽 0..6 = 上 / 右 / 下 / 左 / Enter / Space / Backspace 的默认逻辑键） |
| **B** 逻辑键 → 系统键码 | 逻辑键号 `0..255`（**表内 256 格**，未写到的格 = 0） | 系统键码（构造时整表清 0 后写入 **93 个固定条目**，见下） |
| **C** 系统键码 → 输入位号 | 系统键码 `0..255` | 输入位号；`−1` = 该键码未映射 |

**表 B 的初值（构造时写入；运行期没有第二个写者）**

表 B 是 **256 格**：构造时**整表清 0**，再写下面这 **93 个固定条目**；未列出的 **163 格恒为 0**（⇒ 逻辑键号落到那些格时换成系统键码 **0**，与"逻辑键 0"同效）。**运行期没有第二个写者**：配置与脚本都不写这张表。

**七个默认槽依赖的逻辑键**：构造时槽 0..6 依次绑定逻辑键 **200 / 205 / 208 / 203 / 28 / 57 / 14**，经表 B 换成系统键码 **38 / 39 / 40 / 37 / 13 / 32 / 8** ⇒ 与「输入」章的七个默认位号（上 / 右 / 下 / 左 / Enter / Space / Backspace = 位 0..6）逐一对上。

- 两条的**第 1 个操作数都是槽号**（它同时就是**输入位号**，`0..31`），**第 2 个都是逻辑键号**。读序**先第 2 个（逻辑键号）、再第 1 个（槽号）**；第 2 个读失败时第 1 个还没被读。
- 两条都**只检查第 1 个操作数**：按**无符号**比较 > 31（含负值）⇒ 抛**显示消息型异常**，三张表一格都不写。**第 2 个操作数不检查**：逻辑键号 **0..255** 是表内（未写到的格 = **0**）；≥ 256 或负数是**表外越界读**（**未定义**，⛔ 不抛脚本可见异常、⛔ 不夹到 255、⛔ 不补 0）。
- 两条都在检查**之前**先把帧记录的长度槽写成 **5**（= 2 × 2 + 1，argc 2）；所以即使随后抛异常，推进格数已经不是 0。
- **`0x10c`（追加）** 只做一步：把第 2 个操作数那个逻辑键的**系统键码**（经表 B 取）在表 C 里**登记**为第 1 个操作数（**覆盖**该键码原来的位号）。它**不碰表 A**，也不抹任何旧键码。
- **`0xfd`（改绑）** 做三步，顺序固定：
  1. 经表 A 取该槽**当前**的逻辑键、再经表 B 取它的系统键码，把表 C 的那一格抹成 `−1`（解绑旧键）；
  2. 表 A 的该槽 ← 第 2 个操作数（槽改绑到新逻辑键）；
  3. 把新逻辑键的系统键码在表 C 里登记为第 1 个操作数（与 `0x10c` 的同一步）。
- ⇒ 两条的**唯一差别**是第 1 步（要不要先解绑该槽旧逻辑键的键码）。⛔ 不许把 `0x10c` 实现成 `0xfd`：那会顺手解绑一条别人还在用的键。
- 两条的异常文本不同（`0xfd` 的以 `SetKey` 开头、`0x10c` 的以 `SetKeyMulti` 开头），但两者都指"第 1 个操作数不对"：⛔ 不要拿文本判断是哪个操作数越界。
- 值不做归一：写进表里的是读出来的整数。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某槽改绑到哪个逻辑键（`0xfd`） | 表 A 的第（第 1 个操作数）格 ← 第 2 个操作数 |
| 某逻辑键的系统键码点亮哪一位 | 表 C 的第（表 B 的第 2 个操作数格）格 ← 第 1 个操作数 |
| 旧键被解绑（`0xfd`） | 表 C 的旧键码那一格 ← −1 |
| 某键码未映射 | 表 C 该格 = −1 |

**成立条件**

- **表 C 一格只存一个位号** ⇒ 一个系统键**只会点亮一个输入位**：后写的覆盖先写的。⛔ 不许把它实现成"一个键码对应多个位"，也不许把"解绑"实现成"再加一条映射"。
- **表 A 一格只存一个逻辑键** ⇒ 一个槽只对应一个逻辑键；`0xfd` 的"解绑"只对**旧**逻辑键生效，新逻辑键原来的映射不受影响（除非新旧是同一个键码）。
- `0x10c` 不读表 A：同一个逻辑键重复 `0x10c` 只是重复覆盖表 C 的同一格，**不会**让两个槽同时点亮同一个位。
- 边界：槽号越界**抛**；逻辑键号越界是**表外越界读**（`0..255` 是表内、格值可能是 0；其余**未定义**、不抛）。这和本章前面几条"越界静默跳过"的标量表（`0x107` / `0x10b`）**不同**，⛔ 不要合并实现、也不要把 31 的检查挪到第 2 个操作数上。
- **表 B 没有运行期写者**：它的 256 格只在构造时被清 0 并写入那 93 个条目；配置与脚本都不碰它。⇒ "逻辑键号 → 系统键码"是一次**固定的**两段查表，任何"按配置重排逻辑键"的实现都是新增语义。
- 三张表都是**引擎级**的（不随帧）：换帧 / 装帧不改它们；重建引擎对象会把 A 与 C 恢复成构造初值、把 B 恢复成默认表。
- 三张表**各管一段**、不是同一张：⛔ 不许把"槽 → 逻辑键"与"系统键码 → 位号"合成一格 —— 前者被 `0xfd` 写、后者被两条写；合成后 `0xfd` 的"解绑"就无处落脚。

**可证伪**

- 逻辑键 28 必须换出系统键码 **13**（Enter）；逻辑键 **200 / 203 / 205 / 208** 必须分别换出 **38 / 37 / 39 / 40**（上 / 左 / 右 / 下）。四者互相错位 ⇒ 表 B 的某格写错或下标错位。
- 逻辑键 **0** 与逻辑键 **255** 都必须换出系统键码 **0**（表内未写到的格是 0、不是"未定义"）；把逻辑键 0 实现成"抛异常 / 未映射" ⇒ 表内格被当成了表外。
- `0x10c` 传逻辑键 **99999** ⇒ **不得**抛显示消息型异常（只检查第 1 个操作数）；抛了 ⇒ 把 31 的检查加到了错误的操作数上。
- 槽号传 **32** 或 **−1** ⇒ 必须抛显示消息型异常，且三张表一格都不写。
- 表 B 若能由配置或脚本改写（构造之后还有第二个写者）⇒ 本条错。

## 启动前段的刷新与门（opcode 0x143 / 0xae / 0x130）

这三条都出现在**脚本之前的启动链**上，各自只碰很少的引擎数据；但三者的**分支条件**都可观察 —— 写错一格不报错，只会让启动链走另一条分支。

### 事件刷新：opcode 0x143

<!-- rule: CORE-OPS-EVENT-143 -->

`0x143` **没有操作数**。它依次做四件事：

1. 把本帧的**推进格数**先写成 **1**（= 2 × 0 + 1）；
2. 把引擎级的**队列泵占用标记**置 1 —— ★ 它借用的是泵自己"一趟正在跑"用的**同一个标记**，不是另一个格；
3. 对**文件库的槽位表**逐槽检查（槽号 **1…255**）：**非 0 的槽**各把**一条命令**投进**待处理命令队列**（投递值 = 槽号在高 8 位、低 24 位为 0）；全 0 ⇒ 一条也不投。★ 每次投递的动作本身还带一个"顺手泵一次队列"的尾巴，但此刻**队列泵占用标记**是 1 ⇒ 一次也不泵（借这个标记抑制投递期的泵，就是它在这一步的用处）；
4. 把**队列泵占用标记**清回 **0**、把推进格数清 **0**、**自己把本帧的指令指针推进 4 字节**，然后**尾跳**进事件队列的处理入口。

- 第 4 步之后那个入口是**队列泵**。它的两个早退条件是**区间忙标记 ≠ 0**（区间还没离开）与"队列头等于队列尾"（队列空）⇒ 早退时**直接返回**，控制流落回本条自己算出的"下一条指令"。这是启动链里最常见的路径。
- **投递值的符号很重要**：投递值 = **格号 << 24**，泵把它当 **32 位有符号数**解释 ⇒ 格号 **1..127** 是**正命令**（高 8 位 = 区号、低 24 位 = 该份索引里的条目下标）；格号 **≥ 128** 时最高位已置 ⇒ 该值变成**负数**，按**负命令**解释（目标帧号 = −投递值，量级在 2^24 以上 ⇒ 落在 0..39 之外）⇒ 后果同「目标帧号」的越界处置（负命令支的「目标帧没有装载脚本」与「帧号范围」的未定义行为，见「执行区间的进入与离开」与「换帧」）。表自己的上界仍是 **255**：本条不收窄成 127，只规定 ≥ 128 的那些格按负命令走。
- **队列非空** ⇒ 该入口取一件、并按它自己的要求改变控制流（换帧 / 跳转）；具体处置见「执行区间的进入与离开」的泵合同。
- 推进是**本条自己做的**（先把推进格数清 0、再加 4 字节）：⛔ 不许留给分派器再加一次 —— 那会让每条 `0x143` 跳过 8 字节。
- 那 255 个被检查的格是**文件库的槽位表**里 **1…255** 号槽（整表共 **256** 槽，按槽号索引「已装载文件对象」；格值为 0 = 该号文件没装载）：装载一个数据文件时，把它的对象写进**它自己号**那一格；文件库析构时逐格销毁非空格并清 0；按名查文件时同样从 1 号槽起遍历非空格。★ 它**不是**本条私有的登记表。
- 整表在引擎建立文件库时**显式清 0**（256 格），此后只在文件装载 / 文件库析构时变 ⇒ 第 3 步的**可达条件**是「本次启动里至少装载过一个号在 1…255 的文件」，与脚本内容无关；号 0 那一格本条不检查。
- 该表另有一个**对外查询**（按槽号返回"是否已装载"）；谁调用它、读来做什么属程序侧，不是本条的引擎行为。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 队列泵占用标记 | 置 1 → 清 0（同一趟内；泵自己也会置清它，见「执行区间的进入与离开」的泵合同） |
| 文件库槽位表里非 0 的槽 | 每槽一条投进**待处理命令队列**的命令（投递值 = 槽号在高 8 位、低 24 位为 0） |
| 本帧的推进格数 | 先写 1、再写 0 |
| 本帧的指令指针 | ← 本条位置 + 4 字节 |

**成立条件**

- 顺序固定：置标记 → 逐格投递 → 清标记 → 清推进格数 → 推进 → 尾跳。
- **队列泵占用标记**在这里的作用是**抑制投递期的泵**：它非 0 时，第 3 步那串"投一条"不会顺带泵队列；而泵自己用同一个标记表示"一趟正在跑"（见「执行区间的进入与离开」的泵合同）。⛔ 不许实现成两个开关 —— 那会让投递期的尾巴真的泵起来，或在泵帧里开闸把队列套成两层。
- 本条**不读任何操作数**，因此也不会抛操作数类型异常。

### 存档版本检查：opcode 0xae

<!-- rule: CORE-OPS-SAVE-VERSION-AE -->

`0xae` **没有操作数**。它先把本帧的推进格数写成 **1**，然后读一个**引擎级标志**（=「有一份已读入、待应用的存档」）：

- 标志 **= 0** ⇒ **什么都不做**，直接返回。这条路径的全部效果就是那个推进格数；它**连一个命名键都不读**。
- 标志 **≠ 0** ⇒ 按**两个存档版本键**（主版本 `set:SaveVersion1`、次版本 `set:SaveVersion2`）选一套存档布局，把已读入的那份存档**应用**到当前帧：

  | 主版本 | 次版本 | 处置 |
  |---|---|---|
  | 1 | 20 | 用**布局 1** |
  | 2 | 任意 | 用**布局 2**（不比较次版本） |
  | 3 | 任意 | 用**布局 3**（不比较次版本） |
  | 其它（含主版本 1 且次版本 ≠ 20） | — | **不应用**：除推进格数 1 外什么都不改，直接返回 |

  - **应用**沿用「存档 · 恢复」的装帧原语（见「存档」的恢复条）。**布局 1 的帧暂存块**是：一个 **4 字节长度前缀（长度包含前缀自身）**，后跟**六个 32 位整数**，按**三对**解释 —— 每对的第一个是**整数**、第二个是该表**在代码块内的 32 位字偏移**：
    1. 恢复时先为这一帧的**代码块**分配内存、把代码体整块读进去；
    2. 把三对写进帧记录的三对槽：整数进整数槽，表基址 = **代码块基址 + 4 × 偏移** 进指针槽；
    3. 帧的指令指针初值 = **代码块基址**。

    ⇒ **两张位置表就装在代码块内部**（不是独立数组）；表元素是 32 位整数，含义是**代码块内的 32 位字偏移**。
    ★ **「旧格式」判的是另一个字段，不是那个长度前缀**：存档里这一帧先有一条**定长的记录头**（**32 字节**；读顺序 = 记录头 → 长度前缀 → 负载），**头内 +4 处有一格 4 字节的格式标记**（ASCII 版本标记），它**位于长度前缀之前**、与长度前缀是**两格**。判据是把它按**无符号字符串**（**无符号字节逐比**，最多 4 字节、遇 NUL 即止）与常量 `"080 "` 比：**小于** `"080 "` ⇒ **不按三对解释**（负载不读；旧格式支的完整复原语义本版未读，见残差 `RES-OPS-SAVE-VERSION-AE-LAYOUT1`）；**不小于** ⇒ 按三对解释。同一格还会与**引擎自己的版本标记**（引擎自带的同一份 4 字节 ASCII 标记）比：**大于**引擎那份 ⇒ 报"引擎版本太旧"（这条属错误处置，不改变上面的分档）。
    ⛔ **不许把它当 4 字节整数比较**（那等于把 `"080 "` 折成一个小端 / 大端数，判据方向随之翻转）；也⛔ 不许拿"块长（至少 28）远小于 `"080 "` 的数值"去推"布局 1 的三对支恒不成立"—— 长度前缀与格式标记是**两个不同字段**，两者之间没有任何大小关系。
  - ★ 与前两种布局的一个**实质差别**：布局 1 这一帧的**代码体是从存档里整块读回的**（不是按脚本身份重新装载）—— 因此它的两张位置表也随代码体一起回来，而不是由装载期建立。
  - 三对里只有**前两对**被跳转族使用：**换脚本那一族读第二对的表**（优先）、**另一族读第一对的表**（回退）；**第三对没有已知读者**（保留槽位：⛔ 不许据此删字段，也⛔ 不许给它编语义）。
  - 用该布局重建帧、按每帧记录里的两个位置下标还原执行位置 —— 换脚本位置族优先、还原后推进 **3** 个字；否则另一族、推进 **0**；下标为 **−1** ⇒ 位置不变。★ 指令指针是**算出来**的（代码基址 + 4 × 位置表[下标]），⛔ 不许写成"从存档读回指令指针"。布局 2 / 3 还会把该位置写进当前帧的位置格（两族各一格）；布局 1 不写。
  - **每帧的两个当前位置下标不在暂存块里**：它们装在引擎按帧索引的两个数组里（每帧各一格）。★ 这两个格在发行路径上**没有已知写者**（见残差 `RES-OPS-SAVE-VERSION-AE-LAYOUT1`）⇒ 布局 1 的两族跳转能否拿到非零下标本版**不规定**；⛔ 不许实现成"下标恒 0"，也⛔ 不许因此跳过整个布局 1 的跳转。
  - 应用之后按**当前帧号**分叉：它**等于**存档记下的帧号 ⇒ **恢复帧号**并**清标志**、返回；**不等** ⇒ **帧号 + 1** 并重装，然后返回。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 本帧的推进格数 | ← 1（两条路径都写，且写在读标志之前） |
| 标志 = 0 的支 | 无其它写入 |
| 标志 ≠ 0 的支 | 按（主版本, 次版本）选布局 → 还原当前帧执行位置（推进 3 个字 / 0）；帧号等 ⇒ 恢复帧号 + 清标志；不等 ⇒ 帧号 + 1 并重装 |

**成立条件**

- 标志只有**一处置 1**：该标志由存档装载路径（`0x19f`，本版**未成篇**，见审计缺口）读入成功后置 1（同时把当前帧号清 0）；非 0 支的触发条件因此挂在那个缺口上。复位与本条在应用完成后都把它清 0。⇒ 早退的判据是**标志本身**，不是存档文件是否存在：⛔ 不许拿"有没有存档"替它。
- 主版本 1 的次版本门是 **20**：次版本不是 20 ⇒ 不应用（不是"用布局 1 硬套"）。
- 主版本 2 / 3 **不比较**次版本（次版本原样传给装帧入口）。⛔ 不许把它们也做成"必须等于 20"。
- 推进格数写在**读标志之前** ⇒ 早退路径也写了它（"什么都不做"指不改其它状态，不是"连推进格数都不写"）。
- 非 0 那一段里的两个键名是引擎写死的字符串（不是脚本给的），⛔ 不许当成操作数。

### 读 show-logo 标志：opcode 0x130

<!-- rule: CORE-OPS-SHOW-LOGO-130 -->

`0x130` 有一个操作数：它把引擎级的 **show-logo 标志**读出来，按整型写进**第 1 个操作数**。方向是"**标志 → 操作数**"，不是"操作数 → 标志"。

- 标志的**初值是 1**：引擎初始化时写入。**引擎只保证这个初值与 `0x9` 的复位清 0**；冷启动脚本在第一次读它之前是否执行 `0x9` 是程序行为（本作发行数据的静态冷启动路径没有命中）。
- 清 0 的机器站点在 `0x9`（重置并重装根脚本）的复位例程里（见「帧类指令」的 `0x9`）。该例程只有三个入口：① 脚本执行 `0x9`（该例程本身就是 `0x9` 的处理体）；② **窗口关闭消息**到达时的收尾路径 —— 引擎内部唯一的直接调用；③ 引擎**对外接口**上的一个无参方法（外部宿主可调）。⇒ 复位只由这三条触发。真实的「从游戏内回标题 / 打开菜单」流程是否会派发 `0x9`，取决于脚本（程序侧），本版未取证（见残差 `RES-OPS-SHOW-LOGO-130-RESET-REACH`）。清 0 与重装之间没有读者 ⇒ 先后不可观察；可观察的是「重跑根脚本第一次执行 `0x130` 时已经是 0」。
- 本条**不改标志**、不做范围检查、不改别的引擎状态；它也不把标志的值写回别处。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数 | ← 引擎级的 show-logo 标志（初值 1） |

**成立条件**

- ⛔ 反了方向（把操作数写进标志）会让"要不要显示 LOGO"变成脚本的单向设置，而原引擎做的是**读**。
- 初值 1 是**初始化时写入**的，不是一个编译期常量：重建引擎时同样写 1。
- 标志被清 0 之后本条读 0 —— 这是本条唯一可观察的分支来源。

### 两格中继：opcode 0x74 / 0x7f

<!-- rule: CORE-OPS-PARAM-74-7F -->

两条各有一个操作数，用**同一格**引擎级参数 —— **参数格**（文本自动推进时长，即逐字符显示的每字间隔）：

- **`0x74`**：推进格数 ← 3；读整型(第 1 个) **原样**写进那一格（不归一、不夹取）。
- **`0x7f`**：推进格数 ← 3；把那一格的值经**写整型**原语写进第 1 个操作数。

因此"先 `0x74` 再 `0x7f`"是**值的往返**：写进去的整数读出来还是同一个整数（写整型会编码，读整型会解码；两次编解码互逆）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| `0x74` 写的那一格 | ← 读整型(第 1 个) |
| `0x7f` 读的那一格 | → 写整型(第 1 个, 该格) |

**成立条件**

- 两条**不是**"同一个操作的两种写法"：一条写、一条读；⛔ 不许实现成同一条。
- 那一格的**初值是启动时写进去的**：从命名键 `message:MessageSpeed` 读入（该键在建立配置库时已内建登记，默认 **5**）⇒ 在 `0x74` 之前执行 `0x7f`，读出的是该键的值（除非此前被 `0x1b5` 改过）。
- 只有 `0x1b5` 同时写这一格与命名键；`0x74` **只写格、不写键** ⇒ 用 `0x74` 改的值不会进配置库（重启后回到键值）。
- 这一格是**引擎对象顶层字段**（不随帧）：换帧 / 装帧不改它；重建引擎对象会重新从 `message:MessageSpeed` 取初值。
- 两条都不写返回值（返回值由分派器丢弃）、不碰状态选择字；除那一格与操作数访问原语的缓存外，不改其它引擎状态。
- 消费方见「ADV 文本层」的**逐字符显示**条（每字间隔 = 该格：非 0 且第 27 位未置 ⇒ 置打字位、按它启动文本计时器；等于 0 ⇒ 同帧揭示全部）与「配置」的 `0x1b5`（该条同时写这一格与命名键 `message:MessageSpeed`）。本条只规定"一格读写"。

### 清一个待服务位：opcode 0x0d9

<!-- rule: CORE-OPS-STATUS-CLEAR-D9 -->

`0x0d9` **没有操作数**。推进格数 ← **1**，然后：

1. 把**状态选择字**的第 **12** 位（位号从 0 起数）清 0（读-改-写，其它位原样）。★ 门开着时第 12 位恒 0 ⇒ 这一支是**防御性 / 空转**，本版不把它当可观察副作用。
2. 若**队列泵占用标记**非 0，则对**状态选择字的待恢复副本**做读-改-写、清其第 12 位。

- 这两个字的身份不是本条新定的：泵在挂起调用帧时把状态选择字**整字存进待恢复副本**、把活动的那一份清 0，并在整趟泵里把**队列泵占用标记**置 1；泵期间"对外有效"的状态选择字就是那份**副本**（读者按标记选副本），泵帧结束时再把副本并回活动字 —— 见「执行区间的进入与离开」的泵合同。
- ⇒ 第 2 步清的是**泵期间可被读到的那个值**。只清活动字会让泵帧里的读者仍看到第 12 位（那一位"是否已服务"就会读错）。
- ⛔ 不许把第 2 步实现成"非泵期间也清副本"：那份副本在非泵期间是旧值，清它不可观察，却会掩盖"判据是标记"这件事。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 12 位的待服务标记被撤 | 状态选择字第 12 位 ← 0（门开着时本就是 0） |
| 泵进行中时同一标记被撤 | 待恢复副本的第 12 位 ← 0（这份副本就是泵期间对外有效的状态选择字） |

**成立条件**

- 清位是**读-改-写**：⛔ 不许把整字写 0（那会踩掉别的位，包括等待位 / 影片位）。
- 不读操作数 ⇒ 不会抛操作数类型异常。
- 第 2 步的判据是**队列泵占用标记非 0**，不是"某个对象存在且可用"：⛔ 不许拿别的格子替它；标记由谁置、谁清见泵合同。
- 第 2 步清的字与第 1 步**不是同一个**：泵期间活动字已经是 0，两处清的是"泵期间的那一份"与"平时的那一份"。
- 第 12 位由谁置起、以及它的服务体在「仅当区间忙 = 0 时的一个等待 / 放行步（与第 11 位配对）」（见「位是待服务标记，清不清由服务分支决定」的位序表）之外的**其余分支**，本版**未取证**（见残差 `RES-CLEAR-D9-BIT12`）。

### 引擎级状态字的写与消费：opcode 0x1cf / 0x1bf

<!-- rule: CORE-OPS-STATUS-WORD -->

这一对操作**同一个引擎级状态字**（32 位整数），一个是写、一个是消费；消费还会写一个**相邻的引擎格**。它与「执行与时间」的**主循环模式字**（`0x24e` 写的那个字）**是否同一格未取证**（见残差 `RES-OPS-1BF-MODE-WORD-ALIAS`）；本条只规定这一对自身的效果。

- `0x1cf`（1 个操作数）：把第 1 个操作数**读成整数**后**原样**写进状态字（不归一、不夹取、不做范围检查）。
- `0x1bf`（无操作数），两步，顺序固定：
  1. 若状态字的**第 16 位**为 1 ⇒ 把状态字**整字清 0**（⚠ 不是只清第 16 位）；
  2. 随后若状态字的**第 0 位**为 0 ⇒ 把**相邻格**写成 **1**；否则不动那一格。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 状态字 | ← 第 1 个操作数（`0x1cf`，原样） |
| 「请把状态字清掉」 | 第 16 位（`0x1bf` 见位即整字清 0） |
| 相邻格 | 第 0 位为 0 时 ← 1（`0x1bf`） |

**成立条件**

- **「整字清 0」不是「清那一位」**：把第 16 位的清法实现成 `and ~0x10000` 会让其余位残留 —— 后续读那些位的人会看到本该消失的状态。★ 这是本条最容易写错的一处。
- 第 0 位的判据在**清整字之后**：因此第 16 位与第 0 位**同时为 1** 时，整字被清 ⇒ 第 0 位已是 0 ⇒ 相邻格**会**被写 1。⛔ 不许把两步的顺序倒过来（先判第 0 位会得到相反结果）。
- `0x1cf` 的写是**覆盖**，不是「按位或」：先前置起的位全部丢掉。
- 两条都不产生脚本可观察的返回值。

### 把状态格读进操作数：opcode 0x1cc

<!-- rule: CORE-OPS-STATUS-CELL-READ -->

`0x1cc` 有 1 个操作数：把引擎级**状态格**的整数值**原样**写进第 1 个操作数。第 1 个操作数**只写不读**；这条不改变任何其它引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数指向的整数 | ← 状态格的当前值（原样，不归一） |

**成立条件**

- 这是**读引擎格 → 写操作数**，方向与 `0x1cf`（操作数 → 状态字）相反；⛔ 两条不许共用一个实现（方向反了不会报错，只会把脚本写坏）。
- 值**不归一**：状态格里存的是什么就搬什么（与 `0x1b6` 把布尔归一成 0/1 不同，见「两个引擎标志格」）。
- 该格由别的路径写（`0x19c` 也读同一格）；本条**不保证**它被初始化过。

### 引擎级模式位：opcode 0x19b / 0x19c / 0x1c7

<!-- rule: CORE-OPS-MODE-BIT -->

三条操作**引擎级标志字的一个位**（第 27 位）与七个引擎格。为了让下文的「置 / 清 / 判」不混，这里给它们代号（代号不是名字）：

- `A` / `B` / `D`：`0x19b` 清的三个格，`0x19c` 条件写的那三个格；
- `C`：由 `0x19a` 原样读出的那一格，`0x19c` 的第一个判据；
- `E` / `F`：`0x19c` 的两个附加判据格；
- `G`：`0x19c` 置位支写的那个格（与 A / B / D / E / F 都不是同一格）；
- `Y`：由 `0x1b6` / `0x1b7` 读写的那个格（见「两个引擎标志格」）—— 与 `C` **不是同一格**。

- `0x19b`（无操作数，**清**）：第 27 位清 0（按掩码清，其它位保留）；再把三个格 `D` / `A` / `B` 各写 0（顺序：D 先、A 次、B 后，**都在清位之后**）。
- `0x19c`（无操作数，**置 / 条件**）：
  1. `A` ← 1、`B` ← 0；
  2. 若 `C ≠ 0` ⇒ `D` ← 1，然后进第 4 步；
  3. 否则（`C = 0`）：
     - 若 `E ≠ 0` ⇒ 直接进第 4 步（★ **不动 `D`**）；
     - 否则若 `F ≠ 0` ⇒ **本条到此结束**（保留 A=1、B=0，位与 `D` 都不动）；
     - 否则 ⇒ `D` ← 0、第 27 位清 0，结束；
  4. （置位支）第 27 位置 1，再把 `G` ← 1，并**若第 29 位为 1 就把它清 0**。
- `0x1c7`（1 个操作数，**读**）：第 1 个操作数 ← **第 27 位 ? 1 : 0**（归一成 0 / 1）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 模式位（第 27 位） | `0x19b` 清 / `0x19c` 条件置 / `0x1c7` 读成 0 或 1 |
| 引擎格 A / B / D / G（+ 第 29 位的清） | 由两条无操作数指令写（见上） |

**成立条件**

- 三条**不是同一条**：一条按位清 + 清格，一条按三个格的条件置，一条只读成 0/1。⛔ 不许合并。
- `0x1c7` 的结果**只有 0 / 1**：⛔ 不许把「位是在的」写成 `0x8000000`（读结果的人用它做真假判断）。
- `0x19c` 的四条分岔**互斥且有序**：`C` 非 0 与 `C = 0` 走不同支；`E` / `F` 的判据都在 `C = 0` 之内。⛔ 不许把 `E` / `F` 判到 `C` 的外面。
- `0x19c` 的 `E` 支与 `C` 支**落点不同**：`C` 支置 `D`、`E` 支**不碰 `D`**。⛔ 把两支合成「判到任一格非 0 就 `D` ← 1」会写脏 `D`。
- `0x19c` 的 `F` 支**不改位也不改 `D`**：把 `F` 当成 `E` 的同类会让位被误置。
- `0x1c7` 只写第 1 个操作数，不读它。
- **第 29 位的领域名已定**（见「执行与时间」的服务链位序表）：它是**打字位**，服务体是主循环里的**文本推进器**；
  置位支顺手**清第 29 位**（进入消息逐帧推进即停掉打字推进）。第 27 位的名字归「成对写：opcode 0x88」条，本条不重复。
- **六格的数据效果与读者**（领域名未定的只有 A / C，见残差 `RES-OPS-MODE-BIT-ROLE`）：
  - **D**：非 0 时，消息处理把**输入字第 6 位**置起（= 注入"取消消息跳过"这一路）；它只按"是否 0"判，不是计数。
  - **B**：一个**三态会话值（0 / 1 / 2）**，写它和读它的**都是消息处理自己** ⇒ 不是脚本可读的量；⛔ 不许把它当"位 27 的影子位"。
  - **E**：一个 0/1 的"待处理"标志；★ **它就是 `0x1cc` 读的那个「状态格」**，也是消息处理清第 27 位的前置之一。
  - **F**：唯一读者是 `0x19c` 的第三判据；⛔ 不许把它并进 E。
  - **G**：置起它的是"进入消息逐帧推进"的两条路（本条的置位支与 `0x88` 的非 0 支），读者在消息处理里。
  - **A / C**：数据效果已定（谁写、值域），**领域角色未定**（见残差 `RES-OPS-MODE-BIT-ROLE`）。

### 两个引擎标志格的读与写：opcode 0x19a / 0x1b6 / 0x1b7

<!-- rule: CORE-OPS-FLAG-CELLS -->

- `0x19a`（1 个操作数）：第 1 个操作数 ← 引擎格**原值**（不归一）。
- `0x1b6`（1 个操作数）：第 1 个操作数 ← `另一个引擎格 ≠ 0 ? 1 : 0`（**归一成 0 / 1**）。
- `0x1b7`（1 个操作数）：**另一个引擎格** ← `第 1 个操作数 ≠ 0 ? 1 : 0`（**先归一，再存**）。
  该格是**自动推进（auto-message）的开关**：非 0 时 `0x72` 会按自动消息时长武装计时器、到期放行等推进位；
  它也门住逐帧的自动消息轮询。⛔ 它**不是**"语音在播"那一格（那一格由语音族指令维护）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数 | ← 格 X 的原值（`0x19a`）；← 格 Y 归一后的真假（`0x1b6`） |
| 格 Y | ← 操作数归一后的真假（`0x1b7`） |

**成立条件**

- `0x19a` 与 `0x1b6` **读的不是同一格**，且一条归一、一条不归一：⛔ 两条不许合并。
- `0x1b6` / `0x1b7` 是**同一格的反方向**：一条读成 0/1、一条把 0/1 写进去。⛔ 不许只实现一条。
- `0x1b7` 存的**是归一后的值**：把 `-1` 或 `2` 原样存进去，会让 `0x1b6` 读出来仍是 1（看不出差别），但会让「同一格被当整数读」的其它路径看到不同的数 —— 本条的可观察面是「存进去的只能是 0 / 1」。
- 三条都只碰一个操作数（写），不读它。

### 把当前层号落进引擎格：opcode 0x1ad

<!-- rule: CORE-OPS-LAYER-CELL -->

`0x1ad` **没有操作数**：把**当前层号**（一个引擎级整数，表示当前在跑哪一层脚本；与帧号的关系本版未取证）写进**一个引擎格**。这个格的复位值是 **−1**（引擎做整体复位时写 −1）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 当前层号（单个值） | 引擎格 ← 当前层号（复位值 −1） |

**成立条件**

- 写的是**当前层号**，不是层数、也不是任何记录的地址。
- 该格被复位路径写成 **−1** ⇒ 「未写过」是可区分的（−1 与 0 不同）。⛔ 不许把初值实现成 0。
- 本条不切层（不改当前层号），也不改与该层号关联的记录（记录布局属机器细节）。

### 原值写一个引擎标志格：opcode 0x142

<!-- rule: CORE-OPS-FLAG-CELL-142 -->

`0x142` 有一个操作数。它把该操作数**按整型读出**的值**原样**写进一个**引擎标志格**，然后返回。

- 不读其它操作数、不归一、不做范围检查、不发平台请求。
- 该格**只被对外接口的一次查询读取**（返回值 = 「该格非 0」）；引擎内部没有别的读者 —— 谁调用这次查询、查询结果用来门控什么，在本规范的边界之外（见残差 `RES-OPS-142-CELL-NAME`）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 引擎标志格 | ← 第 1 个操作数的原值 |
| 该格的对外读数 | 对外查询的返回值 = 「该格 != 0」（0 / 1；不改变该格） |
| 该格的复位值 | 1（两处启动初始化各写 1） |

**成立条件**

- 写的是**原值**：写 3 就存 3，⛔ 不许折成 0 / 1（读者自己判非 0）。
- 本条只碰这一格。
- 该格的领域名仍未取证（见残差 `RES-OPS-142-CELL-NAME`）—— 本规则只规定"原值进去、`非 0` 为真（经对外查询读回）"。
