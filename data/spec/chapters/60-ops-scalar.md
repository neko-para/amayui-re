## 引擎级标量与事件

本章 9 条规则 / 18 个 opcode。

## 引擎级标量写（opcode 0x149 / 0x21b / 0x252 / 0x88）

这一族把操作数的值写进**引擎里固定的格**（不是池、也不是按索引的表；一条指令可以写一个或多个格）：格的身份属机器细节，本版只规定「读什么、写成什么形态、有没有归一、有没有分支」。

### 薄标量写：opcode 0x149 / 0x21b / 0x252

<!-- rule: CORE-OPS-SCALAR-THIN -->

三条各有一个操作数，各写**一个固定格**：

- `0x149` 与 `0x252` 把操作数按整型语义读出、**原样**写进各自的格（不归一、不夹取）。
- `0x21b` 把同一个值**归一成 0 / 1**：值为 0 ⇒ 写 0；任何非 0（含负数）⇒ 写 1。
- 三条都：只读**一个**操作数、不调用别的引擎函数、**不把返回值写回操作数**（返回值由分派器丢弃）。
- 写进去的是**解码后**的整数值：池里的编码位模式不参与本规则。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该指令负责的那个引擎级格 | ← 读整型（第 1 个操作数）或它的 0/1 归一 |

**成立条件**

- `0x21b` 的归一不可省：写原值看起来「也能跑」，只有读它的人才会发现区别。
- 三条都不是「写回操作数」：操作数所在池的内容不变。

### 成对写：opcode 0x88

<!-- rule: CORE-OPS-SCALAR-PAIR-88 -->

`0x88` 有一个操作数，读成整型值，然后：

1. 把**同一个值**写进**两个固定格**（两个都写，不看值）；
2. 按值分支：**非 0** ⇒ 把第三个固定格写成**常量 1**；**等于 0** ⇒ 把**状态选择字**（门读的那一个字，见「执行与时间」）的**第 27 位（位号从 0 起数）清 0**（读-改-写，其它位不变）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 两个引擎级格 | ← 读整型（第 1 个操作数） |
| 非 0 支 | 第三个格 ← 常量 1 |
| 为 0 支 | 状态选择字的第 27 位 ← 0 |

**成立条件**

- 两支**互斥**：非 0 时不碰状态字；为 0 时不写第三个格。
- 清位是**读-改-写**：其它位原样保留（把它写成「整字 = 0」会踩掉别的位）。
- 这条与 `0x71`（见「文本子系统的请求：opcode 0x71」）**成对**：`0x71` 在文本子系统返回非 0 时**置**第 27 位，本条在值为 0 时**清**同一位。本版只规定「这里会清」，**不**规定「清了之后放行什么」（本版不规定）。第 27 位**不是等待位**（等待位是第 10 位，见「等待（opcode 0x21c）」）。

### 薄标量写：启动前段五条（opcode 0xfe / 0x10f / 0x248 / 0x261 / 0x8b）

<!-- rule: CORE-OPS-SCALAR-THIN-PROLOGUE -->

五条各读**一个**操作数、各写**一个**固定格；都**不调用别的引擎函数**、**不把返回值写回操作数**（返回值由分派器丢弃）。写进去的都是**解码后**的整数值（池里的编码位模式不参与）。

| opcode | 落点 | 形态 | 检查 |
|---|---|---|---|
| `0xfe` | 引擎级的一格 | 原样 | **值 ≤ 31**（无符号比较），否则**抛显示消息型异常**、该格不变 |
| `0x10f` | 引擎级的另一格 | 原样 | 无 |
| `0x248` | **进程级**的一格（不属于引擎对象） | 原样 | 无 |
| `0x261` | 引擎级"五格连续段"的**最低一格** | 原样 | 无 |
| `0x8b` | **字体对象**的一格 | 原样 | 无 |

- `0xfe` 的范围检查是**引擎自己抛的异常**（显示消息型；见「异常与错误通道」），不是静默截断、也不是夹取：越界时该格保持原值。★ 这个上界与「引擎级状态」的标量表**不同源**：那里 31 也是字面常数（表宽只约束索引 8），这里同样是写死的常数。
- `0x248` 写的是**进程级全局**，不是引擎对象的字段：重建引擎对象**不会**复位它。⛔ 不许把它与引擎级那几条合并成"同一个标量表的相邻格"。
- `0x261` 与 `0x260` 的四格是**同一段连续五格**：`0x261` 是最低一格、`0x260` 是从它上面一格起的四格（见「成对与四格写：opcode 0x1a4 / 0x260」）。⛔ 两条落点不同，不许互换。
- `0x8b` 写的是那个**字体对象**（`0x75` / `0x76` / `0x77` / `0x1a4` / `0x197` / `0x1a5` / `0x2bd` / `0x2fe` 共用的接收者）的一格；其余四条写的是引擎对象顶层的格。⛔ 不许把这一族当成"引擎对象的连续字段"。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该指令负责的那个格 | ← 读整型（第 1 个操作数）；`0xfe` 另加上界 31 |

**成立条件**

- 只有 `0xfe` 有范围检查：把它推广到同族其它四条，会让本该写入的值被拒。
- 五条都**不归一**（不像 `0x21b` 那样归成 0 / 1）：写进去的可以是任意整数。

### 成对与四格写：opcode 0x1a4 / 0x260

<!-- rule: CORE-OPS-SCALAR-PAIR-PROLOGUE -->

两条把**多个操作数**一次写进**相邻的格**，都不调用别的引擎函数、不归一、不写回操作数：

- `0x1a4`（两个操作数）：第 1 个 → 字体对象的一格；第 2 个 → **紧邻的下一格**。读序 **先第 2、再第 1**。⛔ 两个落点不许交换（交换后两个值整体错位，而写入本身不报错）。
- `0x260`（四个操作数）：第 1、2、3、4 个依次写进**四格连续**（第 1 个最低、第 4 个最高）。读序是 **先第 4、再第 3、第 2、第 1**（倒序读、正序写）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| `0x1a4` 的两个格 | ←（第 1 个, 第 2 个） |
| `0x260` 的四格连续段 | ←（第 1 个, 第 2 个, 第 3 个, 第 4 个），按地址从低到高 |

**成立条件**

- `0x260` 的"第 1 个进最低格"是合同的一部分：把读序当写序（倒着写）会让四格整体反过来。
- `0x1a4` 的两格与 `0x76` / `0x77` / `0x78` 写的格在**同一块字段**里但是不同的格。
- 两条都不检查、不建记录：写不进去只有操作数类型异常一条路。

### 带变换的格写：opcode 0x76 / 0x77 / 0x2bd

<!-- rule: CORE-OPS-SCALAR-VARIANT-PROLOGUE -->

三条各读**一个**操作数，写进**字体对象**的格，并且写完都请求**重建字体**（外部请求：字体对象据此重建它持有的字体；重建的内部过程本版不规定）。三条的**写值形态各不相同**：

| opcode | 落点 | 写进去的值 | 写完之后 |
|---|---|---|---|
| `0x76` | 字体对象的一格 | **低 24 位的字节倒序**（第 0 字节与第 2 字节互换、第 1 字节留在中间，高 8 位丢弃） | **调用**重建入口（会返回） |
| `0x77` | 同一段里紧邻的另一格 | 同上 | **调用**重建入口（会返回） |
| `0x2bd` | 字体对象的**两格** | **二选一常量**：操作数 ≠ 0 ⇒ 两格都写 **700**；操作数 = 0 ⇒ 两格都写 **0** | **尾跳**进重建入口（本条不再返回分派器） |

- `0x76` / `0x77` 写的是**倒序后的字节模式**，不是操作数原值：写成原值不报错，只是那两格承载的编号 / 颜色整体错位。⛔ 两条只差落点，不许共用一个格。
- `0x2bd` **不写操作数本身**：它把操作数当**开关**，写的是 700 或 0。⛔ 不许实现成"写操作数原值"（那会同时丢掉 700 与"二选一"）。
- 调用与尾跳的区别是**可观察的**：尾跳之后，本条之后的指令不会被执行（控制流已经交给重建入口）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| `0x76` / `0x77` 的格 | ← `bswap24(读整型(第 1 个))`（低 24 位字节倒序） |
| `0x2bd` 的两格 | ← 700 / 0（由操作数是否为 0 决定） |
| 重建请求 | 一次对字体重建入口的调用（`0x76` / `0x77`）或尾跳（`0x2bd`） |

**成立条件**

- 三者的落点都在那个字体对象里；⛔ 不许把它们写进引擎对象顶层。
- `0x2bd` 的 700 是一个**引擎写死的常量**，不是从操作数算出来的。
- `0x2bd` 的两格相距很远、不在同一段字段里：它们同属那个字体对象，但不是"相邻两格"。

### 按表索引写一格：opcode 0x10c

<!-- rule: CORE-OPS-SCALAR-TABLE-10C -->

`0x10c` 有两个操作数：**第 2 个是索引**、**第 1 个是值**。已观察到的形态是**两级索引**：

1. 先检查**值**：按无符号比较 > 31（含负值）⇒ 抛**显示消息型异常**，不改任何状态；
2. 再用**索引**在引擎里一张表里取一格，得到**第二个下标**；
3. 把值写进**另一段数组**的"第二个下标"那一格。

★ **这条指令对引擎数据的完整效果本版不规定**（原因：那张表与那段数组各记什么、二级下标的取值域都没有取证）。

- 被检查的是**值**，不是索引：**索引完全不检查** ⇒ 越界索引会读到那张表的外面（未定义行为，按崩溃诊断）。
- 读序：**先第 2 个（索引）、再第 1 个（值）**。索引读失败时值还没被读。
- 这条**不是**「引擎级状态」那三条标量表的同族：那三条的索引**直接就是表下标**，这一条的索引先被换成二级下标。⛔ 不许把它实现成第四条标量表。
- 值不做归一：写进去的就是读出来的整数。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 值 → 某一格的写入 | 表[读整型(第 2 个)] 给出第二级下标 i；写第 i 格 ← 读整型(第 1 个) |

**成立条件**

- 两个上界分开看：值 ≤ 31 是引擎里写死的字面常数（越界**抛**）；索引没有上界（越界**未定义**）。
- 表与那段数组各记什么，**本版不规定**（原因：两张表的身份没有取证）：⛔ 不许据"写进去的是什么"替它们编用途。

## 启动前段的刷新与门（opcode 0x143 / 0xae / 0x130）

这三条都出现在**脚本之前的启动链**上，各自只碰很少的引擎数据；但三者的**分支条件**都可观察 —— 写错一格不报错，只会让启动链走另一条分支。

### 事件刷新：opcode 0x143

<!-- rule: CORE-OPS-EVENT-143 -->

`0x143` **没有操作数**。它依次做四件事：

1. 把本帧的**推进格数**先写成 **1**（= 2 × 0 + 1）；
2. 把引擎级的**「正在刷新」标记**置 1；
3. 对一张 **255 格**的登记表逐格检查：**非 0 的格**各向引擎的事件容器送一次**固定常量**（所有格送的是同一个常量）；全 0 ⇒ 一次也不送。★ 每次送的动作本身还带一个"顺手泵一次队列"的尾巴，但此刻「正在刷新」标记是 1 ⇒ 一次也不泵（这就是那个标记的用处）；
4. 把「正在刷新」标记清回 **0**、把推进格数清 **0**、**自己把本帧的指令指针推进 4 字节**，然后**尾跳**进事件队列的处理入口。

- 第 4 步之后那个入口是**队列泵**。它的两个早退条件是"泵已被占用"（另一个标记非 0）与"队列头等于队列尾"（队列空）⇒ 早退时**直接返回**，控制流落回本条自己算出的"下一条指令"。这是启动链里最常见的路径。
- **队列非空** ⇒ 该入口取一件事件、并按事件自己的要求改变控制流（换帧 / 跳转）。那一支**本版不规定**（原因：事件容器与队列处理没有取证）。
- 推进是**本条自己做的**（先把推进格数清 0、再加 4 字节）：⛔ 不许留给分派器再加一次 —— 那会让每条 `0x143` 跳过 8 字节。
- 那 255 格的登记表与事件容器的**领域身份本版不规定**（原因：没有取证）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 「正在刷新」标记 | 置 1 → 清 0（同一趟内） |
| 登记表里非 0 的格 | 每格一次"向事件容器送常量"的请求 |
| 本帧的推进格数 | 先写 1、再写 0 |
| 本帧的指令指针 | ← 本条位置 + 4 字节 |

**成立条件**

- 顺序固定：置标记 → 逐格送 → 清标记 → 清推进格数 → 推进 → 尾跳。
- 「正在刷新」标记的作用是**防递归**：它非 0 时，第 3 步那串"送一格"不会顺带泵队列。
- 本条**不读任何操作数**，因此也不会抛操作数类型异常。

### 存档版本检查：opcode 0xae

<!-- rule: CORE-OPS-SAVE-VERSION-AE -->

`0xae` **没有操作数**。它先把本帧的推进格数写成 **1**，然后读一个**引擎级标志**（领域身份未定）：

- 标志 **= 0** ⇒ **什么都不做**，直接返回。这条路径的全部效果就是那个推进格数；它**连一个命名键都不读**。
- 标志 **≠ 0** ⇒ 进入**版本判定 / 修复路径**：从引擎的命名键存储读两个键（`set:SaveVersion1` 与 `set:SaveVersion2`），按两者的值分支；分支里会**改当前帧号**、改写帧的推进格数，还会把帧的指令指针指到别处。**这一整段本版不规定**（原因：修复路径没有逐条取证）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 本帧的推进格数 | ← 1（两条路径都写，且写在读标志之前） |
| 标志 = 0 的支 | 无其它写入 |
| 标志 ≠ 0 的支 | 未建模（本版不规定） |

**成立条件**

- **早退的判据是标志本身**，不是存档文件是否存在：⛔ 不许拿"有没有存档"替它。
- 推进格数写在**读标志之前** ⇒ 早退路径也写了它（"什么都不做"指不改其它状态，不是"连推进格数都不写"）。
- 非 0 那一段里的两个键名是引擎写死的字符串（不是脚本给的），⛔ 不许当成操作数。

### 读 show-logo 标志：opcode 0x130

<!-- rule: CORE-OPS-SHOW-LOGO-130 -->

`0x130` 有一个操作数：它把引擎级的 **show-logo 标志**读出来，按整型写进**第 1 个操作数**。方向是"**标志 → 操作数**"，不是"操作数 → 标志"。

- 标志的**初值是 1**：引擎初始化时写入。因此启动链里第一次读它一定得到 **1**。
- 清 0 的路径是引擎自己的一段复位例程（谁调用那段例程属启动流程，本版不规定）。
- 本条**不改标志**、不做范围检查、不改别的引擎状态；它也不把标志的值写回别处。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数 | ← 引擎级的 show-logo 标志（初值 1） |

**成立条件**

- ⛔ 反了方向（把操作数写进标志）会让"要不要显示 LOGO"变成脚本的单向设置，而原引擎做的是**读**。
- 初值 1 是**初始化时写入**的，不是一个编译期常量：重建引擎时同样写 1。
- 标志被清 0 之后本条读 0 —— 这是本条唯一可观察的分支来源。
