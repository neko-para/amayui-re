## 执行与时间

本章规定**指令流怎样被驱动**：一次迭代做几件事、什么条件下才执行指令、等待怎样结束、时间从哪里来。
单条指令改了哪些引擎数据属于各指令族章；操作数的读法属于「数据池」。

### 一次迭代做哪些事

<!-- rule: CORE-VM-LOOP -->

正常迭代按固定顺序走：先在**迭代头**按节流决定是否泵一次宿主消息（一次泵 = 在泵点排空当前消息队列；请求序列见「启动期的平台请求」的事件入口，本条只规定节流）；随后**读一次系统毫秒时钟**；再在条件允许时把这次读数交付给**两个声音子系统（音效 / 语音）**各一次；**场景的窗在门之前推进**（见「场景计时窗」），随后在**门之前**决定是否发出**一次渲染步请求**；最后过门——**服务状态选择字里的一个位**，或者**执行一条指令**。泵消息与"服务一位 / 执行一条"可以在同一次迭代里都发生；服务一位与执行指令互斥。

- **门前渲染**：门之前还有一次**渲染步请求**。是否发出由场景闸门决定；本版只确认下列条件全部为真才发：**场景绘制开关 = 1**、状态选择字的**等消息位**为 0、渲染器不忙、不处于「别处驱动」，**且 `0x21b` 的标量为非 0，或状态选择字的等待位 / 影片位为 1**，并且**场景需要重绘**（判据见「帧步进」的 `RES-RENDER-STEP-NEEDS-REDRAW`）。最后这一条是**内层条件**：脏本身**不**触发渲染。这些格的身份、缺省、清点本版不规定（见「帧步进」的残差）。门关着时照常判断。
- **`0x20c` 例外**：门后执行的 `0x20c` 直接请求一次渲染步，**不经过上述门前闸门**。它是否与同一迭代的门前渲染重复，以及两次渲染步的帧记录 / 时间戳语义，本版不规定（见残差）。
- 门前渲染与这一迭代派发哪条指令**无关**；一次迭代仍**至多执行一条指令**，⛔ 没有"一帧执行 N 条"的规则。
- 渲染步的**提交条件**见「帧步进」；内部顺序、38 目标见该条的 `RES-RENDER-STEP-INTERNAL`。

- 时间推进**不在**门后的分支里：它排在门之前，不占"一件事"的名额。
- 第三步有一个开关：引擎处于**暂停**状态且等待位为 1 时整段跳过；暂停是引擎的一个状态，本版只规定它在时间交付与场景推进上的作用，不规定何时进入 / 离开。
- 本迭代内所有子系统共用同一个时钟读数。
- 回消息是宿主相关的行为；本版只登记它存在与节流，泵的请求序列（窥视 / 取一条 / 翻译 / 派发 / 退出消息）见「启动期的平台请求」的事件入口，本条不重复。
- 一条指令的处理可以在**保护区**里抛异常；此时下一次迭代从哪继续由「启动入口：入口 → 初始化 → 主循环」的「异常的处置」三支决定：重试 / 忽略回**保护区入口**（会重做一次**准备段**，含一次消息泵），正常返回只回**迭代头**（按节流泵）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 本迭代的"现在" | 迭代头的一次时钟读数（毫秒） |
| 本迭代做了哪件事 | 消息泵（可以没有）、门前一次渲染步请求（可以没有；`0x20c` 的重复语义见残差）、一个状态位或一条指令（后两者至多其一） |
| 时间是否交付 | 每迭代一次（交给声音）；引擎暂停且等待位为 1 时整段跳过 |
| 本迭代是否请求渲染 | 门前闸门的判定结果（走 / 不走；不作为独立记录字段保存） |

**成立条件**

- 一次迭代**至多**执行一条指令；没有"一帧执行 N 条"的规则。
- 回消息可以有节流，不是每次迭代都做；泵完仍继续本迭代的其余步骤。
- ★ "每迭代读一次时钟"不等于"窗一定推进"：只有"有窗"位为 1 的条目才参与推进（见「场景计时窗」）。

### 门：状态选择字整字为 0 才执行

<!-- rule: CORE-VM-GATE -->

**一条指令只在状态选择字整字为 0 时执行**。整字非 0 时，本迭代不派发指令：只服务其中一个位，然后回到迭代头——时钟读数与时间交付排在门之前。

- 判据是**整字**比较，不是逐位与：任意一个位被置起都会挡住派发。
- 这就是"某条指令看起来没有执行、只有时间在走"的唯一机制。
- **术语**：本版把 `0x88` / 「引擎级模式位」操作的那个字称为「引擎级标志字」，**它就是这里的状态选择字**；`0x1cf` / `0x1bf` 写的「状态字」与 `0x1cc` 读的「状态格」是**别的**引擎格，不是门字。`0x1ce` 置 / 清的就是状态选择字的**第 30 位**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 门开着 | 状态选择字 = 0 |
| 门关着 | 状态选择字 ≠ 0（等多久由位的服务分支决定） |

**成立条件**

- 位由谁置、服务分支做什么、何时清，见各指令条目与「位是待服务标记，清不清由服务分支决定」。

### 位是待服务标记，清不清由服务分支决定

<!-- rule: CORE-VM-STATE -->

状态选择字的每一位表示"有一件引擎级工作待做"。迭代服务**其中一个**命中的位，只服务那一件（位号顺序、以及多个位同时置起时先服务谁，**本版不规定**）；清位由该位的服务分支决定：清掉，下个迭代门就打开；没清，下个迭代继续服务同一位（表现为门持续关着）。**例外**：某位可以在同一次服务里先清后按条件再置（影片位就是这样），此时门继续关着；第 30 位（乱数启用）的服务分支**不清位**，所以启用后门持续关着；停用支因门关而不可达，唯一放行是外部清位写点（可达性未取证）。

- 等待位就是这样：场景还有动画时，服务分支**不清**它，门一直关着（见「等待（opcode 0x21c）」）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 有 N 件待做 | 状态选择字里的 N 个位；每迭代服务至多 1 个，清位与否由服务分支决定 |

**成立条件**

- 本版规定**等待位**、**影片位**两个服务语义（后者见下一则），并登记第 30 位“服务分支不清位”；其余位只登记存在，不解释含义。

### 影片对象表的服务（门之前）

<!-- rule: CORE-VM-MOVIE -->

**影片位不是生命周期服务**：它只让门保持关闭；真正的“播完 / 循环 / 销毁”在**门之前**的影片对象表服务里完成。每次迭代在过门之前，若“有活动对象”标记为 1，就扫描对象表的全部影片槽（槽号 0..999）：

- 先清“有活动对象”，再逐槽处理：
  - 槽为空 / 不是影片对象 ⇒ 跳过。
  - 对象**未启动**（打开 / 绑定失败留下的残留）⇒ 跳过：不进入播完判据、不维持影片位（见残差）。
  - `停止时间 <= 当前位置` ⇒ 进入收尾判据；否则保留对象，标记“有活动对象”。后端如何报告结束 / 新帧标志 / renderer 忙等其它检查本版不规定（见残差）。
  - 收尾判据成立且**循环位**（选项字第 0 位）为 1 ⇒ 回到开头重新启动，保留对象与槽，不销毁、不填纹理；“有活动对象”保持，影片位保持置起。
  - 收尾判据成立且循环位为 0 ⇒ 正常收尾：读选项字 → 若 `(选项字 & 3) != 2`，对该纹理发出一次“填纹理”请求（像素效果本版不规定）→ 停止 / 关闭 / 释放播放后端 → **移除对象表槽**；不释放纹理对象本身。
- 扫描结束后，“有活动对象” = 是否还有**已启动**的影片槽。
- 影片位服务（门上的 `0x2000`）只做：清影片位；若对象表仍有**已启动**影片槽，再置影片位；否则让门在下一迭代打开。它**不**轮询、不销毁、不填纹理。这是“纹理影片”这一支的服务；窗口影片共享位的分派见残差。
- 暂停时 `0x2000` 的服务分支是否执行本版不规定（暂停的进入 / 离开不在本条；见残差）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某个槽上有影片在播 | 对象表该槽非空、对象已启动且未到停止点 |
| 影片占用主循环 | 影片位 = 1；只要对象表还有已启动影片槽，位服务就把它重新置起 |
| 有活动对象 | “有活动对象”标记 = 扫描后是否还有已启动影片槽 |

**成立条件**

- 停止 / 当前位置是外部播放后端报告的**秒**（或等价时间）；取不到时按“尚未结束”处理，不伪造 0。
- 循环只由选项字第 0 位决定；循环重启不清对象、不清纹理。
- 正常收尾不释放纹理对象；`(选项字 & 3) == 2` 只表示**不发出填纹理请求**，不等于“保留最后一帧”（像素效果见残差；绑定被 0x1f8 / 0x1f9 / 0x1fa 换掉时也没有最后一帧可留）。
- 本条只覆盖 `0x20f` 的纹理影片；窗口影片（另一族指令共享影片位）不在本条，见残差。

**残差**

- `RES-MOVIE-FILL`（unknown）：正常收尾的“填纹理”请求的**像素效果**（清黑 / 填最后一帧 / 其它）未逐像素取证；本版只规定调用条件。
- `RES-MOVIE-WINDOW-FAMILY`（unknown）：`0x1c0` / `0x1c6` 的窗口影片与 `0x20f` 共享影片位，但服务分支不同；本版只登记共享位，不把窗口影片写进本条，也不规定共享位的分派顺序。
- `RES-MOVIE-POLL-FAIL`（unknown）：播放后端报告失败 / 取不到停止时间时的收尾语义未取证；本版只规定“取不到 ⇒ 尚未结束”。
- `RES-MOVIE-NEW-FRAME`（unknown）：“后端如何报告结束 / 新帧标志 / renderer 忙”等收尾前检查未成篇；本版只规定“停止时间 <= 当前位置”是收尾判据。
- `RES-MOVIE-PAUSE`（unknown）：暂停时 `0x2000` 分支与门前影片对象表扫描是否执行未取证；本版不规定。
- `RES-MOVIE-BINDING-LIFETIME`（unknown）：播放期间 `0x1f8` / `0x1f9` / `0x1fa` 重建 / 释放同一纹理槽 / 共享对象槽时，影片绑定的所有权与失效语义未取证；本版不规定。
- `RES-MOVIE-DRAW-ORDER`（unknown）：影片帧与场景网格 / 绘制项的显示次序未取证；本版只规定帧写进纹理，不规定呈现层谁覆盖谁。
- `RES-MOVIE-FAILED-OBJECT`（unknown）：打开 / 绑定失败残留对象的服务语义未取证；本版明确让它不进入播完判据、不维持影片位，这是**边界选择**，不是引擎观察。

### 时钟：宿主毫秒时钟，没有固定帧率

<!-- rule: CORE-TIMING-CLOCK -->

引擎**没有**固定帧率、也没有固定步长：每次迭代读一次宿主的系统毫秒时钟，两次读数之差就是这一步推进的时间。

- 场景另存两个时间戳：当前读数与上一次读数（后者在每次推进前被前者覆盖）。
- 时间单位是毫秒，宽度 32 位（会回绕），比较按无符号。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 本步的现在 | 迭代头的时钟读数（毫秒） |
| 场景的上一步 | 场景的"上一次读数" |

**成立条件**

- 实现可以用固定步长**离散化**时钟（那是仿真参数，不是引擎常量）；规范只规定"时间从宿主来、单位毫秒"。
- 睡眠只影响这一步实际过了多久，不改变时间单位。

### 场景计时窗与"有动画"

<!-- rule: CORE-TIMING-WINDOW -->

场景里每个可绘制条目（绘制项 / 网格）可以有一个**颜色渐变窗**：延迟、持续时间、起点、终色、"有窗"位；插值用的"起色"就是该项的**当前颜色**字段，窗不另存起色。

- **起点为 0 是"未盖章"哨兵**：第一次被推进时才盖上当时的场景时钟。盖章与插值可以在同一步；延迟非负时盖章步的进度为 0，因此这一步的绘制色 = 当前颜色（即使延迟为 0）。**负延迟**没有范围检查，本版不规定它的盖章步进度（见残差）。
- **推进时机**：只有"有窗"位为 1 的条目才被推进；场景的窗在门之前推进（见「一次迭代做哪些事」），推进用场景时钟：本迭代的读数先写进场景（场景另存上一次读数），窗的"盖章 / 插值 / 到期"在场景推进里发生。
- **暂停时**：暂停且等待位为 0 ⇒ 场景推进整段不跑；暂停且等待位为 1 ⇒ 暂停不再挡它（否则等待会永远等不到头）。
- **持续时间为 0 不推进**：持续时间 ≤ 0（从未排窗，或已到期——到期那一步把它清 0）⇒ 这一趟不盖章、不插值、不置"有动画"，**也不执行到期分支**；"有窗"位是否因此永久保留，本版不规定（见残差）。
- **场景级「强制完成」档**：命令档在**本帧的渲染步**对**类型 < 0** 的命令把它置 1。
  - **读取点**：**同帧绘制期**的派生（源矩形窗 4.1、命令进度）读到 1 时按"到期"处理（不看时钟）。
  - **颜色窗的推进在渲染步之前**，因此它**看不到**当帧置的 1；⛔ 不许写成"类型 < 0 会让所有颜色窗当帧立刻到期"。
  - **不粘住**：清 0 在**渲染步收尾**（与命令表生命周期同一段）；命令档每帧都会重新置位。
- 若"现在"落在 `起点 + 延迟 + 持续时间` 之内（按 32 位无符号比较，**相等也算窗内**，此时进度为 1）⇒ 置"场景有动画"（个别绘制项另带一个引擎级屏蔽标记，置起时不置；该标记的含义本版不规定）；
  过了延迟之后按 `(现在 − 起点 − 延迟) / 持续时间` 在**当前颜色**与终色之间插值。
- **绘制项的这一步颜色**：无窗 / 延迟内 / 有窗但从未推进（持续时间 ≤ 0）⇒ 当前颜色；推进中 ⇒ 插值结果；到期 ⇒ 终色。这是一个**由当前颜色、终色、窗字段与该步时钟派生的量**（不是独立记录字段，也不是当前颜色字段）：绘制项用它绘制；**当前颜色字段在窗进行中保持原值**。因此窗进行中改写当前颜色会改变后续每一步的起色（同「场景 / 颜色族」的共用口径）。
- **网格的这一步颜色**：无窗 ⇒ 顶点缓冲现状（由 `0x320` / `0x322` 维护，不取当前颜色）；窗推进 ⇒ 按派生色重烘；**派生色落在「无颜色」时是否重烘，本版不规定**（见残差）；有窗但从未推进（持续时间 ≤ 0）⇒ 不重烘。**窗只在被推进的那一步重烘**；`0x320` / `0x322` 的烘色另见「场景 / 颜色族」（同一步以门后写入为准）。没有逐顶点缓冲的网格（顶点数 ≤ 0、未建）窗仍推进，但不重烘。
- **正常到期的共享收尾**（持续时间 > 0；绘制项与网格都适用）：取终色 → 当前颜色 ← 终色 →（网格按该值重烘一次）→ 终色 ← "无颜色" → 延迟与持续时间清 0 → 清该项的"有窗"位 → **窗起点清 0**。★ 源矩形窗与颜色窗共用"有窗"位与窗起点：清位 / 清起点由本段统一执行，源矩形的派生只读、不清（见「绘制项的消费者」4.1）。到期这一步不再按 t=1 的插值重烘一次。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某项的窗是否还开着 | 该项的"有窗"位与起止字段 |
| 这一步画什么颜色 | **派生量**：由当前颜色、终色、窗字段与该步时钟决定；没有独立的记录字段 |
| 场景还有动画 | 场景的"有动画"标记（场景推进在推进各项之前清、窗命中时置） |

**成立条件**

- 等待位的放行看的是**场景的"有动画"标记**（同一次迭代里、门之前的场景推进有没有置它），不是"表里还有没有未到期的窗"。
- 标记的清除与重置都发生在同一个迭代里、门服务等待位之前：场景推进先清标记，窗命中时再置；等待位读的是此刻的标记，不另存"上一次迭代"的副本。

### 中止：opcode 0x01

<!-- rule: CORE-OPS-ABORT-01 -->

`0x01` **没有操作数**。它**不写推进格数**，直接抛**退出型异常**（异常码 **1**）。

- 没有别的引擎数据效果：不写池、不写状态字、不写帧。
- 推进格数保持原值（可能是上一条留下的任何值）：因为执行不再回到分派器，这个值不可观察 —— 所以本条**不是**"把格数写成 1"。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 执行被中止 | 一次退出型异常（码 1） |

**成立条件**

- 与「结束当前脚本」不同：`0x2` 是**正常控制流**（父帧号决定回到哪一帧），`0x01` 走**异常通道**（结束执行，不重试、不跳过）。
- 与「重置并重装根脚本」不同：`0x9` 会重新装载根脚本；`0x01` 什么都不装。
- 异常码 1 与其它退出码（0 / 2 / …）的区分**不可观察**：保护区不读退出类的码，处置一律是汇入唯一出口段（见「异常的处置」）。本条只规定"码 = 1"。

### 执行区间的进入与离开：opcode 0x1f4 / 0x1f5

<!-- rule: CORE-OPS-RUN-BRACKET -->

这两条**没有操作数**，是一对**执行区间**的进入 / 离开标记。引擎里有三个相关格：一个**区间忙**标记、一个**嵌套计数**、两个**时间戳格**（「现在」与「上一步」）。

- `0x1f4`（进入）：若**忙标记为 0** ⇒ 置忙、读一次宿主毫秒时钟、把「上一步」← 原「现在」、「现在」← 本次读数；若**忙标记非 0** ⇒ **只**把嵌套计数 +1（不读时钟、不动两个时间戳格）。
- `0x1f5`（离开）：
  1. 若**嵌套计数 > 0** ⇒ 计数 −1，本条到此结束（不清忙、不泵）；
  2. 否则若**忙标记为 0** ⇒ 本条什么也不做（**未进入就离开是空操作**）；
  3. 否则清忙；然后若**队列占用标记为 0** ⇒ 把控制交给**待处理命令队列的泵**；否则直接返回。
- **泵**（本条只登记它对引擎数据的作用）：队列头 ≥ 队列尾（空）⇒ 立即返回、什么都不改；非空 ⇒ 取**一条**命令、把队列头 +1、置队列占用标记，并**改变当前帧与引擎级标志字**；改成什么值本版**不规定**（见残差）。该分支的完整合同属「执行与时间」的队列分支。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 是否有一段区间正在执行 | 区间忙标记（`0x1f4` 置、`0x1f5` 清） |
| 区间嵌套了几层 | 嵌套计数（`0x1f4` 在忙时 +1、`0x1f5` 在 > 0 时 −1） |
| 本区间的「现在」/「上一步」 | 两个时间戳格（只被 `0x1f4` 写） |
| 待处理命令队列 | 队列头 / 队列尾 / 队列表；`0x1f5` 归零时最多取走一条 |

**成立条件**

- **忙标记只有 `0x1f4` 置、只有 `0x1f5` 清**。别的指令（包括 `0x143` 的刷新）只**读**它来阻止泵，不写它。⛔ 不许把「谁写它」实现成多条指令共管。
- `0x143` 用的「正在刷新」标记是**另一个格**：两者都能挡住泵，但不是同一个开关。⛔ 不许合并。
- **计数与忙标记不对称**：忙时段内每次进入只 +1，出口每次离开只 −1 ⇒ 深度 = 计数 + 1。⛔ 不许把 `0x1f4` 实现成「每次都 +1」（那样最外层的进入会被算成 2 层）。
- 两个时间戳格是**本帧记录里的**两格，与「场景」章的两个时间戳**不是同一对**（见残差）；它们在本作样本里**没有任何读者** ⇒ 领域角色本版**不规定**（⛔ 不许据「它存的是时钟」就把它当计时器 / 等待门）。
- `0x1f5` 在未配对时是**空操作**：不清忙、不泵、不抛。⛔ 不许把它实现成「无条件清忙」——那会让后续的泵在本该被挡的时候开闸。
- 泵**一条**为一趟：⛔ 不许循环取空队列（那会一次迭代执行多条指令，与「一次迭代至多执行一条指令」冲突）。
- 两条都先把**当前帧**的推进格数（见「总览与约定」的长度槽）写成 1（`= 2 × 0 + 1`）；这一写发生在上面任何判断之前。
