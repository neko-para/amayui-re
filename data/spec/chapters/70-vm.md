## 执行与时间

本章规定**指令流怎样被驱动**：一次迭代做几件事、什么条件下才执行指令、等待怎样结束、时间从哪里来。
单条指令改了哪些引擎数据属于各指令族章；操作数的读法属于「数据池」。

### 一次迭代做哪些事

<!-- rule: CORE-VM-LOOP -->

正常迭代按固定顺序走：先在**迭代头**按节流决定是否泵一次宿主消息（节流周期与泵协议见下）；随后**读一次系统毫秒时钟**；再在条件允许时把这次读数交付给**两个声音子系统（音效 / 语音）**各一次；**场景的窗在门之前推进**（见「场景计时窗」），随后在**门之前**决定是否发出**一次渲染步请求**；最后过门——**服务状态选择字里的位**，或**执行一条指令**（两者可以在同一迭代里都发生）。泵消息与"服务一位 / 执行一条"可以在同一次迭代里都发生；**同一迭代也可以既服务若干位、又执行一条指令**：扫描没被任何服务体拦下时在**表尾**派发；第 29 位命中且**文本槽在用标志**非 0 时由**它自己**派发 —— 服务与执行**不互斥**。

- **门前渲染**：门之前还有一次**渲染步请求**。是否发出由场景闸门决定；本版只确认下列条件全部为真才发（各条跳过的是整段还是只跳请求，见「暂停时」）：**场景绘制模式 = 1**；**画面暂停闩 = 0**（置 / 清分别在两个不同的收尾例程里发生、调用者归属本版未取证的那个格，见「暂停时」）；**`0x21b` 的标量为非 0，或状态选择字的等待位（第 10 位）/ 影片位（第 13 位）为 1**；状态选择字的**第 24 位**未置；**没有媒体对象占用**（见「帧步进」的「两项逐媒体对象谓词」）；**区间忙标记 = 0，或等待位 = 1**（忙 ∧ 等待位 = 0 ⇒ 只**不发请求**，场景时钟照盖 —— 见「暂停时」）；**就绪判据 = 1**（**四支析取**的「有没有东西要画」：场景脏 / 三维特效对象的三个待处理格 / 动画槽表 / 绘制项表），**或**这一迭代**有媒体对象到期**。★ 这七支的**规范形态**（含两项逐媒体对象谓词与就绪判据那四支）见「帧步进」的 `CORE-OPS-RENDER-FRAME-STEP`：本节是摘要，不一致时以那条为准。渲染步**内部**另有一道**批次闸**，见「暂停时」的「只挡推进」第 4 条。「需要重绘」不是独立的开关：**场景脏本身只通过「就绪判据」第 a 支进入第 7 支**（所以脏 ∧ 其余六支成立 ⇒ 会请求）。这几个格的身份与缺省是：**场景绘制模式** = 配置 `set:DrawMode` 的值，**脚本 `0x200` 也可以用自己给的操作数直接覆盖它**（`0x200` 先要求该操作数对应的对象已被创建 —— 前置位图来自配置 `set:CreateObject`；不成立则报错、整条不生效、一个字节都不写），缺省 0；复位时按配置 `set:DrawMode` 重设（见「帧步进」）；**画面暂停闩** = 0 / 非 0 的单格，缺省 0，**置 1 与清 0 分别在两个不同的收尾例程里发生（调用者归属本版未取证）**（两支都只在场景绘制模式 = 1 时发生；置 1 之后引擎向自己的窗口发一条**请求把系统光标设为可见**的请求，该请求有一个引擎级门，见残差 `RES-HOLD-LATCH-SEND-GATE`），复位清 0；**`0x21b` 的标量** = 一个布尔量（脚本给非 0 也归一成 1），缺省 0，复位清 0；（另有一个**不是格**的派生布尔：**「有影片对象正被另一处持有」**，每迭代对对象表重扫得出，缺省 0、不持久化；它**不在**门前判据里，只挡推进 —— 见「暂停时」的「只挡推进」第 2 条；扫描谓词本身属影片 / 绘制侧。）★ 仍未取证的只有两处：① **画面暂停闩与哪条宿主窗口消息对应**（现在只能说到"置 / 清分别在两个不同的收尾例程里、调用者归属未取证"）；② 「被另一处持有」的**领域判据**。见残差 `RES-HOLD-LATCH-SEND-GATE` / `RES-WINDOW-MOVIE-HELD`。门关着时照常判断。
- **`0x20c` 例外**：门后执行的 `0x20c` 直接请求一次渲染步，**不经过上述门前闸门**。它自带的前置只有一道：**区间忙标记 = 0** 时先采一次读数写进场景时钟（忙时跳过这次采样，但**照样**请求渲染步）。
- 它与同一迭代的门前渲染**可以重复** —— 门前那次排在这条指令之前，`0x20c` 排在门后；两者之间**没有**「本迭代已渲染过」的记录，渲染步内部也**没有**这种闸（它唯一的提前出口是**批次闸**：渲染器拒绝开始一次批次 ⇒ 整步不做任何事，与迭代身份无关）。⇒ 同一迭代里跑两次渲染步是**允许**的，规范**不**为它加去重。
- 两次渲染步之后都会把同一格「欠一次渲染」的标记（同一个事实的另一种说法：「自上次渲染以来已有新的显示对象」）清 0。该标记**不是**去重闸：门前的两条渲染路径都只清**不读**它；它**唯一**的读者是**显示模式派发**（切换显示模式之后的那段收尾，见「切换显示模式」）—— 标记位为 1 时它**不再发渲染步**，改把该字第 1 位置 1 记「已折叠」（见「帧步进」的「帧标志」）。渲染步入口里**没有**帧记录 / 首帧分支：入口只有一道**批次闸**（见「帧步进」的「渲染步（合同边界）」）。
- 门前渲染与这一迭代派发哪条指令**无关**；一次迭代仍**至多执行一条指令**，⛔ 没有"一帧执行 N 条"的规则。
- 渲染步的**提交条件**见「帧步进」；内部顺序、38 目标见该条的 `RES-RENDER-STEP-INTERNAL`。

- 时间推进**不在**门后的分支里：它排在门之前，不占"一件事"的名额。
- **时间交付是两套到期计时器，不是混音**：这次读数交给**音效通道**与**语音通道**各一次；两者都用它推进各自的到期计时，而不是把时间转给音频输出。
  - **音效通道**：10 个通道，每个有「活动」标记、起点、时长与一个随通道交给**释放入口**的值。交付时：活动且起点为 0 ⇒ 起点 ← 本次读数（**懒盖章**）；随后按「读数 − 起点 ≥ 时长」判到期（**有符号**比较）。未到期 ⇒ 该子系统把「该子系统仍有一件未完成的工作」的标记置起（下个迭代继续交付）；到期 ⇒ 清活动，并把该通道的值交给释放入口。⇒ 交付只推进计时与释放，不混音、不改音量。这 10 格是**引擎自己的**音效通道表；后端另有 15 个可受理的槽（见「音频」章的相关残差），交付只走引擎这 10 格。
    ★ **这 10 格的写者只有三类，交付自己只占第四类**：
    - **登记**：一条「按通道登记一次到期释放」的指令把该通道写成：活动 ← 1、起点 ← 0（未盖章 ⇒ 从这一刻重新计时）、时长 ← 它给的延时、交值 ← 它给的值，并把「待办」置起。⇒ 通道只有在被**登记**之后才参与交付；同一通道再登记一次就是**重设**（起点回到未盖章、时长与交值被覆盖）；通道号 ≥ 10 的登记**一个格都不写**。
    - **按通道停止**：停止类指令把该通道的**活动 ← 0**。它**不改**起点 / 时长 / 交值 —— 那三格只由「登记」写。★ 停止有前置：音频后端未接上时它**一个格都不清**（活动仍为 1，下个迭代交付继续判到期）。
    - **整组清零**：生命周期例程在若干时点把 10 个活动全清、并把「待办」清 0（不逐个通道、不写起点 / 时长 / 交值）。
    - **交付**（本类）：只写**起点**（懒盖章）、**活动**（到期清 0）、**待办**（进入时清、任一通道未到期时再置）。它**不写**时长与交值 ⇒ 对交付来说，这两格在两次「登记」之间是**常量**。
    - **释放入口**只读「后端已接上」与「子系统启用」两个格：两者都非 0 才把该通道的交值转给后端，否则**空操作**并仍报"已处理"。
    - ★ **"播了一个声"不等于"这一格进入计时"**：播放类指令只登记「该通道要播的那个名字」，**不置活动**；把通道送进交付的是**登记**，不是播放。
    - ★ 在**该对象在语料里的全部取址点**上，除上述四类之外没有别的写者。
  - **语音通道**：3 个语音槽，每个有**状态**（低两位 = 完成 / 跳过）、**起点**、**时长**与一个**待办**标记。状态低两位 = 3 的槽先按另外两个语音槽的占用重排（可能把起点清 0、强制重新盖章），随后才进入同一套懒盖章 + 到期判据；到期 ⇒ 清槽状态、按该槽的待办标记调整、并**启动该槽队列里的下一段**（队列的排法与「下一段」的判据见「音频」章的「配音排队与配音组」）；若本次启动了语音，交付返回「有推进」。
  - **返回值的去向**：语音通道返回「有推进」时，主循环检查「音乐压低」的进入条件（「音乐淡出相关状态」格非 0、配置 `sound:MusicFadeOnVoicePlaying` 非 0、状态字第 9 位未置、主循环模式字的第 0 位为 0）——成立 ⇒ 置**第 14 位**（压低待执行）并把「该子系统仍有一件未完成的工作」的标记置起；不成立 ⇒ 什么都不做。第 14 位的服务体在**前置**成立时把它转成**第 9 位**（音乐音量渐变进行中 —— 与 `0xc2` 的淡变是同一个生命周期）并起计时；**前置 = 语音子系统空闲 ∧「该子系统仍有一件未完成的工作」的标记 ≠ 0 ∧ 第 9 位未置**；前置不成立时第 14 位**保留**，下个迭代再判。第 9 位服务体按计时器步进渐变、进度满时清第 9 位。⇒ 语音推进是音乐压低的触发条件，压低时长由第 9 位的计时器决定。
  - **跳过条件**：区间忙标记 = 1 且等待位 = 0 ⇒ 两个接收者本迭代**都不被调用**（不盖章、不计时）；等待位 = 1 时照常交付。
  - **边界**：通道/语音的混音、输出、音量与设备格式属音频子系统与平台；本版只规定「这次读数被用来推进哪些引擎计时记录、到期时改哪些引擎状态」。两个接收者只读写引擎自己的通道记录，并把「到期」交给该子系统的释放 / 启动入口；交付路径本身不向宿主发请求。
- 第三步有一个开关：引擎的**暂停**就是执行区间的**区间忙标记**（同一格：`0x1f4` 置、`0x1f5` 在嵌套计数归零时清；**没有独立的暂停格**）；忙标记为 1 **且等待位为 0** 时，时间交付与影片逐槽计时整段跳过，门前的渲染步**只是不发请求**（**场景时钟照盖**）；等待位为 1 时暂停**不挡**它们。★ 这仍不含独立的**脚本**暂停格：脚本暂停 = 区间忙。
- **暂停不构成死锁**：忙标记只给服务链上第 12 / 13 位的服务体加了「**区间忙 ≠ 0 ⇒ 这一位的服务体不执行**」的前置（该判据只测区间忙，**不看**等待位）；它**不挡表尾派发** —— 扫描没被任何服务体交回迭代头时，本迭代照样派发一条指令。⇒ **在其余位都不拦的情况下**，暂停不阻止脚本推进（第 10 位仍按它自己的判据挡）：离开区间的那条指令仍会被执行到，它清掉忙标记之后队列泵才被放行（见「执行区间的进入与离开」）。影片逐槽计时是否同样被挡，沿用「影片对象表的服务」的现文。
- **门前**各子系统共用同一个时钟读数；门后 `0x1f4` / `0x20c` 都**仅在区间忙标记为 0 时**各自再采样一次，写进同一对场景时钟（见各自条目）。
- **回消息的节流是引擎侧的固定周期**：迭代头有一个计数器（初值 1）；每迭代先看它与常量 **4** 的按位与——非 0（计数 = 4）⇒ 本迭代**泵一次**，泵后计数器回 1，**同一迭代**再判一次并 +1 到 2；为 0 ⇒ 计数器 +1、不泵。⇒ **泵一次之后隔 3 个迭代再泵**，与宿主无关。一次泵 = 反复「窥视队列 → 取一条 → 翻译 → 派发」直到窥视为空；**「取一条」返回 0（退出消息）⇒ 结束执行**（走退出通道）。泵唯一的引擎侧结果就是这个退出判定；它不改门字、不写时钟、不推进任何子系统。
- **边界（宿主）**：队列里有什么、窗口过程做什么、一条消息派发后改哪些引擎状态，都属宿主。本版规定的是「什么时候泵、泵到队列空、退出消息结束执行」——泵的每个请求都是对宿主消息接口的直接调用，引擎只读「取一条」的返回值。这不是弃权，而是**范围声明**：消息语义在平台侧。
- 一条指令的处理可以在**保护区**里抛异常；此时下一次迭代从哪继续由「启动入口：入口 → 初始化 → 主循环」的「异常的处置」三支决定：重试 / 忽略回**保护区入口**（会重做一次**准备段**，含一次消息泵），正常返回只回**迭代头**（按节流泵）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 本迭代的"现在" | 迭代头读一次（门后 `0x1f4` / `0x20c` 可覆盖，见「时钟」） |
| 本迭代做了哪件事 | 消息泵（可以没有）、门前一次渲染步请求（可以没有；`0x20c` 可以在同一迭代再请求一次，**不去重**）、服务若干状态位；至多一条指令（扫到表尾派发，或第 29 位命中且文本槽在用标志非 0 时由它派发） |
| 本迭代是否泵消息 | 迭代头计数器与常量 4 的按位与：非 0（计数 = 4）⇒ 泵一次，泵后同一迭代回 1 再 +1 到 2；否则 +1 不泵 |
| 时间交付到哪里 | 音效通道 10 个通道 / 语音通道 3 个语音槽的到期计时；区间忙标记为 1 且等待位为 0 时整段跳过 |
| 音效通道记录的写者 | 四类：**登记**（活动 / 起点 ← 0 / 时长 / 交值 + 待办）· **按通道停止**（活动 ← 0，且后端未接上时不生效）· **整组清零**（10 个活动 + 待办）· **交付**（起点 / 活动 / 待办）；播放不置活动 |
| 音效通道表的第五组格 | = 每通道「登记的播放名」；交付**不读**它（语义归「音频」章） |
| 语音推进触发了什么 | 语音通道返回「有推进」⇒ 置状态字第 14 位（压低待执行）；第 14 位服务体在语音空闲时转成第 9 位（音乐音量渐变进行中） |
| 本迭代是否请求渲染 | 门前闸门的判定结果（走 / 不走；不作为独立记录字段保存） |

**成立条件**

- 一次迭代**至多**执行一条指令；没有"一帧执行 N 条"的规则。
- 泵是**每 3 个迭代一次**的固定周期（首次之后；泵的那个迭代同时照常执行其余步骤），不是"每次迭代都做"，也不是"由宿主决定"；泵完仍继续本迭代的其余步骤。
- 交付不是"把时间推给音频输出"：它只做懒盖章与到期判定；混音、输出与音量在音频子系统 / 平台侧（范围声明）。
- 语音推进是音乐压低的触发条件；压低状态由状态字第 14 / 9 位承载（第 14 → 9 的交接见「位是待服务标记，清不清由服务分支决定」的位序表）。
- 起点的 0 是「未盖章」哨兵：真实时刻 0 与它撞车，所以懒盖章只能发生在第一次交付，不能写成"每迭代都盖"。
- ★ "每迭代读一次时钟"不等于"窗一定推进"：只有"有窗"位为 1 的条目才参与推进（见「场景计时窗」）。

### 门：整字为 0 直接派发；非 0 先扫服务链，扫完仍派发一条

<!-- rule: CORE-VM-GATE -->

**状态选择字整字为 0 ⇒ 本迭代派发一条指令**。整字非 0 ⇒ 本迭代**先走服务链**：按固定位序逐位检查（位号顺序、多处同时置起时谁先服务，见「位是待服务标记，清不清由服务分支决定」的**服务链位序**表；⛔ 不是位号升序），**每个位的服务分支只服务那一件**。扫描有三种收场（第三种只出现在第 29 位）：

- **某一位的服务体把控制交回迭代头** ⇒ 本迭代到此为止、**不派发**；更晚的位本迭代不再看。
- **扫描走到表尾**（一路没有任何服务体把控制交回迭代头）⇒ 引擎**照常派发一条**指令。
- **第 29 位命中且文本槽在用标志 ≠ 0** ⇒ 由**它的服务体自己**派发一条（不走到表尾，见下一条）；标志 = 0 时它就是上面的第一类收场（服务体交回迭代头、本迭代**不派发**）。这一格是**文本槽在用标志**（槽 1..9 的状态字任一非 0），⛔ **不是**命令队列的占用标记 —— 命令队列的判空是「队列头 ≥ 队列尾」（见「执行区间的进入与离开」的泵合同），唯一的单格占用标记是**队列泵占用标记**（见该条末的近名格表）。

⇒ 「门是忙的」与「本迭代仍派发一条」**不互斥**：门字非 0 只说明"得先扫服务链"，而扫描的结果既可能拦住派发、也可能放行派发。同一迭代可以既服务若干位、又执行一条指令；也可以服务了若干位之后仍被某一位拦下、一条也不执行。

- 判据是**整字**比较，不是逐位与：整字为 0 才是"不必扫链、直接派发"；只要有任意一位被置起，本迭代就先进服务链 —— 最后派不派发由扫描结果决定（见上）。⛔ 不许把它写成"任意一位被置起就挡住派发"。
- **第 29 位的服务体自己也会派发**：这是服务链里唯一"由服务体直接派发"的位。扫描走到第 29 位且它已置起（= 该位**命中**；「命中」的唯一口径见「位是待服务标记，清不清由服务分支决定」）时，它的服务体**先跑一次文本推进器**，然后按**文本槽在用标志**决定：标志 = 0（**无槽**）⇒ **交回迭代头**、本迭代零派发；**否则派发一条指令**（本迭代不再往下扫）。⇒ 这一位的行为分两支：标志 ≠ 0 时「门是忙的」与「本迭代仍派发一条指令」**同时成立**（每迭代派发一条，同时推进器继续按拍推进）；标志 = 0 时打字期间**本迭代零派发**，要等服务体把第 29 位清掉（推进器自己走完，或输入把它提前抽干）才恢复派发。★ **标志 ≠ 0 不只来自演示闸层**：任何槽 1..9 的状态字非 0 都会把它置起（`0x300` 的闸只是其中一种来源；写过状态、第 16 位还粘着的槽同样算）。两支的前置都是「**扫描走到第 29 位且它置起**」（即更早的位都没有把控制交回迭代头 —— 它们可以未命中，也可以命中了但继续往下扫）。位号顺序见「服务链位序」表。★ 该标志在服务体每趟入口**重算**：先清 0，再按槽 1..9 的状态字是否非 0 置 1（槽 0 不参与）——所以**同一趟里随后被抽干的槽仍算在用**，本迭代照样派发。
  ★ 由此，状态选择字里**别的位已置**时脚本仍可能被派发：只要扫到表尾都没有服务体交回迭代头，引擎就派发一条 —— 第 30 位已置的 `0x1ce` 的 0 支就是这样够得着的（见 `CORE-OPS-TEXT-CELL-REVEAL-1CE`；第 30 位自己的服务体**不**交回迭代头）。⛔ 不许把"整字为 0 才派发"当成无例外的公理。
- 这就是"某条指令看起来没有执行、只有时间在走"的机制：**普通打字**期间每次扫描到第 29 位都被交回迭代头（零派发、只有推进器在走）；**演示闸层**开着时则相反 —— 门照忙、指令照跑。
- **术语**：本版把 `0x88` / 「引擎级模式位」操作的那个字称为「引擎级标志字」，**它就是这里的状态选择字**；`0x1cf` / `0x1bf` 写的「状态字」与 `0x1cc` 读的「状态格」是**别的**引擎格，不是门字。`0x1ce` **置 / 清**的就是状态选择字的**第 30 位**（= 逐格揭示活动中，见 `CORE-OPS-TEXT-CELL-REVEAL-1CE`）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 门开着 | 状态选择字 = 0 ⇒ 本迭代直接派发一条 |
| 门关着 | 状态选择字 ≠ 0 ⇒ 本迭代**先扫服务链**：任一服务体交回迭代头 ⇒ **不派发**；扫到表尾 ⇒ **仍派发一条**（等多久由位的服务分支决定） |

**成立条件**

- 位由谁置、服务分支做什么、何时清，见各指令条目与「位是待服务标记，清不清由服务分支决定」。

### 位是待服务标记，清不清由服务分支决定

<!-- rule: CORE-VM-STATE -->

状态选择字的每一位表示"有一件引擎级工作待做"。迭代按**固定顺序**检查位并服务，**每个位的服务分支只服务那一件**；多个位同时置起时，**先被检查到的位先服务**（顺序见下表，**不是位号升序**）。命中一位后，它的服务体**多数**直接回迭代头（⇒ 本迭代不再看更晚的位）；少数服务体按条件把控制交给链上更后的一位（第 14 位总落到第 9 位、第 9 位总落到第 12 位；第 12 位在"置起配对位"那一支交回迭代头、其余两支落到第 26 位；第 30 位**总是**落到第 13 位；第 13 位被暂停挡下时落到第 3 位）⇒ 一次迭代可以服务若干位。清位由该位的服务分支决定：清掉，下个迭代门就打开；没清，下个迭代继续服务同一位（表现为门持续关着）。**例外**：某位可以在同一次服务里先清后按条件再置（影片位就是这样），此时门继续关着；第 30 位（逐格揭示活动中）的服务分支**不负责清它**（只按节拍请求画一格并推进格号），所以活动期间门持续关着。
  第 30 位**没有自带的清位服务**：它的服务支只按节拍请求画一格并推进格号，**它自己一次也不直接写**状态选择字（它调用的那两个子程序不在本条范围）。
  清它的是文本 / 消息推进路径里的一处**共享清理**：「活动位已置 ∧ 重绘待处理位未置 ⇒ 先请求释放该文本槽的排版资源，再清活动位」
  （重绘待处理位已置时只清位、不释放；活动位未置时整段什么也不做，所以它可以被反复经过）。
  这一段有**若干同形副本**（其中一处落在 `0x1ce` 的 0 支里 —— 门忙时它仍可被派发，见下），也是「等推进」第 31 位服务体与自动消息到期路径共用的那一次清理。
  ⇒ 第 31 位（`0x72` 的等推进）的放行**不是**服务体私有地清第 30 位：它是先清第 31 位、再经过这条共享清理；
  「放行只清第 31 位」是错的，「活动位只能由外部输入清」也是错的。
  ★ 这条清理**不是**唯一的清位途径：换页 / 复位 / 恢复历史状态时的**整字重写**会连带把第 30 位清掉
  （它们不属于「揭示结束」，也不发释放请求）。
  **`0x1ce` 的 0 支是其中一处、且可达**：它的前置是「本条在门忙时仍被派发」——
  也就是门忙时那两条派发路径（**扫到表尾** / **第 29 位服务体派发**，见「门：整字为 0 直接派发；非 0 先扫服务链，扫完仍派发一条」）。此时第 30 位可以已置，
  于是它按上面的形态动作（第 30 位未置则什么都不做）⇒ 它是**唯一以第 30 位为目标**的清位点
  （整字重写同样能清第 30 位，但它们不属于本条所说的「清位点」：触发条件与可达性未逐条取证，见残差 `RES-TEXT-CELL-REVEAL-CLEARERS`）。

- 等待位就是这样：消息子系统的计时器仍在窗内、或**「有动画」**标记非 0（窗还在走）时，服务分支**不清**它，门一直关着（见「等待（opcode 0x21c）」）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 有 N 件待做 | 状态选择字里的 N 个位；每迭代按**固定顺序**检查位并服务（可以服务若干位），清位与否由服务分支决定 |

**服务链的位序**（位号从 0 起；"检查序"就是多个位同时置起时的优先级）

| 序 | 位 | 服务体做的一件事 | 服务后 |
|---|---|---|---|
| 1 | 22 | 等消息：等待并取 / 翻译 / 派发一条消息 | 交回迭代头 |
| 2 | 24 | 显示 / 窗口影片的等待步（窗口影片结束时在此销毁并清第 13 位） | 交回迭代头 |
| 3 | 14 | 音乐压低待执行：前置 = 语音子系统空闲 ∧「该子系统仍有一件未完成的工作」的标记 ≠ 0 ∧ 第 9 位未置 ∧ 主循环模式字第 0 位为 0（不成立 ⇒ 第 14 位保留、下个迭代再判）；成立 ⇒ 清第 14 位、置第 9 位并起计时 | 继续扫描（落到第 9 位） |
| 4 | 9 | 音乐音量渐变进行中（`0xc2` 的淡变 / 压低后的恢复共用同一个生命周期）：按计时器步进渐变（进度满）后清第 9 位 | 继续扫描（落到第 12 位） |
| 5 | 12 | 仅当区间忙 = 0：一个等待 / 放行步（与第 11 位配对） | 条件：置起配对位那一支交回迭代头，其余落到第 26 位 |
| 6 | 26 | 本地块内的输入等待（见「`0x7c`」）：读输入字，非 0 则清位并按副进入目标重入 | 交回迭代头 |
| 7 | 20 | 重绘待处理：请求一次重绘 | 交回迭代头 |
| 8 | 30 | 逐格揭示：按节拍请求画一格并推进格号 | 继续扫描（落到第 13 位） |
| 9 | 13 | 影片位：清位；对象表还有非空影片槽 ⇒ 再置位 | 交回迭代头 |
| 10–13 | 3 / 4 / 7 / 8 | 输入跳过效果：按配置 `system:EffectSkipOnClick` 与输入锁存，向效果/绘制侧发一次「跳过」请求 | 交回迭代头 |
| 14 | 10 | 等待位：等待谓词放行时清位 | 交回迭代头 |
| 15 | 6 | 一个子系统的一步 | 交回迭代头 |
| 16 | 27 | 消息逐帧推进门位（又称「跳过位」） | 交回迭代头 |
| 17 | 29 | 文本推进器；命中且**文本槽在用标志**非 0 ⇒ 随即派发一条 | 特例：标志 ≠ 0 ⇒ 随即派发；标志 = 0 ⇒ 交回迭代头 |
| 18 | 31 | 等推进（抑制态）：等待一步 | 交回迭代头 |
| 19 | 0 | 一个计时器的到期位 | 交回迭代头 |
| 20 | 5 | 一个计时器的到期位 + 重置计时器 | 交回迭代头 |
| 21 | 28 | 一个子系统的一步 | 交回迭代头 |
| 22 | 23 | 一个子系统的一步 | 交回迭代头 |

> 第 15 / 21 / 22 行（第 6 / 28 / 23 位）的**子系统领域名**未取证 —— 见残差 `RES-VM-OTHER-BITS-SUBSYSTEMS`；⛔ 不许把它们写成猜测的名字。

每个位由**它自己的服务体**在"本件事做完"时清；位序只排顺序，**不**规定清位。**哪一位由谁清**见它自己的条目；尚未定清点的位列进残差 `RES-VM-BIT-CLEARERS`（知识缺口，⛔ 不许用"服务体清"一句代替逐位取证）。（已知例外：第 30 位**没有自带的清位服务**，由文本推进路径的共享清理清 —— 见本条开头。）

**成立条件**

- **「命中」的唯一口径（服务链语境）**：一位**命中** = 该位**已置起**，**且**本迭代的扫描**到达它的检查点、于是它的服务体被执行**。命中**不等于**拦住派发：有的服务体执行完把控制交回迭代头（⇒ 本迭代不派发），有的继续沿链往下扫（⇒ 本迭代仍可能走到表尾并派发）。反过来两种情形都算**未命中**：该位未置起（没有这件待办），或扫描在它之前就被某个服务体交回迭代头（本迭代没轮到它）。⛔ 不许把「命中」读成"拦截"、也不许读成"只是置起"——两者都会给出门模型的反结论。
- **服务链是一个闭集**：它只检查位序表列出的 22 个位；每个位的服务体只做一件事（把该位的待办交给它所属的子系统一步，或按计时器 / 输入 / 等待谓词清位）。**表外的位不挡派发**：扫描只走表里列出的这 22 个位，走到表尾就派发一条 —— 置起一个不在表里的位不会让本迭代零派发。本版已把下列位的领域语义写成合同或指向其条目：等待位（第 10 位）、影片位（第 13 位，见下一则）、重绘待处理位（第 20 位）、消息逐帧推进门位（第 27 位）、打字位（第 29 位）、逐格揭示位（第 30 位）、等推进位（第 31 位）、音乐压低 / 音量渐变位（第 14 / 9 位）、输入跳过效果位（第 3 / 4 / 7 / 8 位）、计时器到期位（第 0 / 5 位）、本地块内的输入等待位（第 26 位，见「`0x7c`」）。
- **配对位**：第 11 位不是独立位 —— 它由第 12 位的服务体置起、并在第 12 位的服务体里被读（与第 12 位配对）。
- 第 6 / 23 / 28 位是三个子系统的一步；它们的子系统领域名与各位置起者（写者）见残差 `RES-VM-OTHER-BITS-SUBSYSTEMS`（知识缺口，不是"位不存在"）。
- 其余位只登记存在（第 26 位见「`0x7c`」的本地块内输入等待；第 11 位是第 12 位的配对位）。

### 影片对象表的服务（门之前）

<!-- rule: CORE-VM-MOVIE -->

**影片位不是生命周期服务**：它只让门保持关闭；真正的“播完 / 循环 / 销毁”在**门之前**的影片对象表服务里完成。每次迭代在过门之前，若“有活动对象”标记为 1，就扫描对象表的全部影片槽（槽号 0..999）：

- 先清“有活动对象”，再逐槽处理：
  - 槽为空 / 不是影片对象 ⇒ 跳过。
  - 对象**未启动**（打开 / 绑定失败留下的残留）⇒ 跳过：不进入播完判据、不维持影片位（见残差）。
  - `停止时间 <= 当前位置` ⇒ 进入收尾判据；否则保留对象，标记“有活动对象”。后端如何报告结束 / 新帧标志 / renderer 忙等其它检查本版不规定（见残差）。
  - 收尾判据成立且**循环位**（选项字第 0 位）为 1 ⇒ 回到开头重新启动，保留对象与槽，不销毁、不填纹理；“有活动对象”保持，影片位保持置起。
  - 收尾判据成立且循环位为 0 ⇒ 正常收尾：读选项字 → 若 `(选项字 & 3) != 2`，对该纹理发出一次“填纹理”请求（像素效果本版不规定）→ 停止 / 关闭 / 释放播放后端 → **移除对象表槽**；不释放纹理对象本身。
- 扫描结束后，“有活动对象” = 是否还有**已启动**的影片槽。
- 影片位服务（门上的 `0x2000`）只做：清影片位；若对象表仍有**已启动**影片槽，再置影片位；否则让门在下一迭代打开。它**不**轮询、不销毁、不填纹理。这是“纹理影片”这一支的服务；窗口影片共享位的分派见残差。
- 暂停（区间忙标记 = 1）时 `0x2000` 服务与影片逐槽计时都不执行，两者的闸不同：**忙 ∧ 等待位 = 0 时两者都不跑**；等待位 = 1 时**影片逐槽计时**放行（它按「忙 ∧ 等待位 = 0」挡），而 `0x2000` 服务只看区间忙 —— 等待位**不**为它开闸。门前扫描里逐槽计时之外的部分见残差 `RES-MOVIE-PAUSE`。暂停的进入 / 离开由 `0x1f4` / `0x1f5` 的区间忙标记决定（见「执行区间的进入与离开」）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某个槽上有影片在播 | 对象表该槽非空、对象已启动且未到停止点 |
| 影片占用主循环 | 影片位 = 1；只要对象表还有已启动影片槽，位服务就把它重新置起 |
| 有活动对象 | “有活动对象”标记 = 扫描后是否还有已启动影片槽 |

**成立条件**

- 停止 / 当前位置是外部播放后端报告的**秒**（或等价时间）；取不到时按“尚未结束”处理，不伪造 0。
- 循环只由选项字第 0 位决定；循环重启不清对象、不清纹理。
- 正常收尾不释放纹理对象；`(选项字 & 3) == 2` 只表示**不发出填纹理请求**，不等于“保留最后一帧”（像素效果见残差；绑定被 0x1f8 / 0x1f9 / 0x1fa 换掉时也没有最后一帧可留）。
- 本条只覆盖 `0x20f` 的纹理影片；窗口影片（另一族指令共享影片位）不在本条，见残差。

**残差**

- `RES-MOVIE-FILL`（unknown）：正常收尾的“填纹理”请求的**像素效果**（清黑 / 填最后一帧 / 其它）未逐像素取证；本版只规定调用条件。
- `RES-MOVIE-WINDOW-FAMILY`（unknown）：`0x1c0` / `0x1c6` 的窗口影片与 `0x20f` 共享影片位，但服务分支不同；本版只登记共享位，不把窗口影片写进本条，也不规定共享位的分派顺序。
- `RES-MOVIE-POLL-FAIL`（unknown）：播放后端报告失败 / 取不到停止时间时的收尾语义未取证；本版只规定“取不到 ⇒ 尚未结束”。
- `RES-MOVIE-NEW-FRAME`（unknown）：“后端如何报告结束 / 新帧标志 / renderer 忙”等收尾前检查未成篇；本版只规定“停止时间 <= 当前位置”是收尾判据。
- `RES-MOVIE-PAUSE`（unknown）：门前影片对象表扫描里**除逐槽计时之外**的部分是否也以忙标记为前置未取证。下一步：读门前扫描的入口与忙判断的先后。
- `RES-MOVIE-BINDING-LIFETIME`（unknown）：播放期间 `0x1f8` / `0x1f9` / `0x1fa` 重建 / 释放同一纹理槽 / 共享对象槽时，影片绑定的所有权与失效语义未取证；本版不规定。
- `RES-MOVIE-DRAW-ORDER`（unknown）：影片帧与场景网格 / 绘制项的显示次序未取证；本版只规定帧写进纹理，不规定呈现层谁覆盖谁。
- `RES-MOVIE-FAILED-OBJECT`（unknown）：打开 / 绑定失败残留对象的服务语义未取证；本版明确让它不进入播完判据、不维持影片位，这是**边界选择**，不是引擎观察。

### 时钟：宿主毫秒时钟，没有固定帧率

<!-- rule: CORE-TIMING-CLOCK -->

引擎**没有**固定帧率、也没有固定步长：两次**迭代头**读数之差是这两次读数之间的时间；门后 `0x1f4` / `0x20c` 的再采样会改变「上一次读数」（见各自条目）。

- 场景保存**最近两次采样**这一对（与 `0x1f4` / `0x20c` 共享）：当前读数与上一次读数；**本版登记的写者**（场景推进 / `0x1f4` / `0x20c` / `0x23c`）都先搬旧、再写新；其余写者未取证（见残差 `RES-CLOCK-WRITERS`）。其中 `0x23c` 是**无条件重盖**（不看区间忙标记），完整合同见「无条件重盖时钟对」。下文「当前 / 上一」与「现在 / 上一步」指同一组名字。
- 时间单位是毫秒，宽度 32 位（会回绕）。**比较的符号性由各判据自己写明**：颜色窗（绘制项 / 网格）的到期判据按**无符号 `≥`**；消息等待计时器按**无符号 `>`**（相等仍算窗内）——
  两者的差别是 **`≥` 还是 `>`**，见「场景计时窗与"有动画"」；⛔ 不要拿这一句当"所有比较都按无符号"的许可（音效 / 语音的到期判据是**有符号** —— 与「场景计时窗」的窗口到期判据**不是同一族**）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 本步的现在 | 最近一次采样（通常是迭代头读数；门后 `0x1f4` / `0x20c` 可覆盖） |
| 场景的上一步 | 场景的"上一次读数" |

**成立条件**

- 实现可以用固定步长**离散化**时钟（那是仿真参数，不是引擎常量）；规范只规定"时间从宿主来、单位毫秒"。
- 睡眠只影响这一步实际过了多久，不改变时间单位。

### 场景计时窗与"有动画"

<!-- rule: CORE-TIMING-WINDOW -->

场景里每个可绘制条目（绘制项 / 网格）可以有一个**颜色渐变窗**：延迟、持续时间、起点、终色、"有窗"位；插值用的"起色"就是该项的**当前颜色**字段，窗不另存起色。

- **起点为 0 是"未盖章"哨兵，而它与"真实时刻 0"撞车**：盖章的唯一条件是"起点 = 0"。⇒ 若排窗那一刻场景时钟恰为 0，本步的盖章读不成立、窗要到**第一个时钟 ≠ 0 的推进步**才真正盖上 ⇒ 它的起点比"排窗那一步"晚（至多一个采样间隔）。这是引擎的边界结果，⛔ 不许用"另设一个已盖章位"掩盖它。
- **进度不会越界**：到期判据先判、延迟段次判 ⇒ 走到插值那一支时 `现在 − 起点 − 延迟` 已 > 0 且 < 持续时间 ⇒ **进度恒在 (0, 1) 开区间内**，引擎**没有** clamp。⛔ 不许加 clamp（那会掩盖"到期判据先判"这一条）。
- **负延迟没有范围检查**：盖章把起点设在"现在"，而进度按 `现在 − 起点 − 延迟` 算 ⇒ **盖章那一步的进度 = (−延迟) / 持续时间**（不是 0）；`持续时间 ≤ −延迟` 时盖章步就已到期。负延迟下延迟段判据恒假，不改变别的判据。
- **推进时机**：只有"有窗"位为 1 的条目才被推进；场景的窗在**门之前的那个渲染步内部**推进（同一渲染步的**更早子步**，不是"另一个步之前"，见「一次迭代做哪些事」），推进用场景时钟：本迭代的读数先写进场景（场景另存上一次读数），窗的"盖章 / 插值 / 到期"在场景推进里发生。**这一步被跳过的那一迭代，窗不前进，「有动画」与脏两个标记也不重算** —— 它们停在上一迭代的值（跳过点的分类见本节「暂停时」那条）。★ **盖钟（把本迭代的读数写进场景的「现在 / 上一次读数」）在五个「只挡推进」条件之前、且在渲染步调用之外**：那五条成立时渲染步不发请求（窗不前进、两个标记不重算），但**盖钟照样做** —— 渲染步不发请求那一步也照样盖钟。
- **推进置脏（不是绘制期标脏）**：只要窗还在走（延迟内 / 推进中，或网格窗那一步走到到期收尾），场景推进在推进那一步就把**脏**置 1（**无条件**：不看该项的位）、同一步也置**「有动画」**（该项设了「不参与场景动画」位的**除外**，见下条 —— 那一位只压「有动画」，**不压脏**）。这是「帧步进」就绪判据 a 支在窗进行期间为真的来源。⛔ 不许拿绘制期的那次标脏顶替它：「绘制项的消费者」4.1 的逐帧标脏发生在**消费这一项**的时候，本步若没走到那一步（或根本没发绘制请求），它不会发生。
- **暂停时**：暂停就是「一次迭代做哪些事」里的**区间忙标记**（见该条的暂停开关）；忙且等待位 = 0 ⇒ **时间交付**（音效 / 语音）与**影片逐槽计时**都不跑，而**门前的渲染步只是不发请求** —— **场景时钟照盖**（忙判定在盖钟之后）；忙且等待位 = 1 ⇒ 暂停不再挡它们（否则等待会永远等不到头）。（这是**门前渲染步**与**时间交付**的闸；第 12 / 13 位的服务体只看区间忙，见「一次迭代做哪些事」的暂停开关。）
  ★ 这一段的跳过点分两类，别混：**连"盖钟"一起跳过的只有三个** ——（a）**场景绘制模式 ≠ 1** —— 配置 `set:DrawMode` 决定的那个格（脚本 `0x200` 用**它自己的操作数**直接覆盖它；该指令另有一道前置：配置 `set:CreateObject` 的位图里"这个编号的对象已创建"，不成立则整条不生效、连格都不写）；（b）**画面暂停闩 ≠ 0**（置 1 与清 0 分别在两个不同的收尾例程里、调用者归属本版未取证，**缺省 0** 的一个引擎格，**与执行区间的区间忙标记不是同一格**，两者可以各自独立成立。置 / 清**两支都只在场景绘制模式 = 1 时发生**，而且**成对**包住一次**阻塞式宿主对话框**（逐处核对过 3 个调用点：右键系统菜单 + 两处显示模式错误框；其余调用点是否也如此**未逐处核对**，见本条 falsifier）：置起之后引擎打开系统菜单 / 错误消息框，对话框的模态循环期间引擎主循环**不跑迭代**，关闭之后立刻清 0 ⇒ 这一支期间**没有"下一迭代"可被跳过**，它不是"等待永不结束"的来源。置起时引擎另发一条**平台请求**：把**系统光标设为可见**（见「窗口」章的「事件入口与消息泵」）；该请求由一个引擎级**有符号格**的符号位门控，那一格其余的身份与写者本版未取证（见残差 `RES-HOLD-LATCH-SEND-GATE`））；（c）`0x21b` 的标量为 0 **且**状态选择字的等待位（第 10 位）与影片位（第 13 位）都为 0 ⇒ **本迭代不发出门前渲染步请求，也不盖场景时钟**（盖钟、门前判据其余各支、请求、清帧标志一起跳过；★ 盖钟本来就在渲染步**调用之外**，见「推进时机」——"跳过盖钟"指的是跳过门前那一次，不是"渲染步内部不盖"）；迭代**不因此结束** —— 跳过后照常走到门，按门的状态服务位或派发一条指令。等待位 = 1 或影片位 = 1 时（c）**必然放行**（掩码同时包含第 10 位与第 13 位，是**或**不是"且"）。★ 这条只取消**门前渲染步**这一个时钟写者：场景时钟仍由 `0x1f4` / `0x20c` / `0x23c` 推进，所以**标量恒为 0 不会让时间停走**；等待期间（第 10 位置起）门前这一次照常每迭代盖钟。
  （a）与（b）都是**持续状态**、不是瞬时条件 ⇒ 它们成立期间**所有以场景时钟计的量都停走**（消息等待计时器、颜色窗、源矩形窗）。但两者**后果不同、不许合并**：
  - **（a）场景绘制模式 ≠ 1 可以长期成立**（缺省 0、脚本 `0x200` 可写任意整数、配置也可给非 1）⇒ 一个**显式子情形**：等待位 = 1 而模式 ≠ 1 时，等待**自己的计时器也停走** ⇒ 门**永不因时间放行**，只能由**输入跳过**那一支放行（一直持续到模式被改回 1）。这是"等待可能永不结束"的**唯一**来源。
  - **（b）画面暂停闩不是饥饿来源**：它只在一段**阻塞式宿主 UI**期间为 1，而那期间引擎主循环不跑迭代（不存在"被跳过的一迭代"），出对话框即清 0。⛔ 不许把它写成第二种"等待永不结束"。★ 这条改判的边界：只有 3 个调用点逐处核过"夹一个阻塞 UI"；若有任何调用点把闩留着**跨迭代**，（b）就掉进（a）的结论 ⇒ 见本条 falsifier。
  - **（d）执行区间的暂停**同样是持续状态，但它**不挡盖钟**：它挡的是时间交付、影片逐槽计时与门前那一次请求（见下面"只挡推进"表的第 5 条）。★ 这不是缺陷：引擎的时钟只有一个来源，⛔ 不许为"避免停走"让实现用别的时钟去推进计时器（那会与本条其余部分自相矛盾）。
  - **只跳过"推进"、不跳过"盖钟"的条件**（任一成立 ⇒ 窗不前进、两个标记不重算，但时钟照盖）：
    1. 状态选择字的**第 24 位**；
    2. **有影片对象正被另一处持有**（一个**每迭代扫描影片对象表得到的派生布尔**：扫描 1000 个槽、任一槽对象的缓冲此刻被另一处使用即为真 —— 见「一次迭代做哪些事」的「本迭代是否请求渲染」一行；不是独立的格。扫描细节见残差 `RES-WINDOW-MOVIE-HELD`）；
    3. **门前请求判据的第 5 / 7 支不成立**（第 5 支 = 「没有媒体对象占用」；第 7 支 = 「就绪判据 = 1 **或** 有媒体对象到期」。第 4～7 支否决时**钟已搬、请求不发**；第 1～3 支否决时连钟都不盖，见上面（a）～（c）—— 判据见「帧步进」的 `CORE-OPS-RENDER-FRAME-STEP`）；
    4. **渲染步的批次闸拒绝**（渲染器拒绝开始一次批次 ⇒ 整步立即结束、什么都不做）—— 这是**渲染步内部**的那道闸，与第 3 条**门前判据**不是同一道：门前那道决定请求发不发，这一道决定步内是否早退；
    5. **执行区间的暂停**（区间忙标记 ≠ 0 **且**等待位 = 0）—— **盖钟在五条之前、也在渲染步调用之外**，忙判定只能发生在盖钟之后 ⇒ **钟照盖、只跳请求**（渲染步不发出 ⇒ 窗不前进、两个标记不重算；同一忙状态在更早的两处还让时间交付与影片逐槽计时不跑，见「一次迭代做哪些事」的暂停开关）。它**与（b）的窗口消息闩不是同一格**。
    ★ 执行区间的暂停**在这张表里**（第 5 条）：忙 ∧ 等待位 = 0 时门前**只跳请求**，钟照盖；同一忙状态在更早的两处（时间交付、影片逐槽计时）独立挡下 —— 那两处在盖钟之前，见「一次迭代做哪些事」的暂停开关。
  - ★ 次序固定：先三个"整段跳过"（场景绘制模式 / 画面暂停闩 / 门前判据第 3 支：`0x21b` 标量 = 0 且等待位 / 影片位都为 0），再**盖钟**（这一步在渲染步调用之外，见「推进时机」），再这**五个**"只挡推进"的（第 24 位 / 影片对象正被另一处持有 / 门前判据第 5·7 支 / 批次闸拒绝 / 执行区间的暂停）。
- **持续时间 ≤ 0 的窗不走到期收尾**：对**绘制项**，颜色窗那一段**整段跳过** —— 不插值、不写这一步的派生色、不改当前色与终色、不清起止与"有窗"位；它的"到期"只是**读者视角**（`现在 ≥ 起点 + 延迟 + 0` 成立）。对**网格**，这一步把**窗起点清 0** 并清该条的"有窗"位、置「有动画」，同样**不**做终色 → 当前色的收尾。⛔ 不许写成"持续时间 0 的窗走正常收尾"。
- **场景级「强制完成」位**：命令档在**本帧的渲染步**对**类型 < 0** 的命令把它置 1。★ 本版把这个格统一叫**「强制完成」位**（**独立的一格，不是状态字里的某一位**；读侧的效果是中止当前等待）；旧文里的「中止位」是**同一个格**的别名，⛔ 不许实现成两格。
  - **读取点**：**同帧绘制期**的派生（源矩形窗 4.1、命令进度）读到 1 时按"到期"处理（不看时钟）。
  - **颜色窗的推进与「强制完成」的置起在同一步里，但有先后，而且不是"全有或全无"**：
    - **绘制项的颜色窗**在渲染步的**更早子步**推进；「强制完成」的置 1 发生在**它之后**（命令档逐条处理命令时）⇒ **绘制项的颜色窗当帧看不到本步置起的 1**。
    - **网格的颜色窗推进与「强制完成」的置起在同一次调用内交错**（既不是"先把全部网格窗推进完、再置 1"，也不是"先置 1、再推进"）⇒ 同一份网格记录是否看到本步置起的 1，取决于它在本次处理中的位置（处理顺序见残差 `RES-WINDOW-RECORD-ORDER`）。
    - ⛔ 不许写成"类型 < 0 会让所有颜色窗当帧立刻到期"。
  - **不粘住**：渲染步**收尾**（在"「有动画」= 0 ⇒ 清空命令表"这一步**之后**）**无条件**把「强制完成」清 0 —— 不管本步有没有人读过它。命令档每帧都会重新置位。⇒ 它**只活一个渲染步**；同一步内多次读取**不消耗**它（读点只判"是否 = 1"，不清 0）。⛔ 不许把它写成跨步粘住的开关，也⛔ 不许写成"读一次就清"。
- **到期判据**：`现在 ≥ 起点 + 延迟 + 持续时间` 那一刻该窗**即已到期（相等已到期；按 32 位无符号比较，取 `≥`）** —— 绘制项与网格用**同一形状**的判据。
  **未到期时**，延迟段（`现在 ≤ 起点 + 延迟`）**算窗内**（进度 0；到期判据先判）。
  ⚠ 这与消息等待计时器的 `现在 > 起点 + 时长`（**同样无符号，但取严格大于**、相等仍算窗内）**不是同一个比较** —— 两条的差别是 **`≥` 还是 `>`**，⛔ 不许把两条边界写成同一个判据。
  ★ **在「窗口到期判据」这一族里**，按 32 位**有符号**比较的只有**命令记录**那一路：命令表逐条处理**命令记录**时，比较的是**时间戳 + 延迟 + 持续时间**与场景时刻、以及由它们算出的**命令进度** —— 这些按 32 位**有符号** `≥`（见「场景命令记录族」）。**源矩形窗不是这一路**：它按 32 位**无符号** `≥`（见「绘制项的消费者」的 4.1）。⛔ 不许把"源矩形窗"写成有符号，也不许把这两路合并成一句；也⛔ 不许把上面音效 / 语音那条**有符号**的到期判据并进这一族（那是另一族）。
- **等待谓词与这一对格是同一件事**：放行判据 A 里的**消息等待计时器**（`0x238` 写的那一对"起点 / 时长"格）就是等待谓词读的那条窗 —— 引擎里**没有**第二条"场景级窗"。**它是等待位（第 10 位）服务分支的判据**：等待位置起时每迭代调用一次（位未置起就不调用），顺序固定：
  1. 时长 = 0 ⇒ **整段跳过**（不盖章、不到期、不置**脏**）；
  2. 时长 ≠ 0 ⇒ **无条件**把**脏**置 1（含本次就到期的那一次）；
  3. 起点 = 0（未盖章）⇒ 起点 ← 本步场景时钟；
  4. `现在 > 起点 + 时长`（**无符号、相等仍算窗内**）**或**场景的「强制完成」位 = 1（读侧的效果是中止当前等待；**同一个格**，旧称「中止位」）⇒ 起点与时长清 0；否则**返回 1**；
  5. 返回**「有动画」**标记的值（0 / 非 0）。
  ⇒ "谓词返回 1（窗还在走）"与"「有动画」≠ 0"是**两条并列**的挡门理由：放行只在**返回值 = 0** 时发生（还要影片判据为假）。⛔ 不许把两者写成同一条。
- **谓词的副作用**：若本次**没有走窗内那一支**（时长 = 0，或窗已结束且没有返回 1），并且场景的**主循环模式字**（脚本 `0x24e` 写的那个字；★ 它**就是**「场景对象表的清空」里那个**场景级状态位字** —— 同一格、两个名字，清理入口对同一个字做同一条第 16 位判据）带**第 16 位**、此刻「有动画」又为 0 ⇒ 把该字**整个清 0**（不是只清那一位）。该位由脚本给出，引擎从不自己置它。
- 窗内（`现在 < 起点 + 延迟 + 持续时间`）⇒ 置"场景有动画"（**除**下一条说的"不参与场景动画"位 —— 那一位只压**这一句的置位**，**不压**同一步对**脏**的置 1）；过了延迟之后按 `(现在 − 起点 − 延迟) / 持续时间` 在**当前颜色**与终色之间插值。
- **绘制项的"不参与场景动画"位**（该项选项字的最低位，由**创建 / 更新该项的脚本**给出，引擎只读它并只在一处清它）：
  - 置起时，这一趟**不置**「有动画」，但**照常置脏**（脏不吃这一位）；
  - 置起时，该项**默认无视「强制完成」**（不因它到期）——**除非**场景**主循环模式字**的第 2 位也置起，那时照常吃；
  - 该项自己的**步进窗走完**那一步，引擎把它清 0（与清"有窗"位、清窗起点同处）。
  ⛔ 不许把它当成"引擎内部的优化位"：它是程序给的数据；也⛔ 不许把它当成"有窗"位（两者是同一个字里的不同位，清除时机也不同）。
- **绘制项的这一步颜色**：无窗 / 延迟内 / 持续时间 ≤ 0（不插值）⇒ 当前颜色；推进中 ⇒ 插值结果；到期 ⇒ 终色。★ 这几支的**优先级**是"持续时间 ≤ 0 最先"：那种窗整段不走到期收尾（见上一条），所以"到期 ⇒ 终色"只在**持续时间 > 0** 时成立。这是一个**由当前颜色、终色、窗字段与该步时钟派生的量**：它**不落在该条目的任何字段上** —— 引擎每画一项就把它写进**绘制调用方的一个每步暂存格**，随即被这一项的绘制消费、下一项再覆盖。**当前颜色字段在窗进行中保持原值**（只有到期那一步才被写 ← 终色）。因此窗进行中改写当前颜色会改变后续每一步的起色（同「场景 / 颜色族」的共用口径）。
- **网格的这一步颜色**：无窗 ⇒ 顶点缓冲现状（由 `0x320` / `0x322` 维护，不取当前颜色）；窗推进 ⇒ 按派生色重烘；持续时间 ≤ 0 ⇒ 不重烘。**窗只在被推进的那一步重烘**；`0x320` / `0x322` 的烘色另见「场景 / 颜色族」（同一步以门后写入为准）。重烘**唯一的跳过条件是"顶点缓冲未建 / 顶点数 ≤ 0"**（本句只讲**窗推进这一步**；`0x320` 建 / 换时那道「当前颜色是无颜色 ⇒ 不多烘一次」的门是另一条路径，见「场景 / 颜色族」）；派生色是**无颜色**时**照样烘焙**，结果与"不染色"逐字节相同（无颜色是乘法的单位元）⇒ ⛔ 不许实现出"派生色是无颜色就跳过重烘"这一支（引擎内部确实按**派生色的 32 位整字是否等于「无颜色」**分了两支（比的是**派生色整字**，⛔ 不是"混合系数是否全 1"），但两支写进缓冲的字节相同，没有可观察后果）。没有逐顶点缓冲的网格窗仍推进，但不重烘。
- **「无颜色」= 全 1 值**（术语见「总览与约定」）：正常收尾把终色写成「无颜色」、当前色 ← 原终色（见下面"共享收尾"）。它也会作为**当前颜色**出现（写色规则可以写出它）⇒ ⛔ 不许把它当成"这一格没有值"、⛔ 不许当成"这一步不画"或"跳过重烘"的哨兵；作为颜色参与运算时它等价于**不染色**（乘法的单位元）。
- **正常到期的共享收尾**（持续时间 > 0；绘制项与网格都适用）：取终色 → 当前颜色 ← 终色 →（网格按该值重烘一次）→ 终色 ← "无颜色" → 延迟与持续时间清 0。★ 「有窗」位与**窗起点**的清点**按对象分**：**绘制项的到期支只清延迟 / 持续时间**，不碰「有窗」位与窗起点（它们的清除时机与身份见残差 `RES-WINDOW-FLAG-CLEAR`）；**网格的到期支在收尾之后还会清掉自己的「有窗」位与窗起点**（同一份记录副本随后整份写回表）。源矩形窗与颜色窗共用同一对"有窗"位与窗起点：源矩形的派生只读、不清（见「绘制项的消费者」4.1）。到期这一步不再按 t=1 的插值重烘一次。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某项的窗是否还开着 | 该项的"有窗"位与起止字段 |
| 这一步画什么颜色 | **派生量**：由当前颜色、终色、窗字段与该步时钟决定；没有独立的记录字段 |
| 场景还有动画 | 场景的"有动画"标记（也是「场景待处理标记」/「等待谓词的待处理闩」——同一格）：场景推进在推进各项之前清 0；窗还在走时由推进置起（设了「不参与场景动画」位的项**除外**；同一步**无条件**置**脏**）；此外**只要消息等待计时器还有时长（未被清 0），等待谓词每迭代都会把脏置 1** —— 包括这一次就到期的那一次调用（该谓词只写脏、不读它） |

**成立条件**

- 等待位的放行**不直接读**「有动画」这一格（它只经**等待谓词的返回值**进来）：判据是 `¬A ∧ ¬B`，其中
  **A** =（消息子系统的计时器仍在窗内 **或** 等待谓词**返回**的值 ≠ 0）、**B** =（影片对象表里仍有生效参数 `& 5 == 4` 的对象；生效参数 = 待办 ? 待办参数 : 最近一次真正启动的选项字）。
  「有动画」是这条谓词的**返回值**（窗内那一支返回 1，否则返回本标记）；计时器在窗内那一支还顺手把**脏**置 1。它的读者是**闭集四处**（见「场景 / 颜色族」的 `0x202` 条：等待谓词（返回值 + 状态字清零那一步）、命令档出口（与「强制完成」按位或 ⇒ 置**脏**）、渲染步收尾（为 0 ⇒ 清空命令表），以及"它不决定哪些事"那一项）。★ 它**不是**门前的「就绪判据」所读的那一格：第 a 支读的是**脏**，两者是场景上的**两个不同的格**（⛔ 不许合并、也不许把两方的读者混算）——
  ⛔ 不许把"有动画"写成放行判据里**另读一格**的第三条，也不许写成"表里还有没有未到期的窗"。
- 标记的清除与重置都发生在同一个迭代里、门服务等待位之前：场景推进先把「有动画」与**脏**一起清 0；窗还在走时再把「有动画」置回（设了「不参与场景动画」位的项**除外**），**脏**在同一处**无条件**置 1。等待位读的是**此刻的等待谓词返回值**（窗内 ⇒ 1；否则就是本标记）—— 它**不另存**"上一次迭代"的副本。

### 中止：opcode 0x01

<!-- rule: CORE-OPS-ABORT-01 -->

`0x01` **没有操作数**。它**不写推进格数**，直接抛**退出型异常**（异常码 **1**）。

- 没有别的引擎数据效果：不写池、不写状态字、不写帧。
- 推进格数保持原值（可能是上一条留下的任何值）：因为执行不再回到分派器，这个值不可观察 —— 所以本条**不是**"把格数写成 1"。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 执行被中止 | 一次退出型异常（码 1） |

**成立条件**

- 与「结束当前脚本」不同：`0x2` 是**正常控制流**（父帧号决定回到哪一帧），`0x01` 走**异常通道**（结束执行，不重试、不跳过）。
- 与「重置并重装根脚本」不同：`0x9` 会重新装载根脚本；`0x01` 什么都不装。
- 异常码 1 与其它退出码（0 / 2 / …）的区分**不可观察**：保护区不读退出类的码，处置一律是汇入唯一出口段（见「异常的处置」）。本条只规定"码 = 1"。

### 执行区间的进入与离开：opcode 0x1f4 / 0x1f5

<!-- rule: CORE-OPS-RUN-BRACKET -->

这两条**没有操作数**，是一对**执行区间**的进入 / 离开标记。区间自己用**四个**格：一个**区间忙**标记、一个**嵌套计数**、两个**时间戳格**（「现在」与「上一步」）；队列泵另用几格（见下）。

- `0x1f4`（进入）：若**忙标记为 0** ⇒ 置忙、读一次宿主毫秒时钟、把「上一步」← 原「现在」、「现在」← 本次读数；若**忙标记非 0** ⇒ **只**把嵌套计数 +1（不读时钟、不动两个时间戳格）。
- `0x1f5`（离开）：
  1. 若**嵌套计数 > 0** ⇒ 计数 −1，本条到此结束（不清忙、不泵）；
  2. 否则若**忙标记为 0** ⇒ 本条什么也不做（**未进入就离开是空操作**）；
  3. 否则清忙；然后若**队列泵占用标记为 0** ⇒ 把控制交给**待处理命令队列的泵**；否则直接返回。
- **泵的入口与取出**：区间忙标记 ≠ 0 ⇒ 一条也不取、立即返回；队列头 ≥ 队列尾（空）⇒ 立即返回。两条按此顺序判。否则取**一条**命令、把队列头 +1。命令是 **32 位有符号数**，三种取值：`0` = **空命令**（头已前进，此外什么都不做）；**正数 = 统一文件 id**（见「文件与脚本装载」的「统一文件 id 与两个 id 区」：高 8 位是区号、低 24 位是该份索引里的条目下标）；**负数 = 目标帧号取负**（`−命令`）。
- **非 0 命令先做挂起**（两支相同、顺序固定）：记住**当前帧号**；把**状态选择字**整字存进一格"待恢复副本"，再把它清 **0**（门随即打开）；置**队列泵占用标记**。两条支都让**泵帧的父帧号 = 哨兵 −10**：这个哨兵**不是装载器自己决定的** —— 泵在**装帧之前**先把一个「父帧候选」格写成 −10，装载器只是把它照抄成新帧的父帧号；负支不装帧，由泵自己把目标帧的父帧号写成 −10。
  - **正命令**：先让**当前帧号 ← 37**，再按「装载帧」的合同把那个统一文件 id 装进**帧 37**（先释放该槽原有内容；父帧号 ← 装载前预置的 −10（装载器照抄「父帧候选」格）；指令指针 ← 代码区起点；长度槽 ← 0）。装载失败沿用「装载帧」的失败分档（id 非法 / 打不开 ⇒ 显示消息型异常；头坏 / 装载器返回 0 ⇒ 退出型异常），**但当前帧号停在 37、不恢复**。★ 走**退出型**那一档时执行就此结束、队列与「待恢复副本」不再被读 ⇒ **泵帧的清理不在本条范围**：当前帧号 / 待恢复副本 / 队列泵占用三格保持原值，故不可观察。
  - **负命令**：**先**让当前帧号 ← 目标帧号；目标帧**没有装载脚本**（代码区起点 = 0）⇒ 抛显示消息型异常（文本「この階層にはファイルが読み込まれていません．Depth=%d」，`%d` = 目标帧号）——**当前帧号停在目标帧、不恢复**（★ 与「换帧」相反：`0x8` 在同一个失败点恢复调用者）。否则：目标帧的父帧号 ← −10（负支由泵直接写，不经过装载器）、指令指针 ← 该帧代码区起点、长度槽 ← 0。
  - ★ 两支的末态相同：**当前帧就是"泵帧"，它的长度槽 = 0 ⇒ 分派器不推进 ⇒ 下一迭代执行的是该帧代码区的第一条指令**。当前帧号不再改回调用泵的那一帧——那一帧的帧号只在挂起时被记住。
- **泵帧怎么收场**：泵帧的父帧号是 **−10** ⇒「结束当前脚本」认出这个哨兵并做五件事（顺序固定）：① 当前帧号 ← 挂起时记住的帧号；② 那一帧的长度槽 ← **0**（⇒ 分派器不推进，它从**当时**的位置继续）；③ 状态选择字 ← **待恢复副本**，再做两处修正：**第 14 位取活动字的值**（不取副本）、**第 21 位清 0**；④ 队列泵占用标记 ← 0；⑤ 队列非空 ⇒ **立即再泵一条**（链式），空 ⇒ 回主循环。泵帧**不释放**自己的槽（释放判据是"父帧号 + 1 = 当前帧号"，−10 不满足）⇒ 帧 37 里那份脚本一直留到下一次装载。
  - ⇒ 从 `0x1f5` 的出口进来时，"当时的位置"就是**同一条 `0x1f5`**（它没被推进）；队列排空后它再执行一次，见区间忙标记已清 ⇒ 空操作，随后分派器推进 4 字节。所以**队列先排空、脚本才往下走**。
- **帧 37 是泵的专用槽**：每条正命令装载前都**无条件释放**它 ⇒ 脚本自己把帧装进 37 的那份上下文会被下一条正命令丢弃（引擎没有保护，也不报错）。
- ★ **第 21 位**是窗口重画的抑制位（置 / 清成对包住一次显示面重建，读者只有窗口重画路径），**不在门字服务链里**、不挡派发；泵收场把它清 0 ⇒ 一个"暂停重画"位不会跨过泵生存。
- **泵帧运行期间**再有命令被投递：投递口的顺手泵与 `0x1f5` 的出口泵都被**队列泵占用标记**挡下；`0x143` 在尾跳前会先把标记清回 0 ⇒ 它在泵帧内也尾跳进泵。**嵌套泵**（挂起帧与待恢复副本两格被第二趟覆盖）怎么收场未取证（见残差 `RES-VM-PUMP-NEST`）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 是否有一段区间正在执行 | 区间忙标记（`0x1f4` 置、`0x1f5` 清） |
| 区间嵌套了几层 | 嵌套计数（`0x1f4` 在忙时 +1、`0x1f5` 在 > 0 时 −1） |
| 待处理命令队列 | 队列头 / 队列尾 / 队列表；`0x1f5` 归零时最多取走一条 |
| 取走一条后处于"泵帧"里 | 当前帧号（正命令 = 37、负命令 = −命令）；泵帧父帧号 = −10；长度槽 = 0 |
| 泵期间"对外有效"的状态选择字 | 活动的那一格 = 0；待恢复副本 = 挂起时的整字 |
| 泵帧结束时 | 当前帧号 ← 挂起帧；状态选择字 ← 待恢复副本，再把**第 14 位取活动字的值**、**第 21 位清 0**；队列泵占用标记 ← 0 |

**成立条件**

- **忙标记只有 `0x1f4` 置、只有 `0x1f5` 清**。别的指令（包括 `0x143` 的刷新）只**读**它来阻止泵，不写它。⛔ 不许把「谁写它」实现成多条指令共管。
- **挡泵的只有两个标记**：**区间忙标记**（挡泵的**入口** ⇒ 命令只在最外层区间结束时才被取）与**队列泵占用标记**。`0x143`（见「事件刷新：opcode 0x143」）在逐格投递期间置起的就是**后者**（所以那一串"顺手泵一次"的尾巴都被挡下），结束时清回 0、再尾跳进泵 —— **是同一个标记，不是另一个格**。⛔ 不许实现成两个开关：那会让 `0x1f5` 的出口在泵帧里开闸、把队列套成两层。
- **计数与忙标记不对称**：忙时段内每次进入只 +1，出口每次离开只 −1 ⇒ 深度 = 计数 + 1。⛔ 不许把 `0x1f4` 实现成「每次都 +1」（那样最外层的进入会被算成 2 层）。
- 两个时间戳格是**引擎级**的「引擎当前时刻 / 引擎上一时刻」，与 `0x20c` 是**同一对**（它同时是场景时钟的一对，见「场景计时窗」）；`0x1f4` 的写入按普通场景时钟语义被消费 —— 本区间**没有**额外的时序含义。
- `0x1f5` 在未配对时是**空操作**：不清忙、不泵、不抛。⛔ 不许把它实现成「无条件清忙」——那会让后续的泵在本该被挡的时候开闸。
- 泵**一条**为一趟：⛔ 不许循环取空队列（那会一次迭代执行多条指令，与「一次迭代至多执行一条指令」冲突）。
- **"一趟只取一条"与链式不矛盾**：链式再泵发生在**泵帧结束**那一步（第 ⑤ 步），是下一次迭代的入口，不是同一个调用里的循环。⛔ 不许把泵实现成"在取命令的地方循环取空队列"（那会让一次迭代执行多条命令）。
- 两条都先把**当前帧**的推进格数（见「总览与约定」的长度槽）写成 1（`= 2 × 0 + 1`）；这一写发生在上面任何判断之前。

**三个近名格各指一格**（⛔ 不许混用）：

| 名字 | 指哪一格 |
|---|---|
| 槽级「待办」（=「排队」） | 语音槽记录里的那个槽级标记：一段配音排进该槽时置 1，时间交付推进该槽时读它 |
| 子系统级「该子系统仍有一件未完成的工作」 | 声音子系统级的一个标记：交付把一个音效通道 / 语音槽重新置起时置它，第 14 位的服务体读它 |
| 泵「队列泵占用标记」 | 泵自己的那个标记：泵帧运行期间置起，挡下投递口与 `0x1f5` 出口的泵 |

### 无条件重盖时钟对：opcode 0x23c

<!-- rule: CORE-TIMING-STAMP-23C -->

`0x23c` **没有操作数**。它把引擎的**时钟对**重盖一次，**不经过任何门**：

- "上一次读数" ← "现在"（旧值搬过去）；
- "现在" ← **系统毫秒时钟**的一次新读数。

- 不读操作数、不写操作数、不发平台请求、不改门位与忙标记。
- 与「时钟」条登记的那对格子是**同一对**（场景计时窗共享）；本条是它的**无条件**写者。

**状态对应**

| 上一次读数 | ← 现在的旧值 |
|---|---|
| 现在 | ← 系统毫秒 |

**成立条件**

- **无条件**：不看执行区间忙标记、也不看门 —— 这两点与 `0x1f4` / `0x20c` 不同。
- 先搬旧、再写新（与所有已登记写者同序）：⛔ 不许只写"现在"。
- 它不推进场景、不发渲染请求、不触发任何动画。
