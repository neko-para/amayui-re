## 列表项与子系统写入

本章 16 条规则 / 22 个 opcode。

### 设默认组：opcode 0x80

<!-- rule: CORE-OPS-LIST-DEFAULT-GROUP -->

`0x80` 有一个操作数：把它**读成整数**后原样写进引擎里的**默认组**选择子（不归一、不夹取、不做范围检查）。

**默认组**是列表组号为 0 的写入指令（`0x70` / `0x79` / `0x1c1` / `0x303`，以及 `0x73` 的记录写）实际使用的组号。它的**初值是 1**（列表 / 消息子系统建立时写入）；本条把它的当前值换成操作数。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 默认组 | 引擎级的默认组选择子 ← 第 1 个操作数 |

**成立条件**

- 组号 0 **不是**"第 0 组"，而是"用默认组"：初始状态下组号 0 与组号 1 写的是同一条记录。
- 本条**不改任何列表记录、也不建记录**：它只改"以后组号 0 落到哪一组"。
- 操作数不做范围检查：把默认组设到列表组范围之外，会让后续的列表写指令越界访问（未定义行为，按崩溃诊断）。本条不替引擎 clamp。
- 初值 1 是**子系统建立时**写进去的，不是一个编译期常量；子系统的重建路径**本版不规定**（原因：重建入口没有建模）。
- 选择子的值被直接当作组号用，所以它是"组号"而不是"记录指针"或"偏移"。

### 设置一个列表项：opcode 0x70

<!-- rule: CORE-OPS-LIST-SET -->

`0x70` 有五个操作数。它把**第 1 个操作数读成组号**（组号为 0 时换成引擎里的默认组），把后面两对值写进该组的**记录**，并把该组标记为"已登记"：

- **同样的**一对值（第 2 个, 第 3 个）写进**三个**字段对；★ 其中**一对**（本层记录里的"缩放后尺寸"那对）
  随后**被本层的缩放结果覆盖**（显示适配比 = 1 时恰好等于原值；否则不是，见「文本层画布」）⇒
  该指令**返回后**只有**两对**仍是原值，那一对是**缩放后**的层尺寸；
- **另一对**值（第 4 个, 第 5 个）写进**另一个**字段对（本条写入顺序里的第 4 个字段对）。

**字段对的身份**：`0x1c1` 写的是三对 (第 2 个, 第 3 个) 里的**最后一对**（不是 (第 4 个, 第 5 个) 那一对）—— 两条因此互相覆盖该对；`0x79` 与 `0x303` 写的对与 `0x70` 的任何一对都不相同（互不影响）。⛔ 不许把 `0x79` / `0x1c1` / `0x303` 当成同一个 setter 的三种写法。

随后它做**列表登记**，再按**场景绘制模式**分岔配置一张绘制表面。

- **列表登记（合同）**：向列表对象的**列表登记序列**追加一条 `{组号, 该组定位记录位置}`，随后把该序列的**两个游标**（读游标 / 当前游标）都指到刚追加的那一项，并把该组的「已登记」标记置 1。
  - 第二个分量 = **字体对象的定位记录序列**在登记那一刻的**元素条数**（写入时**不减 1**）。★ 因此这个量是**唯一**的：它不来自任何独立计数器。
    ★ **两条序列不是同一条**：`{组号, 条数}` 追加进的这条叫**列表登记序列**（追加者就是本条与 `0x71`）；而"条数"取长度的那条是**字体对象的定位记录序列** —— 它由**若干条**写入路径追加，其中已定的一条是「登记一条字体条目」那条脚本指令（`0x1d2`）：**文本显示门放行时一条；门非 0 时整条跳过、一条也不加**（该条记录携带那条指令的两个操作数；读法与守卫见「登记一条字体条目：opcode 0x1d2」）。★ 其余追加者是**同一趟排版**的正文 / 语音记录写入：它们是**每段一条**（不是每排一行一条）、且都在**排版那一趟里**一次性写好 ⇒ ⛔ 不许把"排版每排出一行就多一条"当来源。⛔ 也不许把两条序列合成一条：合成之后"条数"就没有唯一值（登记自己也会加长它）。
    读出侧把这个值当**下标**用（取那条记录的状态掩码、并交给绘制请求）⇒ 语义上是"**下一条记录将占用的位置**"，不是"已有几条"这个计数、也不是"最后一条的序号"。
  - **两条读法**：① **按当前项发绘制请求**（把第一个分量当绘制组号、第二个当**定位记录下标**交给绘制请求；另一个实参来自槽表，与本对无关）；② **按掩码移动读游标**（不给量 ⇒ 读游标回到当前写游标；给正量 ⇒ 向后、给负量 ⇒ 向前，逐项跳过状态掩码命中的记录；向后到最后一条登记项停、向前到第二分量为 0 或游标到 0 停）。⛔ 两条读法不共用"移动"语义：① 只读不移，② 才动游标。
- **绘制表面（合同）**：模式 = 1 ⇒ 建 / 重建**纹理画布**（尺寸 = 缩放后的层宽 / 高）；模式 ≠ 1 ⇒ 建 / 重建**旧式精灵表面**（尺寸 = 未缩放的层宽 / 高）**并给它设一个颜色键**（取值 = 绘制对象的「精灵基色」格；那一格是**绘制对象自己的一格 32 位颜色**、旧路径只读它，定义见「ADV 文本」的图层条）。⇒ 这两条**不是绘制**：它们不提交任何绘制条目（条目由文本层的绘制路径产生）。旧路径那两支的完整合同见「ADV 文本」章的图层条，本节不重复、也不另立一套。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该组记录的三个字段对 | ← (第 2 个, 第 3 个)（三对各不同字段、**写入时**值相同；其中一对随后被缩放后尺寸覆盖） |
| 该组记录的第四个字段对 | ← (第 4 个, 第 5 个) |
| "该组已登记" | 该组的登记标记 ← 1 |
| 列表登记项 | 一条定长元素 `{组号, 定位记录位置}`（追加序 = 登记序） |
| 读游标 / 当前游标 | 两个序号格；追加后都指向新项；"回到当前项"就是读游标 ← 当前游标 |
| 该组的绘制表面 | 纹理画布（模式 = 1）或旧式精灵表面（模式 ≠ 1，另设颜色键） |

**成立条件**

- 写的是**该组的记录**：别的组的记录不受影响（组号是索引）。
- 第 2、3 个操作数被读**三次**（每个字段对一次），不是三对不同的源；三对字段对的值因此相同 —— 但**字段不同**，不许合并成一格。
- 组号为 0 是"用默认组"，不是"第 0 组"：默认组初值 1，由 `0x80` 改写（见「设默认组：opcode 0x80」）。
- 记录不存在 ⇒ **不检查**：直接按记录指针写字段（解引用空指针，未定义行为，按崩溃诊断）；本条不建记录。
- 登记标记与字段写是两件事：字段写成立不等于"已进列表"。
- 第二个分量的**写入口径与读出解释不同**：写入是"条数"，读出是"下标"。⛔ 不许在写入时减 1（会让遍历从倒数第二条开始），也⛔ 不许在读侧当计数用。
- 登记**不改**定位记录本身、**不改**执行位置：它只追加一对 + 动两个游标 + 置一个标志。
- 登记只影响**该组**：十组的登记标志格是十格独立的。
- 记录里还有别的字段（本版不写）；它们由别的指令维护。

### 文本子系统的请求：opcode 0x71

<!-- rule: CORE-OPS-LIST-TEXT-REQUEST -->

`0x71` 有一个操作数。它做两件**引擎数据**层面的事，然后把其余工作交给文本子系统：

1. 把**本条指令的位置**（本条指令相对代码区起点按 32 位字编号的下标）写进当前帧的一个字段；
2. 向文本子系统转发一次请求：实参是那个操作数，**外加一个引擎级槽的值**（不是操作数，本版不建模它的当前值）。

此外它在**该层复位之后、向平台发任何请求之前**还做三件**与画面无关**的内部记账（合同）：

1. 把**按槽位编号的表**（固定容量、定长元素）的当前内容**整块发布**到它的**存档快照**；
2. 把**按平面编号的表**（固定容量、定长元素）的当前内容**整块发布**到它的**存档快照**；
3. 把文本库的**待办队列抽干一次**（按入队顺序逐条交给队列的消费者），并把队列的高水位**抬到当前头**（头没超过它时不抬）。

两次发布都是**逐字节搬运**，不做变换，也不改**活动表**自身的值；它们**不看场景绘制模式**（纹理画布路径与旧式精灵表面路径**都做**）。方向固定为**活动表 → 存档快照**；快照的**唯一合同内读者**是**存档写出**，**渲染侧与读档侧都不读**它（读档写的是**活动表**，见下）。⛔ 不许把发布挂进模式分支（那会让另一条路径下的存档缺这两块），也⛔ 不许反过来写。抽干**不产生新的入队**，队列为空时什么也不做（高水位不动）。

**两张定长表与它们的存档快照（身份表；⛔ 本节是唯一落点，别处只指向本表）**

| 表 | 活动表 | 存档快照 | 活动表的写者 | 快照的写者 | 活动表的读者 |
|---|---|---|---|---|---|
| **按槽位编号的表**（100 项、定长） | 一对里的**活动**那一块 | **同尺寸**的另一块（由本条发布得来） | **只有**一条"整体清零"指令（逐元素清**固定一格**） | ① 本条的两块发布；② 同一批清零（见下） | 无脚本可见读者；这一段是**存档里的恒零保留区**（见下「按槽位编号的表」；字段语义明确舍弃） |
| **按平面编号的表** = **纹理记录表**（1000 项、定长） | 一对里的**活动**那一块（**场景**对象里那 1000 条记录） | **同尺寸**的另一块 | **四个运行期写者 + 两处标志写 + 读档恢复**：空白创建、按文件号设置（成功 / 失败分档）、释放、区间释放（各自写「来源文件格」；见「纹理：读槽→文件绑定」的写者表）、`0x258` 写「标志两格」、`0x259` 清全部 1000 项的标志两格、**读档恢复**逐项重建 | ① 本条的两块发布；② **两条标志写**（`0x258` / `0x259` —— 它们本来就**同时写两张表**） | 「纹理：读槽→文件绑定」那条指令 —— 它读**活动表**，⛔ 不读快照。★ 另有**读档恢复**这一个读者，但它读的是**存档影像**里的一项（逐项判「恢复重建门 = 1 且来源文件格 ≥ 0」），读完只写活动表 ⇒ 它不是活动表的读者 |

- **存档取快照、不取活动表** ⇒ 存档里的这两块与活动表**差一拍**，但**只差在「只写活动表的三类格」上**：**来源文件格 / 颜色键 / 空白标记**。**最后一次发布**（= 最后一次「请求文本层」）之后由那四个运行期写者（以及 `0x1f9` 的**颜色键**、`0x20b` 的**空白标记**）改的这三类格**不**进存档（要等下一次发布才进）；发布之后立刻存档，则两者逐字节相同。
   ★ **标志两格不是这样**：`0x258` / `0x259`（含清零）本来就**同时写活动表与快照的同一批格** ⇒ 这两类写**立刻**就在存档里、与活动表**不**差一拍；⛔ 不许把"差一拍"套到它们头上（那会让"差一拍"看起来像整表都滞后）。⇒ 差拍的判据是「**这个写者写不写快照**」，不是「这类格重不重要」：**只写活动表的写者**（空白创建 / 按文件号设置 / 释放 / 区间释放 / 矩形填充）都只动活动表。
- **读档恢复写活动表**：按平面编号那张由读档路径**逐项重建**活动表（不写快照 —— 两者的下一次一致由下一次发布带来）；按槽位编号那张**读档不回填**（见下「按槽位编号的表」）。
- **清零 / 标志写与发布是两件事**：清零与标志写**逐项改格值**、并且**活动表与快照的同一批格一起改**；发布只整块搬运。⛔ 不许把清零实现成"发布前先把副本抹掉"，也⛔ 不许实现成整表清零。
- **两张表的领域地位**：按槽位编号那张的**字段语义**本版**明确舍弃**（引擎不解释元素内各分量，且没有脚本可见读者；它的领域身份见下「按槽位编号的表」）；按平面编号那张（= 纹理记录表）的每格**各有归属**（来源文件 / 颜色键 / **恢复重建门** / **零读者标志** / 空白创建标记，见「纹理」章的纹理记录段），本版只规定与可观察行为有关的那几类：**来源文件格**（被按编号取值读）与**标志两格**（被两条标志指令写 / 清；其中**门那一格**的读者是**读档恢复**）⇒ 其余两格"写进去但没有读出点"这件事本身见纹理章的残差。本版只规定这些可观察行为：**整块发布** / **一次按编号取「来源文件格」当结果值**（不是绘制请求实参、不建绘制项）/ **逐元素清固定几格** / **快照的唯一合同内读者是存档写出**。
- ★ 这份快照在**存档写出**里有**三处搬运点**（写出器按**记录种类**分岔，三支互斥，每支各自把快照整块搬进自己的暂存区）⇒ **同一个存档文件里这段只出现一次**（由当次的记录种类选中哪一支），且三支之间**互不共享**：不是一份被引用三次，也不是一段被切成三份。各支的落点见「存档」的负载布局（本作样本的容器里它是负载起点之后的那段定长块）；⛔ 别把这句读成"存档里有三种记录各带一份"。

**按槽位编号的表：存档里的恒零保留区（可观察事实）**

- 它有两份**并排的同尺寸**块：活动表与快照（都归引擎对象所有），每份是 100 项、每项三个整数。
- 引擎对这两张表只做三件事：① **逐项把每项中间那个整数清 0**（活动表与快照同一批格，一次清两份；每项另两个整数**从不被写**，对象新建时即为 0）；② **整块发布**（活动 → 快照，见上）；③ **存档写出**时把**快照**整块搬进暂存区（写出器有**三处搬运点**，见上 —— 同一份存档里这段只出现一次）。
- **没有读者**用它参与判断或计算（唯一的"读"是发布时的整块搬移）；**读档不回填** —— 没有任何路径把这段字节写回活动表或快照。
- ⇒ 这段定长块（每份 1200 字节）在**每份存档里恒为全 0**，读档之后两张表仍是全 0（不是"恢复存档里的值"）。
- ⛔ 不许因为「反正是 0」就省略这段：省略会改变存档长度与后续字段位置（它是**存档格式的一部分**）。
- ⛔ 不许把它登记成第二个领域实体：它的**字段语义**明确舍弃（见上）；也不许把两表实现成一份被引用两次（清零 / 发布 / 写出三处都是「两份」）。

**待办队列表（合同）**

- 队列元素定长、**三个整数**：**(名字, 起, 止)**。
- **抽干**：按入队顺序逐条取出；取一条就把头前移一格，并把**高水位**抬到当前头（**只在头已超过它时**抬）；队列空时什么也不做（高水位不动）。抽干**不产生新的入队**。★ **高水位只写不读**：本版没有观察到任何读者，⛔ 不许为它编语义、也⛔ 不许拿它当"队列里还有几条"的计数（本版没有这种读者）。
- 每条元素交给**唯一的消费者**，消费者的行为是：
  - **起 < 0** 或 **止 ≤ 起** ⇒ **什么也不做**（该条被忽略，不是错误、不报错）；
  - 否则把**名字**（一个整数）格式化成文本形式，用它在一张**按名字索引的映射**里查；
  - **没有** ⇒ 新建一张长度为**止**、初值全 0 的整数数组，并连同名字登记进映射；
  - **有** ⇒ 取出该条目记的**长度**与**起**比：
    - **起 ≥ 长度** ⇒ **扩**：新长度 ← **止**；新数组**先全 0**，再把旧数组的**前「旧长度」格**原样搬到新数组前部，最后释放旧数组；
    - **起 < 长度** ⇒ **不扩**：长度与内容都**不动**；
  - 两条路最后都做同一件事：把**第「起」格写成常量 1**。
- 数组每格是**标记**（0 / 1），不是数值：写进去的恒是常量 **1**，与「起」「止」和名字都无关 ⇒ 它记录的是"这个位置已经被预留过"。

另有一次入口键为「读文本跳过」的调用，那个入口键的当前值由 `0x1ca` 写（见「设一个命名键：opcode 0x1ca」），其处置不在本版。本条还会做一次**有条件的**状态位写：**置状态选择字的第 27 位**（与 `0x88` 清的是同一位）；条件是**文本子系统的一次调用返回非 0**。★ 第 27 位**不是等待位**：等待位是同一个状态选择字的第 10 位（见「等待（opcode 0x21c）」）。⛔ 不许把这两个位当成同一位。

**置起第 27 位之后**：该位是**消息逐帧推进门位**（见「执行与时间」的服务链位序表与「成对写：opcode 0x88」）—— 服务链扫到它时**进入一次消息处理并交回迭代头**，所以**本迭代不派发脚本指令**、也不再置打字位（第 29 位）；当它被清 0（`0x88` 为 0 支 / `0x19b` / `0x19c` 的「三个判据格全 0」支 / 消息处理自己）之后，门不再被这一位挡住，脚本继续执行。★ `0x19c` **不是无条件清 0 的**：它按三个判据格选支 —— `C ≠ 0` 或 `E ≠ 0` 时**置**这一位，`F ≠ 0` 时**不动**它，只有 `C = 0 ∧ E = 0 ∧ F = 0` 才清 0（见「引擎级模式位」）。⇒ 「置起」= 本帧把控制交给消息推进，「清 0」= 放行脚本。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 当前帧"本条指令的位置" | 帧记录的一个字段 ← 本条指令的位置 |
| 文本请求 | 一次请求（操作数 + 引擎级槽的标识；槽值未建模） |
| 按槽位编号的表 / 按平面编号的表 | **活动表**：两块固定容量的定长元素区（容量与元素宽度属机器层） |
| 两张表的存档快照 | **另外两块同尺寸区**；每次文本请求后被发布成与活动表逐字节相同（此后**只有「来源文件格 / 颜色键 / 空白标记」这三类格**要等下一次发布才进快照 ⇒ 存档与活动表在这三类格上**差一拍**；**标志两格与清零不差拍** —— 它们本来就同时改两块；按槽位编号那张的格只由清零改，因此从不差拍） |
| 文本库待办队列 | 元素定长、三索引（头 / 尾 / 高水位）；每次文本请求后被抽干。★ 高水位**只写不读**（抽干时抬到当前头），不是计数、不是判据 |
| 一条队列元素 | 三个整数 **(名字, 起, 止)**：名字是映射的键、起 / 止是所预留区间的两端 |
| 按名字索引的定长整数数组 | 该文本库对象上的一张"名字 → 整数数组"的映射；未命中就按「止」新建一张全 0 的；命中且**起 ≥ 已记长度**时**扩到「止」**（新块全 0、旧内容按旧长度搬到前部、旧块释放；长度只增不减）；每格是标记 0 / 1 |

**成立条件**

- 位置写的是**本条**指令的位置，不是下一条。
- 写的这一格与「换脚本（opcode 0x3）」写的「调用点位置」是**同一帧记录里相邻的两个不同字段，互不复用**：两处的数值算式相同（`(指令指针 − 代码区起点) / 4`），但实现必须用两格，⛔ 不许共用一个字段。帧记录里各格的布局属机器细节。
- 请求里那个**引擎槽**是独立一项实参（不是脚本操作数）：把它记成"操作数"会让一个"永远是 0 的槽"看起来像脚本给的 0。
- 那次状态位写是**置第 27 位**（位号从 0 起数）；条件已取证（文本子系统调用返回非 0）。该位的服务与放行见上「置起第 27 位之后」与「成对写：opcode 0x88」：**置起挡住本迭代的脚本派发，清 0 放行**。⛔ 不许把它写成"本版不规定"。
- 两次发布**无条件**做：⛔ 不许挂在"纹理画布路径"或"旧式精灵表面路径"之一里（否则另一条路径下的存档会缺这两块）。
- 方向固定：**活动表 → 快照**。⛔ 反了会让"写完一段文本"把上一次存档的内容盖回去。两块发布互不影响；发布不改活动表，也不产生新的登记。
- **存档取快照、读档写活动表**：⛔ 不许实现成"存档直接读活动表"（那会让"最后一次发布之后有没有改动"变得不可观察，也与清零碰快照这件事矛盾）；也⛔ 不许实现成"读档把记录块只写进快照"（活动表才是运行期读者看的那份）。
- 发布与抽干都发生在**向平台发请求之前** ⇒ 与画面是否可见无关（场景绘制模式 ≠ 1 时同样发生）。
- 队列**忽略**非法区间（`起 < 0` / `止 ≤ 起`）：该条被丢掉、不建表、不报错。
- 名字是**键**：⛔ 不许拿元素指针 / 入队序号当键（否则同一个名字第二次会新建第二张表）。
- 清零与发布是**两件事**：清零改格值（**活动表与快照的同一批格**），发布整块搬运；⛔ 不许把清零实现成"发布前先把副本抹掉"，也⛔ 不许实现成整表清零。
- **容量就是「止」**：新建与扩容两次都取「止」，⛔ 不许写成 `止 + 1`（多出一格）、也⛔ 不许换成任何"扩容策略"（翻倍 / 向上取整到 2 的幂 / 加固定增量）。判据是"投 `(名, 3, 10)` 之后长度恰为 10"。
- **长度只增不减**：命中的两条路里，只有 `起 ≥ 长度` 会改长度，且改后恒等于「止」；⛔ 不许实现成"每次命中都按「止」重建"（那会把已有的标记清掉）。`起 < 长度` 这条路上除了那一格标记**没有任何写入**。
- **搬的是旧长度格**：扩容只搬旧数组的**前「旧长度」格**，其余靠新数组的全 0 填充；⛔ 不许从旧数组越界读，也⛔ 不许拿"新长度"当搬的格数。
- **同一元素重复投递是幂等的**：第二次 `起 < 长度` ⇒ 不扩、不改内容（第「起」格本来就是 1）。

**可证伪**

- 存一次档、逐字节扫描按槽位编号那段 ⇒ 必须全 0。出现任何非 0 ⇒ 有本版没找到的写者（恒零保留区的结论被推翻）。
- 改存档里这一段为任意值后再读档、立刻再存一次 ⇒ 第二次存档里必须**又是全 0**（读档不回填、存的是引擎自己的状态）；保留了改后的值 ⇒ 读档回填了。
- 存一次档、再调一次「请求文本层」、再存 ⇒ 这一段两次必须**完全相同**（都是全 0）；不同 ⇒ 发布产生了内容。
- 少写这一段再读档 ⇒ 必须失败（文件长度 / 后续字段错位）；"跳过也能读" ⇒ 存档布局里这段不是定长。
- 两次发布都做：把场景绘制模式设成 ≠ 1 后调一次「请求文本层」⇒ 两块快照都必须与活动表逐字节相同；只有其中一块被发布 ⇒ 有一块挂在模式分支里。
- **差一拍只在三类格上**：先用同一个文件号装同一槽、**颜色键取负**（= 无键）→ 调一次「请求文本层」→ 再用**非负**颜色键重装同一槽（**不**发布）→ 存档 ⇒ 存档里该槽的**颜色键格**必须仍是**无键**（旧值），而活动表里已经是"不透明"键；存档里读到**新键** ⇒ 存档直接读了活动表（或颜色键那一格被错当成"也同时写快照"）。同一构造下把**空白标记**那一格换掉（连调两次矩形填充、中间不发布）⇒ 存档里的空白标记同样必须是**旧值**。
- **门那一格有读者**：给某槽装一个可解码的文件（来源文件格 ≥ 0）→ 用 `0x258` 把该槽的**位 0** 置 1（这一写同时进活动表与快照）→ 存档、再读档 ⇒ 该槽**必须被重新装载**（按编号查询尺寸非 0、按编号读回来源文件仍是那个文件号）。把同一次构造里的**位 0 置 0**、其余不动 ⇒ 读档路径**不得**重新装载它（是否被恢复前置的"先释放全部纹理槽"清掉是另一回事，判据是"有没有重新装载"，不是"槽空不空"）。
- 投 `(名, 5, 10)` 后再投 `(名, 0, 3)`：第二次必须**什么也不动**（长度仍 10、第 5 格仍是 1）；长度变成 3、或第 5 格变 0 ⇒ 把"只在 `起 ≥ 长度` 时动手"写成了"每次都重建"。
- 投 `(名, 0, 4)` 后再投 `(名, 6, 10)`：长度必须是 10、第 0 格**仍是 1**、第 6 格是 1；第 0 格变 0 ⇒ 扩容漏搬旧内容（或先清后搬）。同一构造里长度变成 11 / 16 / 6 ⇒ 容量取错。
- 投 `(名, 2, 3)` 后再投 `(名, 4, 8)`：第二次命中且 `起 = 4 ≥ 长度 = 3` ⇒ 必须扩到 8，且第 2 格仍是 1、第 4 格是 1；长度仍是 3 ⇒ 把 `起 ≥ 长度` 的判据写成了 `起 > 长度`。
- 投一条 `止 = 起`、或一条 `起 < 0` 的元素，且该名字**已在**映射里：长度与内容必须**逐格不变**（早退发生在扩容与标记写之前）；长度被撑到「止」、或出现新标记 ⇒ 把 `止 ≤ 起` 的早退写成了 `止 < 起`、把 `起 < 0` 的早退写成了 `起 ≤ 0`。

### 写列表记录十格 + 一个固定格：opcode 0x73

<!-- rule: CORE-OPS-LIST-SUBSYSTEM-SET73 -->

`0x73` 有**十个**操作数（与本版另一条十操作数指令 `0x320` 并列最多）；读序是**先第 10 个、再倒序第 9..1 个**：

1. 把第 10 个写进一个**引擎级固定格**：值为 0 时写成 **1**（不是 0）；
2. 把第 1..9 个按下面的固定公式写进**该组列表项记录的十格**（第 1 个是组号，0 ⇒ 默认组）。★ **这些记录住在字体对象持有的、按组号索引的记录数组里**（⛔ 不是引擎级数组，也不是绘制项表）。这是**引擎数据写**，不是"转发"：
   - 第 4、5、6 个各写一格；
   - 再两格写**和**：第 5 个 + 第 7 个、第 6 个 + 第 8 个；
   - 再两格写第 2、第 3 个；
   - 一格写**常量 1**；
   - 最后两格都写第 9 个；
3. 再看**场景绘制模式**（一个引擎级格，初值 0；写者见「执行与时间」）：它为 **0** 时，向引擎持有的一个对象发一次**消息号为 `0x21`** 的请求，实参 = `2 × 第 7 个`、第 8 个、常量 2；非 0 ⇒ 这一次请求**不发生**。

★ 第 2 步与 `0x70` 的字段对、`0x79` / `0x1c1` / `0x303` 的对都**不重叠**：它写的是记录里另一段连续的十格。

**那十格的去向：它们是一个「单元网格」**

**布局计算**是引擎把该列表项排成单元网格时跑的那一趟，本版给它三条合同（它是这十格的**唯一读者**；本趟**还**读记录上的一对「对齐格」，那两格**不在十格之内**，见第五组；本趟也是下面可证伪的观测点）：
它**输入**（该列表项 + 一个**单元序号**），**输出**（该单元的 **x / y**；以及一格**原样转出的出参**），**返回**（**「参与」** ⇒ 给出 x / y 与那一格原样转出的出参；**「不参与」** ⇒ 没有结果）。它读这十格（另加第五组的对齐对），读法固定为**五组**（**分组是合同**）：

- **闸**：一格（本条恒写常量 **1**）—— 为 0 ⇒ 该列表项**不参与**这次布局（整条布局算式早退）；非 0 ⇒ 参与。
  ★ 这一格的值**不是**脚本给的，是常量 1。
- **矩形**：左格 ← 第 5 个操作数、上格 ← 第 6 个；右 = 第 5 + 第 7、下 = 第 6 + 第 8（所以第 7 / 第 8 是**宽 / 高**）。
  消费端按「右 − 左」「下 − 上」得**单元总宽高**。
- **偏移**：两格 ← 第 2 / 第 3 个操作数；在算出单元矩形之后**加到 x / y** 上。
- **每行格数**：★ **两格都是第 9 个操作数**。一格被**原样写出**给调用方（布局结果的一部分），
  另一格被当**整数除数**参与「单元序号 ÷ 每行格数」—— 所以第 9 个操作数 = 0 时这一步**除零**（见下「每行格数为 0 时的后果」）。
- **一个不参与算式的编号**：第 4 个操作数写进十格之首，**不进**上面任何算式；它随**另一次绘制请求**作为编号交出。
- **对齐对（第五组；不在十格之内）**：记录上另有一对格（**对齐模式 / 基准坐标**，由 `0x303` 写 —— 见「写一对字段（记录必须已存在）：opcode 0x303」）。它**不是**这十格的一员，但**本趟照样读它**，而且它决定这一项**参不参与**与出参 x：
  模式 = 0 ⇒ **不参与**（没有结果，与「闸」为 0 同一种返回）；模式 = 1 / 2 ⇒ 参与，x 按该条的公式（基准 − 半宽 / 基准 − 右界 + 左界）；**其它取值** ⇒ 参与，x = **0**。
  ★ 因此「这一趟只读那十格」是错的：对齐对是**第五组**读入，只是它不在那十格里。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 那个引擎级固定格 | ← 第 10 个操作数，**0 被换成 1**；它是「逐格揭示」动画节拍器的**节拍长度（毫秒）**（初值 500；见「逐格揭示当前文本的启停：opcode 0x1ce」） |
| 该组列表项记录的十格 | ← 由第 1..9 个操作数按上述公式算出（含一个常量 1） |
| 该列表项的单元网格：闸 / 矩形 / 偏移 / 每行格数 / 一个编号 | 记录里连续的十格（闸恒 1；矩形 = 左 / 上 / 右 / 下；偏移两格；每行格数两格同值；编号一格） |
| 可能发生的第二次请求 | 一次请求（消息号 `0x21` + 三个实参），条件是**场景绘制模式 = 0** |

**成立条件**

- "0 换成 1"是这条最容易漏的一步：写原值看起来完全正常。
- 读序是**先第 10 个**、再倒序读第 9..1 个，最后再读第 8、第 7 个（第二次请求的实参）；读操作数本身无副作用，但次序是合同的一部分。
- 记录**不检查是否存在**：直接按记录指针写那十格（解引用空指针，未定义行为，按崩溃诊断）；本条不建记录。
- 第二次请求的条件是**场景绘制模式**，不是操作数：把它当操作数就会读错。该格的初值是 0，因此**未经改写时这次请求会发生**。它的**来源有两个（写点四个）**：① 「绘制模式设置」指令 `0x200` —— 它写的就是**自己的第 1 个操作数**（该指令另有前置：配置 `set:CreateObject` 的位图里"这个编号的对象已创建"；不成立则报错、整条不生效、连格都不写）；② **配置 `set:DrawMode`**：初始化与复位时按它重设，★ **复位路径上先是整块清零（写 0）、随后才按配置重设** ⇒ 复位后的取值 = 配置值；⇒ 那一格的**写点共四个**：初始化取配置、复位块清 0、复位按配置重设、`0x200` 覆盖（见「执行与时间」的「一次迭代做哪些事」与「渲染请求边界」的场景绘制模式条）。★ `0x70` 按场景绘制模式分岔的支路读的**也是这一格**（它按 `= 1` 分岔）—— 两条指令共用同一份场景绘制模式，⛔ 不要各建一个开关。
- 第 10 个操作数**不是列表记录的一部分**：它落进引擎的一个小对象（同一对象的其它格是该节拍器的相位 / 暂停位），并且 **0 会变成 1** ⇒ 它不是"取消定时"，而是"把节拍长度设成 1 毫秒"。
- 第二次请求是**独立的第三件事**：它不改那十格，那十格也不因它而被读。
- 十格的**分组**是合同：⛔ 不许把「闸」与「偏移」当成同一格，也不许把两格「每行格数」实现成两格不同值（本条写的是同一个操作数）。
- **对齐对不在这十格里，但它是布局计算的第五组读入**（`0x303` 写它，见该条）：⛔ 不许说它"与布局无关"，也⛔ 不许把它排进这十格（它另占记录上的两格，与本条写的十格不重叠）。
- 返回词表只有两个值：**「参与」**（有 x / y 与那格出参）与**「不参与」**（没有结果）。⛔ 不许另造"成功 / 无结果 / 失败"的第三套说法：兜底对齐模式是**参与**（x = 0），不是"无结果"。
- 读者用的记录来源与本条写者**完全相同**（同一个指针数组、同一「组号 0 ⇒ 默认组」口径）；⛔ 不许给读者另建一套索引。
- 闸为 0 的后果是**「不参与布局」**，不是「参与但结果为空」：两者在调用方拿到的出参上不同。
- 第 4 个操作数**不参与**上面任何算式：⛔ 不许把它当尺寸 / 坐标 / 除数用。

**每行格数为 0 时的后果**

`0x73` 只是把派生值写进该组的**布局记录**；真正的"按每行格数分行"发生在**消费**这张记录的**布局计算**里。从写入到计算，**整条路径没有任何"每行格数为 0"的判据**：

- **写入侧**只是把派生值拷进记录，**不检查**那一格；
- **布局计算**直接拿那一格做整数除法的**除数**（商的整数部分与余数分别给出"行 / 列"），**前后都没有比较 0**；
- **调用布局计算的各个入口都不碰那一格**（它们只给组号与出参；本作样本里这样的入口有十处）；
- **引擎没有为硬件异常准备任何处置**：没有自己的顶层 / 向量化异常处理器，布局计算函数本身也**没有异常帧**。

⇒ **0 ⇒ 整数除法异常**。它**越过引擎自己的错误通道**（那条通道只承载文本，不承载硬件异常），沿运行库的未处理异常路径走 ⇒ 实际表现是**进程终止**。

★ 它的可证伪观测见下面「可证伪」的第一条（观测点是**实现侧插桩**：进入计算前记输入、返回后读出参 ⇒ 期望**没有返回**）。

**可证伪**

（★ **观测点**：下面四条都读**布局计算的输出 / 返回值**。它不是脚本可观察的（`0x73` 自己不产生返回值）⇒ 观察点是**实现侧插桩**：进入布局计算前记下输入（列表项与单元序号），返回后读它的两个出参与返回值。）

- 把第 9 个操作数设成 0 再跑一次布局：**必须**出现整数除法异常（进入计算前记输入、返回后读出参 ⇒ **没有返回**）；若引擎给出一个值、或引擎自己的错误通道里多出一条文本 ⇒「除数」或「0 检查」写错。
- 把第 7 / 第 8 个操作数各 +1：单元总宽高（= 布局计算用来定单元跨度的「右 − 左」「下 − 上」）必须各 +1（而不是偏移或闸变化）；若不变 ⇒「右 = 第 5 + 第 7」错。
- 只改第 2 个操作数：单元宽高必须**不变**，只有布局计算输出的 x 偏移变；若宽也变 ⇒ 分组错。
- 只改第 4 个操作数：布局计算的输出（x / y / 宽高 / 那一格转出的出参）与返回值必须**不变**，只有随后那次绘制请求的编号变；若布局结果变了 ⇒ 分组错。

### 写一个字体对象字段并尾跳：opcode 0x78 / 0x2db

<!-- rule: CORE-OPS-LIST-SUBSYSTEM-SET-TAIL -->

这两条**同形**，各有一个操作数：把操作数写进**同一个字体对象**的**两个不同字段**（各自一个字段），然后把执行**尾跳**进该对象的**重建入口**（重建入口的返回值直接由分派器接收，本条自己不产生返回值）。

- `0x2db` 写的那一格是**对位模式**，在**那个尾跳入口体内被直接读**（作判据：用于选择字体度量）；离屏文字路径另按它 == 1 做纵向对位（见「渲染请求边界」的离屏文字条）；
- `0x78` 写的那一格是**绘制模式**，**不在**该入口体内读，而由绘制路径（离屏文字请求）读。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 字体对象的绘制模式 / 对位模式 | ← 第 1 个操作数 |
| 交给字体重建入口的请求 | 一次尾跳请求（接收者是那个字体对象，无实参） |

**成立条件**

- 两条**不是同一条**：写的是**不同字段**（同形不等于同义，不许合并成一条实现里的同一个常量）。
- 两条的**初值不同**，因此"没写过的时候"两格的值不同：`0x78` 那一格（绘制模式）初值为 **1**、`0x2db` 那一格（对位模式）初值为 **0**（都在字体对象建立时写入）。⛔ 不许把两格都实现成"初值 0"。
- 尾跳与"调用"不同：本条不压返回点，重建入口的返回值直接回给分派器。
- 两格的领域用途已定：**绘制模式**（`0x78`）与**对位模式**（`0x2db`）；离屏文字请求怎样消费它们见「渲染请求边界」的离屏文字条。
- **尾跳进去的那个重建入口先判名字，再无条件写高度，然后按对位模式分岔**：
  ① 字体的**名字为空** ⇒ 入口**什么都不做、直接返回**（⛔ 不是"重建一个空字体"，也不是"报错"）；
  ② 名字非空 ⇒ 把**两份描述的高度**都**无条件**写成 **−字号**（与对位模式无关）；
  ③ 随后向平台发**一次**"建参考字体 + 取量度"的请求（建字体与取量度是同一段里的两件事），把量度写进字体对象的两张量度结构 —— 一张**文本度量**、一张**字形量度**；
  ④ 最后按**对位模式是否为 0** 分岔：为 **0** ⇒ 跳过派生，两份描述的高度保持 ② 的 −字号、紧接高度的下一格**不动**；**不为 0** ⇒ 对两份描述**各跑一次**派生，派生把「高度」与**紧接高度的下一格**重写。★ 判据是"是否为 0"，⛔ 不是"是否为 1"：对位模式 = 2 也走派生。
  ★ **这套四步之后（参考量度与派生分支都跑完）的入口尾段**还有一段**字形缓冲的重分配与字形装载**（两枚缓冲先释放、再按描述里的一个块算尺寸重新分配、然后逐字装载）。该段**本版不建模**（两块缓冲的领域角色与逐字装载行为见残差 `RES-OPS-SET-TAIL-FIELDS`）⇒ ⛔ 不许据此认为"引擎里没有这一段"，也⛔ 不许据它规定字形位图的内容。

**重建入口的两种形态（同一字体对象上的两套）**

- 同一字体对象上有**两套**重建入口：本条的**两条尾跳进的是不销毁旧句柄的那一套**；另一套在重建前**先销毁三枚已有的平台字体引用** —— 两枚是对象自己的字体引用，第三枚是**当时选在绘制表面上的那一枚旧引用**（销毁它之前先把绘制表面换回原来的字体）；然后再建新字体并取一次**文本度量**。
  ★ **两套取的量度不落同一张结构**：不销毁那一套把参考字体的**文本度量**与**字形度量**各写进自己的一张结构（离屏文字那条**纵向对位用的 ascent 缓存**就在文本度量那一张里，见「渲染请求边界」的离屏文字条）；销毁那一套把新建字体的文本度量写进**它自己的另一张**结构（两者不是同一张）⇒ **离屏文字的 ascent 缓存不受销毁那一套影响**，⛔ 不许把两套的量度当成同一份缓存。
- 两套各自维护**自己的两份描述**（**横排一份、竖排一份**；两套共四份）、各有**自己的名字格**作早退判据：**两个名字格不同格**，⛔ 不许合并。
- **派生次数不同**：对位模式 ≠ 0 时，不销毁那一套对**自己的两份描述（横排 + 竖排）各跑一次**派生（共**两次**）；销毁那一套**只对自己的横排那一份跑一次**（共**一次**），它的**竖排那一份不参与派生**。⇒ 同一对位模式下两套的"参考量度"份数不同（2 : 1）；⛔ 不许用一份缓存同时顶两支，也⛔ 不许把两套合并成同一条入口。

**可证伪**

- 把名字写成空串再跑 `0x78` ⇒ 两份描述的高度**必须不变**；若变成了 −字号（或出现报错）⇒ ① 的早退写错。
- 对位模式 = 2（不是 0、也不是 1）⇒ 派生**必须**跑（高度与下一格被重写）；若跳过 ⇒ 把判据写成了"= 1"。
- 对位模式 = 0 ⇒ 派生**必须不跑**；高度只等于 −字号、下一格保持原值。
- 同一对位模式下比较两套重建入口 ⇒ 销毁旧句柄的那一套销毁过**三枚**旧字体引用（含当时选在表面上的那一枚）、本条这套没有；若两者一致 ⇒ 把两套合并了。
- 只改销毁那一套的名字格 ⇒ 本条这套的行为**必须不变**（反之亦然）；变了 ⇒ 两个名字格被合成一个。

### 写列表项的一对字段：opcode 0x79 / 0x1c1

<!-- rule: CORE-OPS-LIST-PAIR -->

这两条**同形**，各有三个操作数：**第 1 个是组号**（为 0 时换成引擎里的默认组），**第 2、3 个是要写的一对值**。它们把这一对值写进该组记录的**一对固定字段**（两条各写自己那一对），不产生脚本可观察的返回值。

**字段对的身份**：`0x1c1` 写的那一对**就是 `0x70` 用 (第 2 个, 第 3 个) 写进三对里的最后一对**（同一对字段 —— 两条互相覆盖）；`0x79` 写的那一对与 `0x70` 的任何一对都不同，也与 `0x303` 的那一对不同。⛔ 两条不许合并，也不许与 `0x70` 的任意一对共用一个常量。

**两对的领域角色不同**：

- `0x79` 的一对是**该层的文本绘制原点**（层内 x / y）：只改原点，不改尺寸、不建画布（见「文本层：矩形、原点、清空与画布」）。
- `0x1c1` 的一对是**该层宽 / 高的一份未缩放拷贝**（与 `0x70` 的第 2 / 3 个操作数同值，但**不是**建画布用的那一对）：它是**自动折行时右界的来源**（`0x1c1` 可覆盖 `0x70` 的初值；见「ADV 文本」的折行条）。⇒ 改 `0x1c1` 会让折行更早 / 更晚发生，改 `0x79` 不会。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该层记录的文本绘制原点（`0x79`） | 一对坐标 ← (第 2 个, 第 3 个) |
| 该层记录的未缩放宽 / 高拷贝（`0x1c1`） | 一对尺寸 ← (第 2 个, 第 3 个)（自动折行的右界来源） |

**成立条件**

- 读序是**先第 3 个、再第 2 个、最后第 1 个**（对操作数访问无副作用，但次序是合同的一部分）。
- 两条**落点不同**：同形不等于同字段（合并实现会把其中一条写到错的字段上）。
- 记录不存在 ⇒ **不检查**：直接按记录指针写字段（解引用空指针，未定义行为，按崩溃诊断）；本条不建记录。
- 组号 0 是"用默认组"，不是"第 0 组"：默认组初值 1，由 `0x80` 改写（见「设默认组：opcode 0x80」）。
- 记录里其它字段由别的指令维护，本条不碰。


### 写列表项记录的字段（不创建记录）：opcode 0x212 / 0x213 / 0x25d

<!-- rule: CORE-OPS-LIST-FIELD -->

这三条都按**第 1 个操作数**索引列表项记录，把后面的操作数写进该记录的字段（各自一对或一个），**记录不存在时不写该记录**（不创建记录、不改记录的字段）：★ `0x213` 是**例外的一半** —— 它在读到操作数之前就把**当前帧的推进格数**写成本条自己的 **7**（= 2 × 3 + 1）。那一格**不是记录里的一格**，也**不是层指令共用的标记**：**每个 handler 入口**都往它写**自己**的值（`0x212` 写 5、`0x213` 写 7、`0x1f6` 写 1）；见「ADV 文本」的图层条。

- `0x212`（两个操作数）：一个字段 ← 第 2 个；
- `0x213`（三个操作数）：一对字段 ← (第 2 个, 第 3 个)；
- `0x25d`（三个操作数）：另一对字段 ← (第 2 个, 第 3 个)。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该组记录的一个 / 一对字段 | ← 第 2 个（与第 3 个）；`0x212` 的那一格是**该列表项的资源编号** |
| 记录不存在 | 无动作（⛔ 不许顺手建记录） |

**成立条件**

- "记录不存在 ⇒ 无动作"是**可观察的**：它与"顺手建一条空记录"在后续读里表现不同。
- 三条落点各不相同（同族不等于同字段）。
- 这三条不置"已登记"标记：登记是别的指令的事。
- **第 1 个操作数就是槽位下标**（这条族的口径，三条一致）：它**为 0 时取的是槽位 0**，**不是**「用默认组」；`0x80` 改默认组**不影响**这三条。⛔ 三条都不许照 `0x70` / `0x79` / `0x1c1` / `0x303` 的"组号 0 ⇒ 默认组"去实现 —— 那会让 `0x213(0, …)` 写到默认组那一槽上，而取 0 号槽的脚本什么也写不到。
- `0x213` 写的那一对字段是**文本层的绘制键区间（第一组）**（见「文本层：矩形、原点、清空与画布」）；`0x25d` 写的那一对是**另一组键区间** —— `0x71` 清空该层时会按它释放旧绘制条目（同上）。两组**不共享**，也都不与 `0x70` / `0x79` / `0x1c1` / `0x303` 的字段对共享。
- `0x212` 写的那**一格**是**该列表项的资源编号**：布局完成之后，绘制这一项时把这一格的值作为**编号形参**交给绘制入口；在「调用方要求先按编号处理资源」的支路上，同一个值交给资源侧的查询入口。
  ⇒ 它**不是**颜色、**不是**坐标、**不是**键区间的端点；改它只改「画哪一份资源」，不改布局、不改位置。
  它与上面任何一对都**不同格**：`0x213` / `0x25d` 的两对是**区间端点**（成对使用，一端给清空路径），这一格是**单个编号**（单值使用）。

**可证伪**

- 同一层写两份不同的 `0x212` 值再画：绘制请求带的编号必须跟着变，而单元矩形 / 原点 / 折行位置**都不变**；若位置或宽度也变 ⇒ 这一格不是「纯编号」。
- 对**不存在**的组号调 `0x212`：若崩溃 ⇒「无动作」错（对照 `0x303` 的崩溃是**故意**的差异）。


### 写一对字段（记录必须已存在）：opcode 0x303

<!-- rule: CORE-OPS-LIST-PAIR2 -->

`0x303` 有三个操作数：第 1 个是组号（0 ⇒ 默认组），第 2、3 个是要写的一对值（读序 op3 → op2 → op1）。它把这一对值写进该组记录的**一对固定字段**。

★ 与 `0x212` / `0x213` / `0x25d` 的关键差别：这一条**不检查记录是否存在** —— 记录为空时引擎会直接解引用空指针。所以"记录不存在"在这条上**不是**"无动作"，而是**未定义行为**（本作观察到的表现是崩溃；**建议**实现把它记为诊断，例如中止 / 响亮失败）。

★ **字段对的身份**：`0x303` 写的那一对与 `0x70` 的四对、`0x79` 的一对、`0x1c1` 的一对**都不同**；四者里唯一的共享对是 `0x70` 与 `0x1c1` 的那一对（见「设置一个列表项：opcode 0x70」）。

★ **这一对的领域角色是「该列表项单元网格的水平对齐」**（它是「布局计算」的**第五组**读入 —— 那两格**不在** `0x73` 写的那十格之内，见「那十格的去向」；返回词表统一为**「参与」/「不参与」**）：

- 第 2 个操作数 = **对齐模式**：`0` ⇒ 不对齐（该列表项**不参与**这次布局，没有结果）；`1` ⇒ **居中**；`2` ⇒ **靠另一端**；
  **其它任何值（`≥ 3` 与负数同一个出口）** ⇒ **不进任何对齐支**：出参 x = **0**，且**参与**（★ 与模式 0 的**「不参与」**不同：那一个没有结果）。
- 第 3 个操作数 = **对齐基准坐标**（外框的参考 x）：模式 1 时结果 = **基准 − 半宽**；模式 2 时结果 = **基准 − 右界 + 左界**。
- ★ **这一对不是绘制键区间**：它**不是**区间端点、**不被**清空路径当作「按区间释放条目」的键 —— 清空该层时释放条目的键区间是另外两对（见 `0x213` / `0x25d`），与这一对**不共享**。
  改这一对只改**水平位置**，不改「画哪些资源」、不改行高、不改折行。
- ★ **两格都在记录上，但都不在 `0x73` 写的那十格之内**：本条这一对与「单元网格」的十格**不重叠**（见 `0x73` 的「那十格的去向」）；布局计算照样读它（第五组）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该列表项的水平对齐模式 | 记录里一格整数 ← 第 2 个操作数 |
| 该列表项的横向参考坐标 | 记录里另一格整数 ← 第 3 个操作数 |
| 记录不存在 | 引擎崩溃（未定义行为） |

**成立条件**

- 别把这条与"不创建记录、也不崩溃"的那族混成同一实现：一边是"无动作"，一边是"崩"。
- 组号 0 仍是"用默认组"：默认组初值 1，由 `0x80` 改写（见「设默认组：opcode 0x80」）。
- 模式的三支是 **0 / 1 / 2**，其余取值走**同一个兜底出口**（出参 0 + **参与**）：⛔ 不许把它当坐标或位掩码，也⛔ 不许把兜底出口并进模式 0 那一支。
- 模式 0 的后果是**「不参与」**（没有结果），不是「用 0 当基准」：两者在调用方拿到的东西上不同。
- 这一对是「布局计算」的**第五组**读入（不在那十格之内）：⛔ 不许把它当成"与布局无关的绘制属性"。
- 基准坐标只在模式 1 / 2 被读；模式 0 与兜底出口都不读它（值仍被写进去）。
- 两格的身份**不同**：⛔ 不许互换，也不许把模式实现成「基准坐标的符号位」。

**可证伪**

- 模式 = 0：若该列表项仍然出现在布局结果里（或有 x 值）⇒「不参与」错。
- 模式 = 1：把基准坐标 +2 ⇒ 结果 x 必须 **+2**（不是 +1、也不是不变）；若为 +1 ⇒ 公式错。
- 模式 = 2：把右界 +1（宽度 +1，位置不动）⇒ 结果 x 必须 **−1**；若不变 ⇒「减右界」错。
- 模式 = 3：调用方必须拿到**「参与」**且出参 x = **0**；若拿到「不参与」（与模式 0 相同）⇒ 把兜底出口并进了 0 支；若得到「基准 − 半宽」或「基准 − 右界 + 左界」⇒ 进了 1 / 2 支。
- 只改第 3 个操作数：**只有**模式 1 / 2 的结果变，模式 0 **与兜底出口**的什么都不变；若资源编号或折行也变 ⇒ 身份错。

### 重置文本键表：opcode 0xa1

<!-- rule: CORE-OPS-TABLE-RESET-A1 -->

`0xa1` **没有操作数**。推进格数 ← **1**，然后把那张**「文本键 → 整数」表**清空。

★ **这张表是脚本自己的键表**：脚本用 `0xa2` 往里写「键 → 值」，用 `0xa3` 按键取出登记的值来决定控制去向。引擎侧**没有任何代码读它** —— 它不参与配置、不参与存档、不参与显示。它与「配置」的**命名键表不是同一张表**，与脚本**存 / 读整数**用的那张表也**不是同一张**（三张表同型、不同实例）⇒ ⛔ 不许把它们混成一张，也⛔ 不许把「菜单」一类的用途当成它的身份：脚本拿它做什么属于**程序**，不是本规范的内容。

- **初始状态是确定的**：引擎构造时它就已经是一张**空表**（项数 0、没有任何键）。⇒ 在任何 `0xa1` 之前执行 `0xa2` / `0xa3` 都是**有定义的**：`0xa2` 正常写入，`0xa3` 一律缺键。⛔ 这不是「初始状态未规定」。
- **清空的判据是「项数为 0」**：`0xa1` 之后表里没有任何键；「按键取到一个值」只在键存在时成立。
- `0xa1` **不区分键是谁写的**：它清掉整张表 —— 本脚本先前绑的、别的脚本绑的，一起清。
- 表的**容量 / 装载上限 / 扩容步长 / 哈希与探测顺序属实现细节**，本版不规定：它们只影响表内位置，不影响「按键能不能查到」。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 引擎构造之后、首次 `0xa1` 之前：表存在且为空 | 项数 = 0；键数组与值数组已按默认容量分配 |
| `0xa1` 之后：表为空 | 项数 = 0；每个槽的键为空 |
| 表里有键 K | 键数组里存在一条与 K **逐字节相等**且**长度非 0** 的记录 |

**成立条件**

- 这张表**只有一张**（跟着引擎对象走）：不存在「每个脚本一张」或「每个帧一张」。
- 表的内容**只能**通过 `0xa3` 的落点观察：除 `0xa3` 之外没有读入口（所以关于表内容的合同都必须以分派落点为准）。
- 表变空只保证「按键查不到」：值数组里的旧值**不保证被清**（不可达，但实现不许把它们当成有效项）。
- `0xa1` 没有操作数；推进格数 = 1。

### 绑定一个文本键：opcode 0xa2

<!-- rule: CORE-OPS-TABLE-BIND-A2 -->

`0xa2` 有两个操作数：**第 2 个是值**（读整型），**第 1 个是键**（**按文本**读）。推进格数 ← **5**（= 2 × 2 + 1）。它把「键 → 值」写进那张「文本键 → 整数」表（见 `0xa1` 条；`0xa3` 按键读它）：

- **键已存在**（键的**完整文本**相等）⇒ 该键的值被改写（键本身也被重新写一遍），项数不变；
- **键不存在** ⇒ 按键写入，项数 +1（实现可选择哈希 / 探测顺序；只要求「完整文本相等的键可查到」）。
- **表不会满、写入不会失败**：`0xa2` **没有「失败」这种结果**，也不丢弃任何已存在的键 ⇒ 从合同上看这张表**没有「满」这一状态**：任意多个键都能写进去，已写过的键此后任意时刻仍然查得到。表内布局在什么时候变化（容量、装载上限、是否重排）**不可观察**、属实现细节，本版不规定（见下「成立条件」）。
- **存活范围 = 引擎的生命周期**：它在引擎构造时被建成空表，此后**只有 `0xa1` 会清空它**。因此：
  - 帧的装载与退出、脚本的切换、`call` / `ret` **都不清空**它；
  - 一个脚本写的键，在**另一个脚本**里查得到（同一份引擎）；
  - 存档的读回**不恢复**它（它不是存档状态的一部分），进程重启后它回到空表；
  - 除 `0xa1` 之外**没有「按键删除」**：键一旦写入，只能被整表清空、或改写同一个键的值。

**键的文本形态**（`0xa2` 与 `0xa3` 共用同一条口径 —— 同一个源操作数在写侧与读侧必须渲染成**同一串**字节，实现不得各写一份）：

- **一律按文本读**：第 1 个操作数产出一条**以 NUL 结尾的字节串**（长度取到第一个 NUL 为止），表的键就是这条字节串。
- **三族操作数各自怎么变成文本**（其余类型标签一律类型异常，见下一条）：
  - **数值** ⇒ 十进制整数文本：可带负号、**无前导零、无宽度填充、无 `0x` 前缀**；**浮点** ⇒ 定点十进制、**小数点后 6 位**。⇒ 整数 `1` 的键是 `1`，浮点 `1` 的键是 `1.000000`，**两个不同的键**。
  - **内联文本** ⇒ 它在代码流里**按位取反**存放，读出时第一步就是**再取反**（不做这一步会得到另一串字节，而写入本身不报错）。
  - **字符串记录** ⇒ 那条记录里的字节串本身。
- **其余类型标签一律类型异常**：这条通路只接受上面三族 —— **容器句柄**（`0x8003` / `0x8005` / `0x8009` / `0x800B`）与保留标签都落进分派的缺省支 ⇒ **读操作数时抛类型异常**，写入 / 查表都不发生。★ 它**不是**「设置一个字符串」的源侧那条更宽的文本读：那边才把容器句柄解成「第 0 个元素 / 空容器读作全角零」，这条通路**不做**这层解析 ⇒ ⛔ 不许把那条口径搬到键上（那会让空整数容器变成一个非空的「０」键）。
- **相等 = 长度相等且逐字节相等**：不是前缀、不是大小写不敏感、不是「哈希相等」。⇒ `abc` 与 `abcd` 是两个键。
- **空文本键永远查不到**：用空文本写入之后，再以空文本查键仍然缺键 —— 「有键」的判据不是「写过」，而是「存在一条**长度非 0** 且逐字节相等的键」。⇒ 「写了空键」与「什么都没写」，在「能不能查到」上等价。★ 能产出空串的只有**内联文本**与**字符串记录**两条（空文本）；容器句柄那条根本产不出键（见上一条）⇒ 本条不会因为「空整数容器读成全角零」而反转。
- 键的字节串是**引擎码页下的原始字节**，不是 UTF-16；比较不做任何归一化（不做全半角 / 大小写 / Unicode 归一化）。
- 浮点的末位：整数部分与 6 位小数是合同；**第 6 位小数上的舍入由宿主的定点格式化决定**（同一实现必须每次给同一串；跨平台的末位差异不在可移植保证内）—— 与「设置一个字符串」的源侧同一口径。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 表里键 K 的值 = V | 该键登记的值 ← V |
| 表里新增一项 | 项数 +1（仅在键不存在时） |
| 覆盖已有键 | 项数不变；该键的记录被重写 |
| 已到装载上限、仍要新增 | 项数 +1；所有已存在的键仍可查到（容量 / 上限 / 是否重排属实现细节，不可观察）；已存在的键一条都不丢 |
| 表跨脚本可见 | 表是引擎对象的一个成员（只有一张），不是帧 / 脚本的成员 |

**成立条件**

- 读序固定：**先读值（第 2 个），再按文本读键（第 1 个）**。
- 覆盖已有键**不增加**项数；新增才增加。
- 扩容与重排对「按键查值」**不可观察**（不改变任何键的可查性，也不改变命中 / 缺键的结果），只影响内存与耗时。
- 键的比较发生在哈希命中之后的**内容比较**里；哈希只决定表内位置，不影响「能不能查到」。
- 命中判据是「有没有这个键」，与登记的值无关（值为 0 的键仍然命中，见 `0xa3` 条）。

### 按键分派：opcode 0xa3

<!-- rule: CORE-OPS-TABLE-DISPATCH-A3 -->

`0xa3` 是一支**控制转移**，不是「写一个值再继续」。它有两个操作数：**第 1 个是键**（**按文本**读），**第 2 个是默认位置**（读整型）；推进格数 ← **5**（= 2 × 2 + 1）。它按**读键 → 查表 → 写指令指针 → 清推进格数**的次序执行，两支都以后两步收尾；**本条执行完之后**：指令指针 = 目标格 **且** 推进格数 = 0（两次写之间没有可观察点 ⇒ 合同只写「本条之后」的状态，⛔ 不写两次写的先后）：

- **命中**（键存在）⇒ 指令指针 ← 代码区起点 + 4 × **该键登记的值**；
- **未命中** ⇒ 先读第 2 个操作数，指令指针 ← 代码区起点 + 4 × **第 2 个操作数**；
- 两支都把推进格数清 **0** ⇒ 这条指令**不会**自动前进到下一格。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 命中 ⇒ 跳到登记的目标格 | 指令指针 ← 代码区起点 + 4 × 登记值；推进格数 = 0 |
| 未命中 ⇒ 跳到默认位置 | 同上，值换成第 2 个操作数（整型） |
| 目标格号越界 | 指令指针落在代码区外（不夹紧）；下一次取指读到代码区之外的内存 |
| 控制转移 | 推进格数 = 0 |

**成立条件**

- **命中 = 完整文本相等**（与 `0xa2` 同一判据；不是哈希相等、不是前缀相等）。
- **命中与「值是多少」无关**：登记值为 0 的键**仍然命中**（跳到代码区第 0 格），不是「缺键」—— 「登记了 0」与「没有这个键」是两件事。
- **登记的值是格号**（4 字节一格的序号，**以当前脚本的代码区起点为基准**），**不是字节偏移**：同一个格号在另一份脚本里不是同一条指令。
- **分派时不做范围检查**：值为负、或超出代码区，引擎照样把它算进指令指针，**不夹紧、不报错**。⇒ **越界 = 未定义行为**：下一条取指读到代码区之外的内存，按诊断记，后果本版不规定。⛔ 不许实现成「夹到 0」，也⛔ 不许「退回默认位置」。
- **键决定目标**：命中时第 2 个操作数**不被读**（它的类型与值都不参与；类型不受支持也不会失败）。未命中时才读它。
- 键**按文本**读（与 `0xa2` 同一口径）：⛔ 不许按整型读 —— 同一个操作数按整型读会得到另一个东西。

### 载入一个 L2D 资源：opcode 0x341 / 0x345 / 0x34e

<!-- rule: CORE-OPS-L2D-LOAD -->

三条指令是**同一个形状的三个变体**：把一个**文件名**交给 L2D 子系统载入一类资源，其余参数原样透传。

| opcode | 载入 | 整数参数个数（含对象下标） |
|---|---|---|
| `0x341` | 模型 | 1（下标 = 第 2 个操作数） |
| `0x345` | 纹理 | 2（下标 = 第 2 个操作数） |
| `0x34e` | 动作 | 3（下标 = 第 3 个操作数） |

- **文件名是第 1 个操作数**（文本），**最先读**；其余参数按**从后往前**读：`0x341` 读 1 → 2；`0x345` 读 1 → 3 → 2；`0x34e` 读 1 → 4 → 3 → 2。
- 三类参数分别是：**资源 id（文本，第 1 个）**、**对象下标**、以及**透传**（整数，原样交给外部 L2D 模块，**引擎不解释**它们的含义）。
- ★ **对象下标的位置不是同一个操作数位**：模型 / 纹理 = **第 2 个**操作数，**动作 = 第 3 个**操作数。⛔ 不许把三条的下标位写成同一个（那会把动作的透传当成下标）。
- **同一下标上已有对象 ⇒ 先释放该格原有的对象、再放新的**（覆盖，不叠加、不泄漏）；下标**无范围检查**（越界是未定义行为）。
- **不写任何操作数**。
- 载入失败（文件打不开 / 载入器返回失败）⇒ 引擎写一段错误文本并**抛一个「显示消息」型异常**（消息体 = 那段文本）；控制流**不继续**。★ 但 **`0x345`（纹理）不检查外部模块的载入结果**（它无条件报告成功）—— 别把"文件打不开仍抛"与"外部模块失败不抛"混成一件事；模型 / 动作**看**载入结果。
- 成功时没有其它引擎数据效果。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 载入的资源 | L2D 子系统内部（本版不规定其结构） |
| 失败 | 引擎错误文本 + 一次异常 |
| 推进格数 | 5 / 7 / 9（= 1 + 2 × 操作数个数） |

**成立条件**

- 三条的读序**互不相同**：⛔ 不许照"1 → 2 → 3"的顺序读（那会在多个非法类型时抛出位置不同）。
- 文件名是**文本**（不是整数），对象下标与透传参数是**整数**。
- **对象下标**是"落在哪一格"的那一位（模型 / 纹理第 2 个、动作第 3 个）；其余整数是透传，引擎**不解释**。
- 失败路径**抛异常**而不是静默跳过：⛔ 不许只记日志。纹理那条的"无条件成功"只针对**外部模块的载入结果**，文件打不开仍在抛。
- 载入器内部（解码、上传、对象登记）不在本版；本版只规定"对象占用哪个下标、同下标先释放该格原有的对象"。

**可证伪**

- 先 `0x341` 把模型载到下标 k，再用 `0x352` 对下标 k 设标记 ⇒ 必须命中同一个对象；若命中空 ⇒ 下标位判错（或两条不是同一张表）。
- 先 `0x341` 载入到下标 k、再载入到同一 k ⇒ 旧对象**必须被释放**（不泄漏、不叠加）；若旧的那个仍在被遍历 ⇒ "先释放再替换"错。
- 用 `0x345` 载入一份外部模块会拒绝的资源 ⇒ 该指令**仍正常结束**（不抛）；若抛 ⇒ "纹理不检查载入结果"错。反向：文件本身打不开 ⇒ 仍必须抛（两条别混）。
- 用 `0x34e`（动作）载入时让第 2 与第 3 个操作数取**不同**的整数值，再分别对这两个下标设标记：必须命中**第 3 个**那个下标；若命中第 2 个 ⇒ 动作的下标位判错。

### 设定一个 L2D 对象的开始 / 结束标记：opcode 0x352

<!-- rule: CORE-OPS-L2D-MARK -->

`0x352` 有三个操作数：**对象下标**、**方向**、**时间量**。它按对象下标从**对象指针表**里取对象，再按方向写一次"开始 / 结束"标记与时间量。

- 读序 **3 → 2 → 1**。
- ★ **对象指针表就是三条载入指令写的那一张表**（渲染步直接遍历它）—— 没有第二张"登记表"，所以"登记点"就是载入那一次写。
- 方向 = **0** ⇒ 写"开始"支（置开始位、写时间量）；方向 **≠ 0** ⇒ 写"结束"支（置结束位、写时间量）。两支**互斥**，且**互不覆盖**：先开始再结束 ⇒ 两对同时为 1，两个值各自保留。
- ★ **对象槽为空**（或外部模块还没建句柄）⇒ **一个字节都不写**、不报错：判据在**写者**里（取对象在**所有写之前**，空槽时写者自己兜住，等价于"什么都不写"）。
- 不写操作数、不发平台请求；下标无范围检查（越界是未定义行为）。
- 写进去的时间量是**原样 32 位整数**（引擎**不换算**）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 一次"开始 / 结束"标记与时间量 | 该对象的两个字段（开始位 + 时间量 / 结束位 + 时间量） |
| 对象未登记 | 什么都不写 |

**成立条件**

- 方向是**布尔**：0 与非 0；⛔ 不是"1 = 开始、2 = 结束"。
- 对象查表在**所有写之前**：空槽 ⇒ 一个字节都不写（兜在写者里）。
- 两支**只写自己那一对**：⛔ 不许把"开始 / 结束"实现成一对互相覆盖的字段。
- 两个字段的**领域名与时间量单位**属外部 L2D 模块的语义（引擎只原样存 32 位整数、不换算）；本条只钉**写哪两对格、两支怎么互斥**，以及下标与三条载入指令**同一个命名空间**。

**可证伪**

- 对同一对象先以方向 0、再以方向非 0 执行 `0x352`：两对**必须同时为 1** 且两个值各自保留；若第二次把第一对清掉 ⇒ "互斥但不互相覆盖"写错。
- 先 `0x341` 把模型载到下标 k，再 `0x352` 对下标 k 设标记 ⇒ 必须命中同一个对象；若命中空 ⇒ 下标位或"同一张表"判错。
- 对空槽执行：对象表与对象一个字节都不变（不报错、不抛）；对已载入对象执行：只有该对象的两个格变化。

### 设一个引擎整数档：opcode 0x1b1

<!-- rule: CORE-OPS-ENGINE-CELL-1B1 -->

`0x1b1` 有一个操作数，推进格数 = **3**：把操作数**原样**写进引擎的**一个固定整数格**（不归一、不夹取、不做范围检查）。

- 不写操作数、不报错、不发请求、不标脏。
- 全语料对该格**只有写、没有字面读点**；领域角色未取证（残差 `RES-ENGINE-CELL-1B1-READER`）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该整数档 | ← 第 1 个操作数 |

**成立条件**

- 只有一个格：⛔ 不是"按操作数选下标"的数组写。
- 写入是**覆盖**（不累加、不取最大值）。

**残差**

- `RES-ENGINE-CELL-1B1-READER`（unknown）：该格没有字面读点；领域名与是否存在间接消费者未取证。

**可证伪**

- 依次写 1、7：读回必须是 7；是 1+7 或 7 以外的值 ⇒ 不是覆盖写。
- 写 -1：必须原样存 -1；变成 0 / 255 ⇒ 做了归一。

### 设两格（清 0 + 赋值）：opcode 0x238

<!-- rule: CORE-OPS-ENGINE-CELL-238 -->

`0x238` 有一个操作数，推进格数 = **3**：把**消息等待三格**的 **B 格（计时器起点）清 0**、**C 格（时长）← 操作数**（原样）；

**A 格（中止位）不动**。这三格与 `0x243` / `0x305` 写的是**同一组**（见「消息等待三格」与「消息块开始 / 结束」），
⛔ 不是另一组私有格。

- **B = 计时器起点，C = 时长**：这是一对**消息等待计时器**格，读者是等待门的服务分支（见「等待（opcode 0x21c）」的谓词 A）。
  B 里的 **0 = 未盖章**：服务第一次检查这对格时把"现在"写进 B，再拿 `现在 > 起点 + 时长` 判窗。
- 所以"清 B"的领域含义是**退掉上一次的盖章**（下一拍由服务重新盖章 = 从现在起算），
  ⛔ 不是"把一个只写不读的私有格归零"。
- **C = 0 ⇒ 这一对格不挡门**：服务跳过盖章与窗口判定，门只看**等待谓词的待处理闩**。
  `0x243`、以及 `0x305` 的**揭示支**写的 `(1,0,0)` 正是这个形态（时长 0）⇒ 它们之后下一拍就能放行；
  `0x305` 的**打字机支**不写这三格（默认每字间隔 ≠ 0 时走这一支）。
- 不写操作数、不报错、不发请求、不标脏。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 消息等待计时器的起点（未盖章） | B ← 0（下次检查时盖章为"现在"） |
| 消息等待计时器的时长 | C ← 第 1 个操作数 |
| 中止位 | A 不变 |

**残差**

- `RES-ENGINE-CELL-238-READER`（unknown）：**已证** B / C 是消息等待计时器的**起点 / 时长**（读者 = 等待门的服务分支，
  到期或中止时把两格清 0）；只剩 **A 格**的相位语义与边界未取证 —— 服务只把它与 **1** 比较当"中止"，
  它还有哪些写者、各写者对应什么相位（`0x243` / `0x305` 之外）未枚举。

**可证伪**

- 先跑 `0x243`（A=1、B=0、C=0）再跑 `0x238(7)`：A 必须仍是 1、B = 0、C = 7；A 被清 ⇒ 写错格。
- 执行后立刻再执行一次（同参数）：两格值必须不变（幂等）。
- `0x238(0)` 之后立刻 `0x21c`：这对格**不挡门**（时长 0 ⇒ 不盖章、不进入窗），门只看**等待谓词的待处理闩**；
  第一拍被这对格挡住 ⇒ 把"时长 0"当成了一个窗。
- `0x238(200)` 之后把门服务分别放在 `start+199 / +200 / +201 ms` 三个时刻：起点只在**首次检查**盖章 ⇒
  199 与 200 ms 仍不放行、201 ms 必须放行；若每拍都盖章（起点被刷新），门会一直关着 ⇒ 推翻"未盖章才盖章"。

### 写一个固定引擎整数格：opcode 0x2e9

<!-- rule: CORE-OPS-ENGINE-CELL-2E9 -->

`0x2e9` 有一个操作数，推进格数 = **3**：把操作数**原样**写进引擎的**一个固定整数格**（覆盖写，不归一、不夹取、不检查）。
不写操作数、不报错、不发请求、不标脏。该格初值 0（启动时被清零）。

**它是什么**：自动消息（auto-message）时长计算里的**偏移格**（单位与下面的 `N` 相同；它与「行」的对应关系未取证，见残差 `RES-AUTO-MSG-LINE-RECORD`）—— 不是时间量：

```
时长(毫秒) = max(100, TimeX + PitchX × (N − 1 − 该格))
```

- `N` = 该文本层**布局字符格序列**（旧称「行记录」）的**条数**（复位后恰为 1 条起点项，此后每排出一个字符格 +1；⛔ 不是行数、⛔ 不是行记录日志的条数、⛔ 不是文本记录的条数 —— 三条序列的身份与字段表见「ADV 文本」的「三条记录序列的身份」）。算式里的 `−1` 是**算式自带**的（条数 − 1），不是某条记录里的字段。
- `X` 选组（**与"语音是否在播"有关，不是"是否启用自动消息"**）：
  - 语音**不在播** ⇒ 第 1 组（`message:AutoMessageTime1` / `AutoMessagePitch1`）；
  - 语音在播且 `message:AutoMessageOption` 第 0 位为 **1** ⇒ 第 0 组；
  - 语音在播且第 0 位为 **0** ⇒ **本拍不武装计时器**（不设时长，等语音结束再武装）。
- 下限 100 毫秒；单位毫秒。`PitchX` 内建默认 **0** ⇒ 默认配置下该格对时长**没有任何影响**。
- **开关不是这一格**：自动推进由 `0x1b7` 写的引擎格（`0x1b6` 读回）控制；它非 0 时
  `0x72` 才武装计时器。语音在播的那一格由语音族指令维护。
- 消费者：一个**定时器**（起点 = 现在、时长 = 上式、首次放行 = 1 个周期）；到期后
  **放行 `0x72` 的等推进位**（与点击同一对操作），⛔ 不换行、不取下一行 —— 下一行仍由脚本产生。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 自动消息时长算式里那个偏移量（与 `N` 同单位） | 引擎的固定整数格 ← 操作数（覆盖写） |
| 自动消息的推进时长 | 由该格、`N`、组选与两组配置键算出（毫秒，下限 100） |

**残差**

- `RES-AUTO-MSG-TIMER-PHASE`（unknown）：定时器起播时计数值为 **1**（因此首次放行 = **1 个时长**）；
  "语音在播时先不武装、语音结束后用第 0 组重武装"这条链会让**实际等待**看起来像"语音时长 + 一个周期"，
  但这不是 2× 的计数口径 —— 该链没有运行时核对（见下一条残差）。
- `RES-AUTO-MSG-LINE-RECORD`（unknown）：**已定**：`N` 取的就是该层**布局字符格序列**的**条数**（旧称「行记录」），算式里那个 `−1` 是**算式自带**的（条数 − 1）、不来自任何记录的字段，行结束也**不**往这条序列追加。**仍未定**：① 逐字排版是**每字追加一条**、还是把坐标写进**已有**那条（决定「条数 = 字符格数」还是「字符格数 + 1」，也决定 `−1` 是否恰好抵消那条起点项）；② `0x2e9` 写的那一格在发行脚本里偏移的是**什么单位**（字符格数？行数？）。

**可证伪**

- 依次写 1、7：读回必须是 7（覆盖，不是累加）。
- 写 -1：必须原样存 -1。
- `Pitch1 = 0`（内建默认）时把该格写成 7 再走自动消息：时长必须**不变**（该格只通过 Pitch 起作用）。
- `Pitch1 = 1`、`Time1 = 2000`、`N` = 5、该格 = 2：时长必须是 `2000 + 1×(5−1−2) = 2002` 毫秒；
  算成 `2000 − 2 = 1998`（当成时间偏移）或 `2000 + 2`（符号反了）⇒ 本条错。
- 时长算出来小于 100 ⇒ 必须被夹到 100。
