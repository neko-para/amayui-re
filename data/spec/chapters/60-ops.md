## 指令语义

本章规定**单条指令对引擎数据的改变**：读哪些操作数、按什么顺序读、写到哪里、失败时怎样。值的语义（整型编码、浮点转换、类型支持集）属于「数据池」；操作数个数与指令推进属于「脚本与执行」。

本章只写**引擎数据**的效果。向外部的呈现请求（绘制、图像、声音）不在此列：它们是否被受理、像素与声音如何，属于平台与呈现模块；一条指令若只发出这类请求而不改引擎数据，它在本书里的合同就是"无引擎数据效果"。

本版覆盖：**数值搬运**三条、**纹理族**五条、**场景/颜色族**五条、**等待与输入**两条。其余指令尚未成篇。

### 整数加：opcode 0x50

<!-- rule: CORE-OPS-NUMERIC-ADD -->

`0x50` 有三个操作数。它把**第 3 个操作数**与**第 2 个操作数**分别按整型语义读出，把两者之和按整型语义写进**第 1 个操作数**。读取顺序是**先第 3 个、再第 2 个**。

- 第 1 个操作数只被写，**不被读**。
- 三个操作数都经过「数据池」的读整型 / 写整型原语，因此各自的类型标签决定池与转换；不支持的类型标签照「数据池」抛异常。
- 除「脚本与执行」规定的操作数个数槽外，这条指令不改变其它引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数指向的整数 | 读整型（第 3 个）＋读整型（第 2 个）→ 写整型（第 1 个） |

**成立条件**

- 读取顺序是规范的一部分：先第 3 个、后第 2 个；第 2 个读取失败时，第 3 个**已经**被读过。
- 第 1 个操作数不被读：因此"只在写入时才支持"的类型标签在这里不会因为读而失败。

### 整数减：opcode 0x51

<!-- rule: CORE-OPS-NUMERIC-SUB -->

`0x51` 与整数加同形，只差运算方向：读**第 3 个**、再读**第 2 个**，把**第 2 个减第 3 个**的结果写进**第 1 个操作数**。

- 第 1 个操作数只被写，不被读。
- 三个操作数同样经过「数据池」的读整型 / 写整型原语。
- 除操作数个数槽外，这条指令不改变其它引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数指向的整数 | 读整型（第 2 个）−读整型（第 3 个）→ 写整型（第 1 个） |

**成立条件**

- 次序是"第 2 个减第 3 个"，不是"第 3 个减第 2 个"：减法不可交换，写反了不会报错，只会算错。
- 读取顺序仍是先第 3 个、后第 2 个。

### 浮点搬运：opcode 0x2d5

<!-- rule: CORE-OPS-NUMERIC-FLOAT-MOV -->

`0x2d5` 有两个操作数：把**第 2 个操作数**按浮点语义读出，按浮点语义写进**第 1 个操作数**。第 1 个操作数只被写，不被读。

- 两个操作数经过「数据池」的读浮点 / 写浮点原语；跨族转换按「数据池」的口径。
- 除操作数个数槽外，这条指令不改变其它引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数指向的浮点数 | 读浮点（第 2 个）→ 写浮点（第 1 个） |

**成立条件**

- 这条是**搬运**，不是"按整型转写"：目标族的整型编码不会参与（写浮点原语自己处理转换）。
- 第 1 个操作数不被读。

## 纹理族（opcode 0x1f7 / 0x1f8 / 0x1f9 / 0x1fa / 0x1fb）

这五条操作的是场景里的**纹理对象**与**绘制项**：按一个整数编号取记录，按槽建/换/释放纹理对象。
它们都只改引擎数据；底层图像的解码、上传与呈现属于外部模块。

### 拆离纹理：opcode 0x1f7

<!-- rule: CORE-OPS-TEXTURE-DETACH -->

`0x1f7` 有两个操作数：**第 2 个是个数**、**第 1 个是键**；读取顺序是**先第 2 个、后第 1 个**。

- **个数 ≤ 1**：把该键从场景的四张键表（绘制项表与三张辅助表）里删除。
- **个数 > 1**：按**左闭右开**区间 `[键, 键 + 个数)` 删除四张表里的条目；条目内嵌的对象与缓冲一并释放。
- 只要四张表里有任意一张真的删掉了东西 ⇒ 场景被标成"脏"；没有删掉 ⇒ 脏标记不动。
- 本条没有外部请求。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某个键在四张表里都不存在 | 四张表都查不到该键 |
| 场景被标脏 | 场景的脏标记 ← 1（至少一张表删掉了条目） |

**成立条件**

- 区间是左闭右开；负数个数也走"≤ 1"的单键路径。
- 键不存在时该表**静默跳过**，不报错、不代替建默认项。

### 创建纹理：opcode 0x1f8

<!-- rule: CORE-OPS-TEXTURE-CREATE -->

`0x1f8` 有四个操作数：**1 = 纹理 id**、**2 = 宽**、**3 = 高**、**4 = 种类**；读取顺序是 **1 → 4 → 3 → 2 → 1**。

- 先清**引擎级对象槽**里该 id 的对象（非空则释放、置空）。
- 把该 id 的**纹理记录**重置为"没有来源文件、空白创建"：来源文件 = 无，空白创建标记 = 1。
- 清**纹理槽**里该 id 的旧对象；按种类新建一个对象写回该槽：种类 = 3 ⇒ 分割纹理，其它 ⇒ 普通纹理。
- 宽 / 高 / 种类交给对象向底层请求创建（**外部请求**）。
- 底层创建失败 ⇒ 错误文本写进场景错误缓冲并上报；**不抛异常**，本对象**仍留在槽里**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该 id 的纹理记录 | 来源文件 = 无；空白创建 = 1 |
| 该 id 的纹理槽 | 一个新对象（种类决定它是不是分割纹理） |
| 引擎级对象槽 | 该 id 的槽被清空 |

**成立条件**

- 编号**不做范围检查**。
- 种类只有"等于 3 / 不等于 3"两个分支，不是枚举。

### 设置纹理：opcode 0x1f9

<!-- rule: CORE-OPS-TEXTURE-SET -->

`0x1f9` 有三个操作数：**1 = 文件号**、**2 = 纹理 id**、**3 = 颜色键**；读取顺序是 **2 → 1 → 3 → 2**。

- 先清**引擎级对象槽**里该 id 的对象（这一步在读文件**之前**）。
- 按文件号打开并加锁（**外部请求**）；文件号非法、或加锁失败 ⇒ 抛"显示消息"异常。
- 颜色键归一化：负数 ⇒ 0；否则 = 不透明黑 | (值 & 0xFFFFFF)。
- 清**纹理槽**里该 id 的旧对象；解码图像、新建普通纹理对象、上传像素（后三者是**外部请求**）。
- **成功** ⇒ 纹理记录：来源文件 = 文件号、颜色键 = 归一化值、空白创建 = 0。
- **失败** ⇒ 纹理记录：来源文件 = 无；关闭文件后抛"显示消息"异常。
- 关闭 / 解锁在两条路径上都做。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该 id 的纹理来自哪个文件 | 记录的来源文件 |
| 该 id 的颜色键 | 记录的颜色键（归一化后） |
| 该 id 的纹理槽 | 一个新对象 |

**成立条件**

- 先释放对象槽、再打开文件 ⇒ 失败路径上对象槽已经是空的。
- 失败分支只把记录的来源文件写成"无"，不改颜色键与空白创建。

### 释放纹理：opcode 0x1fa

<!-- rule: CORE-OPS-TEXTURE-RELEASE -->

`0x1fa` 有一个操作数：**纹理 id**；**同一个操作数被读两次**。

- 先清**引擎级对象槽**里该 id 的对象。
- 若该 id 的**释放守卫**为 0：把纹理记录的**来源文件**写成"无"；清**纹理槽**里的对象。
- 释放守卫非 0 ⇒ 上面两步都**不做**（只清引擎级对象槽）。本构建里守卫表没有写入点 ⇒ 观察上恒为 0。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该 id 的纹理被释放 | 来源文件 = 无；纹理槽为空 |
| 释放被守卫挡住 | 来源文件与纹理槽都不变 |

**成立条件**

- 不清"空白创建"标记。
- 纹理槽本来就是空 ⇒ 跳过释放，不报错。

### 绘制纹理：opcode 0x1fb

<!-- rule: CORE-OPS-TEXTURE-DRAW -->

`0x1fb` 有八个操作数：**1 = 绘制键**、**2 = 纹理 id**、**3 / 4 = 矩形 x / y**、**5 / 6 = 宽 / 高**、**7 / 8 = 两个数值**。
读取顺序是 **6 → 4 → 5 → 3 → 4 → 3 → 7 → 8 → 2 → 1**。

- 矩形存成**四条边**：右 = x + 宽、下 = y + 高；**不是宽高本身**。
- 第 7、8 个操作数按**整型**读出，再转成浮点，写进绘制项的两个位置；第三个位置写 0。
- 绘制项按**绘制键**取；不存在 ⇒ 先建一个默认项再插入。
- 写入：置"有效"位、纹理 id、矩形四条边、两个浮点与 0；场景标脏。
- 本条没有外部请求；**不检查纹理 id 是否存在**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某个绘制键对应的绘制项 | 绘制项表里该键的记录（缺则新建） |
| 该项用哪张纹理、画在哪个矩形 | 记录的纹理 id 与四条边 |
| 两个数值 | 记录里的两个浮点位（第三个位 = 0） |

**成立条件**

- 两个数值来自**整型**读取 ⇒ 若实参是浮点来源，小数部分会被截掉。
- 数值越界不检查；绘制键不存在是"建默认项"，不是错误。

## 场景 / 颜色族（opcode 0x202 / 0x203 / 0x320 / 0x322 / 0x323）

这五条给场景里**可绘制的东西**上色：绘制项（带矩形与颜色）与网格（带顶点缓冲与颜色）。
它们只改引擎数据；把颜色烘进顶点缓冲、以及在屏幕上画出来，属于外部模块。

两条共用口径：

- **颜色归一化**：透明度 > 255 ⇒ 按 255；透明度 < 0 ⇒ 取现有颜色的高字节；颜色 < 0 ⇒ 取现有颜色；
  结果 = (颜色 & 0xFFFFFF) | (透明度 << 24)。
- **取记录**：按编号查表；查不到 ⇒ **先建一条默认记录**再继续。因此"什么都没做"对颜色可能成立，
  对表不成立（表里一定多了一条默认记录）。

### 绘制项：排颜色渐变窗（opcode 0x202）

<!-- rule: CORE-OPS-SCENE-202 -->

读五个操作数：**编号**、**延迟**、**持续时间**、**透明度**、**颜色**。
延迟与持续时间的单位是**毫秒**；颜色从该项**现有颜色**渐变到归一化后的新颜色。

- 只有该项的"已存在"位为 1 时才排窗：置"有窗"位、把窗起点清成 0（未盖章）、写延迟 / 持续时间 / 终色，
  并把场景标脏、标成"有动画"。
- "已存在"位为 0（含刚建出的默认记录）⇒ **一个窗字段都不写**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某项的渐变窗 | 该项的延迟、持续时间、终色、"有窗"位、起点（0 = 未盖章） |
| 场景有动画 | 场景的"有动画"标记 ← 1 |

**成立条件**

- 起点 0 是"未盖章"哨兵，不是"从 0 毫秒起算"。
- "已存在"门只看该项自己的位；没有别的前置。

### 绘制项：直接设当前颜色（opcode 0x203）

<!-- rule: CORE-OPS-SCENE-203 -->

读四个操作数：**编号**、**一个整数**、**透明度**、**颜色**。按共用口径归一化后写进该项的**当前颜色**。

- **不排窗**：不碰延迟 / 持续时间 / "有窗"位；场景标脏。
- 第 2 个操作数写进记录里的一个整数位，**读者未找到**（本版只规定"写进去了"）。
- **没有"已存在"门**：编号不存在时照写（写进刚建出的默认记录）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某项的当前颜色 | 记录的当前颜色 ← 归一化值 |
| 第 2 个操作数 | 记录里的一个整数位 |

**成立条件**

- ⛔ 不许与 `0x202` 合并实现：一条排窗、一条只改当前颜色，字段集与门都不同。

### 网格：建 / 换（opcode 0x320）

<!-- rule: CORE-OPS-SCENE-320 -->

读**十个**操作数，顺序不是 1..10：**先第 9 个（顶点数）** → 第 5、6 个的**地址** → 第 7、8 个（浮点）
→ 按顶点数逐元素算出第三段 → 第 10 个 → 第 4、3、2 个（浮点）→ **第 1 个（编号）**。

- **顶点数 ≤ 0** ⇒ 写"顶点数非法"的错误文本并走错误通道，**不建网格**。
- 否则：按第 5、6 个操作数的地址读出两段整型数据（每段 n 个元素）；第三个数组的第 i 个元素 =
  **(第 5 段第 i 个解出的高字节) << 24 | (第 6 段第 i 个解出的低 24 位)**。
- 建 / 换该编号的网格：释放原有缓冲，建三个"顶点数 × 4 字节"的缓冲；置"已存在"位、写顶点数与第 10 个操作数、
  写第 2/3/4 与第 7/8 个操作数（浮点）。
- 若该网格**已有当前颜色**（不是"无颜色"）⇒ 按当前颜色重烘顶点色；场景标脏。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 顶点数 / 三个顶点缓冲 / 第 10 个操作数 | 网格记录的对应字段与缓冲 |
| "已存在"位 | 网格记录的位 0 |

**成立条件**

- 这是"替换"不是"追加"：重复调用先释放旧缓冲。
- 编号**不做范围检查**；顶点数只有"≤ 0 / > 0"两分支，没有上限检查。

### 网格：直接设当前颜色（opcode 0x322）

<!-- rule: CORE-OPS-SCENE-322 -->

读四个操作数：**编号**、**一个整数**、**透明度**、**颜色**。

- 按共用口径归一化后写进网格的**当前颜色**，并**按当前颜色烘进顶点缓冲**（混合系数 0）；
  第 2 个操作数写进记录里的一个整数位（**读者未找到**）；场景标脏。
- **不排窗**；**没有"已存在"门**（编号不存在时写进刚建出的默认记录，默认当前颜色是"无颜色"）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 网格的当前颜色 | 记录的当前颜色 |
| 逐顶点颜色 | 顶点缓冲里的颜色 ← 当前颜色 |
| 第 2 个操作数 | 记录里的一个整数位 |

**成立条件**

- 第 2 个操作数不要当"透明度"或"编号"用：它写的是另一个整数位。

### 网格：排颜色渐变窗（opcode 0x323）

<!-- rule: CORE-OPS-SCENE-323 -->

读五个操作数：**编号**、**延迟**、**持续时间**、**透明度**、**颜色**。

- 与绘制项同形：置"有窗"位、把窗起点清成 0、写延迟 / 持续时间 / 终色；场景标脏。
- **没有"已存在"门**：编号不存在时会先建默认记录，然后**照常排窗**。
- 本条**不**直接置"场景有动画"（那由窗的推进决定）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 网格的渐变窗 | 记录的延迟、持续时间、终色、"有窗"位、起点 |

**成立条件**

- 与 `0x202` 的"已存在"门**不对称**：这是真实差异，不许抹平。

## 等待与输入（opcode 0x21c / 0x101）

### 等待（opcode 0x21c）

<!-- rule: CORE-OPS-WAIT -->

`0x21c` 没有操作数。它只做两件事：把当前帧的**推进格数**写成 1（= `2 × 0 + 1`），并**置起等待位**。

- 阻塞**不发生在处理器体内**：置位后门立刻关上，之后由门的服务分支决定何时放行（见「执行与时间」）。
- 本条不读操作数、不写别的引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 脚本在等待 | 状态选择字的等待位 = 1 |
| 本条指令的长度 | 当前帧的推进格数 ← 1 |

**成立条件**

- 实现不许在处理器里循环 / 睡眠等待；那是把门的语义搬进一条指令。
- 放行条件只有"场景不再有动画"（本版；点击跳过不在范围）。

### 采样输入并丢弃（opcode 0x101）

<!-- rule: CORE-OPS-POLL-INPUT -->

`0x101` 没有操作数。按固定顺序做四件事：

1. 采样一次输入到引擎的输入字（**外部请求**；采样本身不在本版范围）；
2. 清状态选择字里的一个位；
3. 把输入字写成 0（**丢弃**这次采样）；
4. 两个引擎级标量分别写 1 与 0。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 输入已被丢弃 | 输入字 = 0 |
| 某位被清 | 状态选择字里对应位 = 0 |
| 两个标量 | ← 1 / ← 0 |

**成立条件**

- 顺序固定：采样 → 清位 → 清输入字 → 写两个标量（后三步不许调换）。
- 采样结果除"写进输入字再清零"外没有其它消费。

## 外部请求

### 播影片（opcode 0x20f）

<!-- rule: CORE-OPS-MOVIE -->

`0x20f` 有三个操作数：**1 = 资源 id**、**2 = 对象表槽号**、**3 = 选项字**；读取顺序是 **2 → 1 → 1 → 3**。

- 按第 2 个操作数查**对象表**；该槽为空 ⇒ 新建一个影片对象放进去；同槽已有对象 ⇒ **不重建**，只改配置与启动。
- 用第 1 个操作数取资源名并打开影片（**外部请求**）；打不开 ⇒ 抛"显示消息"异常。
- **绑定门**：该槽上必须已有纹理绑定，否则抛"显示消息"异常。
- 第 3 个操作数是**选项字**：其中若干位选音轨类别，其余位原样交给对象；音量的合成依赖外部配置，
  本版只登记"对象音量被配置"这件事，不规定键位与合成公式。
- 最后**置起影片位**，并把"有活动对象"写 1。
- 处理器体内**不等待**：建对象、配置、启动之后立即返回；阻塞发生在门的影片位服务分支（本版不规定该分支）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某个槽上有影片在播 | 对象表该槽非空、对象已启动 |
| 影片占用主循环 | 影片位 = 1 |
| 有活动对象 | "有活动对象"标记 = 1 |

**成立条件**

- 选项字里"可跳过"的判据只登记形态，不解释键位。
- 影片时长、解码、声音呈现都属于外部模块。

## 空操作

### 注释（opcode 0x1a7）

<!-- rule: CORE-OPS-NOOP-COMMENT -->

`0x1a7` 带**一个**操作数，但**不读它**：处理器只写"操作数个数"槽（3 = 2×1+1），然后返回。

- 不读操作数 ⇒ 即使载荷的类型标签不受支持，也**不抛异常**。
- 不写任何池、标量或场景状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 无 | 只有分派协议的操作数个数槽 |

**成立条件**

- 这条的合同是"**什么都不做**"：把它实现成 no-op 不是偷懒，而是规范结论。
- 操作数载荷（注释文本）只存在于指令流里，不进入任何状态。

### 未使用（opcode 0x1a8）

<!-- rule: CORE-OPS-NOOP-DEV -->

`0x1a8` **没有**操作数：处理器只写"操作数个数"槽（1 = 2×0+1），然后返回。

- 不读操作数、不写任何引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 无 | 只有分派协议的操作数个数槽 |

**成立条件**

- 与 `0x1a7` 的区别只在操作数个数（一条带载荷、一条不带）；语义都是 no-op。
