## 指令语义

本章规定**单条指令对引擎数据的改变**：读哪些操作数、按什么顺序读、写到哪里、失败时怎样。值的语义（整型编码、浮点转换、类型支持集）属于「数据池」；操作数个数与指令推进属于「脚本与执行」。

本章只写**引擎数据**的效果。向外部的呈现请求（绘制、图像、声音）不在此列：它们是否被受理、像素与声音如何，属于平台与呈现模块；一条指令若只发出这类请求而不改引擎数据，它在本书里的合同就是"无引擎数据效果"。

本版覆盖 **39 条规则**（共 45 个 opcode）：**数值运算与搬运**四条（`0x50` 加 / `0x51` 减 / `0x2d5` 浮点搬运 / `0x55` 整数搬运）、**纹理族**五条（`0x1f7` / `0x1f8` / `0x1f9` / `0x1fa` / `0x1fb`）、**场景 / 颜色族**五条（`0x202` / `0x203` / `0x320` / `0x322` / `0x323`）、**语音族**两条（`0x2f6` / `0x2f8`）、**列表与子系统写入**七条（`0x70` / `0x71` / `0x73` / `0x78` / `0x2db` / `0x79` / `0x1c1` / `0x212` / `0x213` / `0x25d` / `0x303`）、**帧类**六条（`0xa0` / `0x8f` / `0x5` / `0x3` / `0x2` / `0x9`）、**引擎级标量**两条（`0x149` / `0x21b` / `0x252` / `0x88`）、**转发型**三条（`0x1ca` / `0x324` / `0x32f`）、**等待 / 输入 / 影片 / 空操作**五条（`0x21c` / `0x101` / `0x20f` / `0x1a7` / `0x1a8`）。其余指令尚未成篇。

### 整数加：opcode 0x50

<!-- rule: CORE-OPS-NUMERIC-ADD -->

`0x50` 有三个操作数。它把**第 3 个操作数**与**第 2 个操作数**分别按整型语义读出，把两者之和按整型语义写进**第 1 个操作数**。读取顺序是**先第 3 个、再第 2 个**。

- 第 1 个操作数只被写，**不被读**。
- 三个操作数都经过「数据池」的读整型 / 写整型原语，因此各自的类型标签决定池与转换；不支持的类型标签照「数据池」抛异常。
- 除「脚本与执行」规定的操作数个数槽外，这条指令不改变其它引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数指向的整数 | 读整型（第 3 个）＋读整型（第 2 个）→ 写整型（第 1 个） |

**成立条件**

- 读取顺序是规范的一部分：先第 3 个、后第 2 个；第 2 个读取失败时，第 3 个**已经**被读过。
- 第 1 个操作数不被读：因此"只在写入时才支持"的类型标签在这里不会因为读而失败。

### 整数减：opcode 0x51

<!-- rule: CORE-OPS-NUMERIC-SUB -->

`0x51` 与整数加同形，只差运算方向：读**第 3 个**、再读**第 2 个**，把**第 2 个减第 3 个**的结果写进**第 1 个操作数**。

- 第 1 个操作数只被写，不被读。
- 三个操作数同样经过「数据池」的读整型 / 写整型原语。
- 除操作数个数槽外，这条指令不改变其它引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数指向的整数 | 读整型（第 2 个）−读整型（第 3 个）→ 写整型（第 1 个） |

**成立条件**

- 次序是"第 2 个减第 3 个"，不是"第 3 个减第 2 个"：减法不可交换，写反了不会报错，只会算错。
- 读取顺序仍是先第 3 个、后第 2 个。

### 浮点搬运：opcode 0x2d5

<!-- rule: CORE-OPS-NUMERIC-FLOAT-MOV -->

`0x2d5` 有两个操作数：把**第 2 个操作数**按浮点语义读出，按浮点语义写进**第 1 个操作数**。第 1 个操作数只被写，不被读。

- 两个操作数经过「数据池」的读浮点 / 写浮点原语；跨族转换按「数据池」的口径。
- 除操作数个数槽外，这条指令不改变其它引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数指向的浮点数 | 读浮点（第 2 个）→ 写浮点（第 1 个） |

**成立条件**

- 这条是**搬运**，不是"按整型转写"：目标族的整型编码不会参与（写浮点原语自己处理转换）。
- 第 1 个操作数不被读。

### 整数搬运：opcode 0x55

<!-- rule: CORE-OPS-NUMERIC-MOV-INT -->

`0x55` 有两个操作数：把**第 2 个操作数**按整型语义读出，按整型语义写进**第 1 个操作数**。第 1 个操作数只被写、不被读。

- 两个操作数都经过「数据池」的读整型 / 写整型原语；跨族转换按「数据池」的口径。
- 除「操作数个数」槽外，这条指令不改变其它引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 第 1 个操作数指向的整数 | 读整型（第 2 个）→ 写整型（第 1 个） |

**成立条件**

- 这是**搬运**，不是"按位复制"：写整型原语自己处理目标族的编码。
- 第 1 个操作数不被读 ⇒ "只在写入时才支持"的类型标签不会因为读而失败。
## 纹理族（opcode 0x1f7 / 0x1f8 / 0x1f9 / 0x1fa / 0x1fb）

这五条操作的是场景里的**纹理对象**与**绘制项**：按一个整数编号取记录，按槽建/换/释放纹理对象。
它们都只改引擎数据；底层图像的解码、上传与呈现属于外部模块。

### 拆离纹理：opcode 0x1f7

<!-- rule: CORE-OPS-TEXTURE-DETACH -->

`0x1f7` 有两个操作数：**第 2 个是个数**、**第 1 个是键**；读取顺序是**先第 2 个、后第 1 个**。

- **个数 ≤ 1**：把该键从场景的四张键表（绘制项表与三张辅助表）里删除。
- **个数 > 1**：按**左闭右开**区间 `[键, 键 + 个数)` 删除四张表里的条目；条目内嵌的对象与缓冲一并释放。
- 只要四张表里有任意一张真的删掉了东西 ⇒ 场景被标成"脏"；没有删掉 ⇒ 脏标记不动。
- 本条没有外部请求。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某个键在四张表里都不存在 | 四张表都查不到该键 |
| 场景被标脏 | 场景的脏标记 ← 1（至少一张表删掉了条目） |

**成立条件**

- 区间是左闭右开；负数个数也走"≤ 1"的单键路径。
- 键不存在时该表**静默跳过**，不报错、不代替建默认项。

### 创建纹理：opcode 0x1f8

<!-- rule: CORE-OPS-TEXTURE-CREATE -->

`0x1f8` 有四个操作数：**1 = 纹理 id**、**2 = 宽**、**3 = 高**、**4 = 种类**；读取顺序是 **1 → 4 → 3 → 2 → 1**。

- 先清**引擎级对象槽**里该 id 的对象（非空则释放、置空）。
- 把该 id 的**纹理记录**重置为"没有来源文件、空白创建"：来源文件 = 无，空白创建标记 = 1。
- 清**纹理槽**里该 id 的旧对象；按种类新建一个对象写回该槽：种类 = 3 ⇒ 分割纹理，其它 ⇒ 普通纹理。
- 宽 / 高 / 种类交给对象向底层请求创建（**外部请求**）。
- 底层创建失败 ⇒ 错误文本写进场景错误缓冲并上报；**不抛异常**，本对象**仍留在槽里**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该 id 的纹理记录 | 来源文件 = 无；空白创建 = 1 |
| 该 id 的纹理槽 | 一个新对象（种类决定它是不是分割纹理） |
| 引擎级对象槽 | 该 id 的槽被清空 |

**成立条件**

- 编号**不做范围检查**。
- 种类只有"等于 3 / 不等于 3"两个分支，不是枚举。

### 设置纹理：opcode 0x1f9

<!-- rule: CORE-OPS-TEXTURE-SET -->

`0x1f9` 有三个操作数：**1 = 文件号**、**2 = 纹理 id**、**3 = 颜色键**；读取顺序是 **2 → 1 → 3 → 2**。

- 先清**引擎级对象槽**里该 id 的对象（这一步在读文件**之前**）。
- 按文件号打开并加锁（**外部请求**）；文件号非法、或加锁失败 ⇒ 抛"显示消息"异常。
- 颜色键归一化：负数 ⇒ 0；否则 = 不透明黑 | (值 & 0xFFFFFF)。★ 颜色字段的位段与「不透明黑」的具体数值属机器细节，本版不规定（见本章残差）。
- 清**纹理槽**里该 id 的旧对象；解码图像、新建普通纹理对象、上传像素（后三者是**外部请求**）。
- **成功** ⇒ 纹理记录：来源文件 = 文件号、颜色键 = 归一化值、空白创建 = 0。
- **失败** ⇒ 纹理记录：来源文件 = 无；关闭文件后抛"显示消息"异常。
- 关闭 / 解锁在两条路径上都做。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该 id 的纹理来自哪个文件 | 记录的来源文件 |
| 该 id 的颜色键 | 记录的颜色键（归一化后） |
| 该 id 的纹理槽 | 一个新对象 |

**成立条件**

- 先释放对象槽、再打开文件 ⇒ 失败路径上对象槽已经是空的。
- 失败分支只把记录的来源文件写成"无"，不改颜色键与空白创建。
- **显示消息异常**：一条携带错误文本与错误码的异常。抛出即中止本条：本条自己的清理（关闭 / 解锁）在抛出前已经做，已经写下的引擎数据**保留、不回滚**。主循环捕获它之后怎样处置（显示、重试、结束）属于「执行与时间」，本版不规定。

### 释放纹理：opcode 0x1fa

<!-- rule: CORE-OPS-TEXTURE-RELEASE -->

`0x1fa` 有一个操作数：**纹理 id**；**同一个操作数被读两次**。

- 先清**引擎级对象槽**里该 id 的对象。
- 若该 id 的**释放守卫**为 0：把纹理记录的**来源文件**写成"无"；清**纹理槽**里的对象。
- 释放守卫非 0 ⇒ 上面两步都**不做**（只清引擎级对象槽）。本构建里守卫表没有写入点 ⇒ 观察上恒为 0。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该 id 的纹理被释放 | 来源文件 = 无；纹理槽为空 |
| 释放被守卫挡住 | 来源文件与纹理槽都不变 |

**成立条件**

- 不清"空白创建"标记。
- 纹理槽本来就是空 ⇒ 跳过释放，不报错。

### 绘制纹理：opcode 0x1fb

<!-- rule: CORE-OPS-TEXTURE-DRAW -->

`0x1fb` 有八个操作数：**1 = 绘制键**、**2 = 纹理 id**、**3 / 4 = 矩形 x / y**、**5 / 6 = 宽 / 高**、**7 / 8 = 两个数值**。
读取顺序是 **6 → 4 → 5 → 3 → 4 → 3 → 7 → 8 → 2 → 1**。

- 矩形存成**四条边**：右 = x + 宽、下 = y + 高；**不是宽高本身**。
- 第 7、8 个操作数按**整型**读出，再转成浮点，写进绘制项的两个位置；第三个位置写 0。
- 绘制项按**绘制键**取；不存在 ⇒ 先建一个默认项再插入。
- 写入：置"有效"位、纹理 id、矩形四条边、两个浮点与 0；场景标脏。
- 本条没有外部请求；**不检查纹理 id 是否存在**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某个绘制键对应的绘制项 | 绘制项表里该键的记录（缺则新建） |
| 该项用哪张纹理、画在哪个矩形 | 记录的纹理 id 与四条边 |
| 两个数值 | 记录里的两个浮点位（第三个位 = 0） |

**成立条件**

- 两个数值来自**整型**读取 ⇒ 若实参是浮点来源，小数部分会被截掉。
- 数值越界不检查；绘制键不存在是"建默认项"，不是错误。

## 场景 / 颜色族（opcode 0x202 / 0x203 / 0x320 / 0x322 / 0x323）

这五条给场景里**可绘制的东西**上色：绘制项（带矩形与颜色）与网格（带顶点缓冲与颜色）。
它们只改引擎数据；把颜色烘进顶点缓冲、以及在屏幕上画出来，属于外部模块。

三条共用口径：

- **颜色归一化**：透明度 > 255 ⇒ 按 255；透明度 < 0 ⇒ 取现有颜色的高字节；颜色 < 0 ⇒ 取现有颜色；
  结果 = (颜色 & 0xFFFFFF) | (透明度 << 24)。
- **取记录**：按编号查表；查不到 ⇒ **先建一条默认记录**再继续。因此"什么都没做"对颜色可能成立，
  对表不成立（表里一定多了一条默认记录）。
- **起色就是当前颜色**：渐变窗不另存起色 —— 推进时插值读的起色就是该项的**当前颜色**字段（`0x203` / `0x322` 写的那一格）。因此排窗（`0x202` / `0x323`）只写终色；**窗进行中改当前颜色会改变起色**。

### 绘制项：排颜色渐变窗（opcode 0x202）

<!-- rule: CORE-OPS-SCENE-202 -->

读五个操作数：**编号**、**延迟**、**持续时间**、**透明度**、**颜色**。
延迟与持续时间的单位是**毫秒**；颜色从该项**现有颜色**渐变到归一化后的新颜色。

- 只有该项的"已存在"位为 1 时才排窗：置"有窗"位、把窗起点清成 0（未盖章）、写延迟 / 持续时间 / 终色，
  （★ 它与 0x1fb 写的"有效"位是否同一位本版不规定，见本章残差），
  并把场景标脏、标成"有动画"。
- "已存在"位为 0（含刚建出的默认记录）⇒ **一个窗字段都不写**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某项的渐变窗 | 该项的延迟、持续时间、终色、"有窗"位、起点（0 = 未盖章） |
| 场景有动画 | 场景的"有动画"标记 ← 1 |

**成立条件**

- 起点 0 是"未盖章"哨兵，不是"从 0 毫秒起算"。
- "已存在"门只看该项自己的位；没有别的前置。

### 绘制项：直接设当前颜色（opcode 0x203）

<!-- rule: CORE-OPS-SCENE-203 -->

读四个操作数：**编号**、**一个整数**、**透明度**、**颜色**。按共用口径归一化后写进该项的**当前颜色**。

- **不排窗**：不碰延迟 / 持续时间 / "有窗"位；场景标脏。
- 第 2 个操作数写进记录里的一个整数位，**读者未找到**（本版只规定"写进去了"）。
- **没有"已存在"门**：编号不存在时照写（写进刚建出的默认记录）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某项的当前颜色 | 记录的当前颜色 ← 归一化值 |
| 第 2 个操作数 | 记录里的一个整数位 |

**成立条件**

- ⛔ 不许与 `0x202` 合并实现：一条排窗、一条只改当前颜色，字段集与门都不同。

### 网格：建 / 换（opcode 0x320）

<!-- rule: CORE-OPS-SCENE-320 -->

读**十个**操作数，顺序不是 1..10：**先第 9 个（顶点数）** → 第 5、6 个的**地址** → 第 7、8 个的**地址**
→ 按顶点数逐元素算出第三段 → 第 10 个 → 第 4、3、2 个的**地址** → **第 1 个（编号）**。

- **顶点数 ≤ 0** ⇒ 写"顶点数非法"的错误文本并走错误通道，**不建网格**。
- 第 2、3、4、5、6、7、8 个操作数都按**地址**读：各自指向一段逐顶点数组，**不是标量、也不做浮点读取**。
- 三个逐顶点数组（各"顶点数 × 4 字节"）的来源：
  - 第 1 个 ← 第 2 个操作数地址处的 n 个 32 位字**原样**拷贝；
  - 第 2 个 ← 第 3 个操作数地址处的 n 个 32 位字**原样**拷贝；
  - 第 3 个 ← 第 5、6 个地址处的两段逐元素合成：**(解码(第 5 段[i]) 的低 8 位) << 24 | (解码(第 6 段[i]) 的低 24 位)**；解码 = 「数据池」的整型解码。
- 第 4、7、8 个操作数地址处的数组交给**顶点缓冲对象**的装配；装配后的逐顶点布局属外部模块，本版不规定。
- 建 / 换该编号的网格：释放原有缓冲，建上述三个数组与一个顶点缓冲对象；置"已存在"位、写顶点数与第 10 个操作数。
- 若该网格**已有当前颜色**（不是"无颜色"）⇒ 按当前颜色重烘顶点色；场景标脏。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 顶点数 / 三个逐顶点数组 / 顶点缓冲对象 / 第 10 个操作数 | 网格记录的对应字段与缓冲 |
| "已存在"位 | 网格记录的位 0 |

**成立条件**

- 这是"替换"不是"追加"：重复调用先释放旧缓冲。
- 编号**不做范围检查**；顶点数只有"≤ 0 / > 0"两分支，没有上限检查。

### 网格：直接设当前颜色（opcode 0x322）

<!-- rule: CORE-OPS-SCENE-322 -->

读四个操作数：**编号**、**一个整数**、**透明度**、**颜色**。

- 按共用口径归一化后写进网格的**当前颜色**，并**按当前颜色烘进顶点缓冲**（混合系数 0）；
  第 2 个操作数写进记录里的一个整数位（**读者未找到**）；场景标脏。
- **不排窗**；**没有"已存在"门**（编号不存在时写进刚建出的默认记录，默认当前颜色是"无颜色"）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 网格的当前颜色 | 记录的当前颜色 |
| 逐顶点颜色 | 顶点缓冲里的颜色 ← 当前颜色 |
| 第 2 个操作数 | 记录里的一个整数位 |

**成立条件**

- 第 2 个操作数不要当"透明度"或"编号"用：它写的是另一个整数位。

### 网格：排颜色渐变窗（opcode 0x323）

<!-- rule: CORE-OPS-SCENE-323 -->

读五个操作数：**编号**、**延迟**、**持续时间**、**透明度**、**颜色**。

- 与绘制项同形：置"有窗"位、把窗起点清成 0、写延迟 / 持续时间 / 终色；场景标脏。
- **没有"已存在"门**：编号不存在时会先建默认记录，然后**照常排窗**。
- 本条**不**直接置"场景有动画"（那由窗的推进决定）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 网格的渐变窗 | 记录的延迟、持续时间、终色、"有窗"位、起点 |

**成立条件**

- 与 `0x202` 的"已存在"门**不对称**：这是真实差异，不许抹平。

## 语音族（opcode 0x2f6 / 0x2f8）

这一族操作的是**语音组的播放状态**。组号是脚本给的（0、1、2 三组），每组对应声音后端里一条通道：通道号 = 组号 + 一个固定偏移（偏移属机器细节，本规范不规定）。每组的引擎侧状态不是一格，而是**若干格按组号索引的数组**；`0x2f6` 只重置其中 8 格（4 格在语音对象里、4 格在引擎级），**不是该组的全部状态**。

播放本身（混音、设备、缓冲对象）属于外部；这里只规定**引擎数据**被改成什么。

### 停止一个语音组（opcode 0x2f6）

<!-- rule: CORE-OPS-VOICE-STOP -->

`0x2f6` 有一个操作数：读成**组号**，然后依次做三件事。

1. **停止该组**：释放「组号 + 固定偏移」那条通道上挂着的缓冲对象；**该通道有对象才发生**（没有对象时什么也不发）。随后把语音对象里属于该组的 **4 格**清成 0。★ 这一整步只在**声音后端存在**时发生：后端不存在时，引擎连这 4 格也不清（那 4 格保持原值）。
2. **清引擎级格**：把引擎自己记的该组 **4 格**清成 0。无条件，与后端在不在无关。
3. **重算「是否还有语音在播」**：写进一个引擎级标志（**无条件写**，有后端无后端都写）。判定逐组进行（0、1、2）：先看该组第 4 格（语音对象里那个）的**低 2 位**，等于 3 的组被**跳过**（视为已完成，不参与）；其余组去问声音后端「这条通道还在播吗」，遇到第一个"在播"的 ⇒ 标志 = 1，停止询问；三组都问完都不在播 ⇒ 标志 = 0。后端不存在时一次也不问，标志直接 0。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该组在语音对象里的 4 格 | ← 0（**仅当**声音后端存在） |
| 该组在引擎级的 4 格 | ← 0（无条件） |
| 「是否还有语音在播」 | 一个引擎级标志 ← 0 / 1 |
| 该通道的缓冲对象被释放 | 向声音后端发出一次释放请求（仅当该通道有对象） |

**成立条件**

- **先停、再清、最后重算**：次序是规范的一部分 —— **有声音后端时**，重算前该组的"完成"位已经被清成 0，因此它不再被跳过、会被重新询问一次；**没有后端时**，第 1 步整段跳过（那 4 格保持原值），重算也不询问任何通道（标志直接 0）。
- 第 2 步与第 1 步的**条件不同**（引擎级格无条件清，语音对象那 4 格只在后端存在时清）：把两步合并成"一起清"会在无后端时多写 4 格。
- 跳过判据只看**低 2 位**：格的高位不参与判断。
- 标志是"**还有**组在播"，不是"这个组在播"：刚被停掉的组本身不会让它变成 1。
- 这个标志是**共享状态**（别的指令也会写它），不是 `0x2f6` 私有：它的读者之一是消息的自动推进 —— 标志为真时那套节拍改用另一组参数（消息机制本身不在本条）。
- 组号在引擎里**没有边界检查**（越界会写到相邻数组上，未定义）；本版只规定 0..2。
- 那 8 格的**领域用途多数未定**（本版只规定"谁在什么时候被写成什么"）；已知的只有"第 4 格的低 2 位 = 完成/跳过位"。组号与声音通道号的对应关系属机器细节。

### 设置一个语音组的音量（opcode 0x2f8）

<!-- rule: CORE-OPS-VOICE-VOLUME -->

`0x2f8` 有两个操作数：**第 2 个是音量**、**第 1 个是组号**；读取顺序是**先第 2 个、后第 1 个**。

- **组号只有 0、1、2 三个有效值**（每组绑到声音后端的一条通道；后端共 15 条通道）。组号 ≥ 3 ⇒ **拒绝**：写一段固定的错误文本、记一条日志，不改任何引擎状态、不发任何请求。
- 否则音量先**夹到 [−10000, 10000]**（饱和，不是回绕），写进**该通道的音量格**，然后向声音后端发出一次设置请求。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该通道的音量 | 音量格 ← 夹取后的值 |
| 设置请求 | 向声音后端发出一次请求（仅当后端存在） |
| 越界失败 | 一段固定错误文本（引擎状态不变） |

**成立条件**

- 音量格的写入在"向后端发请求"**之前**：后端不存在时格子照样变 —— 这两步不许合并。
- 越界路径在写之前返回：音量格**不变**，也不发请求。
- 夹取是饱和：大于上界取上界、小于下界取下界；中间值原样保留（不做量化 / 对齐）。

### 设置一个列表项：opcode 0x70

<!-- rule: CORE-OPS-LIST-SET -->

`0x70` 有五个操作数。它把**第 1 个操作数读成组号**（组号为 0 时换成引擎里的默认组），把后面两对值写进该组的**记录**，并把该组标记为"已登记"：

- **同样的**一对值（第 2 个, 第 3 个）写进**三个**字段对；
- **另一对**值（第 4 个, 第 5 个）写进**第四个**字段对。

随后它发出一次**列表登记**与一次**绘制请求**（以及一条按"浮点模式开关"分岔的路径）；这部分的内部行为**不在本版范围**（本版不规定）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该组记录的三个字段对 | ← (第 2 个, 第 3 个) |
| 该组记录的第四个字段对 | ← (第 4 个, 第 5 个) |
| "该组已登记" | 该组的登记标记 ← 1 |
| 列表登记 / 绘制请求 | 一次请求（内部未建模） |

**成立条件**

- 写的是**该组的记录**：别的组的记录不受影响（组号是索引）。
- 第 2、3 个操作数被读**三次**（每个字段对一次），不是三对不同的源；三对字段对的值因此相同。
- 组号为 0 是"用默认组"，不是"第 0 组"：默认组是谁本版不写（没有观察）。
- 记录不存在 ⇒ **不检查**：直接按记录指针写字段（解引用空指针，未定义行为，按崩溃诊断）；本条不建记录。
- 登记标记与字段写是两件事：字段写成立不等于"已进列表"。
- 记录里还有别的字段（本版不写）；它们由别的指令维护。

### 文本子系统的请求：opcode 0x71

<!-- rule: CORE-OPS-TEXT-REQUEST -->

`0x71` 有一个操作数。它做两件**引擎数据**层面的事，然后把其余工作交给文本子系统：

1. 把**本条指令的位置**（本条指令相对代码区起点按 32 位字编号的下标）写进当前帧的一个字段；
2. 向文本子系统转发一次请求：实参是那个操作数，**外加一个引擎级槽的值**（不是操作数，本版不建模它的当前值）。

其余动作（两处整块数据拷贝、一次子系统内调用、一次入口键为「读文本跳过」的调用、一次**有条件**的状态位写）**不在本版范围**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 当前帧"本条指令的位置" | 帧记录的一个字段 ← 本条指令的位置 |
| 文本请求 | 一次请求（操作数 + 引擎级槽的标识；槽值未建模） |

**成立条件**

- 位置写的是**本条**指令的位置，不是下一条。
- 请求里那个**引擎槽**是独立一项实参（不是脚本操作数）：把它记成"操作数"会让一个"永远是 0 的槽"看起来像脚本给的 0。
- 那次状态位写**有条件**：本版不写它（条件未取证），所以"本条之后门是否关上"本版不回答（本版不规定）。

### 子系统转发 + 一个固定格：opcode 0x73

<!-- rule: CORE-OPS-SUBSYSTEM-SET73 -->

`0x73` 有**十个**操作数（与本版另一条十操作数指令 `0x320` 并列最多）：

1. **先读第 10 个**，写进一个固定格：值为 0 时写成 **1**（不是 0）；
2. 再把第 1..9 个作为一组交给子系统（转发型合同：交谁 / 交了什么，子系统内部未建模）；
3. 视一个引擎级**16 位槽**的值，可能再发一次带固定消息号的请求（实参里有两个操作数派生值）；那个槽的当前值**没有模型**，所以"门到底开没开"本版不回答。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 那个固定格 | ← 第 10 个操作数，**0 被换成 1** |
| 交给子系统的请求 | 一次调用（第 1..9 个操作数） |
| 可能发生的第二次请求 | 一次请求（消息号 + 两个派生实参），门的状态未建模 |

**成立条件**

- "0 换成 1"是这条最容易漏的一步：写原值看起来完全正常。
- 读序是**先第 10 个**、再倒序读第 9..1 个（读操作数本身无副作用，但次序是合同的一部分）。
- 第二次请求的条件来自**引擎级槽**，不是操作数：把它当操作数就会读错。

### 写一个子对象字段并尾跳：opcode 0x78 / 0x2db

<!-- rule: CORE-OPS-SUBSYSTEM-SET-TAIL -->

这两条**同形**，各有一个操作数：把操作数写进**同一个子对象的某个固定字段**（各自一个字段），然后把执行**尾跳**进子系统（子系统的返回值直接由分派器接收，本条自己不产生返回值）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 子对象的那个字段 | ← 第 1 个操作数 |
| 交给子系统的请求 | 一次尾跳请求（接收者是那个子对象） |

**成立条件**

- 两条**不是同一条**：写的是**不同字段**（同形不等于同义，不许合并成一条实现里的同一个常量）。
- 尾跳与"调用"不同：本条不压返回点，子系统的返回值直接回给分派器。
- 字段的领域用途未定；子系统之后做什么未建模（本版不规定）。

### 写列表项的一对字段：opcode 0x79 / 0x1c1

<!-- rule: CORE-OPS-LIST-PAIR -->

这两条**同形**，各有三个操作数：**第 1 个是组号**（为 0 时换成引擎里的默认组），**第 2、3 个是要写的一对值**。它们把这一对值写进该组记录的**一对固定字段**（两条各写自己那一对，落点不同），不产生脚本可观察的返回值。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该组记录的一对字段 | ← (第 2 个, 第 3 个) |

**成立条件**

- 读序是**先第 3 个、再第 2 个、最后第 1 个**（对操作数访问无副作用，但次序是合同的一部分）。
- 两条**落点不同**：同形不等于同字段（合并实现会把其中一条写到错的字段上）。
- 记录不存在 ⇒ **不检查**：直接按记录指针写字段（解引用空指针，未定义行为，按崩溃诊断）；本条不建记录。
- 组号 0 是"默认组"，不是"第 0 组"。
- 记录里其它字段由别的指令维护，本条不碰。


### 写列表项记录的字段（不创建记录）：opcode 0x212 / 0x213 / 0x25d

<!-- rule: CORE-OPS-LIST-FIELD -->

这三条都按**第 1 个操作数**索引列表项记录，把后面的操作数写进该记录的字段（各自一对或一个），**记录不存在时什么都不做**（不创建记录、不写任何状态）：

- `0x212`（两个操作数）：一个字段 ← 第 2 个；
- `0x213`（三个操作数）：一对字段 ← (第 2 个, 第 3 个)；
- `0x25d`（三个操作数）：另一对字段 ← (第 2 个, 第 3 个)。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该组记录的一个 / 一对字段 | ← 第 2 个（与第 3 个） |
| 记录不存在 | 无动作（⛔ 不许顺手建记录） |

**成立条件**

- "记录不存在 ⇒ 无动作"是**可观察的**：它与"顺手建一条空记录"在后续读里表现不同。
- 三条落点各不相同（同族不等于同字段）。
- 这三条不置"已登记"标记：登记是别的指令的事。


### 写一对字段（记录必须已存在）：opcode 0x303

<!-- rule: CORE-OPS-LIST-PAIR2 -->

`0x303` 有三个操作数：第 1 个是组号（0 ⇒ 默认组），第 2、3 个是要写的一对值（读序 op3 → op2 → op1）。它把这一对值写进该组记录的**一对固定字段**。

★ 与 `0x212` / `0x213` / `0x25d` 的关键差别：这一条**不检查记录是否存在** —— 记录为空时引擎会直接解引用空指针（崩溃）。所以"记录不存在"在这条上**不是**"无动作"。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该组记录的一对字段 | ← (第 2 个, 第 3 个) |
| 记录不存在 | 引擎崩溃（未定义行为） |

**成立条件**

- 别把这条与"不创建记录、也不崩溃"的那族混成同一实现：一边是"无动作"，一边是"崩"。
- 组号 0 仍是"默认组"（哪个组未定）。


## 帧类指令（opcode 0x8f / 0x5 / 0xa0 / 0x3 / 0x2 / 0x9）

这一族改变**指令指针 / 帧**：同脚本的调用、返回、条件跳转，以及脚本级切换（换脚本、结束当前脚本、重置重装）。
★ 帧这个**结构本身**（容量 / 当前帧选择 / 父帧链）的合同在「帧与调用」章；本节只写各条指令的效果。

### 条件跳转：opcode 0xa0

<!-- rule: CORE-OPS-FRAME-JUMP-A0 -->

`0xa0` 有三个操作数：**第 1 个是条件**，另外两个是**两条分支各自的目标位置**。

- 条件**非 0** ⇒ 用**第 2 个**作目标；
- 条件**等于 0** ⇒ 用**第 3 个**作目标；
- 目标等于 **−1** ⇒ **不跳**（本条原地落下，分派器照常推进到下一条）；
- 否则指令指针 ← 代码区起点 + 4 × 目标，且长度槽清 0（不自动推进）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 按条件选一条分支 | 指令指针 ← 代码区起点 + 4 × 命中那一支的目标位置 |

**成立条件**

- 只读「该走的那一支」的操作数：另一支的操作数**不被访问**（类型不支持时也不会因此失败）。
- −1 是「不跳」，**不是**「跳到 −4」，也不是「退出」。
- 目标就是位置（与调用/返回同一口径）；跳转后分派器不许再加一次长度。

### 调用（opcode 0x8f）

<!-- rule: CORE-OPS-FRAME-CALL -->

`0x8f` 有一个操作数：读成**位置**。然后：

1. 把**本指令之后那条指令的位置**压进本帧的返回栈（= 本指令位置 + 1 + 2 × 操作数个数；本指令的操作数个数是 1，所以就是 +3）；
2. 指令指针 ← 代码区起点 + 4 × 位置；
3. "操作数个数"槽清 0 ⇒ 分派器**不再**自动前进。

例外（哨兵）：操作数等于 **−1**（32 位全 1）时，撤销第 1 步的压栈、**不跳转**；该路径**不写长度槽**（它保持 `2 × 1 + 1 = 3`），分派器照常前进到下一条。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 返回地址被记住 | 本帧返回栈顶 ← 下一条指令的位置 |
| 执行转到子程序 | 指令指针 ← 代码区起点 + 4 × 位置 |

**成立条件**

- 压进去的是**下一条**的位置，不是本条的位置：压成本条会原地死循环。
- 控制转移之后分派器**不许**再加一次长度：引擎把"操作数个数"槽清 0 就是这个意思（若不清，每次调用都会多走一条指令）。
- 哨兵 −1 的效果是"什么都不做"，**不是**"跳到负位置"，也不是"立刻返回"。
- 返回栈每帧一份（容量属机器细节，本规范不规定）；栈满时的行为尚未观察。

### 返回（opcode 0x5）

<!-- rule: CORE-OPS-FRAME-RET -->

`0x5` 没有操作数。它先把"操作数个数"槽写成 **1**、把本帧返回栈的栈顶指针减一，然后弹出栈顶的位置：

- 位置等于 **−1** ⇒ **不跳转**：长度槽留在 1，分派器只前进 4 字节（等于"这条返回指令原地落下"）；
- 否则：指令指针 ← 代码区起点 + 4 × 位置，并把"操作数个数"槽清 0（不再自动前进）。

此外，真正跳转的那条路径上，引擎还会从**另一个引擎级栈**里弹出一个值写进一个引擎级槽位。那个栈里存的是什么、那个槽位给谁用，都**没有观察**。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 回到调用点 | 指令指针 ← 代码区起点 + 4 × 弹出的位置 |
| 返回栈变浅 | 本帧返回栈顶指针 −1 |

**成立条件**

- 返回**不换帧**：帧号、局部池、代码区都不变（与"换帧"是两件事）。
- 返回点是**绝对位置**（压进去时已经算好），不是"相对当前指令的偏移"，所以返回不能直接由 `调用` 的位置推出。
- 栈空时的引擎后续没有观察（栈顶指针会越界）：本版**不**把它写成合同（本版不规定）。
- 那个引擎级栈的弹出**没有**建模 —— 它的用途未定（本版不规定）。

### 换脚本：opcode 0x3

<!-- rule: CORE-OPS-FRAME-CALL-SCRIPT -->

`0x3` 有一个操作数：读成**统一文件 id**，把那个脚本装进来执行。执行前它做三件事：

1. 把**父脚本挂起**：记住父脚本的代码区、指令指针与帧记录；父帧的位置字段写上**本条指令自己的位置**（dword 序号，不是 +3），父帧的**长度槽写成 3**（本指令固定 1 个操作数 ⇒ `2 × 1 + 1`）。★ 这两步都在**深度检查之前**：即使随后因深度超限报错，父帧的位置与长度槽也已经被写过。
2. 帧号 +1，给子脚本一个**新的帧记录**（局部池**重新分配**、不继承父池）；子帧的父帧号 ← 调用时的帧号，长度槽 ← 0。
3. 子脚本的指令指针 = 子代码区起点（dword 0）。

返回点**不存在任何"下一条"的槽里**：父帧的指令指针停在调用点，子脚本结束后由父帧自己的长度槽推进到下一条（见 0x2）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 父脚本被挂起 | 父脚本的代码区 / 指令指针 / 帧记录进栈 |
| 子脚本开始执行 | 帧号 +1、新的帧记录（新池）、指令指针 ← 子代码区起点 |

**成立条件**

- 当前帧号 = 39 时再换脚本就报错（判据是**当前帧号**，不是已占的槽数；上限与报错文本见「帧与调用」的帧栈规则）。
- 局部池**不继承**：父池里的值在子脚本里读不到，反之亦然。
- 装载失败（id 非法 / 打不开 / 头坏）⇒ 整个执行中止，**不重试**。

### 结束当前脚本：opcode 0x2

<!-- rule: CORE-OPS-FRAME-EXIT -->

`0x2` 没有操作数、也**不写长度槽** —— 长度槽取 `2 × argc + 1` 只是**直线指令**的规则；控制转移指令各自规定，本条不写。它按**当前帧记录的父帧号**分三支。

- 父帧号 **≥ 0** ⇒ 子脚本结束，控制权还给父脚本：**当前帧号改成那个父帧号**（不是"弹出栈顶"），父帧的指令指针**仍是调用点**，由父帧自己的长度槽推进到下一条；
- 父帧号 = **−1** ⇒ **整个执行结束**；另有两个特殊负值用于存档 / 读档（它们的行为不在本版）；其余负值 ⇒ 错误。

★ **释放是有条件的**：只有「父帧号 + 1 == 当前帧号」时才**释放**当前帧槽（帧缓冲与各数组）；否则只切帧号、不释放 —— 那会在帧数组里留下**空槽**（"换帧"造成）。**空槽**的判据是：该帧没有装载脚本，即它的代码区起点为 0。切完之后从父帧号起**向下（帧号递减）**跳过空槽，直到落在一个非空槽上；帧号降到 0 以下仍为空 ⇒ 错误。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 子脚本结束 | 当前脚本换回父脚本（帧号 / 指令指针 / 帧记录都回到挂起时） |
| 紧邻上层返回 | 当前帧槽被释放（父帧号 + 1 == 当前帧号 时） |
| 根脚本结束 | 执行结束（不再取指） |

**成立条件**

- 它**不写指令指针**：返回后的"下一条"是父帧长度槽的算术结果，不是存下来的返回地址。
- 返回时还把父帧的**位置字段**写成 **−1**（返回记号）；长度槽不动。
- 根帧结束时是"整个执行结束"，不是"返回给谁"。

### 重置并重装根脚本：opcode 0x9

<!-- rule: CORE-OPS-FRAME-EXIT-SCRIPT -->

`0x9` 没有操作数。它**不是返回**：它丢掉**全部**帧（所有挂起的脚本一起丢）、复位引擎级状态，然后以**统一文件 id 0** 重新装载根脚本，从它的 dword 0 开始执行。已取证的复位项：40 个帧槽全部释放、帧号回 0、**父帧号回 −1**（根帧的哨兵）、**状态选择字**归 0、三个**全局池**清回初值（整型池每格写同一个初值、浮点池清 0；字符串池的清空未逐条挂机器站点，见本条残差）；其余复位入口（各子系统自己的重置）本版不逐项建模（本版不规定）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 整个脚本栈被丢弃 | 帧栈清空、帧号回 0 |
| 回到根脚本开头 | 装载统一文件 id 0，指令指针 ← 0 |

**成立条件**

- 调用者**永远拿不回控制权**：`0x9` 之后的执行属于新装的根脚本。
- 与 `0x2` 的分叉判据是**作用域**：`0x2` 看父帧号（帧作用域），`0x9` 是全局重置（无判据、无返回）。
- 它的领域名（"退出脚本"）与真实可达性**仍未定**（本版不规定）：语料里它出现在各脚本共有的前导块中，不能据此说它是"文件末尾结束指令"。

## 转发型指令（opcode 0x1ca / 0x324 / 0x32f）

有一类指令**不改脚本可观察的引擎数据**（`0x32f` 是例外：它按索引清容器里的一格，见该条）：它们把操作数（有时还带引擎里的字段）交给某个子系统的一个入口，由那个子系统去处理。本版对这类指令的合同只有三句话：

1. **交给谁、交了什么**：入口的静态名字（子系统自己登记的分派键）与实参的形态（操作数 / 常量 / 引擎里的一个字段）；
2. **不改变脚本可观察的引擎数据**：本条不写池、不写帧、不写本条以外能读到的引擎状态（`0x32f` 例外：写容器里的一格）；
3. **子系统的内部状态不在本版范围**：它内部做了什么、留下什么，没有观察（本版不规定）。

★ 这条边界就是"规范只写到引擎观察到的请求"：⛔ 不因为"看不见"就写成"什么都不做"——请求本身是可观察的。

### 消息子系统的「读文本跳过」：opcode 0x1ca

<!-- rule: CORE-OPS-FORWARD-MESSAGE -->

`0x1ca` 有一个操作数。它把该操作数交给消息子系统的一个入口（入口键是子系统自己登记的静态名字；具体名字属机器细节），然后返回——返回值由分派器丢弃。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 交给消息子系统的请求 | 一次调用（入口键 + 操作数的值）；引擎数据不变 |

**成立条件**

- 这条**不是**"空操作"：请求发生了（外部可观察），只是引擎数据没被改。
- 该入口的返回值不写回操作数、也不进帧状态：分派器丢弃它。
- 子系统内部留下什么（是否有"跳过"标志、在什么条件下生效）**没有观察** —— 本版不写。

### 把引擎字段里的对象交给入口：opcode 0x324

<!-- rule: CORE-OPS-FORWARD-FIELD -->

`0x324` **没有操作数**。它从引擎的一个字段里取出一个对象，把这个对象当作接收者交给一个入口（尾跳：入口的返回值直接回到分派器），然后返回。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 交给该入口的请求 | 一次调用（接收者来自引擎字段）；引擎数据不变 |

**成立条件**

- 它**不读任何操作数**：操作数个数为 0 是这条指令的长度依据。
- 接收者不是操作数，而是引擎里存着的一个对象指针 —— 所以"没给操作数"不等于"没有输入"。
- 入口之后做了什么没有观察（本版不规定）。

### 把索引交给容器入口：opcode 0x32f

<!-- rule: CORE-OPS-FORWARD-CONTAINER -->

`0x32f` 有一个操作数，读成**索引**，交给一个容器的入口。这条的**引擎数据效果是已知的**：容器里该索引的那一格被写成 0；此外还会向容器的属主发出一次通知（通知的具体行为未建模）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 容器里该索引的一格 | ← 0 |
| 交给容器的请求 + 通知 | 一次容器调用（索引）；通知本身未建模 |

**成立条件**

- 清格是**按索引**的一格，不是整块清：索引别的格不受影响。
- 通知与清格是两件事：只建模清格不等于建模了通知。

## 引擎级标量写（opcode 0x149 / 0x21b / 0x252 / 0x88）

这一族把操作数的值写进**引擎里固定的格**（不是池、也不是按索引的表；一条指令可以写一个或多个格）：格的身份属机器细节，本版只规定「读什么、写成什么形态、有没有归一、有没有分支」。

### 薄标量写：opcode 0x149 / 0x21b / 0x252

<!-- rule: CORE-OPS-SCALAR-THIN -->

三条各有一个操作数，各写**一个固定格**：

- `0x149` 与 `0x252` 把操作数按整型语义读出、**原样**写进各自的格（不归一、不夹取）。
- `0x21b` 把同一个值**归一成 0 / 1**：值为 0 ⇒ 写 0；任何非 0（含负数）⇒ 写 1。
- 三条都：只读**一个**操作数、不调用别的引擎函数、**不把返回值写回操作数**（返回值由分派器丢弃）。
- 写进去的是**解码后**的整数值：池里的编码位模式不参与本规则。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 该指令负责的那个引擎级格 | ← 读整型（第 1 个操作数）或它的 0/1 归一 |

**成立条件**

- `0x21b` 的归一不可省：写原值看起来「也能跑」，只有读它的人才会发现区别。
- 三条都不是「写回操作数」：操作数所在池的内容不变。

### 成对写：opcode 0x88

<!-- rule: CORE-OPS-SCALAR-PAIR-88 -->

`0x88` 有一个操作数，读成整型值，然后：

1. 把**同一个值**写进**两个固定格**（两个都写，不看值）；
2. 按值分支：**非 0** ⇒ 把第三个固定格写成**常量 1**；**等于 0** ⇒ 把**状态选择字**（门读的那一个字，见「执行与时间」）的**第 27 位（位号从 0 起数）清 0**（读-改-写，其它位不变）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 两个引擎级格 | ← 读整型（第 1 个操作数） |
| 非 0 支 | 第三个格 ← 常量 1 |
| 为 0 支 | 状态选择字的第 27 位 ← 0 |

**成立条件**

- 两支**互斥**：非 0 时不碰状态字；为 0 时不写第三个格。
- 清位是**读-改-写**：其它位原样保留（把它写成「整字 = 0」会踩掉别的位）。
- 这条与 `0x71`（见「文本子系统的请求：opcode 0x71」）成对；本版只规定「这里会清」，**不**规定「清了之后放行什么」（本版不规定）。

## 等待与输入（opcode 0x21c / 0x101）

### 等待（opcode 0x21c）

<!-- rule: CORE-OPS-WAIT -->

`0x21c` 没有操作数。它只做两件事：把当前帧的**推进格数**写成 1（= `2 × 0 + 1`），并**置起等待位**。

- 阻塞**不发生在处理器体内**：置位后门立刻关上，之后由门的服务分支决定何时放行（见「执行与时间」）。
- 本条不读操作数、不写别的引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 脚本在等待 | 状态选择字的等待位 = 1 |
| 本条指令的长度 | 当前帧的推进格数 ← 1 |

**成立条件**

- 实现不许在处理器里循环 / 睡眠等待；那是把门的语义搬进一条指令。
- 本版只建模"场景不再有动画"这一条放行条件；服务分支另有一路判定（身份未取证，见本条残差）。点击跳过不在本版。

### 采样输入并丢弃（opcode 0x101）

<!-- rule: CORE-OPS-POLL-INPUT -->

`0x101` 没有操作数。按固定顺序做四件事：

1. 采样一次输入到引擎的输入字（**外部请求**；采样本身不在本版范围）；
2. 清状态选择字里的一个位（**哪一位本版不规定**，见本条残差）；
3. 把输入字写成 0（**丢弃**这次采样）；
4. 两个引擎级标量：**A ← 1**、**B ← 0**（A、B 是两条不同的格；它们的领域身份未取证，本版不规定）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 输入已被丢弃 | 输入字 = 0 |
| 某位被清 | 状态选择字里对应位 = 0 |
| 两个标量 | A ← 1、B ← 0 |

**成立条件**

- 顺序固定：采样 → 清位 → 清输入字 → 写两个标量（后三步不许调换）。
- 采样结果除"写进输入字再清零"外没有其它消费。
- A 与 B 的**领域身份**未取证：本版只规定"两条不同的格、一条写 1、一条写 0"，不规定它们各自被谁读。

## 外部请求

### 播影片（opcode 0x20f）

<!-- rule: CORE-OPS-MOVIE -->

`0x20f` 有三个操作数：**1 = 资源 id**、**2 = 对象表槽号**、**3 = 选项字**；读取顺序是 **2 → 1 → 1 → 3**。

- 按第 2 个操作数查**对象表**；该槽为空 ⇒ 新建一个影片对象放进去；同槽已有对象 ⇒ **不重建**，只改配置与启动。
- 用第 1 个操作数取资源名并打开影片（**外部请求**）；打不开 ⇒ 抛"显示消息"异常。
- **纹理绑定**：按**同一个槽号**索引的**另一张表**里的一项；它与对象表里的影片对象**不是同一个东西**（对象表空只是建对象，绑定表空则抛异常）。本条**只读**它，不建立、也不清除（建立者属别的机制，本版不规定）。
- **绑定门**：该项为空 ⇒ 抛"显示消息"异常。
- 次序固定：建对象（仅当槽空）→ 打开影片 → **绑定门** → 读选项字、配置、启动 → 置影片位。
- 失败（打不开 / 绑定为空）⇒ **已建的影片对象留在对象表里**，影片位**尚未**置，配置与启动都不做。
- 第 3 个操作数是**选项字**：其中若干位选音轨类别，其余位原样交给对象；音量的合成依赖外部配置，
  本版只登记"对象音量被配置"这件事，不规定键位与合成公式。
- 最后**置起影片位**，并把"有活动对象"写 1。
- 处理器体内**不等待**：建对象、配置、启动之后立即返回；阻塞发生在门的影片位服务分支（本版不规定该分支）。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 某个槽上有影片在播 | 对象表该槽非空、对象已启动 |
| 影片占用主循环 | 影片位 = 1 |
| 有活动对象 | "有活动对象"标记 = 1 |

**成立条件**

- 选项字里"可跳过"的判据只登记形态，不解释键位。
- 影片时长、解码、声音呈现都属于外部模块。

## 空操作

### 注释（opcode 0x1a7）

<!-- rule: CORE-OPS-NOOP-COMMENT -->

`0x1a7` 带**一个**操作数，但**不读它**：处理器只写"操作数个数"槽（3 = 2×1+1），然后返回。

- 不读操作数 ⇒ 即使载荷的类型标签不受支持，也**不抛异常**。
- 不写任何池、标量或场景状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 无 | 只有分派协议的操作数个数槽 |

**成立条件**

- 这条的合同是"**什么都不做**"：把它实现成 no-op 不是偷懒，而是规范结论。
- 操作数载荷（注释文本）只存在于指令流里，不进入任何状态。

### 未使用（opcode 0x1a8）

<!-- rule: CORE-OPS-NOOP-DEV -->

`0x1a8` **没有**操作数：处理器只写"操作数个数"槽（1 = 2×0+1），然后返回。

- 不读操作数、不写任何引擎状态。

**状态对应**

| 领域状态 | 机器状态 |
|---|---|
| 无 | 只有分派协议的操作数个数槽 |

**成立条件**

- 与 `0x1a7` 的区别只在操作数个数（一条带载荷、一条不带）；语义都是 no-op。
