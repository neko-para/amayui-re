# data/ledger/ — 台账真源（append-only 文本日志）

## 0. 先分清两个台账（**别混写**）

| | 放什么 | 形态 | 落点 |
|---|---|---|---|
| **需求台账** | 「**还要做什么**」：需求 / 缺陷 + 父子树（人看的进度视图） | **就地编辑的当前文档**（一个节点一个文件） | `data/requirements/`（见其 `README.md`） |
| **知识台账（本目录）** | 「**知道什么**」：可再校验的结论 / 观察 | **append-only 事件流**（一条记录一行） | `data/ledger/` |

两者**共用**派生查询层（`packages/ledger` 的派生 SQLite，落 `.cache/`、可删可重建），
但**各自一份文本真源**：需求的"当前状态"就是真源本身（历史交给 git），
知识台账的"当前形态"是由日志投影出来的。**不要把需求写进本目录，也不要把结论写进需求树。**

## 1. 落点

```text
data/ledger/<kind>/<YYYY-MM>.jsonl    # ★ 真源：一行一条记录（JSON，字段序固定）
```

派生 SQLite 由 `packages/ledger` 生成到 `.cache/`（gitignore），**永不入库**。

## 3. 格式与不变量（★ **唯一真源是自描述，不在本文件**）

| 想知道 | 看哪 |
|---|---|
| 字段 / 枚举 / 锚点两种形态 / 不变量 / 操作 / 怎么查怎么改 | **`pnpm tools ledger describe`**（机器可读加 `--json`） |
| 台账现状：条数 / 有效状态 / 锚点可解析率 / 冲突 | `pnpm tools ledger status` |
| 门禁（6 条不变量，红 = 退出码 1） | `pnpm tools ledger validate` |
| 派生 DB 可删可重建 | `pnpm tools ledger rebuild-db`（缺省 dry-run；打印"两次重建的逻辑内容"摘要） |

本文件**只写非显然的口径与"为什么"**，不复述 schema（否则就会出现第二份 schema，必然漂）。

### 3.1 非显然的口径

* **一条记录 = 一行**，自带 ULID；**字典序 == 时间序** ⇒ 追加序不依赖文件位置。
  两台设备各自追加的是**不同行** ⇒ git 三路合并天然干净；每条结论都有 `git log -L` 可追的问责链。
* **锚点两种形态，都不是行号**：① 二进制 **EA**（语料行区间可以带，但只当**派生索引**）；
  ② **可执行守卫用例** `路径#用例名` —— ★ **文件存在 ≠ 用例存在**，判据必须落到真的**用例名**上
  （短串会在断言消息 / 注释里命中，那是假绿；旧仓 `guard-spec` 的教训）。
* **锚可以指向只读参考仓（旧仓），这是常态而不是错误**：知识记录的观察在 K2 完成锚点重挂之前
  本来就落在旧仓。⇒ 校验必须**显式回答"该绑定落在哪个仓"**（`anchor.repo`），
  且只读参考仓**不在场时是 warning 而不是 error** —— 否则 79 条 `modeled-verified` 会集体假红。
* **`status` 是"作者声称"，`effective` 是"投影现算"**：观察失效 ⇒ 机械降级 `stale`，
  但**日志一个字都不改**（不删除、不改写）；同一 `kind+subject` 上出现多个不同 claim ⇒
  双方都标 `conflict`，并把冲突**作为产物报出来**（不许静默取一个）。
* **任何"改"都是追加一条**：撤回/纠错 = 追加一条 `replaces` 指向它的记录（`pnpm tools ledger retract`）。
  **日志 append-only** ⇒ 不要手改 `.jsonl`、不要删行、不要插中间。
* **"DB 可删可重建"的判据不是"文件字节相同"**：SQLite 文件头带变更计数器、页里可能有空闲区 ⇒
  比的是**逻辑内容**（建表 SQL + 按主键排序的行）的摘要。口径同 `decisions.md` §2 第 3 条。

## 4. 为什么不能反过来（反模式）

把 `.sqlite` 提交进 git / 用 LFS 存 DB（LFS 不解决合并）/ 把 DB 当唯一存储 /
用 `sqlite3 .dump` 当文本真源 / 让 DB 参与写事务再"导出"成文本。
