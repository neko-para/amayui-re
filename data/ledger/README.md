# data/ledger/ — 台账真源（append-only 文本日志）

## 0. 先分清两个台账（**别混写**）

| | 放什么 | 形态 | 落点 |
|---|---|---|---|
| **需求台账** | 「**还要做什么**」：需求 / 缺陷 + 父子树（人看的进度视图） | **就地编辑的当前文档**（一个节点一个文件） | `data/requirements/`（见其 `README.md`） |
| **知识台账（本目录）** | 「**知道什么**」：可再校验的结论 / 观察 | **append-only 事件流**（一条记录一行） | `data/ledger/` |

两者**共用**派生查询层（`packages/ledger` 的派生 SQLite，落 `.cache/`、可删可重建），
但**各自一份文本真源**：需求的"当前状态"就是真源本身（历史交给 git），
知识台账的"当前形态"是由日志投影出来的。**不要把需求写进本目录，也不要把结论写进需求树。**

## 1. 本目录将来放什么

**台账的真源**：append-only 的文本日志（一条记录一行）。派生 SQLite 查询层**不在这里** ——
它由 `packages/ledger` 生成到 `.cache/`（gitignore），且**永不入库**。

## 2. 本轮状态：**没有任何条目（有意为之）**

旧仓的知识资产（`analysis/` `tickets/` `docs-new/`）**一律不迁移**：它们需要清理 / 校验 / 重分类。
见 `docs/00-origin/knowledge-rebuild.md`。**K3 通过前，任何知识条目不得进这里。**

## 3. 格式草案（M3 定稿；此处只立方向）

| 约束 | 口径 |
|---|---|
| 记录 | **一条记录一行**，自带 `ULID` 或 `时间戳+计数器` ⇒ 顺序不依赖文件位置 |
| 分片 | 按 key 前缀或按月 ⇒ 把并发追加的冲突窗口降到接近 0 |
| 合并 | 两台设备各自**追加不同行** ⇒ git 三路合并天然干净 |
| 问责 | 每条结论都有 `git log -L` 可追的链条 |
| compact | 周期性产出 canonical 排序的 snapshot —— **仍然是文本** |
| DB | 派生只读查询层；**删除本地 DB 后必须能用一条命令确定性重建（同输入同字节）** |

### 3.1 非显然的口径（★ 两条：一条决定"怎么校验"，一条堵住"全部假红"）

* **每条结论至少绑一条可再校验的观察**，锚点**只取两种形态、都不是行号**：
  ① **二进制 EA**（语料行区间可以带，但只当**派生索引** —— 换一次反汇编只重建 `EA → 行号` 映射，不改任何锚）；
  ② **可执行守卫用例** `file#用例名`（**文件存在 ≠ 用例存在** —— 旧仓 `guard-spec` 的教训：
  三份台账原先只 `existsSync(file)`，把全部 `guard` 指向同一个文件也全绿）。
* **锚可以指向只读参考仓（旧仓），这是常态而不是错误**：知识记录的观察在 K2 完成锚点重挂之前
  本来就落在旧仓。⇒ 校验必须**显式回答"该绑定落在哪个仓"**，**不许**因为"本仓找不到"就判红 ——
  否则 79 条 `modeled-verified` 会集体假红。
* **观察失效 ⇒ 机械降级 `stale`**（不得再进 accepted，但**不删除**）；**冲突显式化成产物**，不许静默改写已有结论。
* **本目录的写入者只有 K3**：`packages/ledger` 落地（格式 + `--validate` + "DB 可删可重建"守卫）之后，
  这里**仍然没有任何条目**（第 2 节）；旧仓知识一律不迁移，逐条过准入门才准进来。

## 4. 为什么不能反过来（反模式）

把 `.sqlite` 提交进 git / 用 LFS 存 DB（LFS 不解决合并）/ 把 DB 当唯一存储 /
用 `sqlite3 .dump` 当文本真源 / 让 DB 参与写事务再"导出"成文本。
